# AgentPlatform 产品定位与总体设计基线

## 1. 产品定位

AgentPlatform 是面向研发团队的 AI 研发能力平台。它帮助团队把知识、研发工作、工程方法和本地 Agent 执行连接起来，使团队经验能够进入实际研发，研发过程能够受到 Harness 约束，真实执行结果能够反过来改善知识与工程方法。

产品要提升的是团队持续完成高质量研发工作的能力，而不是管理尽可能多的 Agent，或提供一个独立于现有研发工具的通用任务编排器。

**核心目标：让团队知识在研发中被复用，让 Harness 使研发过程可控、交付质量可验证，并让每一轮研发都为下一轮积累有效知识和更好的工程方法。**

## 2. 服务对象与核心问题

服务对象是使用不同本地 Agent 工具、共同承担项目研发工作的团队成员及其维护者。

团队需要解决的问题：

- 有价值的业务事实、技术决策、实现经验和踩坑经验分散在文档、代码、Issue、执行记录和个人经验中，下一轮工作难以准确找到和复用。
- 需求、设计、实施、验证和交付之间缺少连续的工作上下文，交接依赖个人解释。
- 团队虽有规范和最佳实践，但难以稳定进入不同成员、不同 Agent 和不同项目的实际执行。
- 研发结果的质量、返工原因、流程缺陷和成本缺少可信证据，难以判断应该改进知识、Harness、工具还是工作方式。
- 研发中的新经验没有稳定地转化为可检索知识和可执行方法，团队反复解决相同问题。

## 3. 产品价值与两个相互促进的飞轮

### 3.1 团队知识飞轮

**已有知识 → 研发消费 → 产生新事实与经验 → 提炼和治理 → 可复用知识 → 下一轮研发。**

知识管理贯穿研发前、中、后：

1. 开工前，根据项目、Issue、研发阶段和接收者权限，发现并提供相关团队知识、项目资料和历史经验。
2. 研发中，允许成员和 Agent 引用知识、核对来源、反馈缺失、过期、冲突或不适用的内容。
3. 研发后，从实际交付、问题排查、评审、测试和人工反馈中发现可复用经验，形成带来源和适用范围的候选知识。
4. 经适当核实和治理后发布，供后续工作检索和引用；后续使用情况再反馈知识质量。

知识管理不是把所有对话、日志和 Issue 自动灌入知识库。原始活动是证据来源，候选知识是待整理和核验的内容，正式知识是可按权限和适用范围复用的资产。

### 3.2 Harness 进化飞轮

**Harness 指导和约束研发 → 观察真实执行 → 评估质量与效果 → 发现问题和根因 → 改进候选 → 对照验证 → 审核发布与采用 → 观察后续效果。**

Harness 不等于提示词集合。它由原则与规则、Skills、Playbooks、Workflow、Scripts、工具约定和 Evaluation 等共同构成。它既指导 Agent 如何工作，也通过可执行检查和独立评估验证实际效果。

自进化不意味着 Agent 可以直接修改并发布团队默认规则。系统可以自动发现问题、形成候选和执行对照评测；正式发布、项目采用和业务验收仍由各自有权主体负责。

### 3.3 两个飞轮如何连接

- 知识为研发和 Harness 提供业务事实、技术依据、历史问题、已验证经验和评测样本。
- Harness 帮助研发稳定执行团队方法，并通过检查、评估和失败归因暴露知识缺口、过期内容和新的经验。
- 研发工作是两个飞轮共同的事实来源；同一份交付、执行和评价证据可以被不同目的引用，但不因此复制成多份权威记录。
- 知识发布、Harness 发布、项目采用、工作实际使用和业务验收是不同事实，不能相互替代。

## 4. 核心业务能力域

整体架构将业务能力收敛为五个核心域：团队知识管理、产研工作与流程协作、Engineering Harness 治理、执行与交付证据、Evaluation / 度量 / 持续改进。组织与项目权限作为平台基础治理；工作台、来源连接器和宿主适配器作为横向能力。具体职责、事实归属和依赖见[整体系统架构](system-architecture.md)。

### 4.1 团队知识管理

负责团队知识和项目资料的接入、组织、提炼、治理、检索、引用、更新与有效性管理。完整来源、证据、候选知识、正式知识、研发消费和反馈生命周期见[团队知识管理与研发知识闭环](knowledge-management-lifecycle.md)。核心对象和跨能力关系见[核心业务对象与统一关系模型](core-business-object-model.md)。

知识按作用域和内容性质组织：

- **团队知识**：跨项目可复用的业务规则、技术规范、架构原则、通用经验和踩坑记录。
- **项目知识与资料**：项目业务事实、PRD、设计决策、接口约定、项目约束、运行与交付资料。
- **项目代码知识**：指定代码基准下的模块结构、调用关系、实现位置和变更影响；与业务知识分开维护，可独立启用。
- **工作上下文**：当前 Issue 的目标、讨论、决定、交接、候选交付和待办事项。它由工作协作主线维护，不复制成另一套知识库。

不同知识源保留各自的权威位置和访问控制。飞书等外部资料不因接入平台而被要求迁移到 Git。平台需要管理来源、修订、证据定位、适用范围、同步状态和可检索状态。知识可以来自文档、网页、代码、Issue、评审、测试和执行证据，按来源类型采用不同接入与解析方式。

知识生命周期至少区分：来源已登记、内容已取得、已解析、证据可用、可检索、候选已形成、已核验、已发布、已失效或待复核。阶段状态必须反映真实处理结果，不能把上传成功等同于知识可用。

### 4.2 产研工作与流程贯通

负责承载研发目标、责任、工作上下文、协作决定、过程交接和交付结果。

Issue 是一项研发工作的业务归属和责任主线。工作可以由成员直接推进、请求一次性 Agent 协助，或在明确授权后交由 Agent 持续协调。是否拆分子 Issue、调用 Worker 或采用 SOP，按实际工作需要决定。

流程明确必要的阶段、交接条件、输入输出和质量门槛；不把所有探索和研发活动强制转换成固定 SOP。需求分析、技术调查和复杂设计保留 Agent 与负责人的自主判断空间。

### 4.3 Engineering Harness

负责把团队认可的研发方法变成可复用、可执行、可评估的工程能力：

- Principles / Rules：明确不可违反的要求和适用范围。
- Skills：提供可调用的专业能力和操作方法。
- Playbooks：指导某类工作如何分析、决策和完成。
- Workflow / SOP：约束需要稳定执行的阶段、依赖、交接、门禁和返工。
- Scripts / Tools：承载确定性检查、自动化操作和工程验证。
- Evaluation：使用独立标准和证据评估执行过程、交付质量及方法效果。

指导、执行、验证应形成互补。仅记录某个 Skill 是否被加载或某个步骤是否被勾选，不足以证明研发质量。

### 4.4 Agent 执行、观测与持续改进

连接成员获准的本地 Agent、Runtime、工具和工作副本；记录真实可观察的执行、工具活动、结果、制品和原生用量。不同宿主能力不一致时，明确标识来源和覆盖范围；无法取得的数据保持未知，不以推算冒充事实。

观测和评价结果用于三类后续动作：

1. 当前工作修正：由当前负责人在本项授权范围内补证、返工或调整。
2. 知识改进：把经核验的业务事实、技术结论、故障经验和使用反馈沉淀为知识。
3. Harness 改进：把重复出现的流程缺陷、质量盲区和有效实践转化为规则、Skill、Playbook、Workflow、Script 或 Evaluation 的候选变更。

成本用于判断资源投入和质量效率，必须保留供应商原生单位、来源、覆盖范围和未知状态；成本不是独立于研发质量的优化目标。

## 5. 一项研发工作的端到端主线

1. **理解工作**：从 Issue 取得目标、责任和当前决定，识别项目范围、相关团队知识、项目资料及必要的代码依据。
2. **形成工作方法**：按适用范围取得团队规则和项目 Harness，结合工作类型选择 Playbook；只有稳定且有明确输入输出和失败处理的环节才使用 SOP。
3. **组织和执行**：成员或受托 Agent 负责推进；按授权使用本地 Agent、Runtime、工具和协作者。Issue 仍是业务责任主线，Run 记录实际受管执行。
4. **检查和交付**：依据工作约定和 Harness 执行必要检查，固定实际交付版本、检查证据、缺项和待决事项，由有权主体作出业务验收决定。
5. **提炼和反馈**：从交付和研发活动识别值得复用的知识与改进机会，分别进入知识治理或 Harness 改进路径。
6. **供下一轮复用**：已发布的知识和 Harness 版本按项目范围、工作需要和授权进入后续研发，使用效果继续被观察。

不是每项工作都需要完整经过所有流程。知识检索按需发生，SOP 按需委托，Evaluation 按风险和策略触发，跨工作改进只处理有证据和复用价值的问题。

## 6. 关键边界与设计原则

1. **团队研发能力优先于 Agent 管理。** Agent 是执行载体，Agent 数量、角色层级和编排复杂度不是产品成功指标。
2. **知识是基础能力，不是附件。** 研发开始前消费知识，研发过程中校正知识，研发结束后贡献知识。
3. **知识与 Harness 分离又关联。** 知识描述事实、经验和依据；Harness 规定工作方法、约束和验证方式。知识可成为 Harness 的输入，经过验证的方法也可沉淀为知识，但两者分别治理和发布。
4. **Issue 是工作主线，不是知识库。** 当前工作上下文留在原 Issue；可跨工作复用的内容经提炼后进入知识体系。
5. **复用现有协作执行底座。** 沿 Multica 的 Issue、Task、Run、Runtime、Session 和 Usage 原生能力扩展，不建立平行控制平面。
6. **本地执行与中心协作分权。** 中心维护共享工作事实、授权和交接；成员本地环境保留宿主会话、工具和未共享内容。
7. **流程提供骨架，不取代判断。** 固化稳定的阶段、契约和质量门槛；探索性工作由负责人和 Agent 自主完成。
8. **证据先于结论。** 知识、评价、交付和改进均保留来源、版本、适用范围和可信程度。
9. **自动提炼不等于自动生效。** 候选可以自动产生；正式知识、团队 Harness 和项目采用按各自权责治理。
10. **按需启用、渐进建设。** 团队 Wiki、项目资料、代码 Wiki、复杂 SOP 和深度 Evaluation 可独立启用，不要求每个 Issue 都经过全部能力。
11. **团队愿意使用是首要约束。** 不强迫非技术成员使用 Git，不要求成员重复填写已有资料，不以额外仪式换取表面上的流程完整。

## 7. 能力关系与总体架构视图

四个能力域形成一个协同系统，而非四套独立产品：

- 团队知识管理提供跨工作复用的事实和经验。
- 产研工作主线组织目标、责任、决定、协作和交付。
- Harness 把团队方法带入具体工作，并定义过程与质量要求。
- Agent 执行、观测与改进将实际执行连接到交付证据、知识贡献和 Harness 演进。

其中工作主线以 Issue 为业务归属；本地 Agent 执行沿 Multica 原生派发与 Run；知识和 Harness 通过有版本、有范围的引用进入工作；交付与执行证据同时供业务验收、知识提炼和独立评价使用。

## 8. 产品范围边界

当前产品主线聚焦：团队知识进入研发、产研工作端到端贯通、Harness 质量管控、执行证据与评价、知识和 Harness 的持续改进。

以下能力可以作为独立扩展，不作为主线成立的前置条件：项目代码 Wiki 的完整图谱产品、通用企业知识管理、全自动多 Agent 编排平台、通用低代码流程引擎、跨团队权限与复杂组织治理、自动训练或自动修改团队规则。

不预设数据库、API、消息队列、部署拓扑或服务拆分。先确认业务事实、对象关系、来源权威、权限边界和闭环，再确定技术承载。

## 9. 架构完成标准

整体设计必须能够说明并贯通以下链路：

- 新研发任务如何发现并取得可信、适用、当前有效的团队知识和项目资料。
- 不同来源如何接入、解析、保留结构和证据位置、处理修订、权限与过期。
- 研发活动如何产生候选知识，如何核验、发布、撤回和在下一轮被检索、引用及反馈。
- Issue 如何承载目标、责任、上下文、交付和决定，成员与不同 Agent 如何沿同一主线协作。
- Harness 如何按项目和工作范围进入执行，哪些要求是指导、哪些是硬门禁、如何验证结果。
- 执行事实如何关联 Issue、Run、宿主、工具、制品和原生用量，缺失信息如何保持未知。
- Evaluation 如何区分当前工作修正、单次评价和跨工作改进，如何避免自证、重复计量和递归。
- Finding 如何分别进入知识改进或 Harness 改进，候选如何对照验证、审核发布、项目采用和观察真实效果。
- 团队知识飞轮和 Harness 进化飞轮如何共享证据而不复制权威事实。
- 普通研发工作如何在不启用所有扩展能力时仍然顺畅完成。

本基线定义产品目标、能力职责与业务关系。各专题负责对象、状态、事件、契约和来源依据；具体实现决策须在整体关系清楚并完成来源核验后再作出。
