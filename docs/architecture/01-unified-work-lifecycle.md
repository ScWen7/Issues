# 专题一：统一工作生命周期

版本：V1.1 · 交叉审查修订

日期：2026-11-15

关联：[统一架构总览](overview.md) · [统一术语](../../CONTEXT.md) · [源码研究依据](../research/01-source-evidence.md)  
范围：工作机制、产品边界、核心模型和案例；不进入数据库、接口或其他专题的完整设计。

## 1. 专题一的阶段性方案

本专题遵循[架构治理基线](governance-baseline.md)和[统一架构总览](overview.md)：以 Multica 现有 Issue、Sub-Issue、Assignee、Comment、Squad、Project Workflow、Run 和本地 Runtime 作为工作与执行主干。本专题定义研发工作如何使用这些既有能力，不另建工作对象或状态权威。

Issue 既能承载整体目标，也能承载具体分工。父子 Issue 使用同一模型；需要独立分配、状态和交付时拆子 Issue，短协作直接在当前 Issue 上开展。业务 Run 直接关联相应 Issue，Leader 的协调运行属于父 Issue，验收是 Issue 上的工作判断。

本方案不建立与 Issue 并列的独立业务 Task 层，具体分工统一由子 Issue 或同 Issue 委派承担。当前架构基线采用这一取舍；其与设计输入 V1 的 Task 概念差异及用户确认状态见[设计基线与决策效力](overview.md#设计基线与决策效力)，文档换版不产生用户确认。工作生命周期中明确区分随步骤流转的“当前负责人”与全局稳定的“总责人（人工）”，并将 Issue 的工作推进状态与质量核验结论解耦，确立平台强制规则最小清单。

用户要求在 Issue 设计中参考 Multica，减少重复建设。本稿负责明确工作责任和验收语义；Multica 作为底座的方向已确定。后续验证聚焦现有能力覆盖和必要扩展，不重新选择或建设平行协作平台。

## 2. 研发场景与设计目标

产品提出“订单批量导出”时，工作会经历范围澄清、前后端协作、不同成员本地执行、规则变更、验证失败、交接和最终接受。系统需要连续回答：当前答应交付什么、谁负责、下一步由谁做、结果依据在哪里、什么还未满足。

| 场景要求 | 基于现有机制的处理 |
|---|---|
| 团队共同推进一个目标 | 父 Issue 保存整体目标、决定和交付判断 |
| 前后端独立承担工作 | 使用子 Issue 各自分配负责人、记录 Run 与结果 |
| 临时咨询或短协作 | 在同一 Issue 中邀请参与，不强制拆子 Issue |
| Leader 分析和汇总 | 在父 Issue 上产生协调 Run 和活动记录 |
| 反复修复与验证 | 继续原 Issue，沿用执行记录和重试 / 重跑关联 |
| 人工验收 | 对明确候选和完成要求作决定，直接记录在对应 Issue |
| 稳定检查可复用 | 在 Issue 的明确范围内调用 SOP |
| 总结经验和改进能力 | 从原工作引用事实，按需要产生候选贡献或改进工作 |

操作负担应随工作规模变化。一个文案修改不需要任务树、Squad、SOP 或独立验收事项；复杂工作才显式管理分工与依赖。

## 3. 源码依据与复用取舍

固定版本、真实调用链和测试入口见[源码研究依据](../research/01-source-evidence.md)。研究仅阅读源码与代表测试，未运行项目或真实 Agent。

| 事实与约束 | 本版取舍 |
|---|---|
| Multica Issue 已有父子关系、负责人、验收标准和上下文引用 | 直接作为工作对象主干，不另建业务 Task |
| 同一 Issue 提及委派与子 Issue 分配是两条可用路径 | 按独立交付需要选一种；同一工作不同时触发两份执行 |
| 子 Issue 阶段变化可唤醒父负责人，Leader 按变化继续协调 | 复用父级协调，不建立长期挂起的协调 Task |
| 状态目录和 Project Workflow 已控制状态、步骤指令与负责人交接 | 沿用现有语义和配置，不重建固定五态工作机 |
| Run 是执行记录，宿主会话与其已有一定关联 | 从现有链路扩展观测和接续，不用会话或 Task 替代 Run |
| TeamAI 与 LoopForge 都已有实际流程引擎 | 专题二围绕既有工作主干选择和适配执行机制，不保留多个 Issue 控制中心 |
| 现有上下文和证据覆盖有边界，部分行为依赖提示词 | 按具体场景记录已覆盖能力与待补增量 |

### 3.1 为什么具体分工优先子 Issue

子 Issue 可以复用已有负责人、优先级、状态、评论、通知、Run 和交付入口。独立 Task 层则需要重新说明这些能力怎样维护、如何与 Issue 同步，以及用户为什么要同时理解两套工作对象。当前没有证明这项成本必要的场景。

代价是子 Issue 可能显得较重。因此拆分条件是独立责任、跟踪或交付；工具调用、检查命令、短咨询和审批不是默认拆分单位。父子层级按实际需要使用，不为组织图强制多层结构。

同级关联 Issue 适合相关但独立验收的目标；子 Issue 适合当前目标的组成部分。较大目标先使用已有父子工作能力，不预设必须新增 Epic 产品层。

### 3.2 原生复用、配置调整、必要扩展

- **原生复用：** Issue / 子 Issue、负责人、Run、评论与活动、通知、成员与 Runtime 的访问基础、工作副本与已有会话接续。
- **配置或工作约定：** 项目流程、派发方式、完成要求、责任联系、资源共享范围和允许动作。文字约定和代码强制分别标注执行方式。
- **必要扩展：** 当前能力未覆盖的约定版本与证据关联、特定宿主交互采集、SOP 适配、人工验收约束、评价与改进能力。逐项证明缺口后扩展既有链路，不默认建设平行中心。

## 4. 工作对象与执行关系

### 4.1 Issue 与子 Issue

Issue 记录当前目标、范围、负责人、完成要求、项目与必要背景。一个 Issue 可关联多个仓库，父子关系表达工作组成，角色和仓库数量都不是机械拆分规则。

父 Issue 保存整体承诺；子 Issue 保存自己需要完成的部分、输入依赖、局部标准和结果。子 Issue 满足局部要求可以完成，父级仍需判断集成与业务目标。子项取消时，父负责人判断其工作是否仍需要，不以“全部关闭”直接宣告交付。

直接参与者可以与当前负责人不同。为每条回复或每次执行建立子 Issue，会增加维护成本；同一 Issue 上可有分析、实施、Review 等多次 Run。

### 4.2 Run 与会话

沿用 Multica 的 Run 作为受管理执行记录，业务 Run 直接关联当前 Issue。一次 Issue 可以有多个执行者和多次 Run；Leader 的分析与汇总直接记在其负责的父 Issue 上。负责人是 Human、Agent 或 Squad，不改变这种归属原则。

原生重试、重跑、委派和会话接续关系用于解释执行来由，不复制 Run 生命周期。SOP 节点履行、子项交付轮次是流程附属关联：先核对原生父执行、委托、重试和重跑字段的实际语义，再补确实缺少的本轮激活引用；Run 谱系不直接替代业务轮次。新发起的后继执行保留先前失败与结果；宿主内工具调用和模型轮次通常属于本次 Trace，不变成业务分工。

平台 Run、宿主 session 和整张 SOP 的执行实例分别表达实际运行、工具连续会话和流程进展，按各自行为建立关联。SOP 中 Agent 执行优先接入已有运行链；Script、结构节点与 Human Gate 怎样关联执行证据由专题二细化，不先把每个节点改造成 Agent Run 或子 Issue。

纯人工讨论、审批和业务验收记录在 Issue 中；实际人工操作可以附结果、验证记录及自报投入。没有自动采集就不生成虚构 Trace 或运行时长。

### 4.3 完成要求、工作约定版本与交付

每次执行知道当前目标、范围和完成要求。它们被明确修改时形成新的工作约定版本，关联确认决定与受影响的结果；不要求用户填写额外版本表单，也不预设新存储结构。

Artifact 是代码、样例、文档等可引用结果；Evidence 是针对要求和结果的观察。交付记录引用候选、标准、证据、残留限制和接受结论，复用 Issue 与 Run 的工作信息。

## 5. 负责人、派发与执行资源

### 5.1 当前负责人的三种模式

Issue 在任意时点只能有一个**当前负责人（Assignee / 当前处理人）**，负责推进当前步骤的工作。Project Workflow 的步骤交接可以将负责人从 Squad 转给 Human 或另一个 Agent。参与、提供机器、作一次 Review 都不自动取得主责。

| 当前负责人 | 如何推进 | 发生执行时如何留痕 |
|---|---|---|
| Human | 自己分析、执行或邀请 Agent；按需要分配子 Issue | Agent Run 关联所服务的 Issue；人工操作和决定直接记录 |
| Agent | 在约定范围内分析与执行，必要时提出拆分或问题 | 当前 Issue 上保留分析、实施和后续 Run |
| Squad | Leader 选择成员、拆分独立工作、跟进和汇总 | 协调 Run 在父 Issue；执行 Run 在当前工作所在 Issue |

本项目遵守设计输入：指定 Squad 主责才启动该 Issue 的自动小队协调。上游 guest Squad 参与路径与完整主责不同；采用上游时须据此核对入口配置或最小约束，分别记录项目要求和上游各入口的实际行为。

### 5.2 区分“当前处理人”与“总责人”

为了解决 Agent/Squad 自主工作时的责任穿透与兜底问题，平台严格区分**当前负责人**与**总责人**：

1. **当前负责人（Assignee）：** 随工作流步骤（如分析、实施、验证、验收）动态流转，负责具体步骤的执行、委派或协调。
2. **总责人（Accountable Member，人工）：** 在整个 Issue 生命周期保持稳定的真实人员（Member），对 Agent 或 Squad 主导工作的目标达成、业务范围、重大取舍与最终交付质量负最终责任。**总责人不可为 Agent 或 Squad**。总责人可与需求提出人（Requester）或验收人（Acceptor）为同一人，但在整个生命周期内不因步骤交接而发生漂移。

**源码复用与扩展分析：**
- Multica 的 Issue 模型（见 [source-evidence M2](../research/01-source-evidence.md#m2-工作负责人与被邀请参与不同责任归属区分处理人与发起人)）原生区分当前负责人（Assignee）、创建人（Creator）与提出人（Requester）。
- 当由 Member 直接创建 Issue 时，创建人或提出人提供了人工责任追溯线索；但若总责人与提出人不同（例如产品提出需求、研发组长承担总责），或 Issue 由自动化流程创建并指派给 Squad，Multica 原生缺少独立的全局稳定人工总责人概念。
- 因此，平台在业务模型层面将总责人作为【必要扩展】，优先复用创建人 / 提出人作为初始默认值，并支持显式指定与锚定。

| 要明确的事项 | 规则与责任归属 |
|---|---|
| 谁对业务目标与重大取舍负总责 | 稳定的**总责人（Member）**；涉及产品规则找产品决定者，重大范围调整由总责人确认 |
| 谁推进当前步骤 | **当前负责人（Assignee）**；随 Project Workflow 步骤流转（如实施阶段为 Squad，验收阶段交还人工） |
| 谁处理执行阻塞 | 当前负责人为 Human 时直接处理；Agent / Squad 主责时，指明可联系的工程支持成员，不把所有工程阻塞转给业务提出人 |
| 能否使用别人的 Runtime | 按机器所有者已授权的共享范围派发，范围外先取得对应使用授权。已有持续授权有效，不逐 Run 重复确认（平台代码强制校验） |
| 使用机器是否承接业务 | 机器使用按共享授权执行；业务承接按成员已有职责安排或明确确认执行，提供 Runtime 不自动承接业务责任 |
| 使用谁的模型额度 | 执行前明确 Runtime / 执行配置对应的额度提供方与允许用途；没有明确适用安排则等待处理，不自动借用其他成员额度 |
| Leader 运行在哪里 | Squad Leader 同样需要获授权的实际 Runtime 和执行额度，沿用资源安排，不假设中心有免费常驻智能池 |
| 谁可以验收 | 项目约定的验收人或适用完成规则；人工业务判断由指定成员作出，Agent 不能代替人工完成最终验收 |

这些职责可以由同一人承担。项目管理员授予工作访问、成员共享 Runtime、业务负责人允许某项工作，是不同范围的授权；角色知识不会扩大工具或资源权限。专题一负责工作与接管语义，专题 3A 负责现有 Runtime / 能力访问的覆盖与适配，专题五负责必要交互。

### 5.3 Leader 的组织循环

1. 在父 Issue 上读取目标、当前决定、相关知识及已有结果，确认当前流程步骤与总责人约束。
2. 对影响范围和验收的未知项提出问题；涉及重大业务取舍向总责人请示；已获授权且不依赖答案的调查可先开展。
3. 按独立责任和结果选择同 Issue 委派或子 Issue 分工。已有子 Issue 就继续使用，不再制造同义任务。
4. 在可用成员、已授权 Runtime 和执行条件内安排工作。指定子 Issue 已触发执行时，不再为同一工作另发父级提及。
5. 本轮协调 Run 输出安排或判断后结束。评论、子项变化、决定及恢复等必要变化触发后继协调；排队和等待不持续调用模型。
6. 依据有效结果决定下一阶段、定向修复或提交验收。子项完成与取消只是输入事实，不替代整体目标判断。

业务验收驳回后，沿用父 Issue 的重开 / 回退及必要子项修复，Leader 在父 Issue 上继续新的 Run。没有专用协调 Task 的关闭、恢复问题。若流程已经将父 Issue 交给 Human，恢复 Squad 协调须遵循明确交接，后续派发由当前负责人或其明确授权的参与者开展。

### 5.4 子 Issue 指派给 Squad 的规则

在复杂场景下，父 Issue 的 Leader 可能需要将某个专业子领域整体委托给一个垂直小队（如前端小队、算法小队）。平台确立以下分工规则：

1. **允许指派但限一层嵌套：** 本阶段允许将子 Issue 指派给另一个 Squad 作为当前负责人，但【严格限制为一层】（即子 Squad 下只能派发给单个 Agent 或 Member，不得再嵌套创建由第三个 Squad 主责的孙 Issue），防止小队递归发散导致协调失控、额度爆炸与责任迷失。
2. **协调职责与 Run 归属：** 子 Squad 的 Leader 只在其负责的子 Issue 范围内进行分析、分工和跟进，其协调 Run 挂在该子 Issue 上。父 Leader 仅关注该子 Issue 的最终交付物与验证结论，不直接干预或穿透派发子 Squad 内部工作。
3. **源码机制与唤醒对象：**
   - Multica 原生模型允许任意层级的 Issue 指派给 Squad。
   - 子项由 Squad 主责时，针对该负责人的工作唤醒交给子 Squad Leader。启用 `child_done` 且满足阶段或全部子项关闭条件时，`resolveWakeTarget` 按父 Issue 的当前负责人处理：Agent 获得运行安排，Squad 由其 Leader 协调，Member 收到通知。见[专题一固定源码 M3](../research/01-source-evidence.md#m3-leader-是短轮次协调规划质量主要依赖-agent)。
4. **需验证点：** 多层级 Squad 并行时本地 Runtime 的容量排队与并发额度消耗、子 Squad Leader 唤醒与父 Leader 唤醒的时序竞争。

## 6. 生命周期与现有状态

### 6.1 七项能力不变，状态机制沿用

| 能力 | 在既有工作链路中的体现 |
|---|---|
| 输入 | 创建 Issue，记录目标和未知项 |
| 分析规划 | 当前 Issue 的讨论、分析 Run、决定与必要子 Issue |
| 协作组织 | 负责人安排、同 Issue 委派、子 Issue 分配与阶段关系 |
| 执行 | 本地 Runtime 上的实际 Run、制品和 Trace |
| 质量验证 | 针对结果的检查、Review、SOP 门禁和人工判断 |
| 交付关闭 | 对应 Issue 的完成要求、候选和接受结论 |
| 经验改进 | 引用原工作事实产生候选知识或改进建议 |

保留 Multica 的状态目录及其生命周期分类，默认使用下列既有状态。项目可以采用适用工作流程，不把此表另做成新的状态机。

| 既有状态 | 本方案中的工作含义 |
|---|---|
| backlog | 收集或暂不安排执行的工作 |
| todo | 已安排，按现有派发条件准备执行 |
| in_progress | 当前工作在推进，包括分析、实施或返工 |
| in_review | 有候选，正在进行约定的核验 / 验收 |
| blocked | 已识别阻塞，须说明原因和处理对象 |
| done | 按项目约定完成 |
| cancelled | 决定不再推进，保留原因和已发生结果 |

自定义状态按上游生命周期规则解释，不因命名相似就自动继承所有内置行为。Run 的排队、运行和终态继续使用原生运行机制；Issue 状态不复制每个 Run 的状态。

### 6.2 状态推进与负责人交接

Project Workflow 规定 Issue 的阶段、步骤指令和负责人交接。没有显式项目流程时沿用既有默认机制。SOP 后续提供某范围的执行结果，完成步骤与改变负责人仍经这条工作主干。

对普通低风险工作，完成要求可采用项目既定自检或自动检查规则；结果满足即可由有权参与者推进，不强制停留在一轮独立“待核验”。有明确 Review 或人工业务验收要求时，才进入相应步骤并等待其结论。

对于要求人工验收的 Issue，进入成功完成类别（`done` 及同类自定义状态）的所有动作，统一校验指定验收人对当前候选和验收标准作出的有效决定。成员、Agent、流程、PR 自动完成及其他集成入口采用同一规则；`in_review` 记录待审进度，验收决定记录批准事实，详见第 6.4 节清单。

### 6.3 取消、转交和暂停分别处理

上游 Issue 改负责人或改为 cancelled，保留正在运行的执行，停止通过相应控制动作处理。项目流程交接有显式停止旧负责人运行的路径，具体行为以既有规则为准。因此工作停止与进程停止在产品上分别表达：

- 取消 Issue：记录不再推进的决定，沿用既有终态与唤醒处理；关联 SOP 的托管安排停止新节点开工、子项重开及出口推进，同时显示活动 Run 的实际状态。进程停止仍按下一项处理，取消事实不改写已发生执行。
- 停止执行：有权成员明确停止相应活动 Run，并观察结果；分别记录请求送达与执行停止。
- 交接修改工作：明确采用停止旧执行还是隔离新工作副本；确认已有结果和在途变更如何处理后再接续。
- 暂时等待：使用现有 blocked / 工作等待记录及运行控制，注明要等待什么；不预设所有宿主都有无损暂停能力。

如果产品希望提供“取消并停止执行”的组合动作，应作为两个既有动作的明确组合展示后果，而不是悄悄改变所有状态写入的原生含义。

### 6.4 平台强制规则（最小清单）

为了确保协作底线，平台将必须由控制平面代码严格校验并拦截的【平台强制规则】与依赖模型自觉的【工作约定/提示词约定】明确区分：

| 规则内容 | Multica 现状 | 本平台需要的处理 |
|---|---|---|
| **1. 人工验收统一完成校验**<br>要求人工验收的 Issue，所有进入成功完成类别的动作均须引用指定验收人对当前候选与标准的有效验收决定，涵盖 `done` 及同类自定义状态 | **已有状态检查与 PR 自动完成路径**<br>Leader 提示词要求交人工；PR 合并可由系统推进状态，另有单事项关闭自动完成的选项（见 source-evidence M5） | **【必要扩展 + 原生配置复用】**<br>统一覆盖成员、Agent、流程及集成完成入口；决定缺失、候选或标准版本不匹配时保持当前工作状态。此类 Issue 默认关闭原生 PR 自动完成；接入统一校验后，自动入口可依据有效验收决定推进 |
| **2. 人工门禁默认阻塞**<br>人工门禁/审批未回应、超时、关闭通知均不构成批准 | **无**<br>（Multica 无原生 Human Gate 状态机制） | **【必要扩展】**<br>平台规则硬性保证：未获得指定决定者明确同意前保持阻塞，任何超时或已读绝不放行 |
| **3. 执行事实与收尾结论留痕**<br>常规终态回报保留已发生执行事实，后继重跑关联新 Run；清理结论及迟到证据注明来源 | **常规状态保护与专项收敛**<br>普通完成回报受状态条件保护；取消清理确认异常可使 `cancelled` 收敛为 `failed / cleanup_unconfirmed`，见[3A 研究](../research/03a-source-evidence.md#35-取消确认与资源复用的适用范围) | **【原生复用 + 追溯补充】**<br>分别保留取消决定、执行结果和清理结论；专项收敛记录前后状态及原因，后续成功与其原始失败、取消来源可追溯 |
| **4. Runtime 共享授权拦截**<br>使用他人 Runtime 需机器所有者显式共享同意 | **已有代码强制**<br>（校验所有者与共享范围，见 source-evidence M7） | **【原生复用】**<br>直接复用 Multica 机器所有者授权强拦截，非共享成员派发一律拒绝 |
| **5. 受控步骤写入校验**<br>采用步骤控制的工作流按 Run 的有效步骤与本轮激活推进 | **已有步骤名守卫，重入仍有缺口**<br>固定 `fdfbfcd` 的 `workflowStepMoved` 只比较步骤名；A→B→A 后第一轮 A 的 Run 可能重新匹配。未启用交接的 Default 保留原方式，见[治理基线盘点](governance-baseline.md#固定版本的底座盘点) | **【原生复用 + 必要扩展】**<br>在原状态写入链核对当前步骤的本轮激活与调用 Run 引用；旧轮只留历史，当前并行分支按各自有效范围处理。按现有守卫适用范围补齐，不另建工作状态机 |
| **6. 工作范围避免重复派发**<br>同一业务工作、本轮激活的重送只对应一次实际派发 | 原生 Squad 交接去重、Agent pending 合并、评论与唤醒是不同路径；领取互斥控制容量，尚未表达 SOP 范围前置，见[专题二固定源码](../research/topic-02/multica.md) | **【原生复用 + 共享检查】**<br>在既有 Issue / Run 附着 SOP 范围、目标 Issue 和本轮激活引用；Leader、手动、评论和 Workflow 请求在原派发链核对同一安排，重送找回原 Run。不同 DAG 分支和明确独立审查各用自己的范围，不因去重而串行化 |
| **7. SOP 节点与工作派发衔接**<br>托管范围按本轮前置、输入和授权开工 | `stage / child_done` 汇总关闭事实，包含 cancelled；它们不校验候选、结果和必需制品 | **【必要适配】**<br>SOP 提供当前节点就绪及交付引用，由原派发链核对。提前改 todo 或直接触发 Agent 也采用相同检查；撤销托管后阻止新启动。SOP 消费结果另查原 Run 的目标 Issue、本轮候选、制品和核验决定，详见[专题二](02-sop-workflow.md#3-一次-sop-如何运行) |

**前置依赖检查的机制说明：**
- **当前现状：** 当前子 Issue 的 stage 推进是“Leader 判断 + `child_done` 唤醒信号”，而不是平台级硬性前置门禁。
- **阶段性接受依据：** 专题一阶段有意接受这一工作约定，目的是保持小队自主组织与自适应分工的灵活性，避免在早期引入死板僵化的重型调度机。
- **SOP 参与方式：** 对明确托管的范围，SOP DAG 的前置结果进入 Multica 原派发链的共享检查；手动 todo、提及、Leader 或 Workflow 均核对同一范围与本轮激活。未满足前置则保持待启动，独立生产的外部结果沿生产方安排执行、按引用契约消费。这项适配保留已证实的前置缺口，普通自由协作继续采用原生工作机制。

## 7. 讨论、决定和共享上下文

### 7.1 消息怎样影响工作

| 动作 | 工作效力 |
|---|---|
| 评论、进度和通知 | 进入共享记录；是否触发 Agent 沿用具体提及与路由机制，消息保存、派发和实际执行分别记录 |
| 同 Issue 明确委派 | 按访问权和触发规则产生相关 Run，不改变原主责 |
| 创建并分配子 Issue | 形成独立工作；避免再对同一工作发起重复委派 |
| 业务澄清或范围决定 | 有权决定者确认后更新工作约定，标明受影响父子工作 |
| 操作审批或人工门禁 | 绑定对象、候选版本、允许动作和后果；未回应不视为同意 |
| 补充运行中执行 | 记录待投递、已送达及可确认的采用情况；按宿主支持情况报告读取进度 |
| 驳回或接管 | 说明具体缺口 / 作用范围，回到已有 Issue 与运行控制继续处理 |

Decision 优先作为 Issue 中可定位的决定记录组织，引用原讨论、决定者和版本，不以新增独立决策中心为前提。摘要可以帮助接续，但不得覆盖原决定。针对不同问题按既有职责找人，不将每次运行都变成审批。

### 7.2 Work Context 的来源与组装

| 内容 | 权威来源与使用方式 |
|---|---|
| 当前目标、范围、完成要求 | 当前 Issue 约定及确认它的决定；子 Issue 引用所需父级约束 |
| 分工、阶段、依赖与结果 | 父子 Issue、既有阶段 / 工作记录、被消费的结果 |
| 讨论、审批和接管 | Issue 评论与活动中可定位的有效决定 |
| 项目与代码基准 | 本次涉及的每个仓库、实际工作变更和运行环境 |
| 相关知识和能力 | 专题三按项目、角色与工作范围选取，保留来源和版本 |
| SOP 位置与要求 | 本次流程定义、节点要求和选定输入 |
| 验证与交付 | Run 及相关制品、标准覆盖、核验和验收结论 |

上下文通过引用组织。现有 Issue / ContextRefs / 评论 / Run 是基础，按需补齐约定版本、实际资源加载和证据关联。资源已下发、宿主已加载、Agent 已采用和结果正确是不同判断。

新决定生效后，向受影响执行明确补充或调整；旧 Run 仍引用开始时的约定和后续补充记录。新标准验收使用已确认采用新要求的结果和证据。无关工作可以继续。

重要交付证据要在团队可访问的位置；仅存在于离线成员机器上的路径应标明不可用。跨成员交接包括最新决定、代码基准、可交换变更、验证结果和未完成项，不要求继承上一人的私有聊天。

## 8. 本地交互式开发怎样接入

这条路径与平台派发并列考虑。Multica 已有 Run 与 session 的关联及部分同 Agent / Issue、同 Runtime 的接续机制；这不证明任意外部会话都可导入。应先沿用已有适配，再补具体宿主缺口。

1. **常规路径（先关联后工作）：** 开发者在受支持的本地入口选择或关联已有 Issue，再进行当前工作；不需要先建立 Task。
2. **探索性路径（先工作后关联）：** 允许成员在突发排障、技术调查或本地自由探索时先开展工作，事后新建 Issue 或关联到已有 Issue。针对此路径设立明确边界：
   - **归属与标记：** 系统显式记录为“事后关联补录”，保留提交时刻与关联人，不伪造受管 Run 的实时时序 Trace；
   - **证据与核验：** 前期修改说明按执行者自述记录；可追溯到候选、环境和方法的原始日志及测试报告按实际证据类型保留。核验方式依据实际承担职责的主体判定，项目要求独立核验时由相应验证者检查当前候选；
   - **成本归集限制：** 若本地宿主未提供分段遥测，费用只能按整体用量粗粒度估算或标记为“未精确分摊”，不伪造每轮分段数据。
3. **受管理执行与会话解耦：** 受管理执行关联本次 Issue 与实际 Run，宿主 session 只作为接续线索。一个长期聊天可能包含多次执行和多个工作，各段执行按当前工作归属关联。
4. **执行边界切换：** 在可识别的执行边界切换工作归属；选定共享的进展、变更和证据回到 Issue。费用按可观测的执行分段归集，缺少分段数据时标记待归集。
5. **按宿主能力降级采集：** 工具支持多少就采集多少：实际模型、Token、工具调用、代码基准、结果与加载证据。只有总量时标记不可精确分摊，缺失字段保持未知。
6. **非适配入口降级：** 不支持自动接入的会话，可先提交选定结果和人工说明；此时记录已提交材料及采集缺口，私有会话按选定范围共享。

这一节确定产品接入要求与降级边界。专题 3A 负责核对各宿主的可用入口、身份与上下文、运行关联及共享控制，专题四负责观测覆盖和成本口径；不在此新造一套会话或运行引擎。

## 9. 执行契约、证据与验收

### 9.1 共同结果语义与核验方式

执行前明确当前 Issue、适用约定、允许动作、代码基准、必要输入、预期结果和检查方式。执行后提供实际完成范围、变更、证据、制品、未完成项和需要决定的问题。已有信息引用复用，自动可采集的内容无需人重复填写。

子 Issue 的交付分别记录**核验主体及职责、核验方法、证据类型和结果结论**。结果核验方式按实际承担核验职责的主体判定：

1. **自检（Self-check）：** 变更执行者自行承担结果检查，包括自己运行测试脚本或验证 SOP。原始测试日志、报告与执行者说明分别保留。
2. **独立核验（Independent Verification）：** 由承担独立核验职责的 Agent、审查人或项目指定验证流程，针对明确候选和标准给出结果，记录其独立验证来源。
3. **未验证（Unverified）：** 当前要求尚未获得对应检查，例如测试未执行或环境缺失。

测试、Review、SOP 是核验方法，可用于自检或独立核验；分类依据验证职责与实际执行主体。发起一次检查的成员和承担验证职责的主体分别记录。自检可以产生客观测试日志，SOP 的使用也按同一标准判定独立性。

| 证据 | 支持的判断 | 需要补充的边界 |
|---|---|---|
| 执行者说明 | 执行者报告的完成范围与阻塞 | 按自述来源记录，与原始执行日志分别引用 |
| Diff / Commit / Patch | 哪个版本有哪些修改 | 正确性、合入和上线分别引用对应结果 |
| 测试结果 | 指定基准、环境、身份和输入下的已覆盖行为 | 记录实际验证主体、核验方式、方法及覆盖情况 |
| 页面操作或文件样例 | 实际可见的交互、内容和结果 | 不外推所有场景或生产容量 |
| Review / 人工验收 | 指定范围及候选的判断 | 保留判断者、依据和残留限制 |
| 人工放行 | 接受某个动作或已知限制 | 原失败事实仍保留，不改成测试成功 |
| Scorer / 模型评价 | 基于给定证据的评价 | 评价注明证据覆盖，业务验收另按交付要求确认 |

证据应能回答：验证什么要求、针对哪个结果版本、在哪种环境和输入下、由谁怎样观察、结论与未覆盖项是什么、证据当前在哪里。当前验收要求的结论可以是通过、不通过、未验证或有理由的不适用。

### 9.2 工作状态与结果结论分离

平台确立核心原则：**Issue / 子 Issue 的工作状态（status）与结果结论（outcome）严格解耦。**

- **状态表示推进：** `status`（如 backlog, todo, in_progress, done）仅表示该项工作在流程上的流转进展。例如，“执行自动化集成测试”这项工作的状态进入 `done`，仅表示测试流程已执行完毕。
- **结论表示质量：** 工作的产出结论通过挂载的 Evidence 明确表达为“通过（Passed）”或“不通过（Failed / Rejected）”。
- **验证类子 Issue 失败时的处理：**
  - 当验证类子 Issue 发现缺陷或权限漏洞时，**验证工作本身可以置为 `done`**（代表测试执行动作已完结，而不是无限处于进行中或挂起）；
  - 但其输出结果的结论明确记录为“不通过”，并将失败用例、日志与证据挂载在相关 Issue 上；
  - 验证子 Issue 关闭后更新父项的子项进度。启用 `child_done` 且满足阶段或全部子项关闭条件时，由父项当前负责人收到相应工作信号。本轮验证的交付与失败证据可直接查阅；
  - **Leader 决策与定向返工：** Leader 必须依据**证据结论**而非**工作状态**进行判断。绝不能因为所有子 Issue 均为 `done` 就判定父级目标达成。识别到“不通过”结论后，Leader 将需修复的子 Issue（如后端导出）重新置为 `todo`/`in_progress` 进行定向返工，同时将依赖此结果的集成与验证子 Issue 回退至 `backlog` 等待新基准，实现精准局部重试。
- **业务最终验收：** 业务验收直接在父 Issue 上由指定总责人/验收人进行判断，无须建立多余的“验收任务”。验收通过按项目流程完成 Issue；驳回则记录未满足要求，返回相应阶段定向修复。

若目标要求生产上线，完成依据必须包含上线与相应验证；若约定是可合入代码，则按这个边界验收。完成子项、Agent 正常结束、SOP 图成功或 PR 合并都是不同事实，是否足够取决于当前工作约定。

## 10. 多 Issue 并行与异常接续

### 10.1 团队怎样安排并行工作与依赖表达

优先复用已有 Issue 优先级、负责人列表、父子工作、阶段唤醒和 Runtime 容量。团队决定哪些工作先开始，Leader 在当前 Issue 范围组织执行；同一小队可以负责多个 Issue，但每次协调保留各自目标和上下文。

| 关系或约束 | 推进方式 |
|---|---|
| 父子组成 | 子项提供局部结果，父项承担整体判断；不按子项计数代替价值完成，状态与结论解耦 |
| 阶段先后 | 线性阶段依托 Multica 的 stage 与 `child_done` 唤醒机制；进入下一阶段由当前负责人核验前置证据结论后推进，非硬性代码门禁（见第 6.4 节） |
| 跨 Issue 结果依赖 | 明确等待哪项结果及可用条件，引用对方交付；自动依赖能力不足时显示等待，不冒称已有通用 DAG 强制保证 |
| 共享仓库或候选基准 | 工作副本隔离，明确集成负责人；整合后针对共同候选验证 |
| 同一 Leader / Runtime 容量 | 展示已有排队与活动执行，资源等待和失败分开；调整优先级不自动抢占在途工作 |

**依赖表达机制的双轨与局限：**
- **当前局限：** Multica 原生的 `stage` 机制**只能表达线性的先后阶段**（如 Stage 1 全部关闭后触发唤醒进入 Stage 2），无法直接表达交叉依赖或分支网络依赖（例如 A→C、B→D 互不阻塞但各自有先后顺序）。
- **当前取舍：** 专题一阶段接受该线性限制。复杂依赖关系由 Leader 在父级进行智能调度，或交由具体的 SOP 流程引擎在局部执行中管理。
- **专题二衔接：** 自由协作采用 stage 提醒，明确托管范围采用 SOP 前置共享检查；两者的权威归属见[设计基线与决策效力](overview.md#设计基线与决策效力)，具体机制见[专题二](02-sop-workflow.md)。

项目可约定同时推进多少项工作，先以既有优先级、开始安排和资源容量落实；本轮不新增全局 WIP 调度引擎。专题五区分“工作已开始”和“执行正在排队”，专题 3A 核验 Runtime 容量与访问能力。两项 Issue 都紧急时由项目既有责任人决定顺序，而不是让不同 Leader 各自无限抢占。

### 10.2 常见中断

| 情况 | 保留与处理 |
|---|---|
| Runtime 不可用，尚未执行 | 保留 Issue 与安排，说明资源等待；恢复或使用另一个已授权环境 |
| 执行中断联 | 保留最后确认进展，显示当前观察不足；不凭断联判失败，也不立即复制同一修改 |
| 原执行已终止 | 保留原 Run、补丁、结果和原因；后继执行继续原 Issue |
| Leader 离线 | 已派发独立工作继续，中心记录仍可见；协调等待恢复或明确转交 |
| 验证失败 | 保留失败标准、输入、候选和环境；回到需修改的子 Issue，重验受影响集成结果 |
| 制品引用失效 | 标明不可访问，恢复或重新生成；当前交付需恢复可访问的有效证据 |
| 等待人工决定 | 等待、提醒或明确转交决定者；未回答不是同意 |
| 取消、暂停、接管 | 区分工作安排和实际执行控制，沿用第 6.3 节，不假定状态变化已停止进程 |

跨成员交接最低要求是工作事实和可交换结果可以接续，不承诺任意宿主的活跃进程跨机器无损迁移。新的修改开始前，确认原执行结束或采用明确隔离安排；这解决真实交接问题，不引入分布式迁移协议。

返工范围由变更影响决定。无关子项继续保留，消费了被修改结果的验证需重新判断。有限重试沿用已有执行机制和约定预算，超出后呈现已尝试内容与具体问题，不以无限调用掩盖阻塞。

## 11. 与专题二、三、四、五的衔接

### 11.1 SOP 与 Project Workflow

Project Workflow 保留 Issue 的状态、步骤指令和负责人交接主干。SOP 在一个 Issue 或明确工作范围内完成稳定步骤，返回结果、门禁、制品和后续动作依据。完整交付 SOP 同样关联现有 Issue 工作中心。

复杂工作可以按父子 Issue 分配；流程内部的分支、汇合、命令和审批不自动变成子 Issue。Agent 实际执行优先进入现有 Run 链路，Human Gate 关联当前 Issue 的决定；节点记录与平台运行要引用对应事实，不把同一次调用算两遍。

同一托管范围的 Leader、SOP、手动与 Workflow 请求，均由 Multica 原派发链读取当前安排、检查前置与本轮激活；同次重送找回原 Run，不为各入口设独立派发权。Leader 仍可推进未托管范围。要改变、接管或中止托管范围，先在原 Issue 记录有权决定，终止旧安排的新开工资格，核对在途执行与副作用后再接续。流程内部进度由 SOP 管理，业务状态和负责人动作通过已有工作机制推进。

[专题二](02-sop-workflow.md#10-订单批量导出的两条路径)保留两条路径：首次探索时由 Squad 自主分工、验证子 Issue 调用局部 SOP；方法稳定后父 Issue 调用完整交付 SOP，托管并行的前后端子项，并按前置交付激活集成和验证。两条路径复用同一候选、Run 与验收记录，最终接受均归父 Issue 的指定成员。

专题二需要比较 Multica 的状态交接与 TeamAI / LoopForge 的执行控制，选择复用或适配方式。本轮不先选节点语法和引擎，也不预先重写 Runtime 调度。

### 11.2 能力、知识与执行平面

专题三以现有成员、Agent、Runtime 和分发 / 执行边界为起点，负责资源来源、版本、适用性、上下文组装、宿主适配以及实际加载确认。明确纳入本地交互式入口、Runtime 访问与共享、工作副本和恢复能力的覆盖核验，不把它们留给无人负责的“后续设计”。

Issue 工作事实由当前工作记录提供；资源更新不会静默改写历史输入。正式知识与规范经过治理发布，候选经验只代表一个建议。发布 SOP、Skills 和 Rules 也沿用这一资产治理职责。

### 11.3 成本、评价与后台工作

专题四引用 Issue / Run / 制品及资源版本，保留原始 Token、单位、费用来源、失败和返工原因。上报费用、估算费用、只有 Token 与未知分别统计；运行等待和人工劳动分别统计，原生数据缺口显式记录。

一次真实消耗只计一次。子 Issue 上的 Run 归其直接工作；父级、Squad、SOP 和项目只做不同聚合视角，汇总以实际消耗记录去重，父级合计明确包含哪些子项。协调运行、失败尝试、取消后的真实消耗仍需保留。

自动评价、知识抽取和索引属于后台活动，不为每次调用强制创建 Issue。它们记录触发来源、项目 / 团队、所用资源及实际消耗；可关联来源 Issue / Run，归集口径由专题四明确。索引等公共开销不伪装成某一个业务 Issue 的直接费用，未归集部分显式列出。

当改进需要人机协作、独立优先级和交付时，再建立改进 Issue。提案描述资产要改什么、依据是什么；Issue 承载被选择的实施工作。候选先以固定输入 Benchmark 验证，再经审核发布；后续真实工作继续观察效果，原交付不被改进进度拖住。自动评价也不默认递归评价每次评价调用。

### 11.4 工作台呈现

专题五围绕既有 Issue、父子工作、会话和 Run 入口补充当前目标、谁负责、待决问题、资源等待和可验收结果。通知引用原工作，不单独维护完成状态。原始 Trace、资源加载细节和内部编号按需查看，主流程不要求人逐项填写。

## 12. 贯穿案例：订单批量导出

### 12.1 模拟约定

以下采用模拟人物、业务决定、运行和证据推演工作机制。

产品成员林创建“订单批量导出”父 Issue。**林作为该 Issue 的人工总责人（Accountable Member），在全生命周期内保持稳定**，对业务目标、规则变更与最终验收负总责。实施阶段的**当前负责人（Assignee）**指定为交付 Squad，验收阶段按流程交还给林。甲、乙、丙按已约定职责分别支持后端、前端和验证；Leader 由成员周提供已授权 Runtime 和对应执行额度。成员的业务职责、机器共享和允许操作预先分别明确，林只决定业务规则及最终接受，不被默认要求解决所有工程阻塞。

父 Issue 明确要求人工验收，创建时关闭该事项的原生 PR 自动完成。成员、Agent、流程和集成产生的完成动作统一检查林对当前候选与标准的验收决定，成功完成类别包括项目配置的自定义完成状态。

模拟决定 D1：导出当前筛选条件下的全部可见订单，不限当前页；XLSX；列包含订单号、创建时间、状态和实付金额；最多 5,000 条，超出时提示缩小范围，完整保留超限提示与拒绝结果；不新增敏感个人字段；空结果、执行中、失败和重试有明确反馈并控制重复点击。交付范围为可合入代码、经授权 UAT 的业务验收记录和交付说明。

模拟决定 D2：执行中增加付款时间列，未付款留空，时区 Asia/Shanghai；据此修订相关工作约定和验收要求。新增决定不自动扩大已授权外部操作。

| 要求 | 应验证的结果 | 证据 |
|---|---|---|
| A1 范围 | 筛选正确、覆盖跨页结果 | 已知数据的内容和数量对照 |
| A2 权限 | 操作资格及订单可见范围都正确 | 不同身份的正反向测试，包括越权请求 |
| A3 内容 | 文件可打开，金额和 D2 时间规则正确 | 文件内容检查、实际样例读取与业务判断 |
| A4 数量 | 5,000 条成功，5,001 条明确拒绝 | 受控边界测试，不外推生产容量 |
| A5 交互 | 空、加载、失败、重试和重复点击行为清楚 | 实际页面操作与失败场景记录 |
| A6 交付 | 整合基准可定位，UAT 与最终候选一致 | 代码审查、候选引用、环境和验收结论 |

### 12.2 以父子 Issue 表达分工

| 工作位置 | 当前负责人 / 参与安排 | 输出与前置结果 |
|---|---|---|
| 父 Issue：订单批量导出 | 总责人全程为林；实施阶段当前负责人为 Squad；验收阶段当前负责人交还给林 | 整体约定、子项结果、集成证据和最终交付 |
| 子 Issue：后端导出 | 后端 Agent 执行，甲按团队安排处理工程问题 | D1 / D2、后端基准 → 代码与局部自检（自检） |
| 子 Issue：前端交互 | 前端 Agent 执行，乙承担相应工程职责 | 已确认行为与前端基准 → 交互与状态自检（自检） |
| 子 Issue：集成与审查 | 指定成员完成集成，由独立 Review Agent 负责审查 | 前后端已交付结果 → 集成候选及独立审查结论 |
| 子 Issue：导出验证 | 丙承担独立验证职责，通过局部 SOP 执行检查 | 集成候选 → A1–A5 对应的验证结果与证据，独立性来自验证职责与主体 |

前后端可以同阶段并行，采用 todo 并分配执行者；集成、验证子 Issue 创建为 backlog，先记录分工。Leader 收到阶段变化后检查前置结果，再将相应子项移入 todo，触发既有派发机制。stage 负责进度观察与唤醒，backlog 明确承载尚待前置结果的工作。

本例保留验证子 Issue 是因为它有独立责任和交付。若由原执行者完成一项简单自检，可以直接附在原 Issue 上。没有协调子 Issue 和验收子 Issue；Leader Run 与最终验收记录都在父 Issue。

### 12.3 完整推进与异常路径

| 步骤 | 动作 | 同一工作链路上的结果 |
|---|---|---|
| 1 输入 | 林创建父 Issue，明确自身为总责人，选择 Squad 为当前负责人，明确先研究 | 当前目标与未知项进入共享记录；林为稳定人工总责人；不自动创建 Task |
| 2 分析 | 已授权 Leader Runtime 执行分析 Run | Run 直接属于父 Issue，提出业务问题和分工建议 |
| 3 决定 | 林确认 D1，并按工作安排允许实施 | 工作约定明确，成员职责和资源安排可用；无须逐 Run 重复确认 |
| 4 分工 | Leader 创建必要子 Issue 并分配 | 前后端以 todo 启动，集成与验证保持 backlog；同一工作只选一次派发；本轮协调结束 |
| 5 执行 | 甲、乙的执行环境分别工作 | Run、代码变化与自检各归对应子 Issue；成员也可从已关联 Issue 的本地交互入口继续 |
| 6 变更 | 林确认 D2 | 父级与受影响子项引用新约定；向执行补充，新要求使用相应版本的样例验证 |
| 7 断联 | 乙的 Runtime 离线 | 当前 Run 结果待核实，后端独立工作继续；集成和验证仍等前置结果 |
| 8 接续 | 乙确认原进程停止并提供补丁；丁提供允许乙使用的替代 Runtime | 乙保留工程责任，丁仅提供执行资源；已有授权和工具条件满足后，新 Run 读取 D2 与补丁接续，不承诺跨机恢复旧 session |
| 9 集成 | 前后端满足各自自检要求，负责人推进集成子 Issue | 形成候选 C1，保留原结果与整合基准 |
| 10 验证 | 验证子 Issue 调用 SOP，发现导出越过可见范围 | 验证工作本身状态置为 done，但产出结论为“A2 权限测试不通过”，证据绑定 C1；本例此时全部子项关闭，启用的 `child_done` 唤醒仍负责父项的 Squad Leader |
| 11 返工 | Leader 依据证据结论（A2 不通过）而非状态（done）判断，协调定向返工 | 绝不因子项全为 done 误推父 Issue；后端子项重新置为 todo/in_progress 返工；原集成、验证子项回退至 backlog 等待修复，无关前端结果保留 |
| 12 重验 | 后端修复完成置为 done；原集成子 Issue 进入 todo，更新基准并审查形成 C2；随后原验证子 Issue 进入 todo 重验 | C2 审查通过，验证子 Issue 调用 SOP 重新验证通过，A1–A5 证据均绑定 C2 并记录为通过；本轮子项再次全部关闭，`child_done` 唤醒仍负责父项的 Squad Leader |
| 13 提交 | Squad 汇总 C2 候选和完整通过证据；按模拟流程将父 Issue 当前负责人交给林验收 | UAT 准备若涉及额外外部动作先取得对应授权；环境不具备则保持明确等待 |
| 14 验收 | 林作为总责人及指定验收人实际操作并读取文件，对 A1–A6 作出业务接受决定 | 操作记录与验收决定直接属于父 Issue；各完成入口统一核对决定者、当前候选与标准 |
| 15 驳回分支 | 若存在缺口，林按流程回退并明确交回 Squad | 父 Issue 重新推进，Leader 在父级产生新 Run，相关子项定向修复；再次提交新候选 |
| 16 接受分支 | 林接受最终候选 | 按人工验收约定完成父 Issue，记录代码、环境、边界及发布状态 |
| 17 改进 | 后台评价引用权限失败与修复，形成候选检查方法 | 不为每次评价建立 Issue；需要独立改进实施时再建改进 Issue，后续 Benchmark 与审核发布，不改写原交付 |

平台强制规则（第 6.4 节）覆盖全部完成入口：林作出有效验收决定后，获授权的完成动作按该决定推进。PR 合并、Agent 报告结束和子项全部关闭先记录为工作事实；林尚未批准当前候选时，父 Issue 保持原工作状态。改用自定义完成状态也执行相同校验。若项目目标是上线，应在完成要求中加入上线与相应验证。

### 12.4 同一证据怎样被复用

```text
父 Issue：订单批量导出 / D1、D2 / A1–A6（总责人：林）
  ├─ 直属 Leader Run：分析、安排、汇总
  ├─ 后端子 Issue → 实施 Run → 代码与局部自检
  ├─ 前端子 Issue → 断联记录 → 交接输入 → 后继 Run
  ├─ 集成子 Issue → 候选 C1（独立核验）
  ├─ 验证子 Issue（状态 done）→ SOP → A2 不通过证据
  │    └─ 依据不通过结论触发定向返工：
  │         ├─ 后端原子 Issue 返工
  │         ├─ 原集成子 Issue 更新并审查 C2
  │         └─ 原验证子 Issue 重验 → A2 通过证据
  └─ 父 Issue 的人工验收决定（林）→ 交付记录
       └─ 来源引用 → 后台评价 / 候选贡献
            → 有必要时建立改进 Issue → 回归与发布
```

专题二消费失败事实组织返工；专题 3B 组装修复需要的上下文；专题四据同一事实分析成本与质量；专题五展示需要谁采取什么行动。原生 Issue、Run 和相关证据引用承担共同工作主线。

### 12.5 最小路径：修改导出按钮文案

假设成员已有项目权限、可用 Runtime 和明确低风险完成规则，所需信息也已齐备：

1. 成员一次提交“把导出按钮文案改为批量导出，并检查实际显示”，选择执行 Agent / 使用已配置安排。这是创建并开始该 Issue 的一个业务动作。
2. Agent 在此 Issue 上执行，提交修改、实际显示检查和结果；已有信息自动进入工作记录，不创建子 Issue 或另填核验表单。
3. 按本例约定，成员查看结果并接受，是第二个业务动作；如果项目预先允许该类工作按指定检查自动完成，则这一步可由已有规则完成。

这里计数的是两次业务提交动作，不声称当前 Multica 所有界面都只需两次鼠标点击。具体控件与自动化覆盖由专题五验证；有缺失授权、业务歧义或验证失败时才出现对应处理。Human 自己完成时也使用同一个 Issue，直接提交变更与验证，不强制伪造 Run。

## 14. 当前专题取舍与后续研究

| 取舍 | 依据与影响 |
|---|---|
| 使用 Issue / 子 Issue 共模 | 分工复用现有负责人、状态、评论和 Run；拆分按独立责任与结果，避免子项泛滥；偏离 V1 初始 Task 层待用户确认 |
| 区分当前处理人与总责人 | 当前处理人（Assignee）随步骤流转，总责人（Member）全局稳定并负最终责任，避免 Agent 主导时责任悬空 |
| 工作状态与结果结论解耦 | status（如 done）仅表示工作推进进展，质量通过与否依据 Evidence 结论判断，验证失败可置 done 但结论不通过并触发定向返工 |
| 确立平台强制规则清单 | 将人工验收门禁拦截、未响应门禁挂起、他人机器授权等硬性代码拦截与提示词约定清晰切分，守住安全质量底线 |
| 允许子 Issue 指派 Squad 但限一层 | 支持垂直领域小队协作，但严格限制一层嵌套，避免组织递归发散失控与额度爆炸 |
| 线性 stage 局限由专题二消解 | 当前接受 stage 线性推进限制，将 SOP 复杂 DAG 与 Issue stage 的双轨矛盾作为专题二首要问题深化 |
| Run 直接关联业务 Issue | 协调、实施和重试沿用已有运行链，不再维护中间业务 Task |
| 验收直接记录在 Issue | 消除验收任务的重复完成规则；实际检查和接受决定分别有证据 |
| 状态与交接沿用 Project Workflow | 减少主干重建；人工完成要求和新 SOP 能力需明确配置或扩展 |
| 权限与 Runtime 基于现有能力完善 | 明确专题归属和常见工作规则，避免重新设计通用身份系统 |
| 私有会话与后台活动按实际来源接入 | 不强制所有活动业务化；真实覆盖和成本缺失显式保留；允许先工作后关联 Issue 并标注补录 |

## 15. Multica 基座治理对齐

本节为本专题此前涉及执行与流程控制的表述提供统一解释；与旧版冲突时以本节和[架构治理基线](governance-baseline.md)为准。

- Issue、Sub-Issue、Assignee、Squad、Project Workflow、Comment 和 Run 沿用 Multica 原生机制。平台强制规则优先扩展现有状态写入和权限校验，不另建控制平面。
- SOP 的 DAG 可以决定流程节点何时就绪，但不拥有 Issue 状态、Run 生命周期、Runtime 选择或成员权限。节点执行必须调用 Multica 既有派发与 Run。
- 旧版讨论的独立 Delegation Grant 服务、Dispatch Controller 和第二套控制代次不进入架构。已证明的多入口前置、步骤重入与报告消费缺口仍须补齐：优先在原 Issue / Run 保存最少关联，由既有写入链共享检查。附属轮次引用表达流程语义，不授予权限或复制 Run 状态。
- Host、Daemon、Runtime、Provider Adapter、Session、Process、Workspace 和 Artifact 均以 Multica 现有实现为基线；本专题不定义第二套执行平面。
- 历史源码研究和原型测试保留为证据，但不能仅凭原型通过就认定新增控制对象必须进入生产实现。
