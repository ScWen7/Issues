# 研发工作的生命周期

本专题中的工作约定和责任交接遵循[跨层业务契约与协作协议](cross-layer-contracts.md)，对象状态遵循[统一生命周期、状态机与事件模型](lifecycle-state-event-model.md)，并发改派、候选换版与验收竞争、接管和旧执行隔离遵循[核心协作一致性与并发控制模型](core-consistency-concurrency.md)。本专题维护 Issue 责任与工作生命周期的具体规则。

团队在 Issue 上明确目标、负责人、分工和交付。成员可以从平台接下工作，也可以在本机开展调查后，把选定的结论、变更或报告交给团队。接手者在同一 Issue 找到现在要完成什么、哪些结果能用、还需要谁决定什么。[产品总览](overview.md) · [工作台入口](05-unified-workbench.md)

## 1. 项目怎样组织工作

项目列表汇总多项工作的状态和负责人。在 Issue 内讨论和执行，在需要独立承担责任的地方拆分。由人自行完成的小改动，可以只留一条工作记录、实际变更和检查结果。跨仓、跨成员工作仍以一个共同目标组织。

## 2. 工作约定

提出人说明想达到的结果，当前负责人与有权决定范围的成员明确完成要求、所需交付，以及谁可接受。工作约定可直接引用适用的项目规则。项目规定的必需项随本项范围生效，负责人从获准的方法中选择如何满足要求。实施中改变范围时，把决定留在原 Issue，指明受影响的工作、标准及已有结果。接下来采用新要求的执行与交付引用该决定。

## 3. 分工与依赖

| 团队关系 | 工作放在哪里 | 接收方能取得什么 |
|---|---|---|
| 负责人仍承担同一份交付，只需别人解释、查看或帮忙操作 | 原 Issue 的评论、提及或已有线程。一次受管 Agent 协助引用本项 Run | 该次答复、变更或调查记录 |
| 一份结果可以单独指派、等待、接收或退回 | 子 Issue，明确负责人、所需输入、交付和接收方。修正沿用原子项 | 该分工的结果、条件和证据 |
| 工作已经有人负责，其中一段有成熟的检查或执行方法 | 现有 Issue 调用 SOP，节点记录步骤、结果和对应执行 | 该次流程的具名产物与结论 |
| 两项独立工作需使用同一结果 | 各自在所属 Issue 推进，使用方引用生产方交付 | 所用修订、可用条件和来自哪项工作 |

Main Bot 可直接完成其获准处理的工作，也可以把短时协助交给一个或多个获准 Worker。每份委派说明任务范围、输入版本、预期输出和返回位置。同一份分工只经一个入口派发，已指派给子 Issue 的工作由子项接手。项目选用的 Skill、Rule 或 Playbook 可以用于上述任一方式。调用 SOP 时，节点就绪、结果消费和授权内返工由该次 SOP Execution 处理，Issue 负责人接收其出口交付并组织其余工作。

## 4. Issue、执行和交付

父子 Issue 使用同一工作模型，分别承担各自的目标、负责人和完成要求。父项按共同目标判断集成交付。取消子项后，父负责人判断其原有要求是否已取消、替代或仍需完成。

每次受管协调、实施或核验均沿 Multica 原生 Task / Run 链记录。协调 Run 和同项 Worker Run 归其直接服务的 Issue，独立子项的实施和核验 Run 归子项。宿主 Session 可以接续多个 Run。原生委派、技术重试与人工重跑按实际关系保留。一次 SOP 节点履行可引用多次实际 Run。成员亲自操作时，在 Issue 提交说明或产物，记录真实来源。[源码与测试入口](../research/01-source-evidence.md) · [统一术语](../../CONTEXT.md)

## 5. 负责人、派发与执行资源

### 5.1 谁负责当前工作

Issue 可以待指派，同一时点至多有一个当前负责人。建单时可显式选择成员或 Agent，也可按项目当前步骤带入负责人。后续在原选择器改派，或由 Project Workflow 交接。

| 当前负责人 | 推进方式 |
|---|---|
| 成员 | 自行处理、在原评论请 Agent 协助，或拆出独立分工。需要转交整项工作时修改指派。 |
| Agent | 可承担一次明确交付。受托持续协调时，作为 Main Bot 自行执行或安排获准的 Worker，在原 Issue 接收结果并交回保留事项。 |

评论框可预览可能触发的 Agent。实际派发受状态、权限、资源和线程路由影响。指派给成员时走原通知，指派给 Agent 时按当前资格安排执行，已开工以 Run 回报为据。[指派、评论协助与交接](../research/05-source-evidence.md#指派评论协助与交接)

### 5.2 区分“当前处理人”与“总责人”

当前负责人（Assignee）推进眼前的工作，可随步骤交接。Agent 负责当前工作时，人工总责人（Accountable Member）对目标、业务范围、重大取舍及交付承担责任。项目已有分工可直接引用，需要单列人选时可使用 Multica 的单值工作区成员属性。项目要求限制改任时，在相应操作核对权限。

创建人、可追溯的提出人和 Run 的人员归因分别取自建单、需求来源和该次执行记录。需要具名验收时，工作约定指定验收人（Acceptor），可以由总责人担任或另行指定。机器所有者决定谁可以使用其 Runtime，额度提供方决定哪些用途获准。当前负责人按问题寻找业务决定者、工程支持者或资源所有者。[成员属性与归因](../research/05-source-evidence.md#指派评论协助与交接)

### 5.3 Main Bot 怎样持续协调

成员把 Issue 托付给 Main Bot 时说明期望结果，项目已有的规则、完成条件和资源授权可以直接沿用。需要补充的是本项特有的边界或保留决定。此次委托由有指派权的成员确认，在 Issue 上留下工作约定，并将 Assignee 设为受托 Agent。Main Bot 自行选择执行方式。只需一次协助时，在原 Issue 提及 Agent 即可。

协调职责只在明确受托的 Issue 和范围内生效。同一个 Agent 在其他 Issue 接到一次提及、审查或子项实施时，按那次请求执行。Main Bot 从项目可见的 Agent 配置与能力说明选择 Worker，派发前核对本次调用权限。委派一并交代当前步骤、需要的输入和输出，以及遇到哪类问题该找谁。

| 工作进展 | 本轮怎样处理 |
|---|---|
| 接手 | Main Bot 在自己绑定的获准 Runtime 上运行，读取有效工作约定、已有决定、在途分工及当前交付，按第 3 节选择直接处理、同项协助、子项或 SOP。 |
| 等待其他工作 | 对同 Issue 的具体 Worker Run，先按委派评论核实执行归属，再登记 Issue Wakeup 等待其终态。尚未取得 Run 时，保留原分工和复核条件。等待安排生效后即可结束本轮。已取得独立 Multica Run 的 Worker 在各自获准的 Runtime 上继续；宿主会话内部的异步工作须按该宿主的回报能力接收。只让依赖该结果或决定的工作等待。 |
| 收到回唤或接续工作 | 后续协调使用普通 Task / Run。读取原 Issue 的当前指派、授权、工作约定、Run 谱系、候选及消费记录，再判断还有什么要处理。多个唤醒可指向同一轮检查，每份结果按原委派分别核对。 |
| 处理结果 | Worker 完成、失败或取消提示执行已有终态。Main Bot 核对实际制品、证据和版本后，采用可用结果、安排修正或向有权成员提交待决定的问题。子项交付按父子关系接收；SOP 按其受托范围交还出口。 |
| 提交候选 | Main Bot 在原 Issue 汇总当前 Candidate、证据、缺项和待决事项。按第 6 节约定进入检查、具名验收或完成。 |

恢复时遇到已处理的结果，沿用该次消费记录。迟到或原授权下的结果归原 Run 和原候选，由当前负责人判断能否在现行约定下复用。回唤的原生能力与适用边界见[Main Bot 生命周期与 Issue 持续推进模型](../research/mainbot-lifecycle-and-progress.md)。

### 5.4 子项交付如何回到父项

父项把可独立交付的工作分给子 Issue，子项可直接指派给成员或 Agent。若子项也需要持续协调，由有权成员在该子项明确授权。父项当前负责人按约定接收子项交付。

启用 `child_done` 时，满足阶段或全部子项关闭的条件后，父项当前负责的成员收到通知，获准运行的 Agent 获得运行安排。子项取消也可能满足关闭条件，父项负责人仍须核对实际交付与未满足的要求。[父项回唤规则](https://github.com/multica-ai/multica/blob/fdfbfcd5e5d30c135255e63ab9af4c52672b7bbc/docs/engineering/issue-wakeups.md#L462-L477)

## 6. 工作状态与完成条件

### 6.1 项目状态

沿用 Multica 状态目录和项目配置。`backlog` 表达收集或等待安排，`todo` 表达已安排，`in_progress` 表达正在推进，`in_review` 表达候选待核验或验收，`blocked` 指向具体阻塞，`done` 和 `cancelled` 分别记录完成与取消。自定义状态按其生命周期类别解释。Run 的排队、运行和收尾状态由执行记录提供。

### 6.2 状态推进与负责人交接

项目配置了 Project Workflow 时，由原生工作流在进入步骤时移交责任。提交候选后，接收方可检查已交版本，要求补齐材料或移交给约定的验收人。转交待验收时核对该步骤的进入条件。成功结束 Issue 时须满足本项的全部完成条件。成员在一个 Issue 中自行完成的工作，沿用同一套完成约定。

把私有项目 Issue 交给成员时，按接收者自己的身份核对其能否打开该 Issue。直接指派、项目步骤自动交接和批量转交均在责任变更生效时核对。若接收者无权读取，已有工作保留原负责人及步骤，由有权成员调整项目访问或另选接手者。新建时提示创建人另选可见成员，或在工作流允许时留待指派。项目已经可读但缺少一份外部材料时，可以先接手，并在 Issue 标明缺项、补交人和受影响的工作。[原生指派与项目可见性](../research/05-source-evidence.md#项目访问与执行资格)

同项 Worker 回报自己负责的部分和遇到的阻塞。当前负责人判断整项工作是否受阻、是否已具备送审条件。对于受托 SOP，由节点按本次激活推进。项目步骤交接时，接手者从 Issue 读回本次进入步骤的决定、目标及在途工作。已有排队 Run 可能覆盖新触发，是否取得新 Run ID 不能用来判定交接是否生效。

| 完成约定 | 满足什么条件后可以完成 |
|---|---|
| 项目已允许此类低风险工作按检查完成 | 有完成权的成员、Agent 或项目流程核对当前变更及规定的检查结果，在原 Issue 完成。只有执行权时把材料交给有完成权的人。 |
| 本项要求独立审查 | 由承担独立核验职责的成员、Agent 或验证流程给出覆盖当前候选的结论，随后按本项约定处理。 |
| 本项要求具名业务验收 | 指定成员在 Issue 接受当前候选与适用标准，或注明缺项并退回。各成功完成入口均核对这份有效决定，包括成员、Agent、流程、PR 合并及自定义成功状态。 |

受审文件可引用原交付区中的具体附件版本。上游 PR 自动推进可按单个 Issue 关闭。需要具名验收的事项采用此配置，允许自动推进时须将该入口接入上述完成条件。标准或候选变更后核对受影响范围，并取得对当前交付适用的决定。[原生工作流与 PR 完成条件](../research/05-source-evidence.md#指派评论协助与交接)

### 6.3 转交、暂停与取消

改派、撤销持续委托或结束 Issue 时，原协调者失去以该次委托派发和消费结果的权限。工作流把 Assignee 交给验收人时，同样按交接处理；仅请求对方作决定时，可以保留当前指派。再次指派给同一 Agent 也须核对本次授权。

手动改派会保留在途 Run。进入配置了处理人的项目步骤时，原交接预览会列出相关旧 Run，换人且有相关 Run 时默认勾选停止，成员可以取消勾选。接手者逐项判断哪些 Worker 可继续、哪些要停止或隔离。修改同一份工作副本前，确认旧执行结束或隔离其写入。暂停注明等待对象和解除条件。取消 Issue 时记录工作决定，明确活动执行的处置。停止请求、宿主终态及清理结果分别保留。[工作流交接](../research/05-source-evidence.md#指派评论协助与交接) · [取消与清理回执](../research/03a-source-evidence.md#35-取消确认与资源复用的适用范围)

### 6.4 动作生效的条件

| 动作 | 产品规则及其承载 |
|---|---|
| 使用其他成员的机器 | 由 Multica 按所有者共享范围检查 Runtime 访问，另查项目读写和本次工具动作授权。 |
| 回答人工门禁 | 在 Issue 记录指定人对问题、候选、动作范围的答复。未答继续等待，超时可提醒或转交。 |
| 从受控工作流步骤写入 | 在原写入链核对步骤、本次进入步骤的身份和获准执行。同名步骤再次进入时，旧执行的回报仍归原轮次。 |
| 为由 SOP 托管的分工开工 | 协调 Agent、评论、工作流和手动入口均检查同一授权、前置、输入和当前安排。同次请求重送使用原 Run，各自就绪的独立分支可以并行。 |
| 使用子项或 SOP 结果 | 核对生产方、候选、制品与检查结论，按本次交付采用。普通自主协作由负责人判断，托管范围的条件由原派发及结果接收入口落实。 |

## 7. 讨论、决定和共享上下文

### 7.1 评论、决定与接续

评论供协助、解释或补充进展。范围、放行、接管或验收决定记录决定者、对象、版本和作用范围，相关子项引用原讨论。后台通知将成员带回问题，问题按原 Issue 的权限及当前安排处理。

Worker 在结束前就需要答复时，在原委派线程写明问题、受影响的工作和答复人。需要 Main Bot 介入时，Worker 可以在调用权限内显式提及它。也可事先约定由 Main Bot 订阅该 Worker 的评论，并在恢复时核对原线程及尚待答复的问题。成员可以直接与 Worker 对话。涉及工作范围、风险或验收的决定留在 Issue，由相应接收方依当次授权采用。

成员或 Main Bot 要纠正正在执行的动作时，先定位同一 Issue 的具体 Worker Run。在权限和宿主支持的情况下，向该 Run 补充输入并检查投递回执。若只能排到后续回合，原执行的处置要单独确认；紧急停止沿原 Run 的停止入口处理。

### 7.2 Work Context 的来源与组装

| 成员要查什么 | 到哪里取 |
|---|---|
| 本项目标、约定、负责人、父级决定 | Issue、父子关系、评论和活动 |
| 本次工程与业务依据 | 项目仓库与修订、获准的原资料和引用位置 |
| 这段工作实际使用的方法和输入 | Agent 配置、发布版本、SOP 节点和原 Run 的投递或调用记录 |
| 可以接着用的结果与未决问题 | 可取得的变更或制品、对应检查和 Issue 上待作的决定 |

共享上下文通过引用组织。成员交接时按自己的权限读取。仅保存在离线机器上的材料标明暂不可取。投递回执记录送达的材料，实际加载、调用和产物检查分别以各自的证据为准。[团队能力与项目上下文](03b-capability-governance.md)

## 8. 本地交互式开发怎样接入

成员从项目或 Inbox 接下工作，也可以先用自己的 CLI 或 IDE 调查。有现成 Issue 时，将选定的结论或可取回的变更交到原项；调查产生了值得独立推进的新目标时，可为它建 Issue。哪些执行能在途中关联、哪些成果由成员事后署名提交，按实际入口处理。[本机工作与原 Issue](03a-execution-plane.md)

交回结果后，当前负责人按接下来需要谁做什么来安排工作。

| 接下来要做的事 | 谁负责，怎样继续 |
|---|---|
| 请同事查看交付或回答问题 | 在原评论中提及同事，请对方针对该版本或问题回复。原负责人继续推进。 |
| 把剩余工作交给同事 | 有指派权的成员在原 Issue 改派。接手者按自己的权限取得指定版本和代码基准。原作者提到还有改动存在其本机时，由能取得该改动的人补交；接手者可先推进只依赖已交版本的部分。 |
| 本次工作已经满足完成约定 | 有完成权的主体按本项约定核对当前交付。需要指定成员接受时，由该成员对当前候选和标准作决定。 |

已共享的交付按版本和读权提供，当前负责人以原 Issue 上已生效的指派为准。具体操作见[工作台](05-unified-workbench.md)，完成条件见[本项约定](#62-状态推进与负责人交接)。

## 9. 执行结果与验收

开工前明确工作约定、授权、代码基准、必要输入、预期制品和检查方法。交付时引用实际完成范围、变更及检查结果，并说明缺项。从受管执行可取得的字段由 Run 提供。

| 记录 | 可以据此判断什么 |
|---|---|
| 署名说明、Diff、Commit、Patch | 谁报告了什么，哪份基准上发生了什么变更 |
| 测试、操作或文件样例 | 哪个候选在什么环境、输入和身份下满足哪些要求，哪些项未覆盖 |
| 独立 Review | 承担独立检查职责的人或 Agent 对哪些要求作出了什么结论 |
| 人工放行、验收 | 谁接受了何种限制或哪一版交付，适用于哪个动作和范围 |
| 模型或 Scorer 评价 | 给定证据和评价器版本下的质量判断 |

自检、独立核验和未验证按实际承担检查职责的主体区分。测试、Review、SOP 是方法。执行者亲自运行 SOP 时归自检。单项要求可记通过、不通过、未验证或有理由的不适用。

核验工作交回一份符合约定的失败报告时，出具报告的职责可以完成，被检查的候选仍待修正。自主组织的工作由相应 Issue 的负责人将失败交回生产方。SOP 已获返工授权时，可依受托范围重开生产与后续检查；超出范围的处置交回有权负责人。只让依赖失效结果的工作等待新候选。父 Issue 根据本项目标、交付条件和适用的验收决定判断整体完成。

## 10. 多 Issue 并行与异常接续

### 10.1 优先级和依赖

项目负责人按工作优先级和资源容量协调多项工作。资源所有者管理共享，业务负责人处理尚待决定的问题，依赖方等待具体交付。调整优先级只影响后续安排，实际开工和在途进展以 Run 为据。多个项目共用资源时，由涉及的项目和资源负责人约定顺序。

自主分工可用线性 stage 组织子项唤醒，父项当前负责人收到相关变化后核对交付。稳定的分支依赖由 SOP 声明，各分支在自己的必需前置满足后即可推进。跨项使用结果时标明生产方和可用条件。

### 10.2 常见中断

| 发生什么 | 谁可继续、在哪里处理 |
|---|---|
| Runtime 未就绪或执行中断联 | 平台仍开放 Issue、讨论及已共享交付。负责人查看最近确认进展，核实在途执行和副作用后恢复原机或改用获准资源。 |
| Main Bot 的 Runtime 离线 | 其他机器上的同项 Worker 和独立子项可在各自授权内继续。原 Runtime 恢复，或有权成员在所属 Issue 改派后，协调者读取当前指派、在途 Run 和待消费交付。若改绑同一 Agent 的机器，核对该 Agent 在各 Issue 的排队工作。 |
| 候选失败或制品失效 | 失败记录保留原基准与检查。生产方修正或恢复制品，接收方核对新候选。未依赖失效结果的工作可继续。 |
| 需要人决定范围或接受例外 | 在原 Issue 标出问题、可决定的人和影响面。只暂停依赖该答案的工作。 |

接手修改代码时先取得固定基准、可交换的提交或补丁和未完成事项。旧执行已停止或写入已隔离后，接手者以自己的授权继续。一次换机可以使用新 Session 和后继 Run。[跨机接续证据](../research/topic-03a/machine-handoff.md)

## 11. 工作如何支持后续复用

稳定环节可在 Issue 调用 [SOP](02-sop-workflow.md)。正式能力和外部资料按[项目范围、版本和当前授权](03b-capability-governance.md)使用。本次实际执行留在原 Run，用量归直接服务的 Issue，父项和项目按同一用量事实汇总。后台评价、知识提炼和 Benchmark 分别记录自身消耗。

有推广价值的结果可作为方法改进的依据，候选在适用样例上与现有版本比较，由有权成员审核发布。需要独立实施和交付的改进工作可建 Issue。后续采用该版本的工作记录实际效果。[成本、质量与改进](04-cost-quality-improvement.md)
