# 专题三 A · 执行平面与宿主适配

版本：V0.2 探索基线

日期：2026-11-14  
状态：源码研究与设计探索中  
前置：[专题一：统一工作生命周期](01-unified-work-lifecycle.md)、[专题二：SOP 与研发工作流融合](02-sop-workflow.md)  
源码依据：[Multica 执行平面研究](../research/03a-source-evidence.md)

## 1. 目标

建立一套面向团队成员本地 Agent 环境的统一执行平面。平台负责把已授权的工作送达适合的执行环境，管理执行生命周期，收集过程与结果，并在失败、离线、重启和人工接管时保持工作连续性。

专题三 A 聚焦真实执行能力：

- 成员机器及其本地 Agent 工具如何注册、发现和保持在线。
- Run 如何从服务端进入本地环境，经过准备、领取确认、执行、回报和清理。
- 不同 Agent 宿主如何接入统一的执行与观测契约。
- 本地目录、Git 工作树、远端仓库和普通制品如何成为执行输入。
- 会话、工作区和执行结果如何在同机连续、跨机接续及崩溃恢复中保持关联。
- Script 如何作为受管执行类型使用相同的授权、派发、Run 与结果回报链。
- 凭证、项目访问、Runtime 共享、进程树和文件系统如何落实执行边界。
- 开发者从本地 CLI / IDE 主动工作时，如何关联 Issue、选择共享内容并保留真实执行来源。
- 上下文与团队资产如何进入各宿主，以及投递、加载、结构化结果和制品分别有哪些可观察证据。

本专题交付执行平面业务模型、宿主适配模型、工作区与会话连续性模型、生命周期与恢复规则、平台能力契约，以及可运行原型的验收场景。数据库表、接口字段、部署拓扑和具体实现框架在机制评审后展开。

## 2. 研究起点：先区分四个概念

Multica 当前实现揭示了四个容易混淆的层次：

| 概念 | 含义 | 关键问题 |
|---|---|---|
| Daemon / Host Agent | 成员机器上常驻的本地执行管理进程 | 如何连接平台、发现本机工具、领取工作、管理进程与本地资源 |
| Runtime | 平台可调度的具体执行目标，通常对应一台机器上的一个 Agent 工具或自定义 Runtime Profile | 哪台机器上的哪种执行能力可以承接这项工作 |
| Agent / Role | 工作承担者及其指令、模型、技能和配置 | 谁负责这项工作，以什么角色和能力执行 |
| Run / Execution | 一次实际执行记录 | 何时领取、何时真正启动、执行了什么、结果和证据是什么 |

**当前研究判断：Runtime 是可调度的执行目标，Daemon 是该机器上的执行管理者，Agent 是工作身份 / 配置，Run 是一次实际执行。** 后续设计将验证是否需要把 Host、Runtime Profile、Provider Adapter、Workspace 等进一步显式区分。

## 3. Multica 当前执行链：需要吸收的机制

按源码追踪，Multica 的执行路径可概括为：

```text
服务端 Run 队列
  → 匹配 Runtime / Daemon
  → Daemon claim
  → 本地准备（工作目录、上下文、技能、MCP、环境）
  → StartTask 接受本次领取者的开工登记
  → Provider Backend 启动宿主工具
  → 消息 / 工具活动 / 用量持续回传
  → 完成、失败或取消
  → 终态回报与清理
  → 恢复扫描、会话接续和 GC
```

这里有三个特别重要的设计点：

1. **领取与开工登记分开。** Daemon 领取后准备环境，再调用 StartTask；服务端接受登记后标记 running，随后由 Backend 启动宿主。准备完成、服务端登记和进程已启动分别有对应的观测事实。
2. **执行状态需要多个回执。** 已入队、已派发、已领取、已 Start、进程已启动、Agent 已产生语义活动、已得到终态结果，是不同事实。平台需要根据实际可观测能力定义统一状态和证据。
3. **本地执行需要独立的恢复闭环。** 服务端持有工作与 Run 事实；Daemon 持有本机进程、工作目录和宿主会话的管理责任。重启后先恢复原执行和工作材料，再决定继续、重试、转交或等待人工。

详细源码路径和反例见[研究记录](../research/03a-source-evidence.md)。Runtime 注册按 Workspace 进行，命令由 Host 本地解析；授权分别核对 Workspace、Daemon 与 Runtime Owner。取消回执保存恢复指针；已协商的 Provider 清理确认处理同 Agent / Runtime 的后继保护，EnvRoot 锁另负责运行期目录互斥。

## 4. 需要形成的平台执行抽象

本节列出待设计的概念，不预设最终类名或实现结构。

### 4.1 Host / Daemon

Host 表示成员提供的物理或虚拟执行环境；Daemon 是该 Host 上负责注册、心跳、领取、启动、停止、恢复和本地资源管理的常驻服务。

需要研究：

- 一个 Host 能否运行多个 Daemon Profile，多个 Workspace 如何共享同一机器资源。
- Daemon 重启、升级、退出和系统休眠时，运行中任务如何收敛。
- 多个 Daemon 或用户会话访问同一工作目录时，如何协调文件锁、进程和容量。
- Host 的可用性、能力、资源容量和所有者共享授权如何表达。

### 4.2 Runtime / Provider Adapter

Runtime 是可被调度的具体执行目标。Provider Adapter 把平台统一执行契约映射到宿主实际协议。

宿主协议可能包括：

- CLI 参数与标准输入输出流。
- JSONL / JSON-RPC / App Server。
- ACP 等标准化 Agent Client Protocol。
- 厂商 SDK 或本地服务 API。
- 远端托管执行服务。

平台统一的是执行生命周期和结果契约，不要求所有宿主采用同一种底层通信协议。

适配器需要明确支持能力：启动、流式消息、工具事件、取消 / 中断、会话恢复、追加指令、Token / Cost Usage、文件与制品访问、结构化终态结果。能力需要可协商、可报告，并区分“宿主原生支持”和“平台补偿实现”。

能力矩阵还需记录两项事实：Provider Adapter 是否能发布“已经观察到权威终态”（`TerminalObserved`），以及是否能可靠识别会话恢复被拒（`ResumeRejected`）。前者帮助区分等待宿主结果与清理收尾；后者提供明确恢复拒绝证据，新会话重试还结合暂时拒绝、共同错误识别和限定兼容判断。各 Provider 的实际条件、版本探测、执行副作用及结果缺口逐项核对，研究证据见[第 7 节](../research/03a-source-evidence.md#7-新增追踪上下文凭据与会话结果)。

### 4.3 Execution Environment / Workspace

执行环境负责提供 Agent 或 Script 实际工作的目录、代码和配置。

初步拆分：

| 输入类型 | 例子 | 需要解决的问题 |
|---|---|---|
| Git Repository | GitHub 仓库、指定 commit | Checkout、分支 / Worktree、补丁交接、合并和交付 |
| Local Directory | 成员本地已有项目 | 原地执行、路径授权、互斥或隔离副本、清理边界 |
| Non-Git Workspace | 普通目录、文件包、生成式项目 | 快照、增量同步、冲突处理、交付格式 |
| Artifact Input | XLSX、图片、文档、构建产物 | 内容寻址、版本、可访问性、校验和 |
| Multi-Repo Workspace | 前后端多个仓库 | 基准组合、依赖关系、跨仓库候选和统一交付 |

Multica 的 Git Worktree 是 Git 仓库场景下的一种隔离与交付策略，不应直接成为平台所有工作区的统一抽象。平台需要把“工作区生命周期”和“代码隔离策略”分开研究。

### 4.4 Session / Continuity

Session 是宿主工具的会话连续性载体；它与 Run、Issue 和 Workspace 关联，但生命周期不同。

需要分别回答：

- 一项 Issue 多次 Run 是否继续同一宿主 Session。
- 同一个 Agent 在不同 Runtime 上能否恢复同一 Session。
- Session 是否绑定本机凭证、CLI 版本、HOME / CODEX_HOME、工作目录或宿主账号。
- 宿主会话历史丢失、不可访问或恢复被拒绝时，如何生成连续性缺口并从 Work Context 恢复。
- 一个 Run 内部的宿主重试与平台创建新的 Run 如何区分。

平台的长期工作连续性应以 Issue Work Context、Decision、Artifact 和 Evidence 为基础；宿主 Session 是加速连续工作的执行资源。

研究中分别判断“原执行仍活跃”“已收到宿主权威结果”“会话恢复被拒”和“历史材料缺失”。宿主内部重试按原 Run 留痕；已结束执行的后继工作继续采用专题二的新 Run / Node Attempt 关系。是否适合新会话重试，需同时核对恢复失败证据、已经执行的工具动作和可重放范围。

### 4.5 Script Executor

Script 与 Agent 共用 Run、Runtime、授权、工作区和终态回报机制，但执行适配不同：

- Agent Adapter 启动智能体宿主并消费消息流。
- Script Executor 启动受管命令，采集 stdout / stderr、退出码、耗时、制品和副作用记录。

Script 不需要模拟 Agent Session，也不需要伪造模型消息。它应作为统一执行平面中的另一种执行类型。

### 4.6 本地交互式执行的接入

与中心派发并列研究两条入口，沿用同一组 Issue、Run、Session 和证据关系：

| 入口 | 工作归属与共享 | 待追踪机制 |
|---|---|---|
| 中心派发 | 已授权安排经队列领取、准备、执行和回报 | Multica 的 Claim / Start、任务令牌与宿主会话链 |
| 本地主动发起 | 成员在支持的 CLI / IDE 中关联当前 Issue，选择共享的执行段、结果与制品 | 宿主入口怎样建立受管理执行关联，如何切换工作范围、接收补充和回报 |
| 先探索后关联 | 成员选择已有执行片段或结果补录到 Issue，保留真实发生时间、补录来源及采集覆盖 | 可获取的会话记录、实际模型与用量、自述材料和原始证据分别怎样导入 |

一次本地执行同时被宿主观察和平台接收时，研究如何定位同一事实，复用运行与费用记录。Session 可承载多个执行段，关联一个工作范围时只共享已选范围。材料缺失则记录缺口，事后关联按专题一的证据分类处理。

源码追踪优先比较 Multica 的会话关联、TeamAI 的 skill driver 和 agent observation，以及目标宿主的交互入口。先确定入口、身份、执行段与共享控制的业务机制，再选择接入协议。

### 4.7 上下文注入与加载回执

3B 提供适用资产及版本，3A 研究如何在目标宿主上物化这些材料并返回实际加载证据。材料包括 Agent / Role、Skill、Rule、MCP 配置、SOP 和受管 Script 的选定版本及摘要。

需分别记录：期望提供什么、实际取得什么、通过请求还是文件投递、适用宿主与版本、加载证据来自哪里。Multica 的 `ContextReceipt` 已有 delivered、verified、verified_other_version、unverified、not_delivered 等等级；Daemon 在 Backend 执行前构造回执，记录本轮材料和投递通道。verified 来源是指定宿主版本的既有加载探测，当前执行的接收、读取和采用另按实际观测记录；Skill 可用及 MCP 配置存在也分别记录其证据等级。

后续对照 `context_receipt.go`、`execenv/context.go` 及各宿主的 Skill / Rule / MCP 注入入口，形成“资源类型 × 宿主版本 × 投递通道 × 可观察等级”的能力矩阵。3A 提供加载回执，3B 负责资源版本、作用域、审核发布和分发治理。

### 4.8 结构化节点结果与制品回报

专题二要求回报 `pass / rework / fail / human`、具名制品摘要及候选关联。3A 研究这些信息在宿主、Daemon 和控制平面之间的职责划分，先采用以下待验证分工：

| 参与方 | 研究职责 |
|---|---|
| Provider Adapter / Script Executor | 提取宿主可提供的终态、结构化提交和原始输出；Script 保留退出码、标准输出与错误等事实 |
| Daemon / 执行环境 | 在授权范围采集声明制品，记录存在性、大小、内容摘要和可访问位置；保留宿主原始提交及解析状态 |
| 控制平面 | 核对本次 Run、Node Attempt、授权与控制代次、候选及标准引用，持久化回报并处理重复或迟到结果 |
| SOP / 指定核验者 | 按当前工作契约判断门禁和制品要求，决定继续、自修正、返工或请求人工 |

宿主原生结构化结果、显式工具提交和具名产物清单都是待比较通道。解析失败、输出被截断或必需制品未取得时，保留已收到的事实并显示缺失项；Run 的技术结束、节点质量结论、业务接受和资源清理分别记录。具体封装方式在通道核对后确定。

### 4.9 任务身份与成员平台凭证

研究两类凭据的用途：Daemon 连接和管理执行环境的凭据，以及 Agent / Script 执行本次平台操作所用的任务级凭据。平台操作按当前任务授权身份解析；任务身份或令牌缺失时，返回明确缺失原因并等待修复。

优先核对 Multica 的任务令牌、工作区 marker 和 CLI 配置查找顺序，验证环境变量丢失、跳到工作目录父级、换 Runtime、授权撤销后的身份选择。marker 负责提供执行上下文线索，文件读取和进程隔离另由实际执行环境能力约束。

成员为宿主模型服务提供的登录态和额度按既有 Runtime 授权使用；它与平台管理凭据采用不同用途和权限范围。探索目标是复用现有身份与授权机制，明确各宿主和 Script 的实际覆盖。

## 5. 生命周期与恢复必须分层建模

初步将执行生命周期拆为以下阶段：

1. **Eligible**：工作已满足业务与 SOP 的启动条件。
2. **Queued**：已形成待派安排，等待 Runtime 容量。
3. **Claimed**：某个 Runtime 已领取该次执行。
4. **Preparing**：本地工作区、上下文、能力和授权正在准备。
5. **Started**：服务端接受本次领取者的开工登记。
6. **Running**：宿主进程已运行并持续产生执行事实。
7. **Terminal / Outcome Observed**：记录宿主权威结果或平台已作出的完成、失败、取消等判断及其来源。
8. **Settling**：用量、制品、会话、工作区和终态回执正在收敛。
9. **Recovered / Handoff**：原执行恢复、重新派发或交接到新的 Runtime。

这些条目是研究观察点，后续与原生状态及 Node Attempt / Run 关系逐项映射。结果已观察到与资源仍在清理可以同时成立，恢复和交接按原执行事实继续处理。

### 5.1 取消、清理与后续复用

| 已核对的原生机制 | 适用范围与后续研究输入 |
|---|---|
| Provider 清理确认协商 | 当前 `pi / omp / museapp` 在协商对应能力后启用取消清理确认；记录宿主与版本覆盖 |
| 同 Agent / Runtime 后继保护 | 清理等待或清理失败按相同 Agent 与 Runtime 关联影响后续执行；其他工作范围的资源使用需另按其条件判断 |
| EnvRoot 运行期锁 | Daemon 持有本地目录使用锁，与服务端清理确认分别核对 |
| 取消清理专项收敛 | 原生取消登记可在确认清理异常后从 `cancelled` 收敛为 `failed / cleanup_unconfirmed`；保留取消事实、清理原因及恢复材料 |

据此校准专题一的原生复用说明：常规完成回报受状态条件保护，取消后的清理确认有专项路径。平台设计分别保留取消决定、实际执行结果、清理结论、资源占用和后继执行关系，后续用反例确定显示与推进条件。

### 5.2 恢复研究场景

重点研究以下恢复场景：

- Claim 成功但响应丢失。
- 准备环境时 Daemon 崩溃。
- Start 请求成功但回执丢失。
- Agent 进程运行时机器掉线。
- 用户取消与 Daemon 关闭同时发生。
- 宿主已完成但终态回报失败。
- 代码已修改但工作区交付尚未完成。
- 原 Runtime 离线，另一成员接管。
- 原 Leader Runtime 离线，Issue 由其他成员接续协调。
- 已观察到宿主终态，清理仍在进行；取消已登记，清理确认随后失败。
- 准备期间 Grant 被撤销，或控制绑定、节点轮次发生变化；Start 前如何重新核对。
- 本地交互已有执行事实，事后关联或中心重送如何识别同一次执行。
- 结构化结论已收到而制品仍缺失，或旧候选结果迟到时，怎样记录并回报 SOP。

恢复策略需要区分：同一执行重连、同一 Run 的安全重试、新 Run 继续原工作、交接到新 Runtime、人工接管。对外部副作用先对账，再决定是否重放。

## 7.1 第一阶段研究结论

第一阶段源码追踪已完成。当前采用的研究结论是：Host / Daemon / Runtime Instance 分层；机器批量 Claim、数据库逐 Agent 原子领取；Daemon 本地槽、Agent 上限、Runtime 上限三层容量控制；Claim Generation 保护 Start 与重放；心跳租约、Runtime Sweeper、reconnect grace 和启动孤儿恢复分流不同故障。详细证据、SQL 与测试断言见[源码研究记录第 10 节](../research/03a-source-evidence.md#10-第一阶段完成runtime--daemon-注册调度领取与恢复)。
