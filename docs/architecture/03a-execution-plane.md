## 1. 目标

建立一套面向团队成员本地 Agent 环境的统一执行平面。平台负责把已授权的工作送达适合的执行环境，管理执行生命周期，收集过程与结果，并在失败、离线、重启和人工接管时保持工作连续性。

专题三 A 聚焦真实执行能力：

- 成员机器及其本地 Agent 工具如何注册、发现和保持在线。
- Run 如何从服务端进入本地环境，经过准备、领取确认、执行、回报和清理。
- 不同 Agent 宿主如何接入统一的执行与观测契约。
- 本地目录、Git 工作树、远端仓库和普通制品如何成为执行输入。
- 会话、工作区和执行结果如何在同机连续、跨机接续及崩溃恢复中保持关联。
- Script 如何作为受管执行类型使用相同的授权、派发、Run 与结果回报链。
- 凭证、项目访问、Runtime 共享、进程树和文件系统如何落实执行边界。
- 开发者从本地 CLI / IDE 主动工作时，如何关联 Issue、选择共享内容并保留真实执行来源。
- 上下文与团队资产如何进入各宿主，以及投递、加载、结构化结果和制品分别有哪些可观察证据。

本专题交付执行平面业务模型、宿主适配模型、工作区与会话连续性模型、生命周期与恢复规则、平台能力契约，以及可运行原型的验收场景。数据库表、接口字段、部署拓扑和具体实现框架在机制评审后展开。

## 2. 研究起点：先区分四个概念

Multica 当前实现揭示了四个容易混淆的层次：

| 概念 | 含义 | 关键问题 |
|---|---|---|
| Daemon / Host Agent | 成员机器上常驻的本地执行管理进程 | 如何连接平台、发现本机工具、领取工作、管理进程与本地资源 |
| Runtime | 平台可调度的具体执行目标，通常对应一台机器上的一个 Agent 工具或自定义 Runtime Profile | 哪台机器上的哪种执行能力可以承接这项工作 |
| Agent / Role | 工作承担者及其指令、模型、技能和配置 | 谁负责这项工作，以什么角色和能力执行 |
| Run / Execution | 一次实际执行记录 | 何时领取、何时真正启动、执行了什么、结果和证据是什么 |

业务归属沿 Issue、节点尝试和 Run 查找；调度沿 Host、Daemon、Runtime 查找；宿主事件沿 Provider、Session 和执行段查找。工作副本绑定本次执行，交接时引用已发布的提交与制品。一次换机可以沿用原 Issue 和候选，并产生新的 Run 和宿主会话。

## 3. Multica 当前执行链：需要吸收的机制

按源码追踪，Multica 的执行路径可概括为：

```text
服务端 Run 队列
  → 匹配 Runtime / Daemon
  → Daemon claim
  → 本地准备（工作目录、上下文、技能、MCP、环境）
  → StartTask 接受本次领取者的开工登记
  → Provider Backend 启动宿主工具
  → 消息 / 工具活动 / 用量持续回传
  → 完成、失败或取消
  → 终态回报与清理
  → 恢复扫描、会话接续和 GC
```

这里有三个特别重要的设计点：

1. **领取与开工登记分开。** Daemon 领取后准备环境，再调用 StartTask；服务端接受登记后标记 running，随后由 Backend 启动宿主。准备完成、服务端登记和进程已启动分别有对应的观测事实。
2. **执行状态需要多个回执。** 已入队、已派发、已领取、已 Start、进程已启动、Agent 已产生语义活动、已得到终态结果，是不同事实。平台需要根据实际可观测能力定义统一状态和证据。
3. **本地执行需要独立的恢复闭环。** 服务端持有工作与 Run 事实；Daemon 持有本机进程、工作目录和宿主会话的管理责任。重启后先恢复原执行和工作材料，再决定继续、重试、转交或等待人工。

详细源码路径和反例见[研究记录](../research/03a-source-evidence.md)。Runtime 注册按 Workspace 进行，命令由 Host 本地解析；授权分别核对 Workspace、Daemon 与 Runtime Owner。取消回执保存恢复指针；已协商的 Provider 清理确认处理同 Agent / Runtime 的后继保护，EnvRoot 锁另负责运行期目录互斥。

## 4. 平台执行模型

平台按工作归属、资源所有权和实际执行分别保留可追溯的记录。

### 4.1 Host / Daemon

Host 表示成员提供的物理或虚拟执行环境；Daemon 是该 Host 上负责注册、心跳、领取、启动、停止、恢复和本地资源管理的常驻服务。

Host 登记所有者与可用资源，Daemon 按 Workspace 注册 Runtime 和能力。每次领取分别检查成员的项目访问、Runtime 的有效共享、Agent 与 Runtime 的容量，并在本机取得可写目录的锁。多配置共享机器时沿用这些资源约束。同一可写目录有未释放的持有者时，后继等待清理或建立独立副本。

心跳过期先记最后一次到达时间、未确认的执行和待收回资源；恢复的 Daemon 核对原领取代次、进程、工作副本和待回报队列。控制方依据已知副作用和交付材料选择续跑、重新指派或等待有权成员决定。离线期间，目标 Issue 仍可显示原机最后回执、当前负责者、已发布输入、待确认的副作用和可接替的工作。

### 4.2 Runtime / Provider Adapter

Runtime 是可被调度的具体执行目标。Provider Adapter 把平台统一执行契约映射到宿主实际协议。

平台根据协议族、宿主版本、入口和实测能力选择适配器。Codex 的受管入口使用 App Server，Claude Code 使用 SDK 或 CLI 流，部分 Qoder、OpenCode 适配使用 ACP。TeamAI Skill Driver 通过步骤领取和回报推进，Script 通过受管子进程收集退出与产出。成员原有 CLI / IDE 的本地关联与事后分享分别依据当时可获得的 Hook、历史或选区。

适配器声明启动、消息、工具、用量、取消、恢复和制品的可见范围。以一次具体宿主调用为单位，分别记录原生终态、适配器传出的 `TerminalObserved`、进程退出、清理确认和平台收件。恢复拒绝还要结合类型、已观测的工具副作用和本次恢复身份决定下一步。各入口、宿主和证据缺项的展示及处理见[宿主能力矩阵](execution-capabilities.md)。

### 4.3 Execution Environment / Workspace

执行环境负责提供 Agent 或 Script 实际工作的目录、代码和配置。

按执行输入选择工作副本，并保留能够重新取得的基准。

| 输入类型 | 例子 | 需要解决的问题 |
|---|---|---|
| Git Repository | GitHub 仓库、指定 commit | Checkout、分支 / Worktree、补丁交接、合并和交付 |
| Local Directory | 成员本地已有项目 | 原地执行、路径授权、互斥或隔离副本、清理边界 |
| Non-Git Workspace | 普通目录、文件包、生成式项目 | 快照、增量同步、冲突处理、交付格式 |
| Artifact Input | XLSX、图片、文档、构建产物 | 内容寻址、版本、可访问性、校验和 |
| Multi-Repo Workspace | 前后端多个仓库 | 基准组合、依赖关系、跨仓库候选和统一交付 |

同机续用受管目录时，核对工作归属、来源和前任持有的目录锁。已绑定的成员目录可按授权原地执行；允许并发写入的 Git 工作线各自取得独立工作树。候选交付记录仓库与提交，多仓库候选固定整组提交；只存在本机的未提交文件在交接前要登记为快照或制品。换机接续要求接收方取得可读取的提交及制品后创建新副本。第四阶段在独立接收仓库经 Git HTTP 取回 C2 并经附件 HTTP 验证原件。第五阶段又让原任务结束，由另一台独立虚拟机检出同一提交并核对工作簿原件。本次 Git bundle 包含 C2 的可达祖先 C1，以及仓库里的东、西区合成订单。按提交检出用来固定执行版本。分发还须检查接收者有权读取的仓库历史与整个文件包；只授权读东区工作簿的成员通过其具名附件获取该文件。

节点依赖就绪后，调度方还要取得 Agent 容量、Runtime 和可写目录。在 Multica 中，同一 Issue、同一 Agent 的两个讨论可以分别排队，第一项运行时第二项继续等待。不同 Agent 可以分别领取。领取代次和目录锁保护不同的动作。实测中，新代 G2 成功 Start 后，旧代 G1 在其独立目录完成 Prepare 并写下 marker；G1 的 Start 收到 409。按旧代的资源归属 Finalize 后旧空分支被清除，新代提交只含自己的修改。平台将“业务允许开工”和“旧代产生的本地文件已回收”独立记录。[工作副本、排队与跨代实测](../research/topic-03a/workspace-continuity.md)

### 4.4 Session / Continuity

Session 是宿主工具的会话连续性载体；它与 Run、Issue 和 Workspace 关联，但生命周期不同。

每次恢复先明确所需的连续性。继续观察正在运行的宿主时，重新连接原生执行单元；继续一项已结束的工作时，引用原 Issue、决定、候选和结果，按需要启动新的 Run。Daemon 在同一受管 Run 内处理协议重试时保留调用尝试及各次真实用量。

| 接收方需要的材料 | 取回条件 | 缺失时的动作 |
|---|---|---|
| Issue 决定、约定、候选代码 | 接收方能读取目标 Issue，并以自己的仓库或交付权限取得固定提交；核对当前决定与提交 | 列出缺项，请有权成员补发指定版本或明确调整工作范围 |
| 报告、XLSX、非 Git 输入 | 接收方取得具名交付的访问权，按候选、长度、摘要和类型校验原件 | 标记哪份必需制品尚缺，保留已完成的其他检查 |
| 原宿主 Session、未发布草稿、本机凭据 | 原宿主明确支持且授权恢复，或成员主动发布选定材料 | 保留历史缺口。其余必需输入齐备时新开会话，显式投递获准的上下文；原机草稿由持有人另行交付 |
| 原机可能已经发生的写操作 | 从原执行日志、目标系统回执或明确的幂等键核实 | 先查实际副作用；对未确认且可能重复的步骤，留给当前控制者或有权成员处置 |

在已测 Codex 0.144.6 和 Claude Code 2.1.325 中，B 用原 ID 恢复都报告缺少 A 的本地历史，即使切换到 A 的原工作目录。B 新建会话后，当轮模型请求只包含选定的本案例 D2 和 C2 标记，A 的两条私有标记均未出现；A 使用原配置目录恢复后能继续原会话。[双配置目录实测](../research/topic-03a/session-handoff.md)

接管工作保留当前工作范围、原 Run、接替 Run 与各自 Session 的关系。原机回连时，迟到回报沿原派发、尝试与候选处理。[跨环境实验](../research/topic-03a/machine-handoff.md) · [双身份访问与迟到回报](../research/topic-03a/two-runtime-identity.md)

### 4.5 Script Executor

Script 是受管执行类型。派发沿用专题二的节点尝试、Execution Contract、Grant 和 Run。执行器取得工作副本，核对候选提交、脚本版本与本轮输入，在指定目录启动脚本。Run 保留实际退出码、终止原因以及可共享的输出。核验脚本可以由验证方单独维护，执行时固定其版本，避免候选的变更同时改写评判标准。

| 观察结果 | 订单导出实测 | 工作流处理 |
|---|---|---|
| 进程正常结束，检查发现候选缺陷 | C1 的 XLSX 可打开，金额与付款时间都正确，东区多出一条西区订单。退出 0，A2 失败、A3 通过，报告给出 `rework` | 留存 C1 报告和相关制品，对应节点进入返工分支 |
| 进程正常结束，已声明的检查通过 | C2 修正订单可见范围，两个检查均通过，退出 0，报告给出 `pass` | 通过该次 A2/A3 验证。上层仍按约定检查其余标准和人工接受 |
| 核验工具自身未完成 | 缺输入时退出 1，无报告；另有五份真实内容反例均能生成 A3 失败的检查结果 | 工具错误单记，保留已产生的诊断；按原尝试处理重试及副作用 |

TeamAI 的真实本地驱动已在两个命令节点分别消费上述报告，进入 `rework` 和 `pass` 对应的分支。本项目沿用受管命令和可解析输出，把本地工作目录的组织与平台的派发、授权和验收分别处理。[工作簿、验证脚本与真实驱动](../research/topic-03a/order-export-workspace.md)

### 4.6 本地交互式执行的接入

成员从习惯用的 CLI / IDE 开工时，可选 Issue、选共享内容，再继续原会话。平台复用现有 Run、Work Context 与 Evidence。成员只想分享调查结果时，也可以在工作结束后选择一条消息或一份制品。

| 入口 | 开工和归属 | 进入 Issue 的记录 |
|---|---|---|
| 中心派发 | 沿用专题二的派发控制绑定和已有 Run。Daemon 在启动宿主时登记本次调用，取得真实 thread / turn 或 prompt 标识后绑定 | 受管执行的生命周期、约定范围内的过程与回报。本机 Hook 如果能匹配到同一具体线程与回合，或同一次提交，则归入该 Run |
| 本地主动关联 | 成员选 Issue。中心核对项目权限、当前工作范围、适用 Grant 和既有执行。取得可重复使用的关联回执后，从下一个可识别输入或执行段开始生效 | 已有 Run 接收匹配的观察。获准的新执行首次取得开工事实时登记一个 Run。SOP 已掌握派发权时，由现有绑定接纳这次执行，或把已有工作作为外部结果引用 |
| 先探索后关联 | 本机预览，选择发生过的片段、产物与目标 Issue，记录原发生时间、分享时间及成员。命中原 Run 时补证据 | 有宿主依据的内容标“事后导入”，纯说明记为成员自述。没有先前受管身份的工作保留外部执行来源和原始计量引用。按专题一规则展示，任一引用均可追溯到同一原始消耗 |

#### 可用宿主入口

- **TeamAI** 用 Skill Driver 把步骤交给当前编程 Agent，通过领取、确认、提交结果推进。Agent Observation 是这一次步骤执行的工具、模型、环境等记录。实际会话活动和用量来自另行安装的 Hooks 与按宿主格式解析的转录。采用其显式步骤协议与字段来源。项目存储和分配仍由现有控制平面负责。[固定源码与反例](../research/topic-03a/teamai.md)
- **Codex** 在平台或受支持客户端发起执行时使用 App Server，保留具体 thread、turn 和事件中的 item。现有 CLI / IDE 会话按实际宿主版本、已启用 Hooks 或成员连接的同一服务端点接入。历史回读使用只读方法。协作客户端可经 thread/resume 加入原线程，新的执行回合由 turn/start 发起。CLI JSON 输出的 ID 与计量字段按版本单独解释。[固定源码与双轮实验](../research/topic-03a/codex.md)
- **Claude Code** 对成员已经在用的会话使用项目或用户选定的 Hooks，对由平台启动的会话使用 Agent SDK 或 CLI 的流式协议。会话级记录、prompt、工具调用、展示消息、模型响应和转录消息分别保留原生标识。需要历史材料时只在本机读已选会话，再提交选区。[官方协议、SDK 源码与恢复实验](../research/topic-03a/claude.md)

#### 一个 Session 怎样分到多个 Issue

执行段表示一次明确工作归属覆盖的宿主活动。绑定说明由谁选了哪个 Issue、从哪个原生输入开始、哪些后续单元属于同一次执行。执行段可覆盖多个回合。工具多次调用、消息分块、追加指令或同一轮的并行子代理都保留各自来源。切换 Issue 默认于下一轮生效，已经运行的调用及其迟到回报继续归原处。

| 情况 | 关联依据 | 遇到缺项时的处理 |
|---|---|---|
| Codex 主线程或子线程 | 在已确认的宿主来源内使用具体 `threadId + turnId`，事件再关联 `itemId` 和事件阶段。树级 `sessionId` 用于导航，fork 或子代理的工作引用自己的线程及父子关系 | 中途接入先回读可恢复的 turn / item。分叉复制的历史仍引用原生产者，仅新线程实际产生的工作计入新段。流式增量缺序时保留已证实的最终快照与覆盖缺口 |
| Claude 提交、消息和工具 | Hooks 按 `session_id + prompt_id` 识别提交。展示活动保留自己的 turn / message 标识；配对工具使用 `tool_use_id`。已启用 OTel 时，Hook 的 prompt_id 可对到遥测 prompt.id，请求 ID 经 assistant_response 事件对到转录消息 UUID。SDK 另可用输入回执建立对应 | 一轮处理多条输入或后台子代理跨轮返回时，沿实际输入及调用关系归属。缺少对应关系时可分享选中材料，并把整轮费用保留为未精确分摊 |
| 平台本地开始标记、结束标记 | 适配器给本次调用分配持久标识，在同一调用内记录原生标识和起止位置。中断后从原回执继续，记录主动续跑、fork、新进程或重新执行的实际身份 | 原生标识缺失时，成员可以声明选区和工作归属。时间、目录、内容相似度和模型配置仅帮助预览候选，保留关联依据与置信情况 |

一个 Issue 可以拥有多个 Run。一个 Run 可以持续几个宿主回合。终止后另起的实际执行另记 Run 并关联前次。平台适配器在尚未取得宿主执行结果的同一受管启动中进行协议恢复时，保留调用尝试与新增用量。重连、回看、转发和补录只增加观察。若不同 Issue 引用一次已有调查，保留一个生产归属，其余 Issue 引用结果。跨工作范围发生了新执行，才记录该范围新增的消耗。

#### 多路观察和费用归集

1. **先认出执行，再收证据。** 中心派发 ID、成员本地关联回执与宿主执行单元通过可验证的对应关系汇入已有 Run。一条原生执行单元在授权域内只归一个生产执行。来源命名空间是被观察的账号 / profile 或原始宿主实例，按可验证迁移关系延续；采集器名称、日志路径、设备挂载点都不单独决定身份。覆盖重叠的导入逐单元核对。归属冲突保留待核对记录，不重复开工。服务端以唯一绑定和原子写入处理多个入口同时上报，向重试者返回原回执。
2. **观察可以有多份，计量只结算一份。** 同源重发按原生事件标识及事件种类、阶段、分块位置幂等。跨源有共同请求、响应或可证明的同一计量区间时，保留每路来源，选一份口径完整的数据入账。流式增量和最终快照是同一内容的不同表示；并行工具即使用了相同模型响应，也各有工具活动。没有稳定分块位置的重复流以最终快照核对，仍缺的部分标为缺失。
3. **先看数值覆盖了什么。** 逐请求增量按唯一请求结算。会话累计值保留为检查点，仅在同一模型、指标、单位、计量周期且区间独占目标执行时求差。首个基线缺失、计数重置、漏段、切换模型、多个 Issue 交错或只知道会话总额时，保留未分摊量和原因。计数器乱序按原次序校正；较晚收到的旧快照保留历史，当前结算保持最新的有效次序。已确认零与未知分开。
4. **分别记录 Token、估价和实付。** 保留宿主的输入、输出、缓存及其包含关系，模型实际报告与请求配置分列。估算附费率或 SDK 版本、币种、覆盖区间。真实账单另做对账。父级汇总若已含子代理，子代理作为明细展示；部分包含或范围未知时保留未分摊。确定性更高的后到证据通过带版本的更正替换同口径值，保留原值和理由。两个同等可信来源冲突时显示待核对，不以到达先后决定。
5. **复用 Multica 的现成落点。** 先确定实际 Run，再按 Run / provider / model 写入一份当前计量。Issue、SOP、Node Attempt 和其他引用视图通过 Run 读取，项目总额按原始计量单元去重。不同工作区的观察各按本域权限展示，跨域关联需要显式授权；标识可用本域不透明引用，避免暴露私有会话。跨系统幂等、计量覆盖与共享选区是本项目新增设计。[Multica 路径与已跑测试](../research/03a-source-evidence.md#11-第二阶段宿主协议与本地观察)

#### 成员实际共享什么

本地入口先显示目标 Issue、候选、选中的执行段，再分别预览消息、工具、用量和制品。可只选“工具名称与结果”“本段用量”或“一份报告”。工具参数、stdout、diff、附件、子代理内容和消息正文分别选择。转录原件、文件路径、未选对话及旁支内容留在成员本机。对于摘要、摘录或脱敏副本，同时标明变换方式与来源。已分享内容只有在取到原材料并按权限核对时才标为可复核。

| 成员勾选 | Issue 实际得到 | 可以据此确认 |
|---|---|---|
| 一条真实消息 | 已选内容、角色、宿主位置、原发生时间及共享来源。成员编辑后的文字另存说明 | 宿主曾记录所选消息；模型文本中的业务判断仍按其来源核验 |
| 一次工具调用 | 调用标识、发起 / 成功 / 失败等实际观测到的阶段及获准字段。只有发起事件时保留结果缺失 | 调用了哪个工具；有对应结果时才能记录退出或返回事实 |
| 用量 | 获准共享的计数、模型、指标覆盖、来源及精确度；可在正文保持私有时共享计量 | 某执行的可归属消耗。订阅额度和 SDK 估价用各自单位展示 |
| 制品 | 选定文件或不可变版本引用、内容摘要、生产者、候选及团队可访问位置。上传并回读后记录核对的摘要 | 收到了哪个版本。仅有本地路径时显示本机可用，工具声称写文件时先保留声明 |
| 手工描述 | 成员、原文、提交时间、关联范围，可附原始材料 | 该成员提交过这一说明。后续取得的宿主记录或独立复核分别挂接 |

在线写入和离线补传都要核对成员的当前 Issue 权限、选区版本与目标受众。适配器先在本机生成选定投影，再发中心。成员缩小共享范围后停止后续投递，丢弃旧版待发队列；已发布内容的撤回按中心访问规则处理，保留撤回回执。回执记录实际接受、遗漏或拒收的项目，重复提交可取回同一回执。共享只改变材料可见性，执行接管、向宿主写指令、操作项目和最终验收分别使用原有授权。

#### 平台到底确认了什么

每条证据回答一个具体命题，记录来源、获取通道、发生时间、接收时间、候选、覆盖和验证动作。一份报告可同时带有三个事实：成员说明“已跑 A2”、宿主返回命令退出码、平台在指定候选回读报告并验证摘要。三条分别展示。上传回执仅证明平台收到该副本。工具输出中的“通过”来自工具；独立核验要由承担该职责的主体检查候选和标准。来源冲突或后到时保留并列证据与更正，不升级业务状态。

以订单导出为例，乙在同一会话先做私有探索，再为前端子 Issue 实施 D2 的付款时间列。乙从下一轮绑定前端子项，只分享本轮的最终消息、工具结果和补丁摘要。Daemon 和本地 Hook 同时看见该轮，Issue 上仍是一次 Run。丙在验证子 Issue 取得 C1 的 A2 失败报告，父 SOP 只引用这份结果和原费用。C2 重新集成后取得新的验证 Run 与报告；迟到的 C1 观察回到旧候选。林对 C2 和 A1–A6 作最终接受决定。若乙只提供一句“已完成”，Issue 先展示乙的说明，等待可获取的补丁或复核结果。

### 4.7 上下文注入与加载回执

订单导出的决定由 D1 改为 D2 时，控制平面知道哪一版已生效，Daemon 知道哪一版已写入工作目录，宿主却可能继续发送 D1。3B 负责选择和发布有作用域的资产版本；3A 按 Issue、Run、节点尝试、实际宿主调用及回合，记录投递通道和已取得的证据。Issue 的决定引用、宿主证据和候选检查结果可分别查看。[宿主与权限实测](../research/03a-source-evidence.md#12-第三阶段上下文与任务身份)

| 材料 | 可确认的事实 | 对结果的使用 |
|---|---|---|
| Agent / Role、项目说明与任务提示 | Multica 把 Agent 指令和项目说明嵌入 runtime brief，任务提示另行投递。保留材料版本、父材料、通道和摘要。独立 Role 版本由 3B 选择 | 投递回执支持追溯运行配置。确认特定规则进入本轮要关联宿主当轮的证据 |
| Rule 或 Issue 决定 | 区分文件已写、宿主报告读取该路径、版本内容出现在当轮有效输入、只在历史消息中出现。显式补发单列为当轮输入 | Codex 0.144.6、0.167.0-alpha.4 的项目通道和 Claude Code 2.1.325 均实测到磁盘是 D2、下一轮仍只带 D1。恢复原会话时可以同时看到历史 D1 和新增 D2 |
| Skill | 分别确认文件已准备、宿主可发现、正文进入哪轮、谁请求调用。Claude 可用同一工具调用 ID 关联前后事件，Codex 显式选择可核对当轮输入 | 只为实际观察到的步骤出具回执。历史中再次出现技能正文沿用原出处 |

| SOP、受管 Script | 保留节点选定的 SOP / Script 版本、候选、预期制品与材料摘要。Script 的实际工作目录、运行版本、退出和输出由执行器回报 | 第四阶段已用真实工作副本和独立核验器核对启动与产物，节点按实际尝试消费结果 |

Multica 在调用 Backend 前构造 ContextReceipt。文件通道的 `verified` 由既有探测版本和当前宿主版本匹配而来；Skill 与 MCP 也各有可观测范围。原生服务端按 Task 保存最新回执。平台应另为每次宿主尝试及相关回合保留证据，关联相同材料的补发、重试与恢复；回执缺失时显示“已写入，本轮加载未知”，证据互相冲突时保留版本和来源。日常只共享经成员授权的摘要、宿主标识和必要片段。隔离探针用合成标记定位实际请求。[上游实现与覆盖](../research/03a-source-evidence.md#12-第三阶段上下文与任务身份)

重要决定换版后，先查哪些工具动作已发生、哪些输出仍可用。在宿主支持的入口由当前控制者显式补发 D2，并按本轮记录投递方式；如需重新启动宿主并恢复原会话，先核对工具副作用和原执行段，再核对新调用实际载入的版本。旧尝试和原候选保留自己的证据。候选能否满足 D2，由针对该候选的内容检查决定。

### 4.8 结构化节点结果与制品回报

订单导出的交付包含三个独立结果。执行器确认脚本如何结束；验证者依据候选工作簿给出具名的 A2、A3 检查结论；控制平面判断哪次派发有权提交、哪次节点尝试可以消费这份报告。SOP 与 Issue 引用同一份原始证据。

| 责任方 | 需要落实的判断 |
|---|---|
| Agent Adapter / Script Executor | 记录宿主终态或进程退出、报告来源和核验器版本，读取本次调用声明产生的具名输出。对格式错误、检查输入缺失和业务断言失败分别给出原因 |
| Daemon / 执行环境 | 记录 Issue、源 Run、节点尝试、候选提交、工作约定和实际工作目录。对原始字节取完整 SHA-256、长度与类型。报告经结构化通道提交，XLSX 等二进制走保真附件通道，保留原件与预览的关系 |
| 控制平面 | 按经过认证的派发记录复核 Grant、源 Run、目标、尝试、候选、规则和核验器版本。比对附件接收侧摘要。以同次派发的具名回报为单位原子登记；同内容重发沿用原回执，同位置异内容标记冲突，保留原件 |
| SOP / 指定核验者 | 当前尝试满足检查和必需制品契约后才消费。授权仍有效的旧尝试报告归到历史。失败和返工保留可用诊断；正式接受沿用专题一的决定及标准 |

LoopForge 的原生节点在同一持有者代次内允许较早尝试的成功到达。订单导出的终点还涉及候选换版，因此本项目在接收方核对尝试、候选和交付来源后才消费成功或失败。TeamAI 的远端发布与接手则提供了写入前复核控制版本的依据。[两库交接源码与原生验证](../research/topic-03a/upstream-handoff.md)

文件名相同的 C1、C2 具有各自的提交、尝试和摘要。一份可跨角色读取的完整文件也可能恰好等于某角色错误导出的文件；内容去重以摘要为依据，读取权限按交付关系判定。Multica 在两次上传同一工作簿时生成了不同附件 ID，重试时由上层保持同一逻辑交付。LoopForge 普通 Runner 输出可完整传回文本，但在本次 XLSX 的真实 HTTP 报文中改变了字节。Multica 的附件通道以原字节完成往返。[制品通道实测](../research/topic-03a/binary-artifacts.md)

失去回执的发送方可以重发原记录。C2 在 Multica 服务端首次提交后，夹具让发送方收到 503；真实 Daemon 留住待发送结果并重发，中心最终保留一条完成评论。C1 在 C2 之后重放，两份报告各留在自己的任务。共享撤销时，中心已经取消、任务令牌已经失效，本机子进程仍然可能在运行；收到宿主停止回执后再登记本地停止。已取消任务的迟到完成请求即使得到 HTTP 200，仍要读中心状态确认它实际接受了什么。[终态重发、晚到与停止实测](../research/topic-03a/result-handoff.md)

### 4.9 任务身份与成员平台凭证

共享 Runtime 上有三个可分别追溯的主体。订单导出实验中乙共享机器，丙发起验证任务并持有验证 Agent，服务端认证该 Agent 的评论并关联源任务。乙可以收回机器使用权；Issue 责任、评论作者与业务验收分别沿用原有工作关系。[共享 Runtime 实验](../research/topic-03a/shared-runtime-identity.md)

| 检查点 | 已验证的原生行为 | 本项目处理 |
|---|---|---|
| 领取与开工 | 交付时核对 Runtime 当前共享关系并签发任务令牌。实验中令牌 user_id 属于乙，任务 originator 属于丙 | 保存资源所有者、任务发起人、执行 Agent、Runtime 和 Run 的关联。Daemon 的管理凭据与宿主模型登录态各用于自己的服务 |
| CLI 选择任务身份 | 在受覆盖的任务上下文中，环境信号或受管工作目录的 marker 可标识身份。定向测试覆盖有效任务令牌、缺失、父目录与跳过成员配置 | 已识别的任务缺凭据时停止平台操作，记明原因。用执行环境约束管理凭据的可见性，记录脚本是否处于已验证的隔离条件 |
| Issue 访问和回报 | 原生服务按任务发起人（缺失时取总责人）和 Agent 所有人的项目可见范围检查目标。源 Issue 读取 200；源 Issue 和另一可见 Issue 评论均为 201，均以真实 Agent 和同一源任务署名；无权访问的私有项目返回 404 | 保留可见 Issue 间的一般协作。受托 SOP 回报另核当前 Delegation Grant 的操作、目标、控制代次、节点尝试、Run 与候选；迟到证据保留在原尝试 |
| 撤销与到期 | 收回共享后任务取消、Agent 解绑，原令牌对源 Issue 读写均为 401，迟到评论零条。仍运行的同一任务中，到期令牌 401、有效令牌 200 | 在实际接收操作时复核授权。分别记录平台撤销、宿主停止、工作副本回收和对历史材料的读取权限 |

授权只回答谁可以提交到哪里。平台成功回读报告时确认作者、来源、目标、摘要和报告中的检查值。候选结果由具体标准判断，业务接受沿用专题一规定的验收决定。

B 接管并使用自己的任务凭据后，目标 Issue、已交付附件和 B 的 Runtime 用量可读；同内容但属私有 Issue 的附件及 A 的 Runtime 用量各自按原有权限处理。[双机请求和原生授权](../research/topic-03a/two-runtime-identity.md#两台-github-托管虚拟机上的原生授权与回放)

## 5. 生命周期与恢复必须分层建模

以下观察点分别来自 Issue / SOP、中心调度、Daemon 和宿主。展示一次执行时保留各事实的来源与时间。

1. **Eligible**：工作已满足业务与 SOP 的启动条件。
2. **Queued**：已形成待派安排，等待 Runtime 容量。
3. **Claimed**：某个 Runtime 已领取该次执行。
4. **Preparing**：本地工作区、上下文、能力和授权正在准备。
5. **Started**：服务端接受本次领取者的开工登记。
6. **Running**：宿主进程已运行并持续产生执行事实。
7. **Terminal / Outcome Observed**：宿主回合完成时登记原生结果。中心接受完成回报、登记失败或决定取消时另记中心事实。两条记录可在不同时刻到达。
8. **Settling**：用量、制品、会话、工作区和终态回执正在收敛。
9. **Recovered / Handoff**：原执行恢复、重新派发或交接到新的 Runtime。

观察点挂在已有 Run 和节点尝试上，按其实际发生顺序回放。取得宿主结果后资源可能仍在清理；收到中心取消决定时，进程也可能仍在运行。

### 5.1 取消、清理与后续复用

| 已核对的原生机制 | 适用范围与处理 |
|---|---|
| Provider 清理确认协商 | 当前 `pi / omp / museapp` 在协商对应能力后启用取消清理确认；记录宿主与版本覆盖 |
| 同 Agent / Runtime 后继保护 | 清理等待或清理失败按相同 Agent 与 Runtime 关联影响后续执行；其他工作范围的资源使用需另按其条件判断 |
| EnvRoot 运行期锁 | Daemon 持有本地目录使用锁，与服务端清理确认分别核对 |
| 取消清理专项收敛 | 原生取消登记可在确认清理异常后从 `cancelled` 收敛为 `failed / cleanup_unconfirmed`；保留取消事实、清理原因及恢复材料 |

据此校准专题一的原生复用说明：常规完成回报受状态条件保护，取消后的清理确认有专项路径。平台设计分别保留取消决定、实际执行结果、清理结论、资源占用和后继执行关系，逐项向当前控制者显示。

### 5.2 恢复与接管

| 中断位置 | 谁核对什么 | 下一步 |
|---|---|---|
| Claim / Start 响应丢失或 Prepare 中断 | Daemon 查原领取代次、开工回执、目录持有者；中心按原派发核对 Grant 与控制代次 | 重送同次登记。领取已被替换时，旧代回收自己的准备资源，现有代次继续 |
| 原机失联，后继申请接管 | 当前派发控制者查工作进度、租约、已发布材料及可能的外部写入。有权成员按 Issue 的分工授权交接；接替者使用自己的任务身份 | 保留失联事实。原任务仍在 A 名下时，B 通过有效指派取得自己的 Run。原尝试仍适用时复用其工作契约，发生返工或候选换版时按专题二建立对应尝试 |
| 终态已产生，中心回执丢失 | 原 Daemon 从持久队列重发相同的具名回报。接收方核对身份、源 Run、候选、尝试和内容 | 已接受同一内容时返回已有回执；同位置异内容留冲突；旧轮的已授权回报仅进历史，当前轮只消费一次 |
| 取消与停止、清理交错 | 中心查当前授权及取消状态；Daemon 查原进程、工作副本和清理确认 | 撤回共享后旧任务身份失效。机器级完成回报即使取得传输回执，也以中心回读的状态和结果为准；已登记的取消与本机实际停止分别展示 |
| 结果先到，制品迟到，或会话恢复遭拒 | 接收者核对具名原件；适配器核对拒绝种类与已发生动作；有权控制者判断可重放范围 | 只补相应材料。新会话显式投递获准上下文；外部副作用待核实的步骤保持待决。Runner 离线期间 Issue 的协作与验收职责仍由既有责任关系承担 |

#### 订单导出的实际接续

A 的 C1 核验发现跨区订单，报告停在本地发送队列。B 接管后按自己的权限取回 C2、报告和工作簿，验证结果挂在处理 C2 的尝试。A 恢复后发送 C1，再重发相同回报。原生系统把 A、B 两份结果各写回所属 Task；平台结果接收原型按当前尝试消费一次，将 C1 归于历史。20 分钟宽限、模拟心跳已过去 21 分钟的对照中，原任务以 runtime_offline 失败，同一 Agent 得到一条 deferred 重试。撤权分支中旧任务令牌收到 401，中心保留取消状态及零条完成评论。独立虚拟机的接收端也已使用 B 本轮凭据完成读回与回传，生产权限校验与两套 Daemon 回调在中心虚拟机执行。审批和 Issue 最终接受仍由原有责任关系处理。[实验条件与复跑](../research/03a-source-evidence.md#14-第五阶段跨主机接续与设计收口)

## 7.1 第一阶段研究结论

第一阶段源码追踪已完成。当前采用的研究结论是：Host / Daemon / Runtime Instance 分层；机器批量 Claim、数据库逐 Agent 原子领取；Daemon 本地槽、Agent 上限、Runtime 上限三层容量控制；claim-aware Start 采用 Claim Generation 校验及幂等重放，legacy 路径保留兼容语义；在线新鲜度、按最后心跳起算的 reconnect grace 与任务 backstop 分别判定；普通 Daemon 与 Qoder 托管连接分别核验授权，启动孤儿恢复分流进程重启。详细证据、SQL 与测试断言见[源码研究记录第 10 节](../research/03a-source-evidence.md#10-第一阶段完成runtime--daemon-注册调度领取与恢复)。

本轮已校准新旧 Start、超时组合、托管授权与源码引用。其中共享 Runtime 的任务身份和有效权限已取得第三阶段服务端实测；Prepare 的跨代写入与原生 Issue / Agent 串行行为已在第四阶段以 PostgreSQL、独立工作副本与 helper 进程复核。证据与承接阶段见[研究记录第 10.9 节](../research/03a-source-evidence.md#109-本轮收口与后续验证输入)。
