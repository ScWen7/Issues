# AgentPlatform · 架构基线冻结与渐进落地规划

## 1. 本文目的

本文把已完成的产品定位、整体架构、对象关系和双飞轮场景验收收敛为可持续引用的架构基线，并给出按业务闭环推进的渐进落地顺序。

本文件不定义技术实现细节，不指定数据库、向量引擎、消息队列、API、服务拆分、部署拓扑或 UI 原型。每个阶段先验证业务闭环和现有底座能力，再决定最小技术承载。

## 2. 冻结的产品基线

### 2.1 产品定位

AgentPlatform 是面向研发团队的 AI 研发能力平台：以团队知识为基础、以 Issue 产研工作为主线、以 Engineering Harness 管控研发质量，通过真实执行与交付证据、Evaluation 和持续改进，让团队经验进入研发、研发结果反哺知识与工程方法。

### 2.2 五个核心业务能力域

| 能力域 | 核心职责 | 独占的业务事实 |
|---|---|---|
| A. 团队知识管理 | 来源、证据定位、知识提炼、核验、发布、检索、复用、更新和失效 | Source / Knowledge 生命周期与知识反馈 |
| B. 产研工作与流程协作 | Issue、责任、Work Agreement、业务决定、Project Workflow、受托 SOP Execution | 工作目标、责任、决定和流程实例 |
| C. Engineering Harness 治理 | Principles、Rules、Skills、Playbooks、SOP Definition、Scripts、Scorer / Rubric | Harness 资产定义、修订、核验和发布 |
| D. 执行与交付证据 | Multica 执行接入、宿主观察、Artifact、Candidate、Evidence 和交付回交 | 平台侧执行关联、交付制品与可核验证据引用；Run / Usage 仍归 Multica |
| E. Evaluation、度量与持续改进 | Evaluation、Finding、Proposal、Benchmark、成本质量分析和效果观察 | 评价、问题归因、改进候选和对照结果 |

### 2.3 不构成额外产品能力域的事项

身份、权限、项目配置、资产采用、工作台、来源连接器和宿主适配器，是实施时必须处理的横切设计事项。它们不能被解释成第六个能力域、额外架构层级或必须独立部署的系统。

### 2.4 必须保持的架构不变量

1. Issue 是一项研发工作的唯一业务归属；当前目标、责任、决定和完成状态不能由 Run、SOP、Evaluation 或工作台投影代替。
2. Multica 是既有 Issue / Task / Run / Runtime / Session / Usage 协作执行底座；AgentPlatform 不复制第二套控制平面。
3. Knowledge 与 Harness 分别治理。知识说明事实和经验；Harness 规定方法、约束和验证方式。
4. SOP Definition 属于 Harness；SOP Execution 是 Issue 下明确受托的流程实例。
5. Artifact、Candidate、Evidence、Evaluation、Acceptance Decision 是不同事实；评价不能替代业务验收。
6. 同一 Evidence 可被交付、知识和 Evaluation 引用；不复制多份权威事实。
7. Release、Project Adoption、工作选择、投递、宿主加载、实际使用和生产效果分别记录。
8. 成员本地宿主、凭据、Session、工作副本和未共享内容仍归成员控制；未知的执行事实和用量保持 Unknown。
9. 知识提炼和 Harness 改进不阻塞当前 Issue 的业务交付；候选、审核、发布和采用分别治理。
10. 普通研发按需使用知识、Harness、SOP 和 Evaluation，不强制走完整仪式化流程。

## 4. 首期产品范围

### 4.1 首期要证明的价值

首期不是建设完整的五域平台，而是让一个真实项目中的一项研发工作完成以下闭环：

**Issue 建立工作约定 → 获取相关且有权的项目 / 团队知识 → 选择必要 Harness → 成员或本地 Agent 执行 → 交回可核验交付 → 有权成员验收 → 提炼一条有价值的知识候选 → 下一项工作能够检索和复用。**

首期需要同时验证两件事：研发过程没有因为平台增加额外负担；沉淀的知识确实能减少下一轮重复调查或踩坑。

### 4.2 首期必须具备

| 能力 | 首期范围 | 暂不要求 |
|---|---|---|
| 研发工作 | 复用 Multica Issue、责任、评论、决定和既有派发机制；Work Agreement 的关键要求能被执行者取得 | 新建通用项目管理、任务管理或复杂组织产品 |
| 知识输入 | 至少一条真实来源路径，保留来源身份、版本 / 时间、可访问性和定位；支持按项目与 Issue 检索 | 一次性支持所有文档格式、复杂多模态解析、完整代码图谱 |
| 知识治理 | 能从工作证据形成候选，人工可核验、修订、发布、失效；正式知识可回溯来源 | 全自动知识发布、复杂知识本体和自动知识等级晋升 |
| Harness | 能选用项目现有 Rules / Skills / Playbooks，固定本次使用版本或内容摘要，明确必需项和建议项 | 通用低代码 Workflow、所有研发类型完整 SOP 化 |
| 执行 | 先复用现有 Multica Run / Runtime 能力；至少一个真实宿主可完成授权执行或成员主动关联并交回结果 | 一次性覆盖所有 Agent 宿主的深度 Hook / OTel / 用量能力 |
| 交付 | 固定 Artifact / Candidate，保留关键检查证据，由 Issue 有权成员作业务验收 | 自动替代人工业务验收、完整制品管理平台 |
| 反馈 | 能记录知识有帮助 / 无关 / 过期 / 错误反馈，并从交付提炼候选知识 | 自动根因归因、自动改 Harness、全量 Evaluation |

首期的具体来源和宿主选择应基于现有项目已接通的来源、Multica 当前支持的 Runtime 和真实成员工作环境确定；不能在未核验前假定某个连接器或宿主能力已经可用。

### 4.3 首期明确不做

- 不重建 Multica 已有的 Issue、Task、Run、Runtime、Session、Usage、Project 和派发能力。
- 不建设独立的组织管理产品、通用工作流引擎或通用 Agent 编排平台。
- 不强制每项研发启动 SOP、独立 Evaluation 或 Benchmark。
- 不把所有聊天、评论、日志、代码和测试结果自动转成正式知识。
- 不要求团队成员改用 Git 管理知识，不复制飞书等权威来源的编辑责任。
- 不在宿主未上报时推算 Credits、Token 或费用。
- 不把知识发布、Harness 发布、项目采用、工作投递和实际使用合并成一个状态。

## 5. 渐进落地路线

路线按可验证的业务切片推进，而不是按五个能力域各自建设完整子系统。每一阶段都必须交付一个成员可以实际使用的纵向闭环。

### P0 · 现有底座与真实工作基线核验

**目标：确认首期能复用什么、缺什么，不先造新机制。**

- 核验 Multica 当前 Issue、指派、评论、Task / Run、Runtime、Artifact / 交付入口和权限边界。
- 核验目标项目真实使用的需求 / 设计资料来源、成员读权和可用读取方式。
- 选定一个真实项目、一类常见研发工作和一个当前可接入的本地 Agent 宿主。
- 记录当前人工流程：如何找资料、如何准备上下文、如何验证、如何交付、如何记录经验。
- 形成宿主 / 来源能力矩阵和首期缺口清单，明确未知项。

**退出条件：** 能用现有系统完成一项工作的基本派发 / 接续与交付；首期来源和宿主路径有真实证据；明确哪些能力必须补充、哪些直接复用。

### P1 · 最小研发交付闭环

**目标：让一项 Issue 从开始到验收可接续，且知识与 Harness 进入真实工作。**

- 从 Issue 取得正式目标、责任和当前决定；执行者能取得完整有效工作约定。
- 按项目、任务意图和读权限检索少量高相关知识 / 项目资料，返回来源与版本依据。
- 选择项目已有的必需规则和建议方法，记录本次实际固定的版本 / 内容摘要。
- 由成员或至少一个真实本地 Agent 宿主执行；不支持自动观察的部分允许成员明确提交回执。
- 固定 Artifact / Candidate 和关键 Evidence；由 Issue 有权成员作出验收决定。
- 知识贡献入口允许从当前 Issue / 交付提出候选经验，当前交付不等待候选发布。

**退出条件：** 真实成员能在不重复填写大量信息、不切换多套系统的情况下完成一项工作；接手者能理解当前状态；交付可核验；本项使用的知识 / Harness 版本可追溯。

### P2 · 知识沉淀与下一轮复用

**目标：证明知识飞轮真实运转，而不是只把资料存进去。**

- 将 P1 产生的候选知识与原 Issue、Artifact、Evidence 关联。
- 知识维护者可核验事实、适用范围、来源许可、冲突和时效，形成正式修订并发布。
- 下一项可比 Issue 能按项目和工作意图检索该知识，并查看依据。
- 记录选择、投递以及宿主可观察到的加载 / 使用反馈；不可观察环节保持 Unknown。
- 对知识错误、过期、来源撤权和替代版本提供明确的复核与停止投递路径。

**退出条件：** 至少一条从研发证据产生、经核验发布、被后续工作实际选择的知识闭环；成员确认它减少了重复调查或降低了踩坑风险。

### P3 · Harness 质量管控闭环

**目标：让团队方法从“建议文档”进入真实执行与质量检查。**

- 明确一类高频、质量风险明确的研发工作及其最低交付标准。
- 将稳定有效的经验转化为 Rule / Skill / Playbook；仅对稳定步骤定义 SOP。
- 对确定性要求提供 Script / Test / Tool 检查；模型评价只补充确定性手段难以判断的质量维度。
- 固定 Harness 版本、适用范围、例外和项目采用；在途工作保留原版本。
- 记录执行偏差、人工纠正、返工和检查结果，形成可比较基线。

**退出条件：** 对选定工作类型，Harness 能被实际选用；至少一个质量要求有独立可验证的检查；相较未采用前的基线，质量或返工指标有可解释的变化。

### P4 · Evaluation 与 Harness 自进化

**目标：从真实研发发现问题，验证改进后是否真的更好。**

- 选择性触发 Evaluation；固定目标、输入证据、评价器版本和成本预算。
- Finding 分诊知识、Harness、项目约定、Agent、Runtime / Tool 和 Evaluation 自身问题。
- 知识候选和 Harness 候选分别治理；Harness 改进使用固定样本和基线做对照 Benchmark。
- 通过审核后发布，项目有权成员决定采用；生产效果用后续真实工作观察。
- 对退化、误判、样本不可比和成本超限提供停止 / 回退路径。

**退出条件：** 至少一个 Harness 改进从 Finding 到候选、对照验证、发布、项目采用，再到真实生产效果观察的完整闭环；未证明改善时能够停止或回退。

### P5 · 扩展与规模化

只有在前述闭环证明价值后再扩展：更多来源类型和增量同步、批量资料处理、复杂 PDF / Office / 表格解析、项目代码知识、更多宿主的深度观察、更多研发 Playbook / SOP、跨项目知识复用和团队级质量分析。

## 6. 贯穿所有阶段的横切验收

身份权限、项目配置、工作台、来源连接器和宿主适配器不按阶段单独建设为产品模块，而是在每条纵向切片中按需实现并验收：

| 横切事项 | 每阶段必须检查的内容 |
|---|---|
| 身份与权限 | 当前成员 / Agent / Runtime 是否有权读取来源、选择资产、执行动作和共享结果；撤权后新操作是否停止 |
| 项目配置与采用 | 团队默认、项目覆盖、本项例外和在途工作如何判定；知识与 Harness 分别采用 |
| 工作台 | 是否从成员正在做的事情出发提供最少必要信息和操作；是否避免重复录入与重复入口 |
| 来源连接 | 是否保留原来源身份、修订、读取权限、处理状态和证据位置；同步失败是否可见 |
| 宿主适配 | 是否有真实工具返回、Session / Run 关联、终态和用量回执；能力缺失是否明确标 Unknown |

横切事项的验收不要求一次覆盖所有身份类型、来源或宿主；但每个已支持路径都必须明确权限和证据边界。

## 7. 关键产品指标与首期验证方式

不以模块数量、Agent 数量、自动化步骤数或知识条目数量作为成功标准。首期重点观察：

| 维度 | 建议观察指标 | 验证问题 |
|---|---|---|
| 工作连续性 | 接手所需补问次数、状态 / 交付信息缺失率、因上下文断裂造成的等待 | 另一成员能否不依赖原执行者口头解释继续工作？ |
| 知识有效性 | 检索结果适用率、来源可追溯率、过期 / 错误反馈率 | 找到的是否是当前项目真正适用的知识？ |
| 知识复用价值 | 被明确选择 / 引用的知识比例、重复调查减少案例、知识帮助反馈 | 知识是否改变了下一轮研发，而不是只被检索到？ |
| Harness 质量 | 必需检查执行率、缺陷逃逸、返工率、人工纠正原因 | 方法是否实际约束了执行并改善结果？ |
| 研发效率 | 从开始到可验收的周期、阻塞时间、重复工作量 | 是否减少了等待与返工，而非只增加流程？ |
| 执行可信度 | Run 与宿主回执关联率、未知字段比例、重复计量率 | 统计是否来自真实执行，而非推测？ |
| 成本 | 按来源可确认的原生 Token / Credits / 费用及治理成本 | 质量不下降的前提下，单位有效交付成本是否改善？ |

所有指标都要按工作类型、风险、项目和观察窗口解释；首期先建立可复核基线，不预设未经实测的目标数值。

## 8. 阶段门与推进规则

1. 每阶段只选择一个明确的业务切片和可验证结果，不以“模块完成”作为阶段完成标准。
2. 先复用现有 Multica、宿主和资料来源能力；只有缺口有真实证据时才增加平台自有能力。
3. 每个阶段必须包含正向路径、权限 / 失败路径和人工接管路径。
4. 只有当前阶段退出条件满足，才扩大来源类型、宿主范围或自动化程度。
5. 不能证明的执行、用量、加载和实际使用保持 Unknown；不得以模型推断填补证据缺口。
6. 知识候选审核和跨工作改进不阻塞当前 Issue 的业务验收。
7. P3 / P4 的质量改进必须有基线和可比较样本；没有足够样本时结论为 Inconclusive。
8. 技术实现方案应针对当前阶段缺口单独设计，不提前冻结未来阶段的服务拆分和基础设施。

## 9. 当前下一步

当前应先执行 **P0 · 现有底座与真实工作基线核验**，而不是开始建设 P1 的所有能力。

P0 的输出应包括：
- 一条真实项目研发工作从创建到交付的现状流程图；
- Multica 原生能力复用清单与缺口清单；
- 实际来源、读取权限、修订和可定位能力的核验结果；
- 至少一个本地 Agent 宿主的真实派发 / 主动关联 / 交付路径及证据覆盖；
- 首期选定工作类型、成员操作负担和当前质量 / 返工基线；
- P1 的最小改动范围与明确不做项。

P0 完成前不设计全量技术架构，不新增通用服务，不开始原型或批量实现。
