# 团队知识管理与研发知识闭环

## 1. 职责与目标

团队知识管理负责让团队已有资料和研发中新产生的经验，成为可追溯、可检索、在适用范围内可复用的知识。

它不是文档编辑器、对话归档、向量数据库或第二套 Issue 系统。它连接权威来源、证据处理、知识治理和研发消费；各来源仍维护自己的原始事实，Issue 仍维护当前工作的业务上下文，Run 仍记录实际受管执行。

**核心链路：来源接入 → 内容取得 → 结构化解析 → 证据形成 → 知识提炼与治理 → 发布 → 检索与工作引用 → 使用反馈 → 更新或失效。**

该链路允许增量处理、批量处理和不同资料类型的专用解析，不要求每份材料都生成一篇 Wiki，也不要求每项研发工作都显式经过知识审批。

## 2. 知识管理的边界

### 2.1 四类不同对象

| 类别 | 回答的问题 | 权威归属 |
|---|---|---|
| 来源与原始资料 | 原始内容在哪里、谁能读、哪个修订有效？ | 飞书、代码仓、外部文档、项目系统等原来源；平台自有资料由平台维护者管理 |
| 证据 | 某个结论依据原文哪一段、代码哪一处或哪次实际结果？ | 由来源解析和处理过程形成，固定来源版本、位置、内容摘要和处理记录 |
| 知识 | 团队可以复用的事实、经验、解释和结论是什么？ | 团队或项目知识维护者负责审核、发布、修订和退役 |
| Harness | 研发应该如何工作、必须遵循什么、如何验证？ | 团队 / 项目 Harness 资产维护者负责定义、验证和发布 |

Issue 工作上下文和执行资源不是知识资产：
- Issue 保存当前目标、责任、讨论、决定、交付和待办。跨工作复用的内容经过提炼后才进入知识体系。
- Run、Session、Agent、Runtime、工具调用和执行回执是工作事实或资源。它们可以成为知识证据，但不自动变成知识。
- Harness 可以引用知识作为依据；知识也可以由已验证的 Harness 实践产生，但两者分别治理和发布。

### 2.2 团队知识、项目知识与代码知识

| 知识范围 | 内容 | 复用边界 |
|---|---|---|
| 团队知识 | 跨项目可复用的技术经验、通用业务规则、研发实践、共性问题与踩坑经验 | 按团队授权和明确适用范围跨项目复用 |
| 项目知识 | 项目业务事实、需求解释、架构决策、接口约定、项目特有约束、故障经验 | 默认限定在项目范围；跨项目复用须重新确认派生许可和适用性 |
| 项目代码知识 | 指定仓库和代码修订下的模块结构、调用关系、实现位置、依赖与变更影响 | 绑定代码基准；随代码变更识别受影响内容 |
| 工作上下文 | 当前 Issue 的目标、讨论、决定、执行和交付 | 留在原工作主线，通过引用供接手者使用，不复制成知识库 |

团队 Wiki、项目资料和项目代码 Wiki 可以分别浏览或独立启用，但统一遵循来源、证据、权限、版本和引用原则。代码知识不替代业务知识；PRD 不证明代码实际实现；代码静态分析也不证明线上运行行为。


### 2.3 Team Knowledge 与 Project Knowledge 的作用域

Team Knowledge 与 Project Knowledge 共用本生命周期中的来源、Evidence、Knowledge Item / Revision / Release、反馈、检索和失效治理机制；它们不是两套独立知识系统，但有不同的权威归属和治理责任。

| 维度 | Team Knowledge | Project Knowledge |
|---|---|---|
| 资产归属 | Team | 单一 Project |
| 默认维护责任 | 团队领域维护者 | 项目业务 / 技术责任人 |
| 默认可见范围 | 团队授权范围 | 项目成员及项目授权范围 |
| 默认适用范围 | 明确声明适用的多个项目 / 工作条件 | 当前 Project 的业务、系统、版本和环境 |
| 跨范围复用 | 按团队授权和适用条件被项目引用 | 必须经来源派生许可、去敏、重新核验后形成新的 Team Knowledge |
| 发布决定 | 团队有权领域责任人 | 项目有权维护者 |

**知识作用域、适用范围、可见权限和来源派生许可是四个不同维度。** 某条 Team Knowledge 适用于项目，不代表该项目的所有成员都自动有权查看它的证据原文；项目成员有权读取原文，也不代表有权将其派生给团队。

Project Sources 与 Project Knowledge 也必须区分。PRD、接口文档、项目决策原文和代码仓继续由原系统维护；Issue 可以按来源当前权限直接引用这些材料，不要求先转成 Project Knowledge。只有具备跨工作复用价值、需要稳定解释和维护的项目结论，才提炼成 Project Knowledge。

Project Code Knowledge 是绑定仓库和 Commit / Tree 基准的可选代码认知能力。模块地图、调用关系和当前实现状态不自动成为 Team Knowledge 或 Project Knowledge；需要表达设计动机、业务不变量或长期经验时，再引用代码证据形成相应范围的知识。

Team Knowledge 被项目引用时保留原资产身份和版本，不复制正文、不转移维护权。只有项目需要固定某项团队知识作为持续采用的基线时，才通过既有 Project Adoption / Project Configuration 采用具体版本；一般知识检索不要求每条知识都经过 Adoption。若知识内容需要成为强制执行规则，应另由 Harness 资产独立治理和发布。

Project Knowledge 跨项目复用不是直接修改原资产的作用域。它必须形成新的 Team Knowledge 候选，逐份核对来源派生许可和目标团队受众，去除项目私有信息，重新验证跨项目适用条件、反例和限制，再由团队领域责任人发布。原 Project Knowledge 保持其项目范围、版本和责任不变。

## 3. 来源接入与资料处理

### 3.1 来源连接与资料收件区是两种不同职责

**来源连接（Source Connection）**表示平台持续访问某个权威来源的能力和授权，例如飞书知识空间、Git 仓库、外部文档服务或项目资料目录。连接记录来源身份、可访问范围、同步方式、游标、授权状态和最近成功核对时间。连接不等于复制全部内容，也不代表所有内容均已解析或可检索。

**资料收件区（Source Inbox）**是等待处理的资料入口，承载一次明确提交或导入的材料，例如成员上传的 Markdown / PDF、粘贴的 URL、HTML 导出、单条灵感或从已有来源选中的文档。收件区记录提交人、提交意图、所属团队 / 项目、处理策略和当前处理状态。

两者不可混为一谈：
- 持续同步的来源连接可以发现多批新修订，并把待处理内容送入处理队列。
- 收件区可以接收没有持续连接能力的一次性材料。
- 从连接来源选择一份资料进入本次知识处理，不应重新创建来源连接。
- 删除收件区中的一次导入，不等于删除权威来源；断开连接也不等于自动删除已发布的知识。

### 3.2 不同资料采用不同取得和解析策略

| 来源类型 | 取得与解析重点 | 证据定位 |
|---|---|---|
| Markdown / 纯文本 | 保留标题层级、列表、代码块、表格和链接 | 文件修订、标题路径、段落 / 块位置 |
| HTML | 保留正文结构、标题、表格、链接，剔除导航和无关模板 | 页面 URL、页面修订 / 抓取时间、DOM 逻辑位置或标题路径 |
| 飞书文档 / Wiki | 使用授权 API 取得文档元数据、块结构和内容；必要时使用导出文件作为兼容路径 | 文档与块 ID、父子关系、块类型、修订和读取时间 |
| PDF / Office | 解析文本、页码、标题、表格和版面结构；扫描件先 OCR 并保留 OCR 可信度 | 文件修订、页码、段落 / 表格 / 单元格位置 |
| 表格 / CSV | 保留工作表、表头、行列、类型和公式 / 值的区别 | 文件修订、工作表、单元格或行列范围 |
| 代码仓 | 绑定 commit / tree，解析文件、符号、模块、依赖和调用关系 | 仓库、commit、文件路径、符号或行范围 |
| Issue / 评审 / 执行记录 | 只读取获准共享的业务讨论、决定、交付、检查和回执 | Issue / Comment / Run / Artifact 的稳定身份和具体版本 |
| URL / 个人灵感 | URL 取得正文与来源元数据；一句话灵感保留作者原意和提交时间 | URL 与抓取修订，或原始提交记录 |

解析结果必须保留原始结构与来源定位，不能只保留无上下文的文本切块。OCR、模型摘要、推断出的关系等派生内容需标明处理方法和可信程度。

### 3.3 处理状态必须表达真实进展

对每个来源修订或收件材料，至少区分：

1. **已登记**：知道资料身份、范围和处理意图。
2. **待取得 / 取得中**：尚未拿到完整内容或正在分页读取。
3. **已取得**：完整内容或可核对快照已保存，记录来源修订与摘要。
4. **解析中 / 已解析**：按对应格式完成结构解析，保留位置。
5. **证据可用**：解析结果可定位、可核对，权限和完整性满足后续处理要求。
6. **知识处理中**：正在去重、归类、关联、提炼或批量合并。
7. **可检索**：已进入授权范围内的检索索引，且索引与知识修订一致。
8. **已发布**：正式知识版本已生效，可按范围消费。
9. **待复核 / 已失效 / 已撤回**：来源、权限、内容、适用范围或结论发生变化，需要停止或限制新的使用。

这些状态不是必须严格串行的全局大状态机。来源同步、解析、知识提炼、索引和发布是不同处理阶段；允许某个修订已解析但尚未发布，也允许已有知识在新修订处理期间继续按策略使用上一个有效版本。任何“成功”状态都必须对应具体处理回执。

### 3.4 增量与批量处理

增量同步按来源修订、文档块或代码基准识别变化，重处理受影响范围，保留未变化内容和历史引用。删除、改名、权限变化和来源撤回应形成明确变更事实，而不是简单地从索引中消失。

批量导入不应把每份材料孤立地生成最终知识。应采用：
1. 逐份材料取得和解析，保留独立来源身份、修订和证据；
2. 按共同主题、目标知识或项目问题聚合候选，识别重复、冲突和互补证据；
3. 在统一上下文下合并提炼，逐条结论仍可追溯到对应证据；
4. 统一检查范围、权限、时效、冲突和发布结果；
5. 分别回写每份材料的取得、解析、证据和知识处理状态。

部分材料失败时，成功材料仍可继续处理；合并结果必须明确列出缺失材料，不能把不完整批次标记为全部完成。

## 4. 从证据到知识

### 4.1 证据先于结论

证据是某一来源修订中的可定位内容或实际事实，不是模型生成的摘要。每份证据至少能回答：
- 来自哪个来源、哪个修订或哪个原始业务对象？
- 位于哪个章节、块、页码、表格、代码符号或执行结果？
- 取得和解析时间是什么，解析方式与覆盖范围是什么？
- 当前读者是否有权查看原文、摘要或派生结论？
- 该证据支持什么结论，是否存在反例、冲突或缺失？

模型可以帮助抽取、分类、聚类和起草，但不能将模型推断伪装成原始证据。由多份证据支持的结论应逐项引用；事实、经验归纳、假设和建议分开表述。

### 4.2 知识内容类型

知识条目应表达可复用内容，而不是以来源文件类型决定知识形态：

- **事实 / 约定**：当前业务规则、接口约定、项目限制、系统行为。
- **决策 / 理由**：某项技术或业务决策及其适用背景、取舍和替代方案。
- **实践 / 方法**：被实际使用并有证据支持的操作方法、设计模式和检查策略。
- **问题 / 踩坑经验**：问题现象、触发条件、根因证据、解决方案和预防方式。
- **解释 / 导航**：帮助理解系统、模块、业务概念或资料关系的说明。
- **待确认认识**：有价值但证据不足的假设或问题，明确标为未确认，不作为强制依据。

每个正式知识条目应有稳定身份和不可混淆的修订，至少说明：标题与内容、知识类型、适用范围、维护者、来源证据、有效状态、创建 / 核验时间、替代或关联条目。必要时注明适用版本、环境、前置条件、反例和不适用范围。

### 4.3 候选知识与正式知识

研发活动或资料处理产生的是候选知识，不直接进入正式知识默认检索结果。候选知识至少包含：
- 可复用的具体结论，而非泛泛总结；
- 来源 Issue / Run / Artifact / Comment 或外部资料修订；
- 支持证据及其位置、摘要和当前可访问性；
- 适用团队 / 项目 / 工作类型及不适用范围；
- 与现有知识的重复、冲突、补充或替代关系；
- 事实、经验、假设和建议的区分；
- 推荐维护者及所需的确认动作。

治理方式按风险和证据强度分层：
- 低风险、来源清晰、范围局部的事实更新，可由有权维护者快速确认或按预授权规则自动更新。
- 可复用实践、跨项目经验和技术建议，需要核对来源、可迁移性、反例及受众。
- 业务规则、安全要求、架构原则和团队强制规范，需要相应责任人确认；不能由 Agent 自行提升为强制规则。

发布是形成可复用知识的治理决定，不意味着原始来源转移所有权。派生知识需获得来源内容在目标受众和用途上的授权；源权限撤回时，受影响的派生知识应暂停投递并复核。

## 5. 知识检索与研发消费

### 5.1 从工作意图触发检索

知识检索不是每次都把团队 Wiki 全量塞入上下文。检索应从当前工作意图出发，组合：
- Team 与 Project 的范围；
- Issue 的目标、类型、标签、讨论和当前阶段；
- 本次承担的角色与实际子任务；
- 代码仓、分支 / commit、服务和模块；
- 当前接收者的身份、项目参与关系和来源权限；
- 知识的有效状态、适用版本和更新时间。

检索先判断范围和权限，再做关键词、结构化条件或语义召回；排序需综合相关性、适用范围、有效性、来源权威、证据强度和新鲜度。不能因为语义相似就把其他项目私有资料或已失效结论提供给 Agent。

### 5.2 返回可核查的知识包

面向成员或 Agent 的知识结果不只是文本片段。每项结果应保留：
- 知识身份与修订；
- 结论摘要和适用条件；
- 来源证据定位与来源修订；
- 可信状态、最近核验时间和冲突提示；
- 允许的使用范围及当前读权；
- 是否为团队正式知识、项目知识或未确认候选。

复杂问题可先给摘要，再按需展开证据和原文，避免上下文膨胀。关键决策和强制规则必须能点回依据；没有可靠知识时明确报告未找到，不得编造“团队约定”。

### 5.3 记录消费，而不是只记录召回

需要区分以下事实：
- **命中 / 展示**：检索结果返回或出现在界面；
- **选择 / 引用**：成员或 Agent 明确选择该知识用于本项工作；
- **投递**：知识内容实际发送到某个宿主或工作上下文；
- **加载 / 可见**：宿主或运行入口提供了相应内容的证据；
- **实际使用**：有可核验迹象表明知识参与了决策、工具调用或交付；通常需要宿主 / 工具证据，不能仅由投递推断；
- **反馈**：成员确认有帮助、无关、过期、错误或冲突。

不同宿主可观察能力不同，无法证明的环节保持 unknown。使用次数和点赞可帮助排序，但不能替代事实核验或知识质量评价。

## 6. 知识更新、冲突与失效

来源发生变化时，按来源身份和稳定位置找出受影响证据、知识条目、检索索引及在途工作引用。不能因为来源更新就无差别重写所有知识。

| 变化 | 处理原则 |
|---|---|
| 来源新增内容 | 取得新修订，解析变化部分，判断是否产生新证据或知识 |
| 来源正文修改 | 标记受影响证据和知识待复核；确认结论是否仍成立，保留历史修订 |
| 来源删除 / 撤回 | 停止新引用；依据撤回范围处理派生知识和现有投递 |
| 来源读权收缩 | 重新计算可见范围；不再向失权者提供正文、摘录或可反推私有内容的派生结果 |
| 多来源结论冲突 | 并列展示来源、时间、适用范围和权威等级；无法判定时保留冲突并请求有权责任人确认 |
| 知识长期未核验 | 按类型和风险设置复核条件；未确认当前有效性时降低检索优先级或停止作为强制依据 |
| 新知识替代旧知识 | 建立明确的替代关系和生效范围；历史工作继续引用当时实际使用的修订 |
| 使用反馈指出错误 | 记录反馈及关联工作，触发核验；未经确认不直接覆盖正式知识 |

知识失效不等于删除历史。历史工作保留当时采用的版本和证据身份；查看原文仍需遵守当前来源权限。对已经投递到宿主的内容，平台不能假定可以远程抹除，应明确记录已发生的共享事实和后续隔离措施。

## 7. 研发如何反哺知识

知识候选可以来自：
- Issue 中经确认的业务澄清、决策及其理由；
- 交付过程中发现并修复的缺陷、根因和预防办法；
- 评审、测试和验收中反复出现的遗漏或有效检查方式；
- Run、工具和 Runtime 的可核验执行事实；
- 人工接管、返工、阻塞、撤回和成员反馈；
- Evaluation 的 Finding 及其支持证据；
- 已发布 Harness 的实际效果与适用边界。

提炼时要回答：发生了什么、证据在哪里、解决办法是否验证、适用哪些情况、是否含项目私有信息、是否与现有知识冲突、下一位研发者怎样使用。

一次失败不必然形成团队知识；一次成功也不自动证明方法普遍有效。只有具备可复用价值和足够证据时才提出候选。项目事实先留在项目范围；跨项目推广须重新判断来源许可、适用性和团队受众。

## 8. 知识与 Harness 的双向关系

### 8.1 知识可以成为 Harness 的输入

知识只有在被转化为明确、可执行、可验证的要求时，才应进入 Harness：
- 业务事实或技术约束可成为 Rule / Principle 的依据；
- 经验证的工作方法可成为 Skill / Playbook；
- 稳定的步骤、依赖、门禁和失败处置可成为 Workflow / SOP；
- 可判定的质量要求和历史失败样本可成为 Evaluation / Rubric / Regression Case；
- 需要确定性重复执行的检查可成为 Script / Tool。

转化必须补齐目标、适用范围、例外、验证方式、维护者和版本。仅有经验描述时，先作为知识供 Agent 参考，不应强行转成规则。

### 8.2 Harness 也会反哺知识

Harness 执行与评估可能发现：
- 团队知识缺失或资料未被找到；
- 知识过期、冲突或适用范围错误；
- 规则难以执行、定义含糊或与项目事实冲突；
- Playbook 有效但缺少可解释的经验依据；
- SOP / Workflow 反复返工或出现不合理门禁；
- Evaluation 样本不足、标准不适用或评分器不可靠。

这些发现先作为 Finding 或反馈证据，再判断应更新知识、改进 Harness、修复 Runtime / Tool，还是调整项目工作约定。不能把所有失败都归为知识问题或 Harness 问题。

### 8.3 共享证据、分开治理

同一 Finding 可以同时支持知识改进和 Harness 改进，但两者形成独立候选：
- 知识候选由相应知识范围的维护者核验、授权和发布；
- Harness 候选由对应资产维护者验证、审核和发布；
- 项目是否采用知识或 Harness 版本，由项目有权成员决定；
- 后续工作是否实际使用，分别记录；
- 任一候选被拒绝或退役，不自动改变另一候选的状态。

不建立一个把知识条目、Skill、SOP、Evaluation 和项目配置混成一类的通用资产对象。

## 9. 与现有对象和系统边界的关系

| 现有对象 / 能力 | 知识管理如何使用 | 不应发生的事 |
|---|---|---|
| Source Connection / 外部来源 | 提供内容、修订、权限和同步事实 | 将外部来源内容复制后冒充平台权威原文 |
| Inbox / 导入批次 | 接收待处理资料，记录处理意图和进度 | 把 Inbox 变成第二套项目任务管理 |
| Issue / Comment / Decision | 提供研发目标、人工确认、业务决定和知识候选来源 | 把所有 Issue 讨论自动发布为团队知识 |
| Run / Session / Observation / Usage | 提供真实执行、工具活动、交付和计量证据 | 将日志或模型推断直接当作已确认知识 |
| Artifact / Candidate / Evidence | 提供具体交付版本和核验依据 | 复制一份交付权威内容作为知识源 |
| Evaluation / Finding / Proposal | 提供质量判断、问题归因和改进入口 | 把 Evaluation 分数直接当知识结论或业务验收 |
| Release / Project Adoption | 分别发布知识版本并决定项目采用 | 将发布、采用、实际使用合并成一个状态 |
| Harness 资产 | 引用知识依据、吸收已验证经验、提供质量反馈 | 让知识库和 Harness 重复维护相同规则正文 |
| 工作台 | 让成员从 Team / Project / Issue 找到、贡献和核验知识 | 以内部知识模块或索引结构组织用户工作 |

知识管理需要维护自己的知识事实和处理状态，但执行解析、同步和评价时应复用既有受管执行入口与 Run 证据；不能新建平行 Issue / Task / Run / Runtime 控制面。外部来源的读取权限和平台自身知识受众授权必须同时满足。

## 10. 最小闭环与架构验收

用一项真实研发工作验证以下链路：

1. 从现有权威来源接入一份项目资料，能够保留结构、修订、来源位置和权限。
2. 将资料解析为可核查证据，按项目范围形成候选知识，并识别与已有知识的重复或冲突。
3. 经适当治理后发布项目知识。
4. 新 Issue 开始时按工作目标和权限检索该知识，Agent / 成员能看到摘要、适用范围和原始依据。
5. 研发中发现原知识缺失或错误，可从 Issue / Run / 交付证据反馈。
6. 形成候选修订，核验后更新或退役旧知识；历史工作仍能追溯原版本。
7. 若问题说明需要改变团队方法，另行形成 Harness 候选，使用独立评测与回归样本验证，按权限发布和采用。
8. 下一项可比研发工作能够消费更新后的知识和 Harness，并留下有证据的使用反馈。

验收重点不是索引召回率单一指标，而是：来源是否可信、结构与定位是否保留、权限是否正确、结论是否有证据、检索是否适用、更新是否及时、知识是否真正进入研发、研发反馈是否能触发正确的治理路径。

本设计定义知识业务生命周期与跨能力关系，不决定具体存储、向量数据库、检索引擎、解析供应商、API、任务队列或部署方式。实现技术选型应在来源类型、权限、更新频率、资料规模、检索质量和团队使用成本明确后再做。
