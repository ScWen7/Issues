# 项目代码 Wiki

专题三 B · 产品设计建议稿

一名新加入的工程师打开项目，希望弄清系统由哪些部分组成、一次请求如何跨仓处理，以及修改一处接口会影响哪里。代码 Wiki 让成员和 Agent 从系统说明读到具体实现，再用固定版本的代码、配置或测试核对结论。成员可以在项目中独立浏览、搜索和纠错，也可以把某一节引用到正在处理的 Issue。

DeepWiki 将架构说明、图示与源码链接组织成可直接阅读的仓库 Wiki。这里采用“先读懂，再回源”的阅读方式，并把设计单位扩到团队项目：涉及多个仓库时，每个仓库分别标出基准与覆盖范围。[DeepWiki 产品说明](https://docs.devin.ai/work-with-devin/deepwiki)

## 从系统地图读到代码

| 从哪里开始 | 成员能做什么 | 如何核对 |
|---|---|---|
| 项目总览 | 了解系统边界、组成仓库、主要模块，从业务名称或技术名称找到入口 | 查看本次覆盖哪些仓库、各自的代码基准和更新时间 |
| 模块说明 | 读懂模块职责、公开接口、数据和依赖，跳到相邻模块 | 关键结论指向具体仓库、修订、文件或符号，显示相关配置和测试 |
| 关键流程 | 从一次业务动作逐段追踪入口、服务、数据读写与返回，包括跨仓调用 | 每一段给出连接依据。静态分析只能推测的调用标明待核实，并给出可继续检查的位置 |
| 变更影响 | 从改动的接口或模块找到潜在调用方、测试和受影响的说明页 | 展开依赖依据和覆盖范围，成员判断要重新检查哪些地方 |

按目录阅读、按名称检索都能进入同一页。若提供问答，回答也应回到相同的版本、段落与代码位置。代码图谱适合辅助查找关系，读者可以始终沿页面和源码导航。

## 谁维护，以及哪一版可信

项目维护者选择获准分析的代码仓、模块范围和基准。项目可沿用 Multica 已关联的仓库或本地目录。引用分支时固定本次实际读取的修订；本地未提交修改仅在成员明确共享且可标识快照时作为相应工作副本的依据。团队资料的编辑、浏览与发布无需独立 Git 仓。[原生项目资源与工作边界](03b-capability-governance.md#从已有-issue-开始)

代码、配置和测试由工程仓维护。自动生成的页面归纳指定版本能观察到的实现；由维护者补充的设计动机、历史取舍单独署名，可引用已确认的决定。成员发现错误时可提交改正及依据；源代码有误则回工程工作流修正。需求口径和生效政策通过[团队 Wiki 与项目资料](team-project-wiki.md)引用原文。要回答“线上现在怎样运行”，须再取得对应环境的部署版本及相关运行证据。

仓库基准变化后，找出正文依据或跨仓引用发生变化的页面，优先更新受影响的章节，保留人工补充的原文及待复核标记。一次读取失败、动态路由无法解析、引用位置已删除，各自标出缺项；有权读者可查看旧版本及其适用基准。私有仓读权限制同样适用于目录、搜索摘要、生成正文和关系图。无法按来源拆分的组合段落，在该成员视图中省略。Issue 或 Run 已使用的引用保留原修订，重新打开时按当前权限展示。

## 订单导出的阅读路径

以下为设计示例。新人从“订单导出”流程页定位前端请求、后端权限过滤以及工作簿生成。若静态代码只显示权限查询发往另一服务，页面标出能核对的调用位置；要说明那台服务的内部判断，还需取得对应版本且可读的实现。核验人可将“权限过滤”章节和测试位置引用到订单 Issue，再与业务负责人确认的区域口径比对。工作交接仍沿原 Issue 继续。是否通过由核验报告和验收决定给出。

## 首轮产品验证

取一个获准项目，让熟悉项目的维护者先标出一条关键流程及源码依据。让新成员在没有 Issue 的情况下从项目入口找到同一流程，记录找对的模块、断开的跨仓关系、错误结论及回源耗时。再让 Agent 为一个已有 Issue 定位相应代码，检查引用能否重现。最后更换一个接口的代码基准并撤去一项仓库读权，核对页面更新、人工说明复核、历史引用和各阅读入口的可见范围。

已有研究覆盖 TeamAI 的代码 Wiki 检索、来源锚点与范围过滤，及 Multica 的项目资源入口。代码说明能否忠实解释团队的真实系统、跨仓更新是否及时、能否缩短新成员定位时间，需以上述场景实测。首轮可比较模块目录和关键流程两种入口中，哪一种最能帮助新人找到正确实现。[来源检索研究](../research/topic-03b/knowledge-sources.md) · [代码图谱的证据边界](../research/topic-03b/existing-session-sources.md)
