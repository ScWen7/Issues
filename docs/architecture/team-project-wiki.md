# 团队 Wiki 与项目资料

团队与项目可按需启用资料 Wiki，并从[协作工作台](05-unified-workbench.md)引用其内容。

新成员想知道“团队通常怎样核验导出权限”，产品人员想知道“订单项目目前按什么口径导出”。前者要找适用的团队方法，后者要查当前项目的权威说明。两人都可以直接进入 Wiki 浏览、搜索、核对依据或提出修订。人在工作台维护资料，Agent 在同一授权范围内按需检索，使用者无需操作团队 Git 仓。

飞书知识空间已经提供目录节点和权限，飞书中的资料可以保留原来的作者、位置和编辑方式。Wiki 将多个来源按主题组织，分别展示原文、整理说明和适用范围。[飞书知识空间文档](https://open.feishu.cn/document/server-docs/docs/wiki-v2/wiki-overview)

## 资料由谁维护

| 内容 | 维护位置与责任 | 读者怎样判断能否采用 |
|---|---|---|
| 团队 Wiki 条目 | 有权成员按业务领域或工作主题直接撰写、编辑、关联依据。条目记录维护者、修改历史和适用范围。普通说明按日常编辑权限保存修订 | 先看解决什么问题、适用哪些项目，再核对出处。需要成为团队正式规范时，由相应维护者审核适用范围与采用条件 |
| 项目资料 | 项目成员可在项目范围编写说明、上传有权保存的材料，或关联已有飞书 PRD、评审纪要和接口说明。关联文档的作者仍在原系统修改正文；上传件标明来源、取得时间和修订 | 按项目和主题找到材料，看到它是当前源修订还是一次导入的快照。开发人员可从需求章节追到对应代码基准，核对预期与实际行为 |
| 从项目提炼的团队经验 | 项目成员根据具名证据起草可复用结论，说明适用情形并去掉项目私有细节。来源维护者确认可派生的内容和受众，团队维护者核对方法后发布 | 团队成员读获准文案。项目证据的可见性仍由来源授权决定。后续项目采用时，负责人核对本项目的业务口径 |

Wiki 承载业务含义、约定和经核查的经验。[项目代码 Wiki](code-wiki.md)回答给定代码版本的结构、调用和影响范围。PRD 描述期望行为，代码说明指向实现，判断线上行为还要查看对应环境的发布或运行证据。

## 一名成员怎样找到并使用依据

1. **进入团队或项目。** 团队视图按领域与主题组织共用知识，项目视图汇集本项目资料及引用的团队条目。成员可从这里直接搜索，也可从某项工作的资料引用进入。维护者能看到来源最近一次成功读取的修订、可检索范围和待处理的更新。
2. **从问题定位到原文。** 例如搜索“东区账号能导出哪些订单”，先在当前读者有权访问的项目与团队范围查找，再列出命中的章节、适用项目、修订和维护者。读者可先看摘要，再展开证据段落、打开原文。若回答综合多份材料，每个关键结论都标明所依据的位置。
3. **处理不一致。** 如果现行 PRD 与旧评审纪要口径不同，显示各自的日期、适用范围与冲突段落。已有替代关系时直接引向有效版本；仍有歧义时，由对该规则负责的产品人员确认。成员可在条目反馈缺项，涉及本次交付的决定回到原 Issue。
4. **带进工作。** 成员或 Agent 可把获准章节、来源修订和选用理由引用到当前 Issue 或 Run。核验者由此取对应权限规则，开发者另取实现所需段落。工作中已有足够依据时，沿原有 Issue 继续。[工作台使用边界](03b-capability-governance.md#从已有-issue-开始)

## 改稿、失效与历史引用

外部文档改稿后，按来源的有效修订刷新，保留稳定的章节定位和变更范围。人工导入的资料由维护者替换新修订。旧资料若已被替代，读者可以查历史和替代项；执行记录继续指向当时实际采用的版本。来源暂时读不到时显示最近核对时间和当前状态，重新投递前核对现行修订及读权。确认撤回或接收者失权后，停止向该接收者提供正文及摘录，历史引用可见范围仍按当前授权判断。已发布经验若失去必需的派生许可，暂停其后续分发并交维护者复核。[来源刷新与权限实验](../research/topic-03b/project-knowledge.md) · [知识贡献实验](../research/topic-03b/knowledge-contribution.md)
