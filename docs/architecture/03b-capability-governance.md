## 2. 一条规则怎样生效

**草稿、发布、选用和执行分别留据。** 草稿可以继续修改；发布把当时的材料和引用冻结为可追溯的版本。发布版本的正文与脚本分别有摘要。重试相同发布返回原记录和首发人，同一版本号收到异内容时保留冲突。多人同时发布时，以提交人审阅过的当前版本为前提，先提交的更新生效，迟到者重新查看差异。回退到早先内容以显式发布或经批准的版本选择留下新记录。已使用过的版本保留历史引用，下载继续检查当前读权。

**选择从本次工作的需要开始。** 对验证节点，先取得 Issue 当前决定、项目范围、角色和 SOP 已固定的必需材料，再在接收者可读且已发布的版本中选择。团队默认与项目替代同时存在时，项目发布者应明确取代哪一个可被覆盖的团队版本；团队强制底线继续随契约传入。团队新增版本、项目替代仍指向旧基准时，新的受影响选择显示两个版本和待确认差异。两个互相独立的参考 Skill 可以并列；两个同名规则对同一验收项给出冲突结论时，由有权成员解决后确定唯一判断依据。

**确定版本和保留内容是两步。** 发布回执指向原来源修订与发布对象，SOP 的选择记录指向发布版本。规则正文与核验脚本的内容分别标识，案例用同一发布把两者组合起来。执行侧记录期望送达的内容摘要、实际取得的原始字节摘要和验证方式。对归档、适配后文件、实际模型输入分别声明摘要对象与算法。规则已送达但本轮加载未知时，界面保留这个事实；连送达证据都缺时显示“投递状态未知”。旧内容已退役、接收者失权、必需版本缺失、字节不符分别处理，不在后台换成另一版。当前试验固定一组同变的 Rule 与 Script；两种资产仍独立标识，普通参考材料可单独选用。

| 上游实际行为 | 本项目取舍 |
|---|---|
| TeamAI 项目规则能覆盖同名根规则，两个活跃命名空间也可能同时交付同名 Rule。同步遇锁时命令可正常退出而磁盘仍是旧版 | 保存项目替代关系并读回实际材料。采用其来源选择与不可变脚本快照机制，平台发布对接已有团队和项目权限。[TeamAI 实测](../research/topic-03b/teamai.md) |

## 3. 发布时已有工作正在运行

| 变化 | 在途实例 | 新实例与后继动作 |
|---|---|---|
| 出现可选的新能力版本，Issue 决定和已签订的工作契约仍然有效 | 沿用固定版本，恢复后仍查原引用 | 根据新实例的可见范围与兼容约束选择发布版本 |
| 新业务决定改变当前交付标准，例如 D2 新增付款时间 | 有权控制者列出受影响项、已执行动作与可复用输入，保留 D1 时的结果。原契约中的规则或脚本需要换版时，按专题二暂停受影响范围并明确交给后继实例 | 后继实例固定 R2 与对应核验器，创建或采用其获准的 Run、尝试和候选。接收者仍可读原线程全部材料时，宿主可继续原线程，显式补发 D2；有当前回执后按新标准核验 |
| 成员失去读取权限、资产被撤回或本机缓存发生变化 | 在下载和实际开工处重新检查。已在运行的进程沿 3A 的停止及副作用核对处理；历史仅在有权读取时可查 | 必需材料明确列为缺项，恢复版本或获准替换后再继续受影响节点。未受影响的工作沿原依赖推进 |

一次模板更新与一次业务决定分别处理。D2 由 Issue 维护，发布者把可复用的验收办法发布为 R2，脚本 S2 实现可执行的检查。R2 已发布时，控制者仍可查明 D1 的历史证据；同一条 D2 也可在多个获准的项目中采用不同版本的适配材料。[专题二的在途换版约定](02-sop-workflow.md#41-定义与制品版本)

## 4. 订单导出第一轮

1. 团队发布 R1 与四列核验器 S1，订单和另一个项目都可使用团队默认。订单项目取得 D2 后，项目发布者将 R2 与五列核验器 S2 作为对团队 v1 的明确替代。旧实例保留 R1；另一个项目仍选 R1。
2. 同一个真实 Codex 线程先读 R1。磁盘换成 R2 后继续，实际请求只有旧材料，核验契约暂缓放行。在下一轮显式补发完整 R2，回环端从当前输入核对其字节摘要；控制者随后才按新契约启动核验。三次调用在开始前已分别绑定 Issue、实例、Run、尝试和预期规则。
3. 对同一份四列工作簿，S1 验得通过，S2 验得 A2 通过、A3 失败并要求返工。对已有真实五列 C2，固定 S2 产出与 3A 完全相同的报告。接收方拒绝声称使用旧核验器的回报，对正确报告的两次投递只消费一次。订单 C1、C2 的原报告都依据 D2，四列对照另行生成。
4. 项目没有发布权的贡献者、没有订单项目读权的验证者、失效的项目覆盖和被替换的缓存都各有明确结果。实验里第二位有权发布的成员重试同一版本，历史仍指向首发人。工作台可从 C2 的节点结果查回所选发布、实际脚本摘要和哪一次宿主输入收到了当前规则。[研究记录、结果和复跑](../research/03b-source-evidence.md)

## 5. 项目知识怎样进入一次工作

产品负责人继续在订单需求原文修改约定。项目登记权威来源、适用范围和哪些工作需要哪些章节。Issue 的 D2 决定这次交付的标准。需求文档说明开发怎样实现，核验笔记说明验证者怎样检查。成员可以从工作台的引用回到自己有权阅读的原文。

**文档修订按章节追踪。** 章节保留可检索的标题。队列引用只记录来源、源修订、稳定的标题块 ID、正文块 ID 和正文摘要。原文将“开发说明”改名为“开发时区”，又在前面插入一个可选章节，既有引用仍能定位开发章节。时区正文变化后，平台能沿旧正文摘要找出用过它的 Run 和回合。共同业务约定的正文摘要保持相同，独立核验笔记也有自己的修订记录。

同步只在同一修订的全部分页读完、且源头仍指向这版时更新索引和“最后核对时间”。分页中断或编辑者在读取中再次改稿，就保留上次完整快照并显示“待复核”。确认删除章节或撤回整份来源时，停止该材料的新交付，向有权维护者列出受影响的执行。来源暂时失联时，工作台保留最后一次成功核对的时间。

**成员在项目中搜索，执行者按当前工作取材。** 在工作台当前任务中搜索时，平台先核对成员、项目与 Run 绑定，从该角色的工作范围中取候选章节，再按成员的源读权匹配标题与正文。结果展示命中的标题、片段和出处。验收所需的段落记为必需项，缺项时仅受影响节点等待补齐。可选材料按相关性选入，省略后节点照常推进。向普通成员提示“必需材料待补齐”，来源名称和权限诊断仅向有权维护者展示。

| 订单 D2 的接收者 | 本次交给宿主的章节 | 选择理由 |
|---|---|---|
| 开发者 | 可见订单与付款时间的业务约定、付款事件的时区转换 | 实现导出逻辑需要这两个段落 |
| 独立核验者 | 同一业务约定，另加核验笔记中的区域、角色检查 | 依据同一业务标准，从不同账号检查实际结果 |
| 两者均省略 | 可选的空列表文案、旧版开发说明、财务私有段落 | 分别为本次未选、已被修订替换、属于另一项目 |

**排队保留引用，交付时复核。** 入队时固定接收成员、项目角色、Issue、节点、Run、尝试和所选章节修订。送进宿主前再查成员资格、源读权及其有效期、源修订。测试中，核验者退出项目或源授权恰好到期，已排队的输入均停止交付。本原型固定整份源修订，因此即使只改了开发章节，核验的旧队列也要重新选择；核验者重选后得到相同正文。影响历史结论则按实际使用的章节摘要判断，本次开发章节改版仅命中开发回合。计划记录解释原先选了什么，宿主回执把实际进入当前输入的段落与回合绑定。

**权限收缩后切换线程。** 开发者失去需求文档读权后，旧队列停止交付，保有读权的核验者继续工作。Codex 0.144.6 的四次真实回合表明，即使当轮发送的指令完全省去了旧段落，沿用开发线程时，宿主仍把先前的两段作为历史放进模型请求。同一宿主进程、同一工作目录新建线程后，两段均未出现在请求中。因此，旧线程包含已撤权材料时，后续工作从新线程按现有权限装配上下文，受影响必需项继续等待。历史投递回执保留原时间与摘要，查阅原文另验当前授权。[订单案例、宿主请求与复跑](../research/topic-03b/project-knowledge.md)

## 6. 一次返工怎样成为团队经验

C1 和 C2 在同一个订单 Issue 上按 D2 使用同一核验器。C1 的东区导出混入西区订单，A2 失败并返工。C2 修复后 A2 通过。两份报告的付款时间项 A3 均通过。可复用的经验是用不同权限的账号分别导出，检查各自的订单集合，并单独核对付款时间。成员提交候选时保留两次核验的 Run、候选、原报告摘要和检查位置。多位观察者从这两次执行提出同一条经验时，复用同一个提案，保留原作者与评审决定。

| 成员要做的事 | 核对的权利与依据 | 可见的结果 |
|---|---|---|
| 在项目内追溯返工 | 对相应项目报告有当前读权，沿固定修订查到具体检查项 | 原报告、证据指针、项目订单标识仅在授权范围内展示 |
| 从报告提炼团队可用文本 | 来源管理者按提案修订、确切文案、证据修订和目标受众批准派生使用 | 含项目订单标识的初稿被驳回并保留理由，作者改写后的正文另行授权 |
| 正式发布到团队 | 本例由有团队发布权且可读两份证据的独立评审者确认 | 团队成员取得经验正文、适用范围与版本。项目报告与评审记录按各自读权打开 |

成员个人失去源读权时，关闭该成员对原证据的访问。团队已获单独授权的经验继续依其发布授权使用。每份证据保留内容摘要和单调递增的变更代次。撤回再恢复原文会推进代次，重复上报当前内容则沿用原代次。派生授权撤回、证据被修订或来源撤回时，将已发布经验转为待复核，暂停新投递，既有 Run 仍保留当时采用的版本与正文摘要。仅原报告元数据变动时，评审者可复核新证据并取得对应授权，确认相同正文继续使用原版本。证据与原结论发生矛盾时交回评审。来源撤回后可由发布者具名退役。已退役的版本保持退役，来源恢复后重新作出发布决定。[C1/C2、授权与复核对照](../research/topic-03b/project-knowledge.md)

## 7. 一个节点怎样同时使用 Role、Skill 和 Playbook

订单开发者要产出工作簿，独立核验者要检查同一份候选。两人遵循同一个 Issue 决定 D2，所需方法和操作权各自不同。Role 描述谁负责什么、要交付什么。Skill 提供可选择的方法和入口。Playbook 给出可选的工作顺序。SOP 节点持有必需输入、业务标准和具名制品要求，操作权来自成员、来源和执行授权。

**先固定本次工作，再选择材料。** 从有权签发的派发记录取 Issue、项目、角色、节点、尝试、候选、契约和本次额度。执行者提供自己的身份。先取当前决定、适用项目章节、职责和节点明确要求的 Skill，再按当前角色的偏好尝试 Playbook 等补充材料。两个引用指向同一发布时只算一次。正文摘要用来对照模型实收内容，发布清单另固定来源、类型、正文摘要、声明的要求及所需操作。这样，任何人在正文不变时去掉“需要执行权限”或隐去冲突要求，都会使这次选材失效。真实投递前重查原文修订、接收者及执行授权。

| 同一订单节点遇到的情况 | 平台怎样处理 | 谁作决定 |
|---|---|---|
| 材料齐全，预算充足 | 开发收到导出 Skill 和抽样做法；核验收到检查 Skill 和角色比对做法。两边分别保留 D2 和各自的权威章节 | 派发控制者采用既有工作契约，执行者按需使用可选方法 |
| 预算只够必需项 | 保留完整验收要求、角色职责、必要章节和 Skill，记录省略的 Playbook 及原因，继续本次执行 | 常规取舍按节点已有约定自动完成 |
| 必需项仍然放不下 | 开始执行前列出所需容量与当前额度，等待调整。可换获准宿主、增配额度，或由控制者重订可独立交付的节点范围 | 额度或节点范围由已有授权的控制者调整 |
| 一个可选方法要求省略付款时间 | 省略该方法，记录与 D2 的具体冲突，保留相容材料 | 当前业务决定已给出答案 |
| 节点固定了两个必须采用的方法，对同一列给出相反操作 | 暂停受影响节点，列出冲突项及两个版本。本例项目维护者选择已修正的五列版本，沿用 D2，再做交付核对 | 调整项目方法由有权维护者处理。若团队确要变更验收条件，由 Issue 有权人更新决定，按专题二接续受影响工作 |

**按哪一种预算做判断要能回查。** 这一轮使用“选中正文的 UTF-8 字节数”，可以精确复现只差一个字节的情形。原生 Skill 目录、宿主指令、历史、工具定义和输出预留会另外占用模型窗口。接入具体宿主时要记录其支持的计量方式、预留和估算误差；使用量与实际费用沿用 3A 和专题四的证据。本轮冲突检查使用已经由发布方声明的具体要求，例如“付款时间列包含或省略”。自由文本出现新的歧义时，由发现者带回原文片段和受影响的验收项，再由相应负责人处理。

**入选、本轮收到、实际执行、业务通过分别可查。** 订单对照中，纯目录回合只见 Skill 名称和描述。工作回合经原生 Skill 入口收到完整正文。六个获准回合全部对上所选材料摘要。预算不足、硬要求冲突和排队后撤权的六次派发均未发出模型请求。工作簿由另行记录的 Python 进程生成并核验，即使模型输入完整，C1 的东区越权仍要求返工。本轮试验中，正常取材、仅保留必需项、选用修正版三组 C2 均通过相同核验。[订单的完整实测、数据及复跑](../research/topic-03b/role-composition.md)

## 8. 同一核验契约换到另一成员宿主

订单的五列 D2、C2 候选、三份 XLSX 及核验标准都已固定。成员 A 的 Codex 和成员 B 的 Claude Code 本地各有一项同名订单工具。需要跨宿主保持的是同一次工作的要求，以及它信任的工具来源。成员身份、工具授权、Run 和宿主会话随实际执行者分别签发与记录。

**按项目发布定位能力。** 节点选定订单项目的只读核验工具、服务版本和输入契约。适配器在接收者的 Runtime 解析该服务，本例用已核对的 stdio 启动目标、程序摘要和接口声明确定来源。宿主可用不同名称表达同一工具。工作台按“项目发布 → 本次连接 → 实际调用 → 结果”回溯，并保留每一步的提供者。项目来源和个人来源占用同一配置别名且缺少可信绑定时，停止本次派发。项目来源缺失时，即使个人工具同名且接受相同参数，也保留缺项。

| 发生的事 | 订单节点怎样推进 |
|---|---|
| 成员的项目和个人工具都叫 inspect_order | Codex 业务线程限制可用 MCP 服务。Claude Code 采用本次签发的严格配置及明确的工具允许和禁止项。两个宿主均用实际发现结果对照项目来源。待核验节点继续工作，成员原有个人配置保留。 |
| 项目工具缺失，或项目别名指向成员个人服务 | 在宿主盘点或派发预检处停下，记录阻塞原因。派发控制者可把同一只读核验交给具备项目能力的成员。新 Run 沿用原 Issue、节点、尝试、候选及验收标准，取得独立授权后重验。 |
| 工具已发现，执行前收回授权 | 工具收到调用时核对实际任务身份、派发代次、候选及访问权。此次拒绝回到原回合，只产生拒绝回执。工作台显示“工具拒绝，未取得核验报告”。 |
| 原人失去权限，另一成员具备能力 | 派发控制者确认该操作只读，保留 Issue、节点尝试、D2、候选和制品摘要，以接替成员自己的授权和新 Run 重验。若是可能有写入的操作，先按 3A 核对原动作结果，再决定如何接续。 |
| 原机迟到回报，或接替者重复投递 | 结果先按原 Run 和宿主调用归属，接收时再查当前派发与授权。接替者的有效报告消费一次。原回执仍可从原 Run 查到。 |
| 身份和调用都正确，候选本身有缺陷 | 保留实际工具调用及结果。C1 的核验正常完成，报告判定订单范围失败并要求返工；C2 才获两项通过。Issue 的正式接受继续由有权验收者决定。 |

**可供成员查看的证据。** 打开订单核验节点，能看到作用项目、派发成员、候选、实际宿主、所选工具来源、核验结论和阻塞原因。追查异常时再展开宿主回合、原生调用标识、服务回执、结果摘要和制品。工具出现在目录、模型请求调用、服务实际执行、模型收到结果、节点消费报告均有各自依据。一次宿主回合可以包含两次模型请求和一次工具调用，计量沿用对应 Run 和请求身份。[双宿主订单实验与复跑](../research/topic-03b/cross-host-handoff.md)

## 9. 成员已打开的会话怎样接管

既有会话可复用的前提是成员授予可用的控制入口，本次工作所需的历史、模型、工具和 Hook 能够核对，且在发出订单提示前能控制下一次输入。成员同意把某些回合用于模型上下文、同意把哪些内容共享到 Issue，分别记录。执行端在成员本机核对历史，中心只按选区接收回执。

| 派发时观察到的状况 | 订单节点的处理 |
|---|---|
| 成员已经交出本轮输入权，历史授权覆盖宿主会携带的全部回合，模型、项目工具和配置来源均相符 | 在原 Session 开新的执行段，绑定当前 Run 和节点尝试。核对实际模型请求、原生调用、服务返回及具名制品，再接收报告 |
| 历史授权收回、出现未共享回合、原配置版本缺失、个人 MCP 仍开放，或未知 Hook 可以接触订单输入 | 保留原因，改走新受管会话，按当前权限组装上下文。相同成员和原派发仍有效时沿用原 Run 和节点尝试 |
| 成员与平台都能往原线程继续输入，当前缺少可靠的交接或串行控制 | 从新会话开始本次受限工作。两个 Codex 客户端的实测表明，刚完成历史核查也可能在发单前出现新的私有回合 |
| 执行时撤权或 Hook 改写工具返回 | 服务拒绝时保留拒绝回执。服务返回与模型所见的摘要不符时保留原生 ID 和两份摘要，按契约判定。当前 D2 要求原报告，因此该次没有消费，获准后可以重跑只读核验 |

本轮验证覆盖真实 Codex 前台终端与第二客户端，以及 Claude Code 已建立控制流的运行进程。Codex 端点访问、会话历史共享和订单执行权限分别核对。Claude 通过原生 prompt 和工具 ID 把前置、后置或失败 Hook 归回原调用。另一个 Hook 确实产生了新的外部动作时，单独取得其执行凭据再归属。[原会话实验与复跑](../research/topic-03b/existing-session.md)

## 10. 3B 收口与专题四交接

已完成规则与脚本发布换版、项目知识选取与贡献、角色与方法组合、双宿主工具执行，以及成员已有会话接续的产品设计和订单核验。通用原则作为有作用域和版本的材料进入节点。涉及强制检查的条款另绑定业务依据和核验项。项目代码图作为知识来源时，引用固定到仓库、提交、位置和读权。真实企业 IDE 接入、商业模型端点、私有代码图换版与失权列入现场验收。[对照产品输入的覆盖评审](../research/topic-03b/existing-session-sources.md)

专题四沿用已有 Run 和执行段。订单回合中两次模型请求、一次工具调用及其 Hook 可以分别关联到同一份结果。拒绝、改写后重验和业务返工均保留原因与实际工作量。首先验证固定订单节点的请求归属和去重，再区分供应商账单、宿主估价与未知费用。
