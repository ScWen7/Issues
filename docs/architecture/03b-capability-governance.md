# 团队能力与工作上下文

本专题涉及对象的状态语义、转换条件和跨层事件遵循[统一生命周期、状态机与事件模型](lifecycle-state-event-model.md)。本专题维护具体行为与适用边界，不另行定义冲突的状态体系。

成员接手一项工作时，应能知道做什么、需要哪些工具和资料、自己有权使用哪一版。项目与团队维护可复用的能力，成员按工作需要选用。在 Issue 中确认范围和业务决定，实际使用的资料、工具与结果沿对应 Run 和交付追溯。

## 1. Issue 的上下文

成员接手待办或子项时，沿原线程获取所需信息。一次性业务决定由原 Issue 保存，项目和团队资料按需引用。

### 从已有 Issue 开始

Multica 普通指派携带 Issue 身份与可选交接说明。Agent 从 Issue 描述、相关评论线程和必要的父项约定取得上下文。项目标题、说明、关联工程仓和绑定本机的目录也可随执行取得。当已有信息足以工作时，直接使用当前 Agent 和已配置的 Skill。需要额外资料时，再按当前项目、角色、任务和读权限确定来源。[指派与评论读取](https://github.com/multica-ai/multica/blob/fdfbfcd5e5d30c135255e63ab9af4c52672b7bbc/server/internal/daemon/prompt.go#L377-L395) · [父项与子项](https://github.com/multica-ai/multica/blob/fdfbfcd5e5d30c135255e63ab9af4c52672b7bbc/server/internal/daemon/prompt.go#L81-L109) · [项目资源](https://github.com/multica-ai/multica/blob/fdfbfcd5e5d30c135255e63ab9af4c52672b7bbc/apps/docs/content/docs/project-resources.zh.mdx#L12-L27)

## 2. 团队与项目资源

团队维护可跨项目采用的能力；项目保存自己的约定、工程基准与获准工具。同一资产适用于哪些工作，在相应范围内确定。

### 团队与项目怎样维护可复用内容

| 内容 | 维护者与采用方式 |
|---|---|
| 当前工作 | 成员在 Issue 维护目标、范围、决定、交接和完成条件。子 Issue 引用适用的父项约定。执行与交付沿原 Run 或成员共享的来源记录。 |
| 项目资料与团队知识 | 作者在原资料系统维护正文，也可直接在平台撰写自有说明。工作引用具体修订、章节和获准的内容。需要独立查阅、订正与组织资料时，可启用[团队 Wiki 与项目资料](team-project-wiki.md)。 |
| 项目代码与实现说明 | 工程仓维护代码、配置和测试。按仓库、修订及位置引用。需要跨模块和跨仓阅读时，可启用[项目代码 Wiki](code-wiki.md)，由项目维护者核对解释与代码基准。 |
| 项目 Agent 配置（Harness） | 项目维护者选择 Agent、Skill、规则及获准工具，说明项目默认组合和角色差异。成员按本次任务和自己的授权使用。直接使用已配置的 Agent 与工作区 Skill 有原生入口，项目级组合与选版是产品设计扩展。[原生资产与回执](../research/topic-03b/composition-native.md) |

团队成员在团队或项目范围维护、选用和发布能力。工程 Git 仓可以提供已有规则、代码与可重现的修订。使用团队资料与能力直接沿工作台或原资料系统进行。两个 Wiki 分别按需启用，普通协作可直接引用现有文档与工程仓。

## 3. 资产分类与边界

| 成员要使用什么 | 作用 |
|---|---|
| Role | 在 Multica Agent 配置上说明职责、可执行的工作和交付要求。成员或工具权限由原授权决定。 |
| Skill、Plugin、MCP 工具 | Skill 提供可调用的方法，Plugin 和 MCP 提供实际工具与服务。沿原生绑定、投递和连接路径工作，注明来源、适用范围和版本。[工作区及仓库 Skill](https://github.com/multica-ai/multica/blob/fdfbfcd5e5d30c135255e63ab9af4c52672b7bbc/apps/docs/content/docs/skills.zh.mdx#L93-L105) |
| Rule、Principles、Playbook | 规则与原则声明必须满足的要求和作用域。Playbook 提供某类工作的可选方法，负责人据此判断如何推进。 |
| SOP、Script | 维护者发布稳定的流程或命令。SOP 规定受托范围内的专业步骤，Script 固定程序与输入输出，执行关联原 Run。[SOP 与工作流](02-sop-workflow.md) · [受管脚本的承载](03a-execution-plane.md#4-受管脚本与本地用量的能力边界) |
| 知识 | 以来源、有效版本、适用范围和维护者说明一项事实或经验。其对本次工作的适用性由 Issue 上的工作约定决定。 |

## 4. 发布、版本和作用域

团队、项目和个人可以有各自的默认项。正式发布内容有维护者、适用范围、来源修订、版本、内容摘要和生效状态。源文档用原系统修订，代码说明使用其代码基准。发布后修订产生新版本。项目按资产身份和版本明确指定覆盖的团队默认项，同名资产按来源识别。团队默认换版时，有权维护者查看差异，决定新工作应使用何种组合。在途执行保留实际采用的版本。

发布时核对权限和发布者已审阅的基准。相同发布请求返回原记录。相同版本有不同内容或来源时，提示差异，等待处理。若其他维护者已发布新基准，提交者先查看变化再确定是否发布。撤回或访问权变化后，停止向失权范围再次投递。仍在运行且可能已写入的工作，按受影响范围与已发生的副作用决定如何接续。[发布、覆盖与作用域](../research/03b-source-evidence.md)

### 普通 Skill 与验收资产的固定版本

Multica 固定版本 `fdfbfcd` 的工作区 Skill 提供编辑历史与恢复。普通 Skill 的旧缓存缺失时可以取得服务端当前内容，原生删除还会清除其版本历史。插件另外支持指定版本安装。工作约定要求结果可复现时，在开工时固定 Rule、Script 与依赖的内容引用，核对实际字节摘要。退役后仍需核对历史结果时，记录获准保留的内容或可追溯引用，按查看时的权限读取。[原生资产行为](../research/topic-03b/native-assets.md#multica)

验收规则正文、脚本、安装包和实际输入可有不同的摘要。引用注明摘要对象与算法。维护者发布了新资产后，已交付的结果沿原标准保留。项目若决定改用新标准，重新核验受影响的候选并记录适用范围。[规则换版与结果归属](../research/topic-03b/native-assets.md)

## 5. 一次工作如何选择和投递能力

团队发布使一种方法在获准范围内可用。项目维护者在项目配置中选择采用的版本、适用范围和用途。符合范围的新工作沿用项目约定。负责人可选择适用的建议方法。必需规则进入本项工作约定，可引用项目中的有效版本。负责人在自己的授权范围内补充本项要求。项目规则需要例外或变更时，由有权修改该规则的成员确认，Issue 保留对本次范围有效的决定。

1. 从当前 Issue、父项和项目配置取得适用约定，仅为实际工作缺项补资料或能力。
2. 按接收者当前权限与本次分工选取资料。把项目强制规则、有效业务决定与执行必需输入放在优先位置，其余方法可按需采用。
3. 引用选中的来源、版本、适用范围及受影响的工作。使用原生 Context、Skill 和 Plugin 路径投递，由对应宿主获取。
4. 需要核对实际采用情况时，分别记录准备、写入、发现、调用以及当前模型输入的证据。只有投递回执时显示“已投递”。工作所需的工具报告另查服务返回与对应工件。[逐调用证据](03a-execution-plane.md#contextreceipt-与逐调用证据)
5. 必需项因预算、权限或冲突无法取得时，暂停依赖它的环节，由有权成员调整范围、选版或补充材料。其他获准工作可以继续。

选用的方法与本项必需规则冲突时，负责人按必需规则行事，说明舍弃该方法的原因。两项必需规则冲突时，由相应范围的有权成员澄清，依赖该决定的工作等待。受管执行在准备时选取材料，本地主动关联从下一可识别的执行段取证，事后补交按交付版本与已有证据判断采用情况。[接手时补查](03a-execution-plane.md#接手者取得哪一版工作) · [角色、规则与预算的组合实验](../research/topic-03b/role-composition.md)

### 步骤驱动与观察

采用 TeamAI Skill Driver 的步骤协议时，当前会话或宿主子代理按 `next / ack / report` 领取、确认与报告步骤。回报关联原 Issue、Run、节点和能力版本。同一回报重送可识别为同一步骤。执行派发、Runtime 的选择、授权和成员交接沿 Multica 的既有入口。宿主只支持报告时按实际能力接收结果。[Driver 与宿主能力](../research/topic-03a/teamai.md)

AgentObservation 将来自 Backend、Hook、OTel、转录或成员说明的记录关联到既有执行，注明来源、原生身份、实际覆盖范围、共享授权和发生时间。计量按可信映射回到同一请求或 Stage，无法证明归属的记录单列。[本地主动会话与观察](03a-execution-plane.md#5-本地主动会话与-agentobservation)

## 6. 工具授权与跨宿主接续

使用指定项目工具时，先核对已发布的服务身份、接口契约、项目范围与版本，再核对本次实际发现、调用和服务受理的对象。项目服务在受理时检查当前成员、Run、工作范围与授权。同名、同参数的本地工具仍按个人来源呈现。服务原始报告、模型在 Hook 后收到的内容、节点采用的报告各自带有来源。[双宿主调用与结果回流](../research/topic-03b/cross-host-handoff.md)

| 情形 | 接续方式 |
|---|---|
| 成员交出下一次输入控制，历史、模型、工具和 Hook 均符合本轮授权 | 在原 Session 建立本次执行段，核对实际输入、调用和报告。中心仅接收成员同意共享的部分。 |
| 私有历史不适用于本轮，或无法控制并发输入与工具来源 | 从现有入口开新会话，按当前权限重建材料。相同成员、尚未开工且原派发仍有效时，可沿用原 Run。 |
| 工具调用前或服务受理时权限撤回 | 停止新调用或记录服务拒绝回执。相关节点等待获准的来源，已发出的调用核对实际效果。 |
| 服务报告与 Hook 处理后模型所见内容不一致 | 记录原生调用 ID 及两份摘要，按本次契约判断能否采用。要求两者一致的核验会拒收该结果。 |
| 原执行结束后需要复验，或由另一成员接手 | 另行派发产生后继 Run。接手者用自己的 Runtime 和凭据，引用原候选、被拒报告和待完成的动作。 |

上述控制与观察在 Codex 0.144.6 的开放端点、Claude Code 2.1.325 的受控入口有局部实证。能否接入一名成员正在使用的企业 IDE，取决于该入口、版本与授权。[现有会话实证](../research/topic-03b/existing-session.md)

## 7. 知识来源与有效性

### 来源刷新、选取与历史重带

项目外部文档定位到所用修订、章节或块，代码定位到仓库、提交及实现位置。检索、摘要展示和再次投递均使用读者的当前权限。普通资料更新后，按实际引用章节和摘要判断受影响的工作。既有 Run 保留所用版本。

刷新中断时保留上次成功核对的版本与时间。必需资料的有效性或读权暂时无法确认时，向接收者标明缺项，由有权维护者查看原因。权威来源的撤回、删除或完整修订是改变来源有效性的依据。恢复使用还需核对当前读权。Codex 对照实验显示，原线程在新指令中没有正文时仍可能向模型携带历史材料。历史含失权内容时，用新会话按当前权限重建；此前共享的事实保留原时间和来源。[来源刷新与会话历史](../research/topic-03b/project-knowledge.md)

### 从项目证据到团队经验

项目成员从实际工作中提出有复用价值的知识、规则或方法，说明它适用于哪些工作。原业务材料继续依来源权限读取。跨项目使用时，可在获准范围内发布派生内容。

1. 提案引用原 Issue、证据和适用范围。同一提案的重送复用原记录，修订后的文案重新标明来源和目标受众。
2. 来源管理者授权具体版本的证据用于指定的派生文案及受众。独立的团队发布者核对证据、验证结果、许可和发布权。正式读者获得获准的文案、版本和适用条件。
3. 任一必需来源撤回该项派生许可后，受影响的组合经验暂停新投递，其他来源和受众的许可照原范围处理。相同内容恢复时，当前授权和独立复审齐备后才恢复投递。已退役版本另需发布决定。已送达副本能否处理，由对应宿主提供依据。
4. 将经验升级为验收规则时，按[质量与改进设计](04-cost-quality-improvement.md)固定候选、对照样例与成功标准，经审核发布。由有权成员决定后续 Issue 的适用规则，原交付沿当时约定判断。

来源授权、逐稿审核、单来源撤回和恢复在本地模型中有实验记录。生产环境的授权仍由实际平台、来源系统和运行入口共同落实。[经验贡献与撤回实验](../research/topic-03b/knowledge-contribution.md)
