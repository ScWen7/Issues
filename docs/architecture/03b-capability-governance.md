# 专题三 B：TeamAI 团队能力与知识治理融合

版本：V1.1 · 来源授权、发布版本与实际消费交叉审查 · 2026-11-15

本专题吸收 TeamAI 的资源组织、作用域、版本、检索、分发、Skill Driver 和 AgentObservation 机制，并融合进 Multica 已有 Agent / Skill / Plugin / Context / Run / Runtime 体系。

本专题不建设第二套 Agent 注册、Skill 执行、上下文投递或 Run 管理系统。治理规则见[架构治理基线](governance-baseline.md)。

既有 TeamAI / Multica / LoopForge 源码研究和订单实验保留为证据：[3B 源码与订单实验](../research/03b-source-evidence.md) · [跨宿主工具与接续](../research/topic-03b/cross-host-handoff.md) · [项目知识](../research/topic-03b/project-knowledge.md)。

## 1. 能力治理的目标

让团队能持续回答：

- 某项 Agent 能力由谁维护，适用于哪个团队、项目和工作类型？
- 当前有哪些可用 Role、Skill、Rule、Playbook、MCP 工具和 Knowledge？
- 一次工作为什么选择这些资产，实际投递了哪个版本？
- 宿主是否收到、发现、加载或调用了这些资产？
- 资产修订、撤回或权限变化后，哪些新工作受影响？
- 真实执行中的问题如何反馈成可审核的资产改进？

这些问题属于能力与知识治理；Issue 和 Run 的事实仍来自 Multica。

## 2. 复用 Multica 的资产和执行基础设施

| 能力 | Multica 已有基础 | TeamAI 增量融合 |
|---|---|---|
| Agent | Agent 定义、Provider、模型、运行配置、Agent 选择 | Role 组合、团队规范、职责与输出契约 |
| Skill | Skill 发现、准备、分发和宿主加载通道 | 团队 / 项目作用域、版本治理、来源和适用条件 |
| Plugin / MCP | 插件与工具配置、连接和工具调用 | 项目可信来源、允许范围、工具来源核验和授权策略 |
| Context | Agent brief、项目说明、上下文准备、ContextReceipt | Knowledge 检索、章节引用、选择理由、材料预算与实际使用证据 |
| Run / Session | Multica 执行和宿主会话 | Skill Driver 以现有执行单元推进步骤，不创建第二套 Run |
| Trace / Result | 宿主消息、工具活动、终态和结果 | AgentObservation 补充来源、请求身份、共享范围和覆盖缺口 |

只有 Multica 的现有资产结构无法表达的治理信息，才以最小元数据或扩展方式补充。

## 3. 资产分类与边界

- **Role**：说明承担者的职责、目标、权限边界和交付要求。优先作为 Multica Agent 配置的治理视图或组合模板，不创建第二种 Agent 执行实体。
- **Skill**：可被宿主发现和调用的专业能力。沿用 Multica 已有 Skill 机制，补充发布者、作用域、版本、来源和适用条件。
- **Rule / Principles**：团队或项目必须遵守的约束。需声明适用范围、强制级别、冲突处理和实际投递通道。
- **Playbook**：指导 Agent 如何分析和推进某类工作的可选方法，不是固定 SOP，也不拥有派发权。
- **MCP / Tool**：实际可调用的外部能力。目录可见、连接成功、工具被发现、调用发起、服务执行和结果返回是不同事实。
- **Knowledge**：具有来源、适用范围、版本和有效性的可检索知识。知识不能替代 Issue 当前工作决定。
- **SOP**：属于专题二，资产治理负责其发布和版本，运行承载仍由 Multica Issue / Run。
- **Script**：固定版本的受管命令资产。确定性命令经 Multica Run / Daemon 托管是已识别扩展，现有订单实验走 TeamAI 命令驱动；执行归属、取消和制品通道统一见[3A Script 缺口](03a-execution-plane.md#7-只有真实缺口才允许扩展)。

## 4. 发布、版本和作用域

资产治理按以下规则组织：

1. 每份资产有明确所有者、类型、来源、适用范围、版本、内容摘要和发布状态。
2. 作用域至少区分团队、项目和个人；更窄范围的资产不能静默覆盖更高层强制规则。
3. 发布版本不可变。修订形成新版本，明确替代关系和兼容条件。
4. 项目覆盖按资产身份和版本指明被替代的团队默认项，同名资产仍按各自来源选择。团队默认换版后，仍以旧版为基准的项目覆盖在新选择时列出差异，由有权成员重新确认。已固定的实例沿用原选择，继续投递时复核当前权限。
5. 资产撤回或权限变化时，阻止后续新投递和失权材料再次进入模型输入。继续 / 恢复的历史含失权材料时改走干净 Session；在途执行依据影响范围与已发生副作用决定暂停、接续或换版。单纯版本修订与权限撤销分别处理。
6. 已发布版本的历史引用保留；历史可追溯不代表当前仍有权读取原文。
7. 发布时先检查当前发布权。在同一资产和作用域内重放同一版本，若内容、来源修订、决定和替代关系一致，返回原记录和首发人，保留现行版本及撤回状态。同版本的内容或上述关联变化时报冲突。提交新版时比较发布者审阅过的基准与当前发布版本；另一发布者已推进基准时，迟到的提交者须重新审阅差异。上述陈旧基准与上级换版已有单进程选版反例，多成员交错发布仍待集成验收。[订单发布验证](../research/03b-source-evidence.md#一次有前后顺序的订单实验)

由 Evaluation / Findings 产生的改进，先固定候选内容，在明确实验范围完成专题四的 Benchmark，再进入正式发布审核。实验 Run 可按授权选择候选并保留实验标识；普通业务 Run 仍选择已发布版本。知识改进的验证可采用固定检索问题、来源及正确性标准，规则或 SOP 改进采用对应回归任务，详见[专题四](04-cost-quality-improvement.md)。

### 普通 Skill 与验收资产的固定版本

Multica `fdfbfcd5e5d30c135255e63ab9af4c52672b7bbc` 为普通工作区 Skill 提供编辑历史与恢复能力。插件包另有发布及指定版本安装机制。普通工作区 Skill 在旧引用缓存未命中时可接收服务端当前新版，插件 Skill 遇到 hash 漂移则拒绝。原生删除 Skill 会清除其版本历史。验收 Rule / Script 因此要固定不可变内容引用，在开工前核对实际原始字节摘要，退役后保留获准的历史内容或不变引用。复用底座分发和发布设施，补齐这组验证资产约束。[固定源码、原生测试与订单取舍](../research/topic-03b/native-assets.md#multica)

发布记录关联原来源修订和发布对象，SOP 选择记录关联本次发布版本。Rule 正文与 Script 分别标识，可由同一发布组合；分发包、适配文件、正文的摘要注明对象与算法，通过发布映射关联。保存草稿、正式发布、节点选版和实际运行各有记录。LoopForge 原生反例中，未重新发布的目录修订可进入新 Run 或显式刷新，旧同 ID 成功节点仍保留；融合产品按明确发布版本与新标准重验受影响结果。[原生换版反例](../research/topic-03b/native-assets.md#反例保存检查脚本后旧成功会发生什么)

## 5. 一次工作如何选择和投递能力

资产选择应围绕 Multica 当前 Issue / Run 的实际工作范围：

1. 从 Issue 取得目标、当前决定、项目和责任角色。
2. 读取已发布 SOP / Playbook 或节点要求；确定必需与可选材料。
3. 在成员有权访问的资产范围内检索候选，应用团队底线、项目覆盖和角色适用条件。
4. 记录选中版本、来源、摘要、选择理由及省略原因。
5. 将选定材料交给 Multica 现有 Context / Skill / Plugin 投递路径。
6. 通过 ContextReceipt 和宿主原生证据核对：已准备、已写入、可发现、实际进入当前输入、被调用，不能混为一个“已加载”状态。
7. 资产撤权、修订或投递失败时，按缺项和影响范围阻止相关工作，不以同名个人资产或旧缓存静默替代。

资产治理不自行创建 Run。每次实际宿主调用和加载证据应关联 Multica 的原生 Run / Session / Turn / Request。原生 ContextReceipt 表示准备与投递，按 task 的重报会覆盖；D1→D2、实际调用与模型输入分别保留关联证据，详见[3A 的逐调用证据](03a-execution-plane.md#contextreceipt-与逐调用证据)。

### Role、Rule、Skill 与 Playbook 怎样组合

订单核验角色必须取得 D2、候选与权限核验要求，可选 Playbook 提供分析方法。先放入团队强制规则、当前 Issue 决定和节点必需材料，再按角色挑选 Skill 与知识；预算不足时先省略可选方法并记录原因。若可选 Playbook 要求作者自审，而强制 Rule 要求独立核验，省略该 Playbook，记录冲突并继续独立核验。必需材料仍放不下，或节点固定的两项必需要求相互矛盾时，只暂停受影响节点，等待有权成员调整额度、范围或方法。工作分配与验收标准仍由 Issue / SOP 确定。

目录只列名称和描述时记录“可发现”；原生 Skill 入口取得正文时记录调用与对应回合；实际文件核验再产生独立结果。订单实验已验证正常取材、只保留必需项、修正版三种 C2 路径，以及预算不足、硬冲突和排队后撤权的拒绝对照。角色检索只遍历本轮适用与有权读取的来源，必要知识缺失时阻止受影响动作。[组合与预算实测](../research/topic-03b/role-composition.md)

## 6. Skill Driver 与 Multica Run 的关系

TeamAI Skill Driver 的价值是让当前 Agent 按约定领取、确认、执行和回报工作步骤。融合时：

- Driver 作为 Multica Run / Session 内的步骤协议或宿主工具能力运行。
- next / ack / report 等步骤状态只表达 Driver 对步骤交接的记录，不另建平台 Run 或成员工作状态。
- 子代理由宿主原生机制或 Multica 已有 Agent 协作能力承载。
- Driver 不自行分配 Runtime、不绕过 Multica 权限，也不直接完成 Issue。
- Driver 回报关联原 Run、Issue、SOP 节点和资产版本；重复回报按稳定步骤身份幂等处理。
- 如果某宿主无法在当前会话或子代理中承载 Driver，应记录能力缺失并选择已支持路径，不伪造支持能力。

## 7. AgentObservation 与执行事实

AgentObservation 是对已有执行事实的增强视图，不是第二套执行账本。

建议记录或引用：

- 来源：Multica Backend、Hook、OTel、转录、文件观察或成员自述；
- 原生身份：Session、Thread、Turn、Request、Message、Tool Call、API Call；
- Multica 身份：Run、Runtime、成员、Issue；
- 发生与接收时间、采集范围、共享授权和数据摘要；
- 事件类型：Prompt、Assistant、Tool、Result、Usage、Context、Stop 等；
- 可信等级：宿主原生记录、平台确认、采集器推断或成员自述；
- 缺失和覆盖边界。

同一事件被多个观察源捕获时保留多份 Observation，但映射到同一原生事件和计量单元。无法证明归属时保留为未归属观察，不自动挂到最近的 Run。

## 8. 工具来源与跨宿主授权

项目工具必须能证明来源，不以名称相同或参数相同作为可信依据。

- 发布时固定工具来源、服务身份、接口契约、适用范围和版本摘要。
- 投递时复核成员、Issue、Run、项目权限及工具授权。
- 宿主侧核对实际发现的服务与工具；调用时核对原生调用身份和当前授权。
- 服务回执、模型收到的结果和节点消费的报告分别留证。
- 权限撤销后拒绝新的调用；在途调用按 Multica 原有取消和副作用核对机制处理。
- 接替成员使用自己的 Runtime、凭证和新 Run；不继承前成员的私有会话或凭证。

### 工具结果与已有会话接续

一次核验依次核对：项目发布的服务身份 → 本轮实际发现的工具 → 原生工具调用 → 服务取得并处理的请求 → 服务原始报告 → 模型收到的 Hook 后结果 → 节点消费的候选报告。名称或参数相同的个人工具保留个人来源，按契约拒绝冒充项目工具。服务端受理时再查成员、Run、当前工作范围、候选和工具授权；仅列目录或发出调用，各自保留发生事实。[双宿主服务调用与结果回流](../research/topic-03b/cross-host-handoff.md)

| 会话或调用变化 | 工作如何继续 |
|---|---|
| 已有 Codex / Claude 会话有可用控制入口，历史授权、模型、项目工具与 Hook 均可核对，且下一次输入已交接 | 在原 Session 建立当前执行段，关联现有 Run 与节点尝试；逐项核对实际输入、调用和报告 |
| 历史包含未经授权用于本轮模型输入的回合，或现有配置含未知 Hook、不符的个人工具 | 使用现有新会话入口按当前权限组装材料；相同成员、尚未开工且原派发仍有效时保留原 Run |
| 成员与平台仍能并发向原线程输入 | 本次受限工作改走可控新会话；双客户端实验已观察到核查后插入新私有回合 |
| 调用前失权，或服务执行时当前授权失效 | 不发起调用或保留服务拒绝回执，相关节点显示缺项 / 拒绝，等待获准路径 |
| 服务返回与模型收到的 Hook 结果摘要不同 | 保留原生调用 ID 和两份摘要；订单契约要求一致，因此不消费该回合的报告 |
| 原任务已终结，另行派发只读复验 | 建后继 Run 关联原 Run 和拒收证据；只读核验的目标、候选、版本仍适用时保留原节点尝试，记录两次真实执行和成本 |
| 换成员、旧机晚到或接替者重复回报 | 接替者使用自己的授权与新 Run；旧报告归原 Run / 候选，当前有效报告消费一次 |

已有 Codex 0.144.6 前台端点、Claude Code 2.1.325 控制流、晚到工具与 Hook 改写分别有实际记录。模型使用历史的授权与中心共享选区各自记录；中心只收获准选区。企业 IDE 与组织账号条件按现场集成验收。[成员会话与复验归属](../research/topic-03b/existing-session.md)

## 9. 知识来源与有效性

知识管理补足 TeamAI 的知识机制，但不建立第二套项目事实系统：

- 权威产品 / 项目文档仍由其原系统维护；平台登记来源、修订、章节或块身份和摘要。
- 检索结果必须携带来源、版本、适用范围和权限。项目 Wiki 和代码知识图谱可作为来源。采用代码关系时固定仓库、提交、位置与关联依据，按接收者当前读权检索和投递。已有固定源码及范围过滤测试，私有代码图改版与撤权后对订单节点的实际影响仍待现场验收。[设计输入覆盖评审](../research/topic-03b/existing-session-sources.md)
- 选入宿主的材料与 Issue 当前决定分别管理；知识不能覆盖当前 Decision。
- 来源更新后识别受影响的新投递和历史使用，不静默替换在途版本。
- 来源失效、撤回或权限变化时停止新投递，并显示缺项；已发布的脱敏 / 派生知识需遵守来源授权。
- 从执行中提炼的经验先成为候选，审核通过后才发布为正式知识或能力资产。

### 来源刷新、选取与历史重带

来源内容按权威修订、稳定章节 / 块身份和正文摘要选取。刷新失败保留前次成功快照及核对时间；当前性或读权尚未证实时不返回片段，向普通接收者显示缺项，有权维护者可查具体原因。读取中断、源再次改稿或授权服务失联各留事实。删除结论以权威撤回或完整修订为据，临时失联与失权分别处理。来源恢复相同完整版本可更新核对时间，历史仍按实际送达版本和摘要查询。

来源修订变化后，队列按所固定源修订重新选择；检查历史影响时再按章节和正文摘要定位实际变更。核验材料文字未变与开发段落已变可以分别处理。Codex 实测撤回开发者读权后，即使当前指令为空，原线程仍把先前正文带入模型请求；同进程新线程才消除这条历史。因此继续 / 恢复前核对历史授权，包含失权正文时新建线程按当前权限重建，必需知识仍缺则等待。已发送内容保留历史事实，展示原文仍验当前读权。[四回合对照与来源变化](../research/topic-03b/project-knowledge.md)

### 从项目证据到团队经验

C1 / C2 的区域订单核验形成经验候选。含项目订单号的初稿在项目内被驳回，修订稿只描述用区域与跨区账号校验订单集合、另查付款时间列的方法。提案、来源授权、团队发布与业务规则变更分别记录。

1. 同一主题、Issue、节点与证据定位重复提交复用提案；修订形成新稿，旧稿的授权和驳回事实保留。
2. 来源管理者对每份必需证据签发派生使用授权，绑定提案修订、确切文案摘要、证据修订及目标受众。项目源读权、对外提炼权与团队发布权分别核对。
3. 改进候选先按固定问题、来源和成功标准完成验证，独立团队发布者按当前读权核验原证据、验证结果及许可后发布。普通团队读者只收到版本、范围与获准文案；项目报告、订单号、私有路径及审核记录按项目权限提供。
4. 个人失去原报告读权只影响该人的源访问；团队已获独立授权的经验按派生许可使用。任一来源管理者可撤回自己所管来源对指定文案及受众的许可，组合经验立即待复核并暂停新投递，其他来源和受众许可保留原值。
5. 来源变更代次区分修订、撤回、恢复与重复上报。来源恢复成相同字节仍需当前代次的新授权和独立复审；恢复授权只完成许可，复审通过才恢复投递。相同正文及受众可沿用原资产版本，新增复审凭据；正文改变则发布新版本。
6. 证据与结论矛盾时交回评审，具名退役保留历史；已退役版本在来源恢复后仍保持退役，重新发布须新决定。既有 Run 保留当时实际采用的版本与正文摘要。

这些是已验证的单来源撤回、同字节恢复和独立复审规则，融合到 Multica 资产发布与访问链；原生资产设施缺少的授权关联按最小扩展补齐。[贡献审核、45 项基线与 5 项单来源回归](../research/topic-03b/knowledge-contribution.md) 记录本地模型和上游实验，真实组织权限同步、持久发布与并发去重，以及离线成员本机副本的撤回仍待集成验收。中心暂停新投递与已送达副本的处置分别留据。团队经验升级为验收 Rule 时，再走规则发布和对应 Issue 工作约定确认。

## 11. 验收标准

1. Role / Skill / Rule / Playbook / Knowledge 能声明所有者、作用域、版本、来源和适用条件。
2. 资产选择能追溯到 Multica Issue / Run，不创建第二套工作对象。
3. 实际投递沿 Multica Context / Skill / Plugin 路径，能够区分准备、写入、发现、加载和调用。
4. 同名个人工具不能冒充项目发布工具；撤权后不能继续新调用。
5. Skill Driver 使用既有 Run / Session，步骤回报可幂等，不建立第二套 Run。
6. 多源 AgentObservation 不重复创建执行或计量事实。
7. 知识修订和撤回能识别受影响的投递，历史证据保留来源和授权边界。

## 12. 订单贯穿案例与交叉审查反例

案例沿用[订单推演假设](overview.md#订单贯穿案例)：可见订单、XLSX、5,000 条上限，D2 新增付款时间列。D1 四列对照与 D2 五列分别标识。C1、C2 都用 D2，C1 区域权限 A2 失败并返工，C2 的 A2 / A3 通过；角色、数字和业务选择是案例假设。

正常路径：Issue 确认 D2 → 项目发布对应 Rule / Script → 角色选择必需规则、核验能力与知识 → 3A 核对实际输入、项目工具调用和报告 → 节点按本轮候选消费 → 有权成员验收 → C1/C2 事实进入提案 → 来源按确切文案与受众授权 → 固定候选验证 → 独立审核形成团队经验。正式资产版本归统一发布链，工作事实与实际执行沿 Multica。

| 反例 | 设计处置 | 证据状态 |
|---|---|---|
| 任务固定旧 Skill 引用，缓存缺失后中心返回新版 | 普通 Skill 沿原生更新语义；验收 Rule / Script 核对不可变版本与实际摘要，失配则停相关核验 | 固定 Multica 原生对照已测；验收资产扩展待集成 |
| 删除普通 Skill 后要复查旧 C1 使用内容 | 退役时保留获准历史内容或不变引用，当前查看另验读权 | 原生历史删除行为已测；历史留存融合待验 |
| D2 已写入文件，但当前模型仍见 D1 | 查看本轮输入证据，显式补发 / 合规新会话重装；新标准重验受影响候选 | Codex / Claude 换版已测 |
| 排队后撤权、历史含已失权正文 | 重新核对本轮权限；停旧投递，按当前权限建干净线程 | 队列和真实历史重带对照已测；继续入口集成待验 |
| 同名个人工具、晚到项目工具、Hook 改写结果 | 分开核对来源、发现、服务返回和模型所得；契约不符拒收，原任务终结后另行派发的复验用后继 Run | 双宿主及成员会话已测；统一消费集成待验 |
| 仅 C1 来源管理者撤回派生许可，后来恢复相同字节 | 暂停组合经验，当前代次重新授权并独立复审；旧派发保留 | 本地贡献模型与单来源回归已测；真实发布链待验 |
| 可选方法与强制核验冲突，或两个必需项相互冲突 | 省略冲突的可选方法并继续；必需项冲突或必需内容超出预算时暂停受影响节点 | 角色组合正反例已测 |
