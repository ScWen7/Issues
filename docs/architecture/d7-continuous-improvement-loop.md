# D7 · 持续改进内循环契约

> 本文定义 AgentPlatform 如何从真实工作中发现问题、形成改进候选、验证、审核发布、实际采用并回收效果。
> 既有对象定义见[核心对象模型](core-object-model.md)，评价与提案状态见[统一生命周期、状态机与事件模型](lifecycle-state-event-model.md)，计量与评价口径见[成本、质量评价与持续改进](04-cost-quality-improvement.md)。
> LoopForge 的 Run Evaluation 与受限建议应用、TeamAI 的独立评分 Run、Benchmark 与自改进流程提供机制参考，见[LoopForge SOP 生命周期研究](../research/loopforge-sop-lifecycle.md#62-run-evaluation)与[TeamAI 流程、版本与评测研究](../research/topic-02/teamai.md)。
> 本文定义产品和架构契约，不决定数据库表、API、模型供应商或部署结构。

## 1. 目标：让真实工作产生可验证的改进

持续改进不是 Agent 每次结束后自动写一份总结，也不是把所有执行轨迹自动训练成 Skill。它是一条有证据、有责任人、有比较基准、有发布门槛、有实际采用反馈的闭环：

**真实工作 → 结果与执行事实 → 评价 / 问题发现 → 改进提案 → 候选变更 → 对照验证 → 审核发布 → 项目 / 工作采用 → 真实效果回收 → 新一轮发现。**

内循环必须同时满足：
1. 改进来自真实工作中的可定位问题或可证明机会；
2. 每项结论能够回到来源 Issue 和可定位证据；涉及 Run、Candidate、Evaluation 或方法采用时，引用实际存在的对象和版本；
3. 改动对象和适用范围明确，不把局部经验直接推广到团队；
4. 候选先验证后发布，发布与采用分开；
5. 后续效果以真实生产工作验证，不能只用生成它的同一评价器自证；
6. 改进失败、效果未知或发生退化时，可以停止推广、回退默认选用并保留历史事实。

## 2. 内循环分成三个层次

| 层次 | 触发与处理 | 结束条件 | 不应做什么 |
|---|---|---|---|
| L1 · 当前工作自修正 | Issue / SOP 发现缺项、失败、阻塞或交付不符合约定；负责人在原授权内修正、补证、返工或请求决定 | 当前 Candidate 满足要求并被消费，或明确阻塞 / 退回 / 取消 | 不因每次失败都建立团队 Improvement Proposal |
| L2 · 单次执行评价 | 对有评价价值的 Run、Candidate、交付或流程实例发起独立 Evaluation；可由显式 SOP 质量门、抽样策略或负责人复盘触发 | 评价有明确结论、证据覆盖和缺项；结果回到原 Issue / SOP 或维护者 | 不把评分直接当验收；不把评价 Run 成本计入生产 Run |
| L3 · 跨工作持续改进 | 重复 Finding、显著返工 / 成本异常、稳定的新做法或系统性缺口进入提案；维护者判断范围并组织候选与 Benchmark | 通过对照、审核、发布、采用和生产观察，形成可复核的效果结论 | 不让单个 Agent 自行修改团队默认 Skill / SOP / 工作流并立即生效 |

三层之间不是必经审批链。L1 可以直接结束；L2 可以只用于观察和诊断；具有跨工作价值且证据足够的问题或 Finding 可以进入 L3。

## 3. 从生产工作取得可信输入

### 3.1 生产事实与评价事实分开

内循环可以读取：
- Issue 的 Work Agreement、授权、工作过程、决定和完成结果；
- Run 的实际 Agent、Runtime、模型 / 工具观察、终态、重试和归属；
- Candidate、Artifact、Evidence、Acceptance Decision 及其版本；
- SOP Execution、Node Activation / Attempt、门禁、返工和人工介入；
- 原生 Usage 与明确来源的 Credits、Token、请求数、费用或其他单位；
- 成员反馈、退回原因、阻塞与接管记录。

每项输入必须保留来源强度和覆盖范围。成员自述、宿主原生回执、确定性测试、独立审查、业务验收和模型评价不能互相冒充。缺少本地 Runtime 用量、工具活动或模型输入观察时保持 unknown，不以估算补成真实事实。

### 3.2 评价触发应有选择

评价可以由三种入口发起：
- **显式门禁**：SOP / 工作约定声明必须对当前候选或节点执行评价，结果决定是否允许后继；
- **策略抽样**：对某类工作按明确采样比例或风险条件评价，避免所有 Run 都承担同样评分成本；
- **人工 / 维护者发起**：在失败、返工、争议或复盘时针对具体对象评价。

策略抽样的对象、比例、周期和资源预算应可审查。高风险工作可提高覆盖；低价值重复工作可降低覆盖。不能因为某个 Agent 自评“质量很好”而免除独立门禁。触发类型、风险分层、预算预留、预算耗尽、重试和防递归按[评价触发与资源预算治理](d11-evaluation-trigger-budget-policy.md)执行。

### 3.3 Evaluation 使用独立执行身份

评价器可以有自己的 Multica Run，引用被评 Run / Candidate，但保留自己的执行身份、输入证据、评价器版本和 Usage。被评 Run 的生产事实不可被评分覆盖；评价失败只表示评价执行失败，证据不足也不等于被评工作失败。

TeamAI 的可借鉴机制是：在已结算的生产 pass 之后启动独立评分 Run，评分读取具体 Run / Step / Pass 和当时 Scorer 版本；评分启动失败保留待处理，不改变原执行结论。LoopForge 则使用独立的 Run Evaluation 记录读取原 Run 的事实和轨迹，提供评价及受限建议。两者的具体实现见[上游机制取证](../research/d7-continuous-improvement-evidence.md)。AgentPlatform 沿现有 Run 链承载评价执行，不新增评价专用 Runtime 或第二套任务系统。

## 4. Evaluation 如何形成可行动的 Finding

Evaluation 不只输出一个总分。每条 Finding 至少包括：
- 被评对象和固定版本（Run、Candidate、SOP、资产或配置）；
- 发现的问题、严重度、发生位置和适用范围；
- 支持结论的 Evidence / Trace / 测试 / 业务反馈；
- 根因假设及置信度，明确区分事实与推断；
- 影响：返工、失败、成本、人工介入、延迟、风险或覆盖缺口；
- 建议的下一步和建议修改对象；
- 是否可能跨工作复用，以及还缺什么证据。

Finding 应归类到可治理的原因，而不是直接归咎于模型：
- 输入或上下文缺失 / 过期；
- Work Agreement 或验收标准不清；
- SOP 依赖、分支、门禁或返工预算不合理；
- Skill / Role / Rule / Playbook 冲突或缺失；
- 工具能力、权限、Runtime 或环境问题；
- 模型 / 路由 / 参数选择不适合；
- 验证器、评价器或计量采集本身错误；
- 外部依赖、数据或人为决定；
- 原因未知或证据不足。

一个 Finding 可以由多份评价或多次工作共同支持；相同现象不代表相同根因。维护者需要合并重复提案时保留每个源 Issue / Run 和样本引用。

## 5. 从 Finding 到 Improvement Proposal

### 5.1 进入跨工作改进的条件

以下情况可以提出 L3 改进：
- 同一类问题在多个独立 Issue / Run 中重复出现；
- 单次问题虽只出现一次，但影响严重且可复现；
- 有对照证据证明某个方法、工具或流程变更可能改善结果；
- 现有流程存在系统性缺口，导致无法观察、无法恢复或无法验收；
- 成本明显增加且可以区分工作量变化与单位工作效率退化。

不能仅凭一个模型评价分数偏低、单次主观感受或单一失败日志自动推广修改。提案必须由维护者确认其跨工作价值、适用范围和风险。

### 5.2 提案必须固定什么

Improvement Proposal 至少引用：
- 来源 Issue 和支持问题的可定位证据；涉及 Finding、Run、Candidate、Evaluation 或 Evidence 记录时，引用相应对象及版本；
- 根因假设、置信度与尚未验证的部分；
- 拟修改的资产或配置及当前基线版本；
- 预期改善的目标和可能退化；
- 适用团队 / 项目 / 工作类型及不适用范围；
- Benchmark 样本、评价器、成功标准和资源预算；
- 来源授权、数据共享范围和审核责任人。

人工工作中的问题或交付前的启动故障，可以依据原 Issue 的成员记录、决定、失败回执或其他可定位事实提出改进，无需先形成 Run、Candidate 或独立 Evaluation。缺少的观察与归因证据在提案中列明，再由维护者决定是否补充评价。

提案可以包含多个变更，但每个变更要有明确对象和发布路径。重复提交同一候选沿用原提案；内容修改形成新候选修订，并绑定新的实验结果。

## 6. 候选改进与验证

### 6.1 先判断修改对象

| 改进对象 | 例子 | 生效路径 |
|---|---|---|
| Knowledge | 项目资料索引、团队经验、来源说明、过期规则 | 固定来源与权限，验证检索问题、正确性和实际投递，再由知识维护者发布 / 更新 |
| Capability | Role、Skill、Rule、Principles、Playbook、Harness、工具配置 | 固定内容和依赖版本，验证角色职责、权限、工具调用和产物，再由资产维护者发布 |
| Process | SOP 节点、依赖、门禁、返工策略、Project Workflow、分工 | 用历史样本和受控实验验证交接、并行、拒绝、超时、恢复和验收；SOP 由资产维护者发布，项目配置由有权成员采用 |
| Runtime / Adapter | 宿主协议解析、Observation、Usage 归属、能力映射 | 用真实宿主版本、请求身份、回执和重复 / 缺失场景验证，按执行集成的变更流程发布 |
| Evaluation / Measurement | Scorer、Rubric、采样策略、计量口径 | 先用固定样本校准评价器和计量，再独立发布版本；不能通过降低标准制造“改善” |

一个提案可以涉及多种对象，但它们的发布者和生效边界不同。不能因为一个 Benchmark 通过，就自动同时修改团队 Skill、SOP、Runtime 配置和项目工作流。

### 6.2 改进候选修订与交付 Candidate 的区别

本专题中的“改进候选”是 Improvement Proposal 内固定的一份待验证变更修订，包含变更对象、基线、依赖和内容摘要。它不是 D6 的交付 Candidate：交付 Candidate 固定某项 Issue 的 Artifact 送审组合；改进候选修订固定拟发布的方法、能力、知识或流程变更。两者分别由交付验收与改进提案治理，不建立一个跨领域通用 Candidate 对象。

### 6.3 候选与基线隔离

候选变更必须固定实物版本、依赖、适用配置和实验范围。实验不能直接覆盖团队默认资产，也不能污染在途生产 Issue：
- 团队通用资产的候选在隔离副本或专用实验范围验证；
- 项目配置实验限定项目和明确样本；
- SOP 候选固定 Definition 及子流程版本；
- Runtime / Adapter 候选固定宿主、Backend 和协议版本；
- 评价器候选固定 Rubric、模型 / 参数、工具和输入样本。

历史 Run 继续引用当时实际使用的版本。新候选通过不意味着历史执行自动升级到新版本。

### 6.4 Benchmark 必须证明可比

对照前固定：
- 任务输入、代码 / 文件基准和上下文版本；
- Work Agreement、SOP / Skill / Rule 及依赖版本；
- 样本集及其摘要、代表性和已知偏差；
- 评价器 / Rubric、权重、聚合方式和重复次数；
- 实验变量与需要固定的其他条件；
- 质量目标、成本目标、允许退化阈值和成功标准；
- Runtime、模型、工具链、effort、权限和执行环境差异；
- 计量覆盖和未知费用范围。

如果模型、Runtime 或工具链无法保持一致，必须记录差异并判断是否仍可比较。只有相同实验定义和可比覆盖范围的样本才可以支持“改善”结论。

### 6.5 不以单一指标优化

Benchmark 至少从适用维度评估：
- 目标达成 / 任务成功；
- 确定性测试和交付完整性；
- Finding 数量与严重度；
- 返工、重试、阻塞和人工介入；
- 执行耗时、等待和恢复表现；
- 工具调用和可观察的资源消耗；
- Token、Credits、请求数、原生费用及其覆盖；
- 权限、隐私、安全和越权风险；
- 评价器自身的稳定性与证据充分性。

成本下降不能抵消质量、安全或完成条件退化。成本比较只在原生单位、任务难度、输入范围和覆盖足够可比时成立；未知用量不纳入“更便宜”的证明。质量提升也不能靠降低 Rubric、减少检查范围或丢弃失败样本实现。

### 6.6 回归样本从失败中增长

每个已确认且具有代表性的失败，应评估是否进入回归集。新增样本需固定：
- 原始输入与必要上下文；
- 失败时的资产 / 配置版本；
- 期望行为和可判定标准；
- 原始失败证据与复现步骤；
- 是否已被其他样本覆盖，及覆盖关系。

Benchmark 同时保留针对性失败样本和其他代表性工作，避免只对提案自己的样本过拟合。样本、Rubric 或候选变更后，旧通过记录仍指向旧实验定义；必要时重跑受影响范围。

## 7. 审核、发布、采用和回退

### 7.1 发布不是自动采用

候选验证达到预先声明的成功标准后，进入有权维护者审核。审核核对：
- 候选实物、依赖和版本；
- Benchmark 样本与证据是否充分、是否可比；
- 质量和成本是否满足阈值，有无不可接受退化；
- 权限、来源授权、兼容和适用范围；
- 发布说明、回滚目标和后续观察要求。

审核通过后发布不可变 Release。Project Adoption 是另一项有权决定：项目可以将版本设为默认，负责人也可在具体 Issue 选择获准版本。新工作记录实际选择版本；在途工作继续使用已固定版本，除非有权负责人显式决定迁移并安排重验。

### 7.2 不同对象按不同方式生效

- Knowledge / Capability / SOP：由资产维护者发布不可变版本，再由项目或具体工作采用。
- Project Workflow / 分工配置：由有权成员在原项目配置或 Issue 决定中明确范围、生效时间和在途工作处理，不通过资产 Release 冒充。
- Runtime / Adapter：由执行集成维护者发布适配版本，明确支持的宿主版本和回执覆盖；项目 / Runtime 绑定按授权选择。
- Evaluation / Measurement：新版本只影响后续评价或明确重评任务，不重写历史评分和计量结论。

### 7.3 发布后观察与回退

发布记录引用候选、Benchmark、审核人、适用范围、默认 / 可选状态和回滚目标。后续生产工作记录实际使用的 Release / 配置版本。按同类工作观察质量、返工、人工介入、耗时、恢复和原生计量；区分离线 Benchmark 结果与真实生产结果。

出现明显退化、越权、错误归因或样本不具代表性时：
- 暂停继续扩大采用；
- 将项目默认指回先前获准版本，或将候选标记为 Deprecated / Withdrawn；
- 在途工作按各自固定版本和安全影响决定继续、迁移或停止；
- 保留已发生 Run、Evidence、Decision 和采用记录；
- 形成新的 Finding / Proposal，不能通过覆盖历史版本“抹掉”问题。

## 8. 成本与质量如何共同驱动改进

成本是改进证据，不是唯一目标函数。

- 生产 Usage 归属实际生产 Run；失败、取消和返工的真实消耗都保留。
- Evaluation、Benchmark、知识整理和改进执行有自己的 Run 与 Usage，不混入生产成本。
- Provider / Model 原生单位分别统计；Token、Credits、请求数和 USD 不在缺乏依据时互相换算。
- Runtime 未上报的用量保持 unknown；不得按耗时、模型名称、订阅计划或估算价格伪装成真实费用。
- 同一执行的多源观察先按原生计量身份去重，再归集；父 Issue、子 Issue、SOP 和项目视图按底层唯一计量单元并集汇总。
- 比较候选时同时报告计量覆盖；若候选 A 上报完整而候选 B 大量 unknown，不能得出 B 更便宜的结论。
- 成本优化必须满足质量、安全和交付完整性的硬门槛。任何质量退化超过预设阈值，即使成本下降也不能发布为改善。

## 9. 持续改进闭环的职责归属

| 环节 | 责任主体 | 决定权 |
|---|---|---|
| 生产与提交结果 | 当前 Issue 负责人、Main Bot、Worker、成员 | 在各自授权内执行和交付 |
| 当前问题修正 | Issue 当前负责人或受托 SOP | 在 Work Agreement / 返工预算内处理 |
| 单次评价 | 获准 Scorer / Reviewer / 评价 Run | 提供评价结论，不自动验收或发布 |
| Finding 归并与提案分诊 | 对应资产维护者或项目维护者 | 决定是否形成跨工作提案、范围与优先级 |
| 候选和 Benchmark | 提案负责人及实验执行者 | 按固定实验定义产出证据 |
| 资产审核与 Release | 对应资产维护者 / 有权审核人 | 决定发布哪个不可变版本及适用范围 |
| Project Adoption | 有权项目成员；具体 Issue 由其负责人按授权选择 | 决定项目默认或本项采用版本 |
| 效果回收 | 评价与度量能力，维护者复核 | 判断效果是否成立、是否扩大 / 暂停 / 回退 |

Agent 可以分析、归纳、提出候选和执行获准的 Benchmark；不能自行批准自己的提案、修改团队默认资产并立即推广，也不能用自己的评分代替独立审核。

## 10. D7 完成标准

D7 的架构设计收敛须满足：
1. L1 当前工作修正、L2 单次评价、L3 跨工作改进有清晰边界；
2. 生产 Run、Evaluation Run、Benchmark Run 和改进 Run 的身份与成本分开；
3. Finding 能定位来源事实、根因假设和证据强度；
4. Proposal 固定变更对象、基线、适用范围、样本和成功标准；
5. Benchmark 有可比基准、回归样本和多维质量 / 成本门槛；
6. 发布、项目采用和具体工作实际使用是三个独立事实；
7. 发布后能观察真实生产效果，样本不足时保持待观察；
8. 退化时可暂停默认采用或回退，不抹去历史执行；
9. 任何自动化建议都不能绕过权限、审核和业务验收；
10. 全链路沿现有 Issue、Run、Candidate、Evidence、Evaluation、Improvement Proposal、Release 和 Project Adoption 对象协作，不另建平行执行控制面。

## 11. 后续技术设计前置

仍需单独验证：
- 各宿主实际可提供的 Usage / Trace / Tool Activity 覆盖及其身份映射；
- 评价策略在真实团队运行中的比例校准、资源预算和停止阈值；
- Evaluation 输入快照、评价器版本和结果回写的幂等边界；
- Finding 去重、归因置信度与来源撤回；
- Benchmark 样本权限、可复现环境、可比性和污染隔离；
- Release / Project Adoption / 在途工作固定版本的权限与回滚边界；
- 真实生产效果的观察窗口、样本量和停止推广阈值。

这些是后续实现和验证任务，不构成新增领域对象或第二套 Run 系统的理由。
