# 统一工作台的职责与信息来源

工作台对跨层契约的呈现遵循[跨层业务契约与协作协议](cross-layer-contracts.md)，对象状态遵循[统一生命周期、状态机与事件模型](lifecycle-state-event-model.md)。工作台读取权威对象的并发写入结果、未完成动作、冲突和恢复状态时，遵循[核心协作一致性与并发控制模型](core-consistency-concurrency.md)，不把投影当作权威写入。

工作台让成员从项目、待办或本地工具进入同一项工作。项目负责人能找到什么事在等谁，当前负责人能分工和交付，接手者能取得可以继续使用的材料。各入口引用同一个 Issue、实际执行和交付版本。更改责任、授权资源或接受结果时，由管理该事实的原有入口校验并记录决定。[架构总览](overview.md)

## 事实来源与操作归属

| 成员要判断什么 | 工作台从哪里读 | 哪个动作在哪里生效 |
|---|---|---|
| 项目中哪件事轮到谁 | 项目 Issue 列表、当前负责人、项目状态、有效的等待原因；Inbox 记录指派、提及和待处理问题 | 调序使用项目权限；改派、评论协助和独立分工在原 Issue 或子 Issue 上办理。打开通知定位原问题，已读只改变收件记录。 |
| 当前要按什么要求交付 | Issue 的目标、适用约定、父项决定、当前候选及所需检查 | 有权成员在 Issue 确认范围、决定或交接。项目工作流沿原状态与指派入口移交当前工作。 |
| 某段工作由谁安排、是否已启动 | Issue 上记录的分工、Main Bot 的具体委派、SOP 实例中就绪和等待的节点、对应 Run 的领取、开始与结果 | 负责人在 Issue 组织自主工作或授权 SOP。受托的 Agent 或脚本节点经 Multica 原派发入口开工。人工节点回到原 Issue 等待决定。资源所有者在 Runtime 维护共享权限。 |
| 成员与 Agent 可以使用哪些方法和资料 | 项目配置、已发布的能力版本、来源修订、读权及宿主实际取得的材料 | 能力在所属团队或项目发布和采用；外部正文由来源维护者修订。需要组织长期资料时，可接入[团队 Wiki 与项目资料](team-project-wiki.md)或[项目代码 Wiki](code-wiki.md)。 |
| 一次执行交出了什么 | Issue 中成员署名提交的材料、原 Run 回报、制品版本、检查覆盖和缺项 | 成员提交具体版本；流程只在受托范围消费结果。正式接受由 Issue 的完成约定确定。 |
| 哪些方法值得改进 | 评价关联的执行与交付、可复核的发现、候选方法、对照结果和实际用量 | 维护者在相应范围审核并发布方法，项目决定采用。后续工作回报实际使用与结果。 |

私有项目交给成员时，以接收者能打开原 Issue 为交接条件。工作交给 Agent 后，工作台分别呈现实际发生的指派、排队与开工。若指派已生效但机器授权不足，原 Issue 显示执行受阻，有权成员可处理共享、重绑或改派；仅离线且已经排队时，显示等待当前机器上线。提示使用当前查看者有权看到的信息。[责任交接](01-unified-work-lifecycle.md#62-状态推进与负责人交接) · [原生入口与用例](../research/05-source-evidence.md#项目访问与执行资格)

## 交付与接手

平台派发从原 Issue 关联实际 Run。本地进行中的工作，在能识别下一段执行的宿主入口关联到 Issue；成员在本机确认目标与共享范围。事后交付可以直接使用原评论、附件或已授权的仓库引用。可共享的材料与成员自己的说明分别选择，至少有一项被选中时方可提交。成员亲自交回的说明保留署名和时间，能核对宿主来源的材料另附对应记录。[执行入口及证据范围](03a-execution-plane.md) · [宿主能力矩阵](execution-capabilities.md)

接手者从原 Issue 取得已交付版本、实际代码基准、可用检查和提交者已说明的缺项。评论上传的同名同类型文件沿用 Multica 交付区的版本归集，引用检查或决定时固定所选附件 ID；仓库交付固定到对应修订。成员可浏览最新文件，过去的决定仍指向当时使用的版本。接收者以自己的权限打开附件副本或外部来源，取得基准后在自己的工作副本继续。尚留在原机的内容，由能取得它的成员补交；已共享的材料可以先用于不依赖该内容的工作。[原生交付区与执行记录](../research/05-source-evidence.md#做决定看结果与处理异常)

交付需要验收时，工作台显示这次送审的材料组合及适用标准。打开旧通知或旧决定时可查看当时的组合，并定位当前待处理版本。验收人在查看期间遇到换版，提交时会看到哪些材料已改动，再对当下的版本决定。普通附件已删除或来源读权被收回时，历史决定保留原引用，读取结果标为缺失或无权访问。接手者能据此请生产方补交或恢复授权。[候选与验收竞争](core-consistency-concurrency.md#63-candidate-与验收竞争)

请同事帮助检查时，在交付评论中提及接收者。移交整项工作时，由有权成员修改原 Issue 的指派。通过通知返回时，重新读取当前负责人、交付版本和权限。候选或安排已变更时，保留旧通知的来源并定位当前待处理项。[原生指派与协助](../research/05-source-evidence.md#指派评论协助与交接) · [工作责任与完成条件](01-unified-work-lifecycle.md)

## 等待、决定与完成

工作台按已有证据指出被影响的工作和下一处理人。只有排队回执时显示「已排队」。收到目录等待回执时显示「等待本地目录」，在查看者有权且可定位时链接占用的 Run。正常释放后系统自行接续，有权成员也可取消等待的 Run。若执行缺少机器授权，由资源所有者处理共享；依赖交付未齐时，可追到生产结果的子项；存在业务取舍时，指向原 Issue 上有权决定的成员。其他已就绪的分工按原授权继续。换人协调沿该 Issue 改派，改绑 Agent 的 Runtime 则需核对该 Agent 跨 Issue 的在途与排队工作。[工作生命周期](01-unified-work-lifecycle.md) · [Multica 原生行为](../research/05-source-evidence.md)

提交给人决定的问题应标明候选、标准、所需动作和生效范围。流程交回检查结果后，项目工作流可以先把待验收事项交给指定成员。执行者可以补材料，检查者可以报告失败或缺项；有权验收的成员随后接受当前候选或将具体要求退回修正。成功完成入口校验适用于本项的决定。普通事项按项目既定的检查和完成约定收尾。状态或人员发生变化时，依据原 Issue 的当前事实重新判断操作资格。[流程结果与交还](02-sop-workflow.md) · [Issue 完成约定](01-unified-work-lifecycle.md)

## 方法怎样进入下一项工作

当发现值得复用时，从原交付和评价引用证据，提交适用范围内的修订。维护者查看候选对照、回归结果和来源许可，再按职责发布。项目维护者采用适用版本；工作负责人能查看本项采用的方法、正式完成要求以及为该次执行取得的实际使用回执。改进后的结果回到采用该版本的工作记录。[能力选用与发布](03b-capability-governance.md) · [评价、改进与采用](04-cost-quality-improvement.md)

工作台按原生单位和供应商展示用量，同时保留实际覆盖范围、缺报和明确为零的观测。查看改进效果时，业务执行、事后评价与比较实验的消耗分别归集。评价结论、某次交付被接受、某个方法已发布和已实际采用，各自追到产生该事实的对象与版本。[成本与质量口径](04-cost-quality-improvement.md)
