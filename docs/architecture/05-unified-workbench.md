# 专题五 · 统一工作台的信息架构与关键交互

协作主线产品设计 · 2026-11-15 · 依据 Multica 融合架构 V1.1

研发成员可以在工作台接下一项工作，也可以把自己在本机做出的结果交给同事。项目负责人从项目列表看哪件事需要调序或换人，接手者在原 Issue 看目标、决定和交付。有明确检查、验收或复用要求时，在这项工作的相应位置处理。

以下给出首期工作路径和十二类工作在现有入口中的位置。文案修改与跨成员订单分别说明简单和复杂交付。产品需求沿用[设计输入](../../Team%20Agent%20Collaboration%20Platform.md#专题五统一工作台产品设计)。[原生路径与源码依据](../research/05-source-evidence.md)、[三组场景走查](../research/topic-05/workbench-walkthrough.md)和[可交互的低保真原型](../../prototypes/topic-05/workbench.html)供评审。下载 HTML 后可在浏览器离线打开，角色、操作与后续补证均为演练数据。

## 一、入口与工作位置

### 从哪里开工，怎样把结果交给同事

| 成员正在做什么 | 成员怎样交给团队 | 接手的人能取得什么 |
|---|---|---|
| 从平台接工作 | 从项目或 Inbox 打开 Issue，可以自己做、在评论请 Agent 协助，也可以改派。指派引起的受管执行在对应 Run 回报 | 从原 Issue 看当前负责人、讨论、变更和交付。需要独立承担一份交付时再进入子 Issue。 |
| 在本地 CLI 或 IDE 中已经开工 | 在支持关联的入口选定 Issue，从下一个可识别的执行段起关联。在本机预览拟共享的消息、工具结果或文件，确认范围后提交。其他段落保留在原会话 | 在对应 Issue 读到获准共享的部分。有原生身份可核对时关联已有 Run。同事按 Issue 和来源权限读取已共享的内容。接管本机会话需另有宿主授权。 |
| 已经做完一段调查或修改 | 在已有 Issue 提交说明、链接、补丁或报告。需要团队接着推进新事项时可建 Issue。宿主只支持手工提交时，直接用原评论与附件交付 | 看到谁在何时提交了什么，能点回的证据附上来源。只有成员说明时按署名说明呈现。同一执行被再次引用时保留原归属。 |

本机自动关联和共享选区是产品设计，具体可用程度随宿主和入口而异。成员选取哪些内容交给团队，与当次模型可读取哪些会话历史分别授权。独立 CLI / IDE 仅提供部分事件时，按该入口实际取得的记录展示。[三种工作入口的证据与边界](execution-capabilities.md#一个执行怎样进-issue怎么停)

### 协作中的工作位置

| 从哪里进入 | 人来这里做什么 | 首先看到什么 | 动作回到哪里 |
|---|---|---|---|
| 项目工作列表 | 项目负责人排优先级，成员找到轮到自己的事 | 沿用现有项目 Issue 列表和视图。行内给出标题、当前负责人、项目状态；有可靠依据时补充具体等待原因及下一处理人 | 改优先级沿原项目权限；点工作行进入同一 Issue。控制台仅知道排队时，显示已知队列状态及最近回报 |
| Issue 详情 | 当前负责人组织工作，旁观成员看结果，验收人决定接受或退回 | 当前工作约定、当前候选、负责人、待处理问题；关键失败或缺项就近显示。随后是分工、交付与讨论；执行明细按需展开 | 分工、交接、评论、验收决定和成果都指回本 Issue 或对应子 Issue。业务状态由现有写入入口维护 |
| 我的工作与 Inbox | 找到指派给我的工作、提及或待我决定的问题 | 现有通知入口保留上下文；对待决问题显示具体对象、需要作何决定、我为何能处理 | 打开通知定位原问题，已读只更新收件状态。提交决定时重新读取原 Issue 的权限、候选、标准和轮次 |
| 人员、Squad 与 Runtime | 成员配置身份、工作角色和机器共享；负责人定位资源问题 | 按原有对象查看成员、队伍、设备与可见状态；从受影响的 Issue 可追到获准查看的资源 | 调整共享由有权资源所有者操作；接管某项工作由该 Issue 上有权的成员决定，两种操作分别记录 |
| 团队 Wiki 与项目资料 | 成员按主题找当前适用的口径，作者撰写或订正资料 | 目录、适用范围、来源、维护者、当前有效性 | 平台自有页面在原页修订，外部正文回原来源更新。工作可引用选定章节。[产品设计](team-project-wiki.md) |
| 项目代码 Wiki | 新成员了解架构，开发或核验成员追踪某版本的实现 | 项目与基准、模块、关键流程、代码锚点 | 沿说明核对代码、反馈解释错误或引用片段，必要时回到原 Issue。[产品设计](code-wiki.md) |
| 团队能力与流程 | 维护者配置可复用能力，实施者核对所用方法 | 适用项目、选用版本、角色、工作流和核验条件 | 正式能力与 SOP 由有权维护者发布，Issue 或 Run 记录实际采用的版本 |
| 项目分析及改进 | 查一个失败反复发生的原因，确定哪项改动值得采用 | 从交付可追到 Findings、原执行和明细用量；跨工作查看可比样本、候选及回归结果 | 评价保留版本和证据。资产发布、项目工作流配置采用、Issue 业务接受分别回到相应有权主体 |

指派使用原 Issue 的负责人选择器。请人或 Agent 协助使用原评论、提及与回复，并沿用触发预览。按项目流程转交时使用原交接预览。收件箱可把成员带回对应 Issue，“待我决定”只需筛出仍有效且由该成员决定的问题。Run 完成提醒按实际采用的上游版本呈现。[Multica 的指派、协助与交接](../research/05-source-evidence.md#指派评论协助与交接)

接管、改版或候选更新后，旧通知保留原发生事实，打开时提示当时问题已变化并定位当前对象。[原生收件箱与工作路径](../research/05-source-evidence.md)

## 二、订单 Issue 的关键交互

| 时刻 | 形成决定所需的最少信息 | 人能做什么，结果写在哪里 |
|---|---|---|
| 林创建父 Issue | 目标、所属项目、当前负责人，以及需林决定的业务问题。人、Agent 和 Squad 都可担任当前负责人 | 林选择 Squad 并允许分析；Leader 在自己的已授权 Runtime 启动协调。分工出现后再展开前端、后端、集成、验证子项 |
| 林确认工作约定 D2 | 导出范围、区域权限和文件基准沿用，新增付款时间、未付款留空及指定时区；列出受影响工作 | 在父 Issue 保存有来源的业务决定；让相应子项和执行引用新约定。接收者能分别看到材料已投递和当轮实际输入的证据 |
| 丙核验 C1 | 东区文件混入西区订单 B-201。A2 区域权限失败，A3 内容检查通过。即使脚本正常退出，交付仍需返工 | 展开原报告、候选及具名工作簿。Leader 协调后端修复，原集成和验证子项等待新输入，无关前端结果继续可用 |
| C2 在同一 D2 下复验 | 东区样例仅有 A-101、A-102。C2 的 A2、A3 有通过回执。可按标准逐项看候选、核验主体、方法、制品及未覆盖要求 | 先展示原回执能支持的两项。由交付 Squad 的 Leader 安排 A1 范围、A4 数量、A5 交互及 A6 交付材料，丙协调独立复核，林在具备获准 UAT 条件后作出业务判断；C1 负例保留供比较 |
| 证据具备，交回林验收 | 当前候选 C2、D2、A1–A6 的候选绑定及授权环境，当前负责人、指定验收人和决定范围 | 演练中显式切换到补齐材料的情形。林核对 UAT 与候选一致后可以接受。若林退回，须指出有异议的要求；对应检查随即显示退回原因，原验收材料保留。受理时再次核对决定资格与版本。重复提交返回同一决定，旧候选的操作返回原历史与当前待办 |
| 验收后的质量与改进 | 当前交付的接受记录、先前失败 C1、后继修复和实际分单位用量 | 从失败证据提出“按区域核对导出范围”的候选改进。在实验范围固定输入与候选，对照通过后由有权维护者审核发布；后续 Issue 的实际效果另行观察 |

实际订单报告使用合成订单和固定工作簿，可从[场景走查](../research/topic-05/workbench-walkthrough.md)定位。A1–A6 完整交付和林的接受是专题一案例的后续设计分支；原型单独标识补充的演练证据。

**决定的交互。** 普通回复保留为评论。需要正式批准时，界面给出问题、候选、标准及按钮的具体后果。看证据、补充说明、放行某个 SOP 节点、接受整个 Issue 各有明确作用范围。候选过期时允许查看原材料；若当前用户无源读权，只显示其获准查看的关联与缺项。前端的按钮状态提供解释，对于约定人工验收的 Issue，每个完成入口都须核对指定成员对当前候选与标准的有效决定。[专题一的验收规则](01-unified-work-lifecycle.md) · [专题二的结果消费](02-sop-workflow.md)

**交付的定位。** Multica 的交付区已将评论中同名且同类型的上传归集为多个版本，并可按附件 ID 选择相应版本。成员找最新文件或查看旧稿，沿用这个入口。约定具名验收时，在决定中引用当时的候选、标准和具体附件，有来源 Run 时一并引用。C2 到达后，C1 的失败记录仍指向当时检查的文件。材料因权限或删除无法取得时标出缺项。[原生交付区与 Runs](../research/05-source-evidence.md#做决定看结果与处理异常)

## 三、十二类用户工作如何承接

下表记录已走查的场景和只确定了入口的工作。后续细化范围取决于成员在实际协作中需要做哪些判断。

| 原输入的工作 | 首要入口与关键动作 | 本轮深度 |
|---|---|---|
| 1 项目、Issue 与工作分解 | 项目列表进入父 Issue；按独立责任与交付建子 Issue，短协作留在原 Issue，节点尝试通过 SOP 查看 | 订单与轻量工作走查 |
| 2 Human / Agent / Squad 负责人 | 创建或交接时选择当前负责人，可按工作约定标明总责人或指定验收人。Squad 主责时由 Leader 协调，被提及的其他 Squad 可协助 | 订单分工、交还与验收走查 |
| 3 Squad 协作与任务树 | 父 Issue 先看负责人、必需结果与异常，再按需要展开子项。由哪个 Run 完成工作可从子项追溯 | 并行分工、定向返工走查 |
| 4 共享会话与上下文 | Issue 讨论与已确认决定联动。成员从本机会话选择分享范围；继续原会话时重新核对历史授权 | 已设计关联、预览、选择共享范围和手工补交；可自动取得的内容按宿主入口区分 |
| 5 本地资源管理 | 从资源等待原因跳至获准查看的 Runtime；所有者可管理共享，Issue 负责人可在现有授权内安排接续 | 双 Issue 与 Leader 离线走查 |
| 6 人工介入、审批、接管 | Inbox 或 Issue 定位当前问题。显示当前资格、待处理人、例外范围和接管对在途执行的影响 | 候选验收、退回和接管走查 |
| 7 SOP 设计与执行 | 设计入口维护定义、必需前置、门禁与输出并发布；Issue 调用固定版本，从本轮运行定位失败节点、重验与结果 | 运行和结果走查，完整编辑与版本差异待细化 |
| 8 团队能力管理 | 从原有 Agent / Skill 查看适用项目和已配置版本；有不变版本要求时，从节点查本次选择、实际投递和回执 | 选版与投递有入口，跨项目覆盖及发布交互待细化 |
| 9 项目知识管理 | 通过团队 Wiki 查业务口径和原文，通过项目代码 Wiki 阅读实现、比较基准及定位代码。两者均可独立进入，Issue 按需引用 | 两份可选扩展草案已形成，启用时分别验证真实资料与多仓代码的阅读、维护和引用 |
| 10 执行与交付追溯 | 在 Issue 内从候选打开原报告、制品版本及执行。明确直属/子树范围、核验者和实际使用标准 | C1/C2 与旧证据走查 |
| 11 成本与质量分析 | Issue 看交付质量、已知用量和覆盖，项目看分项及趋势。执行、评价和 Benchmark 按实际 Run 去重，Credits 按供应商分列 | 原生显示函数与独立探针回放；订单成本保持未知 |
| 12 评测与持续改进 | 从 Findings 定位证据、受影响资产和候选；比较基线与候选、审核实际采用组合，再追后续工作的结果 | 端到端关系已映射，评审与发布工作区待细化 |

SOP 设计视图与运行视图分别面向模板维护者和现场负责人。LoopForge 的人工节点界面已能给出待确认问题、相关 Findings、通过后去向及定向返工动作；本设计采用这些交互信息，将决定绑定到 Multica Issue 上的有效候选。[LoopForge 人工节点](https://github.com/Tencent/LoopForge/blob/97b3cdc2f29a88e8767a8dc6c03bfb8865622653/web/app/approvals.js#L17-L87)

改进评审应让维护者知道哪些样本可以比较、哪些被排除以及排除原因。TeamAI 的配对与报告机制可供复用。团队经验按源证据和受众核对授权，将经验提升为验收规则时，还要明确其对当前 Issue 工作约定的影响。[TeamAI 对照配对](https://github.com/Tencent/teamai-cli/blob/556b5246f2c13ad28b8b79b5b513a78ed8ab9dae/src/benchmark/pairing.ts#L20-L96) · [资产治理](03b-capability-governance.md) · [专题四的候选验证](04-cost-quality-improvement.md)

### 方法怎样进入下一项工作

订单交付曾发现区域数据越界。若团队希望退款导出也检查这个问题，项目成员可以从原失败报告提出一条可复用的方法，写清适用条件，跨项目分享时只提供获准共享的内容。经验适合写成说明时，按来源许可和知识审核路径发布。需要变成可执行检查时，再以候选 Skill 或 SOP 与当前版本作对照，由有权维护者审核并发布适用范围与版本。[经验贡献](03b-capability-governance.md#从项目证据到团队经验) · [候选对照与发布](04-cost-quality-improvement.md#54-benchmark-对照)

退款 Issue 的负责人从该项目已配置的能力中选择适用版本，并向本项目业务负责人确认权限口径。实施者在原 Issue 交回本次结果，并引用能从 Run 核对的版本和调用记录。维护者之后能区分这项方法已发布、已被选用、已产生实际结果三个时点。是否减少返工取决于后续可比工作的结果。项目仅需调整负责人或步骤时，有权成员直接在原项目工作流中采用该项调整。[工作中的选用与投递](03b-capability-governance.md#5-一次工作如何选择和投递能力) · [发布后观察](04-cost-quality-improvement.md#55-发布后观察)

## 四、轻量完成、并行等待与接管

**轻量完成。** 对“把导出按钮改为批量导出”，Issue 直接显示目标位置、约定文案和检查实际显示的方法。成员亲自修改时，可在同一 Issue 提交变更和显示结果。项目已允许按该检查完成、本次未另约人工验收时，有完成权的成员即可结束该项。交给 Agent 时，显示其 Run 交回的变更和检查结果。若本次约定由成员查看后接受，结果交到该成员的待办。既有原型的两次业务提交对应这一种安排。发现改动还涉及导出权限时，由当前负责人在原 Issue 指出新增范围，待有权成员决定后按新约定继续。[专题一的轻量路径](01-unified-work-lifecycle.md#125-最小路径修改导出按钮文案)

**项目中谁在等谁。** 订单与另一项调查同时进行时，成员从项目列表可直接进入需要动作的原记录。

| 项目列表上看到什么 | 谁可以采取什么动作 | 什么时候可以继续 |
|---|---|---|
| 调查已就绪，正在等可用的 Leader Runtime。若只知已排队，标明原因待确认 | 两项工作竞争同一资源时，由项目既有责任人决定先后，具备项目优先级修改权限的成员据此调整 Issue。机器所有者决定是否另行共享资源 | 已开始的工作继续原安排。调查实际开工后，列表从对应 Run 取得开始回报 |
| 订单集成在等后端修复。行内可进入后端子 Issue，查看负责人和缺少的交付 | 后端负责人在子项提交修复。集成负责人核对所收版本。前端已交付部分仍供集成使用 | 修复已交回且具备本轮集成条件后，由集成负责人组织新候选 |
| 订单在等林确认付款时间口径，指向父 Issue 的具体问题 | 林在父项作出决定，当前负责人把它交给受影响的后端与核验子项 | 受影响的工作依新约定继续，其他已就绪子项可照常推进 |

**离线后接手哪一项工作。** 在需要换人的父项或子项使用原生改派。成员打开父项或子项时，先看到当前负责人、最近一次可靠交付、在途执行和仍缺的决定。

- 周提供的 Leader Runtime 离线后，恢复原机可继续使用原队。改绑 Leader Agent 的 Runtime 会一并迁移它在各 Issue 中排队或延后的工作，已由旧机领取的执行仍留在旧机。若由成员接替，则由有权成员在父项将接手者设为当前负责人。接手者查看各子项和剩余交接，使用自己获准的资源继续组织。旧 Leader 恢复后按父项的当前指派行动。其他机器上的前后端子项仍由原负责人推进，订单最终验收仍交林。
- 若只有后端实施者离线，在后端子项明确移交实现工作。接手者先看已交回的变更、能否取得工作副本及旧执行是否还可能写入。确认旧执行已结束或其写入已隔离后再接续。集成负责人收到当前候选的交付后继续。旧机重连时，旧回报仍可从原 Run 查看，父项沿现有协调安排推进。

### 用量展示与工作对象边界

- **用量有覆盖范围。** Multica 的 Issue Runs 视图可以从已有明细按供应商汇总 Credits。服务端 Issue 摘要和每日看板查询有各自的字段边界，本地 CodeBuddy 的 Backend 到 Daemon 仍缺 Credits 通路。仓库单 Stage 的 0.69 来自独立协议探针；本订单没有可归属 Credits。固定版费用函数将未知费率下的 24 个 Token 格式化为 `$0.00`。应显示“24 Token · 费用未知”，并按指标展示覆盖。三个适用 Run 中，显式零、仅 Token、完全缺报各一项时，Credits 的已知小计为零，覆盖 1/3。[展示回放与数据边界](../research/topic-05/codebuddy-display-replay.md)
- **从工作台进入分工。** 成员从父 Issue 打开独立交付的子 Issue。答复问题回到原讨论，查看一次执行打开对应 Run，查看局部流程中的检查步骤打开该次 SOP。[工作对象](overview.md#5-统一工作对象)
