# 专题五 · 统一工作台的信息架构与关键交互

研发成员可以在工作台接下一项工作，也可以把自己在本机做出的结果交给同事。项目负责人从项目列表看哪件事需要调序或换人，接手者在原 Issue 看目标、决定和交付。有明确检查、验收或复用要求时，在这项工作的相应位置处理。

## 一、入口与工作位置

### 首版协作路径：从本地工作到同事接手

甲负责「导出结果缺少末页订单」。乙第二天接着处理，需要找到甲交出的那版补丁，知道从哪个代码版本开始，以及哪部分还得找甲。成员从以下入口开工，交付都留在同一个 Issue。

| 甲从哪里开工 | 怎样把成果交回 | 乙从原 Issue 看到的来源 |
|---|---|---|
| 已在本机完成调查或修改 | 在原评论写出结论、所用代码基准和已做的检查，上传选定补丁，或引用获准共享的提交。任何 CLI 或 IDE 的成员都能走这条路。新的工作目标也可创建 Issue 承接 | 评论有提交人，交付区能打开具体附件版本。甲自行填写的基准及检查按甲的说明展示。有原生执行记录且能核对归属时，附上原记录。 |
| 本机工作进行中 | 在能识别原生执行段的入口选定 Issue，从下一次可识别输入开始关联。提交前，甲在本机确认目标 Issue，预览并勾选这次要分享的材料。其余入口使用上面的评论和附件 | 乙只读到已提交且向自己开放的内容。宿主记录标明实际覆盖的执行段，未共享的聊天仍留在甲的会话。[各宿主开放此入口的条件](03a-execution-plane.md#首版提供进行中关联的条件) |
| 从项目或 Inbox 接工作 | 甲可自行处理，也可在原评论中请有权调用的 Agent 协助。Agent 在获准的 Runtime 上执行并交回结果，甲仍负责这项工作 | 在同一交付区读版本，按需从该次交付打开实际关联的 Run。沿用 Run 已回报的基准、制品或检查，缺项可由甲在评论补充，并保留甲的署名。 |

**乙打开交付时。** 甲已交 `last-page.patch` v1，注明基于 `orders@71c2a90`。甲在交付区选中 v1，界面显示文件名和版本序号，以这次上传的附件 ID 记录引用。若交的是仓库提交，则记录固定的提交修订。成员只需选择版本，编号由平台保存。原交付区的“最新版本”链接用于浏览后来上传的文件。乙打开作为附件上传的补丁，并凭自己的仓库读权取得基准，在自己的工作副本上应用。如果乙缺少仓库读权，在 Issue 内有权读取的附件副本仍可打开，也可以请有权成员提供可用基准。对于只贴了外部链接的材料，乙打开正文时依原来源校验读权。甲再次上传同名同类型补丁后，乙可切换到新版本，原有检查和讨论仍指向 v1。[Multica 交付区与具体版本](../research/05-source-evidence.md#做决定看结果与处理异常)

甲分别选择要交回的文件和要公开的补交说明。只交 v1 时，乙看到补丁、基准及来源。甲可以将其余本地工作保持私密。本例中，甲上传补丁时未附检查记录，受管 Run 交回同一版本时也未附检查报告。沿两条路径接手的人都还需核对导出的末页是否完整。若甲同时留言「本机还有一处修改待补」，乙能看到这项缺口，先处理 v1 已覆盖的部分，依赖余下修改的工作等甲补交。只交说明时，乙能读到甲的留言，补丁由甲随后上传。选区为空时，提交按钮不可用。

**请乙看看，或让乙接手。** 只需乙检查补丁时，甲在交付评论中提及乙，乙回复后由甲继续。需要乙推进整项时，有指派权限的成员在原负责人选择器改派给乙。乙取得 Issue 责任，甲仍可补交手里的修改。两人按本项既定完成约定收尾，只有约定指定成员接受时，才把当前交付及适用标准交给该成员。[指派与评论协助](../research/05-source-evidence.md#指派评论协助与交接) · [Issue 完成条件](01-unified-work-lifecycle.md#62-状态推进与负责人交接)

**首版在 Multica 上怎样落位。** 评论、附件版本、项目仓、指派、提及和已有 Run 使用原生入口。成员能在目标 Issue 发表评论即可交回结论，上传补丁或引用外部材料时按各自权限办理。请 Agent 执行时才需要相应的调用资格与 Runtime。在支持进行中关联的本地入口增加 Issue 选择和共享预览。在原交付区，把选定文件版本与本次注明的基准、已有检查、可核对的来源和已声明的缺项放在一起，各项按读者的权限展示。普通文件仍可直接上传，缺少基准只影响依赖该基准的接续动作。[Multica 底座边界](governance-baseline.md) · [接手场景走查](../research/topic-05/workbench-walkthrough.md#甲交回补丁乙接着处理)

### 协作中的工作位置

| 从哪里进入 | 人来这里做什么 | 首先看到什么 | 动作回到哪里 |
|---|---|---|---|
| 项目工作列表 | 项目负责人排优先级，成员找到轮到自己的事 | 沿用现有项目 Issue 列表和视图。行内给出标题、当前负责人、项目状态；有可靠依据时补充具体等待原因及下一处理人 | 改优先级沿原项目权限；点工作行进入同一 Issue。控制台仅知道排队时，显示已知队列状态及最近回报 |
| Issue 详情 | 当前负责人组织工作，旁观成员看结果，验收人决定接受或退回 | 当前工作约定、当前候选、负责人、待处理问题；关键失败或缺项就近显示。随后是分工、交付与讨论；执行明细按需展开 | 分工、交接、评论、验收决定和成果都指回本 Issue 或对应子 Issue。业务状态由现有写入入口维护 |
| 我的工作与 Inbox | 找到指派给我的工作、提及或待我决定的问题 | 现有通知入口保留上下文；对待决问题显示具体对象、需要作何决定、我为何能处理 | 打开通知定位原问题，已读只更新收件状态。提交决定时重新读取原 Issue 的权限、候选、标准和轮次 |
| 人员、Squad 与 Runtime | 成员配置身份、工作角色和机器共享；负责人定位资源问题 | 按原有对象查看成员、队伍、设备与可见状态；从受影响的 Issue 可追到获准查看的资源 | 调整共享由有权资源所有者操作；接管某项工作由该 Issue 上有权的成员决定，两种操作分别记录 |
| 团队 Wiki 与项目资料 | 成员按主题找当前适用的口径，作者撰写或订正资料 | 目录、适用范围、来源、维护者、当前有效性 | 平台自有页面在原页修订，外部正文回原来源更新。工作可引用选定章节。[产品设计](team-project-wiki.md) |
| 项目代码 Wiki | 新成员了解架构，开发或核验成员追踪某版本的实现 | 项目与基准、模块、关键流程、代码锚点 | 沿说明核对代码、反馈解释错误或引用片段，必要时回到原 Issue。[产品设计](code-wiki.md) |
| 团队能力与流程 | 维护者配置可复用能力，实施者核对所用方法 | 适用项目、选用版本、角色、工作流和核验条件 | 正式能力与 SOP 由有权维护者发布，Issue 或 Run 记录实际采用的版本 |
| 项目分析及改进 | 查一个失败反复发生的原因，确定哪项改动值得采用 | 从交付可追到 Findings、原执行和明细用量；跨工作查看可比样本、候选及回归结果 | 评价保留版本和证据。资产发布、项目工作流配置采用、Issue 业务接受分别回到相应有权主体 |

指派使用原 Issue 的负责人选择器。请人或 Agent 协助使用原评论、提及与回复，并沿用触发预览。按项目流程转交时使用原交接预览。收件箱可把成员带回对应 Issue，“待我决定”只需筛出仍有效且由该成员决定的问题。Run 完成提醒按实际采用的上游版本呈现。[Multica 的指派、协助与交接](../research/05-source-evidence.md#指派评论协助与交接)

接管、改版或候选更新后，旧通知保留原发生事实，打开时提示当时问题已变化并定位当前对象。[原生收件箱与工作路径](../research/05-source-evidence.md)

## 二、订单 Issue 的关键交互

以订单批量导出为例。产品成员林负责范围和整单接受，交付 Squad 组织前后端、集成和核验，核验者丙向交付方提供检查结果。工作台在当前 Issue 里呈现相应动作。

| 谁在处理 | 进入 Issue 时需要看见什么 | 采取动作后谁能继续 |
|---|---|---|
| 林提出工作，随后补充付款时间规则 | 目标、约定、负责人及仍待决定的问题。讨论里能定位林确认的规则与影响范围 | 父项引用已确认的规则。受影响的后端与核验子项使用新口径，其他工作可继续。 |
| 丙发现东区导出含有西区订单 | 对应候选、失败的权限要求、账号范围及实际工作簿。其他检查各自保留结论 | Leader 把修复交给后端。集成负责人等待修复并形成下一版候选，已经交付且未受影响的前端成果继续使用。 |
| 新候选交回，仍有检查缺项 | 已核对的权限与文件内容，仍缺的筛选范围、数量和页面交互等依据，每份材料对应的候选及核验人 | Leader 安排补交，丙汇总核验结果。林可以查看进展，材料齐备后核对验收环境及交付版本。 |
| 林决定接受或退回 | 指定验收人、当前候选及适用标准，接受的范围和退回的去向 | 接受写回父 Issue。退回指出具体要求并交给对应负责人。重复提交关联同一决定，过期候选定位到其历史和当前待处理项。 |

案例中的 C1、C2 是两版候选，D2 是加入付款时间后的业务约定。固定样本只覆盖两项通过结果，完整交付与验收是产品交互示例。[订单样本和原型覆盖](../research/topic-05/workbench-walkthrough.md)

**决定的交互。** 普通回复保留为评论。需要正式批准时，界面给出问题、候选、标准及按钮的具体后果。看证据、补充说明、放行某个 SOP 节点、接受整个 Issue 各有明确作用范围。候选过期时允许查看原材料；若当前用户无源读权，只显示其获准查看的关联与缺项。前端的按钮状态提供解释，对于约定人工验收的 Issue，每个完成入口都须核对指定成员对当前候选与标准的有效决定。[专题一的验收规则](01-unified-work-lifecycle.md) · [专题二的结果消费](02-sop-workflow.md)

**交付的定位。** Multica 的交付区已将评论中同名且同类型的上传归集为多个版本，并可按附件 ID 选择相应版本。成员找最新文件或查看旧稿，沿用这个入口。约定具名验收时，在决定中引用当时的候选、标准和具体附件，有来源 Run 时一并引用。C2 到达后，C1 的失败记录仍指向当时检查的文件。材料因权限或删除无法取得时标出缺项。[原生交付区与 Runs](../research/05-source-evidence.md#做决定看结果与处理异常)

## 三、十二类用户工作如何承接

| 成员要做的事 | 入口与动作 | 处理结果 |
|---|---|---|
| 组织项目工作 | 在项目列表排先后，在 Issue 内分工。独立负责且能单独交付的部分建子 Issue | 各负责人和接收方能沿父项看到交付关系。 |
| 指派或邀请协助 | 在负责人选择器改派，在讨论中提及协作者 | 工作流与显式指派决定主责，协作者的回复和执行留在相应工作下。 |
| 协调 Squad | Leader 在父项展开子项、交付要求和阻碍，可追到子项对应的 Run | 负责人能定位哪份交付等待修正以及谁能继续。 |
| 共享讨论或本地成果 | 从本机会话预览并提交选定内容，或用原评论和附件手工交回 | 同事按权限看见所交范围及来源。 |
| 管理本地资源 | 从等待中的工作进入获准查看的 Runtime。资源所有者调整共享，Issue 负责人组织接续 | 能分别看清机器的可用性和工作的当前负责人。 |
| 介入、决定或接管 | 从 Inbox 或 Issue 定位具体问题，确认决定对象、当前候选和在途执行 | 正式决定回到相关 Issue。接力执行按接手者获得的授权开始。 |
| 维护或调用 SOP | 维护者定义步骤、前置、门禁与输出后发布。工作负责人在 Issue 选用适用版本 | 运行视图能定位当前节点、失败原因、返工目标及交回的结果。 |
| 选用团队能力 | 从 Agent 或 Skill 找适用范围、配置和版本。从工作回看所用方法和取得的回执 | 发布方能查到适用版本，执行者能据 Run 核对本次实际加载或使用的证据。 |
| 查项目知识 | 按需进入团队 Wiki 或项目代码 Wiki，也可在 Issue 直接引用已有资料 | 业务口径可追到修订和章节，代码说明可追到仓库、基准和实现位置。 |
| 查看交付及来源 | 从 Issue 交付区选择具体附件版本，按需展开直属或子项的 Run | 接手人能从共享制品追到工作约定和已有检查。 |
| 查成本和质量 | 从 Issue 看交付与分单位用量，从项目看趋势与覆盖 | 业务执行、评测和 Benchmark 各有归属，成员能区分已知用量、明示为零和缺报。 |
| 提出改进并采用 | 从失败记录定位证据和受影响能力，以可比样本对照候选版本，再由有权维护者发布 | 下一项适用工作选择该版本，实际采用记录和工作结果可供回查。 |

SOP 设计视图面向方法维护者，运行视图面向当前工作负责人。人工节点显示待确认的问题、相关发现、通过后的去向和可选返工目标。维护者比较改进候选时，可以查看参与比较的样本、被排除的样本及原因。把团队经验用作某项工作的验收要求时，由该 Issue 的有权成员确认适用口径。[SOP 与工作流](02-sop-workflow.md) · [能力与资料](03b-capability-governance.md) · [评价与改进](04-cost-quality-improvement.md)

### 方法怎样进入下一项工作

订单交付曾发现区域数据越界。若团队希望退款导出也检查这个问题，项目成员可以从原失败报告提出一条可复用的方法，写清适用条件，跨项目分享时只提供获准共享的内容。经验适合写成说明时，按来源许可和知识审核路径发布。需要变成可执行检查时，再以候选 Skill 或 SOP 与当前版本作对照，由有权维护者审核并发布适用范围与版本。[经验贡献](03b-capability-governance.md#从项目证据到团队经验) · [候选对照与发布](04-cost-quality-improvement.md#54-benchmark-对照)

退款 Issue 的负责人从该项目已配置的能力中选择适用版本，并向本项目业务负责人确认权限口径。实施者在原 Issue 交回本次结果，并引用能从 Run 核对的版本和调用记录。维护者之后能区分这项方法已发布、已被选用、已产生实际结果三个时点。是否减少返工取决于后续可比工作的结果。项目仅需调整负责人或步骤时，有权成员直接在原项目工作流中采用该项调整。[工作中的选用与投递](03b-capability-governance.md#5-一次工作如何选择和投递能力) · [发布后观察](04-cost-quality-improvement.md#55-发布后观察)

## 四、轻量完成、并行等待与接管

**轻量完成。** 对“把导出按钮改为批量导出”，Issue 直接显示目标位置、约定文案和检查实际显示的方法。成员亲自修改时，可在同一 Issue 提交变更和显示结果。项目已允许按该检查完成、本次未另约人工验收时，有完成权的成员即可结束该项。交给 Agent 时，显示其 Run 交回的变更和检查结果。若本次约定由成员查看后接受，结果交到该成员的待办。发现改动还涉及导出权限时，由当前负责人在原 Issue 指出新增范围，待有权成员决定后按新约定继续。[专题一的轻量路径](01-unified-work-lifecycle.md#125-最小路径修改导出按钮文案)

**项目中谁在等谁。** 订单与另一项调查同时进行时，成员从项目列表可直接进入需要动作的原记录。

| 项目列表上看到什么 | 谁可以采取什么动作 | 什么时候可以继续 |
|---|---|---|
| 调查已就绪，正在等可用的 Leader Runtime。若只知已排队，标明原因待确认 | 两项工作竞争同一资源时，由项目既有责任人决定先后，具备项目优先级修改权限的成员据此调整 Issue。机器所有者决定是否另行共享资源 | 已开始的工作继续原安排。调查实际开工后，列表从对应 Run 取得开始回报 |
| 订单集成在等后端修复。行内可进入后端子 Issue，查看负责人和缺少的交付 | 后端负责人在子项提交修复。集成负责人核对所收版本。前端已交付部分仍供集成使用 | 修复已交回且具备本轮集成条件后，由集成负责人组织新候选 |
| 订单在等林确认付款时间口径，指向父 Issue 的具体问题 | 林在父项作出决定，当前负责人把它交给受影响的后端与核验子项 | 受影响的工作依新约定继续，其他已就绪子项可照常推进 |

**离线后接手哪一项工作。** 在需要换人的父项或子项使用原生改派。成员打开父项或子项时，先看到当前负责人、最近一次可靠交付、在途执行和仍缺的决定。

- 周提供的 Leader Runtime 离线后，恢复原机可继续使用原队。改绑 Leader Agent 的 Runtime 会一并迁移它在各 Issue 中排队或延后的工作，已由旧机领取的执行仍留在旧机。若由成员接替，则由有权成员在父项将接手者设为当前负责人。接手者查看各子项和剩余交接，使用自己获准的资源继续组织。旧 Leader 恢复后按父项的当前指派行动。其他机器上的前后端子项仍由原负责人推进，订单最终验收仍交林。
- 若只有后端实施者离线，在后端子项明确移交实现工作。接手者先看已交回的变更、能否取得工作副本及旧执行是否还可能写入。确认旧执行已结束或其写入已隔离后再接续。集成负责人收到当前候选的交付后继续。旧机重连时，旧回报仍可从原 Run 查看，父项沿现有协调安排推进。

### 用量展示与工作对象边界

从 Issue 展开的 Run 明细按宿主和原生单位汇总，标出该指标覆盖了多少次适用的执行。只有 Token、费率未知时显示“24 Token · 费用未知”。三次执行中，一次明确报告零 Credits，一次只报 Token，一次缺报，界面显示已知小计零 Credits、覆盖 1/3。各供应商的 Credits 分列。原始记录、统计口径和可核对的展示结果见[用量展示研究](../research/topic-05/codebuddy-display-replay.md)。
