# 核心协作一致性与并发控制模型

本文定义多个主体、执行环境和流程同时操作时，AgentPlatform 如何保持工作事实、执行事实和交付依据一致。它建立在[核心对象模型](core-object-model.md)及[统一生命周期、状态机与事件模型](lifecycle-state-event-model.md)之上。

本文描述产品级一致性语义和恢复要求，不指定数据库、消息中间件、锁服务、API 或部署拓扑。具体实现必须沿用 Multica 已有写入与派发入口，并以固定版本源码和实验确认覆盖范围。

## 1. 设计目标与边界

平台不是要求所有对象在一个全局事务中同时变化。成员本机、宿主进程、中心协作和外部代码仓不可能共享一个原子事务。系统需要保证的是：

1. **权威事实不分叉**：每类事实有唯一权威对象和有效写入入口。
2. **并发决定可判定**：两个主体同时修改同一事实时，必须有明确的胜出、拒绝或人工合并结果。
3. **跨层动作可恢复**：状态已经生效但通知、派发或下游处理失败时，可以安全续做。
4. **结果消费可验证**：每个流程节点和工作只消费明确版本、明确来源且符合当前约定的结果。
5. **旧执行不能越权**：撤权、接管、候选换版或流程重入后，旧执行的迟到回执不能改变当前事实。
6. **不确定性不被伪装成成功**：断联、回执缺失、用量缺失和外部副作用未知均保留未知状态。

本模型允许跨对象最终一致，但不允许同一权威对象出现无法解释的并行有效决定。

## 2. 一致性边界：按权威对象写入

### 2.1 对象级权威写入

| 权威对象 | 可改变的事实 | 其他对象如何使用 |
|---|---|---|
| Issue | 工作约定、负责人、业务状态、决定、当前候选和完成状态 | SOP、Run、工作台和通知读取 Issue 的当前有效版本 |
| Project 配置 | 项目成员、工作流、采用的能力版本、资源策略 | 新工作按适用配置版本建立约定；在途工作按已固定版本处理 |
| SOP Execution | 受托范围、流程实例状态、节点激活、尝试、结果消费和出口 | Issue 与后继节点消费其明确交回的结果 |
| Run | 受管派发、领取、启动、停止请求和实际执行回执 | SOP、Issue、Evaluation 和用量视图引用 Run 的事实 |
| Artifact / Candidate | 具体制品版本及候选组成 | 检查、验收和后继工作固定引用具体版本 |
| Evaluation / Asset Release | 评价结果、候选审核和发布事实 | Issue 或项目维护者按其职责消费，不反向改写被评对象 |

一个对象的状态变化必须经过其权威写入入口。工作台可以聚合展示多个对象，但不得通过更新投影、通知或缓存来代替权威写入。

### 2.2 不做全局事务

一次跨层操作通常由多个独立写入组成。例如，Issue 接受委托、SOP 建立实例、节点请求派发、Run 启动、结果回交分别属于不同权威对象。

这些动作不假设能在同一个数据库事务内完成。跨对象流程使用**持久化意图 + 可重试推进 + 结果核对**。某一步失败时，保留已经生效的事实，从最后一个已确认边界继续，不回滚已经真实发生的外部执行。

### 2.3 先写权威事实，再产生下游动作

一个需要触发跨层动作的业务转换，必须先在权威对象上确认有效，再产生可恢复的后续动作。

- 先确认 Issue 指派或 SOP 节点激活，再请求派发。
- 先确认停止或撤权决定，再通知 Daemon 停止执行。
- 先记录 Candidate 和其固定组成，再启动针对它的核验。
- 先记录验收决定，再推进满足条件的 Issue 完成。
- 先发布资产版本，再允许项目采用该版本。

不能先向下游发消息，再把未确认的业务意图当作已经生效的状态。

## 3. 并发控制

### 3.1 同一权威对象的竞争写入

对同一 Issue、SOP Execution、Project 配置或其他权威对象的竞争修改，采用**基于当前版本的条件写入语义**：

1. 操作者读取对象当前版本及需要修改的字段。
2. 提交命令时声明所依据的版本或等价的当前状态条件。
3. 权威入口核对权限、前置条件及版本仍有效。
4. 只有满足条件的写入生效，并产生新的对象版本和对应事实。
5. 其他基于旧版本的竞争写入被拒绝或要求重新读取；不能静默覆盖胜出者。

这是产品语义，不限定必须使用数据库乐观锁。若上游入口已提供等价的原子条件更新，直接沿用；若无法保证，需在该写入入口补足。

### 3.2 字段级合并的适用范围

不能把所有 Issue 更新都视为互斥，也不能把所有字段都自动合并。

- 对负责人、业务状态、当前候选、工作约定、完成决定等影响责任或后续执行的字段，按整体业务条件竞争，不能 last-write-wins。
- 对评论、独立附件、观察记录等可追加事实，允许并发追加，但各自保留身份、来源和时间。
- 对标签、排序等低风险集合字段，只有在语义明确且不改变授权或完成条件时才可采用集合合并。
- 对同一工作约定的目标、范围、验收标准或授权变更，发生并发修改时必须由有权成员合并为一个新版本，不能逐字段拼出未经确认的组合。

### 3.3 不同对象之间的并发

不同权威对象可以独立推进，但消费方必须重新核对当前依赖：

- Issue 改派不自动改写已有 Run；执行处置按 Run 和 Runtime 规则单独发生。
- SOP 节点与无依赖关系的节点可以并行；共享写入资源必须隔离或显式串行。
- 多个节点可以引用同一个 Artifact 版本，但每个消费方分别记录自己的消费和核验结论。
- 父子 Issue 各自推进；父项在消费子项结果时核对交付版本及当前父项约定。
- 同一 Agent 或 Runtime 的资源竞争由执行派发与资源租约处理，不通过修改 Issue 负责人伪装成资源锁。

## 4. 版本、轮次与 fencing

### 4.1 关键操作绑定版本

以下操作不能只依赖可变的“当前”指针：

- 执行开始时固定工作约定版本、项目采用的能力版本、输入材料和执行授权。
- SOP 节点激活固定流程版本、工作约定、输入基准或结果，以及授权范围；处理已有交付时同时固定输入 Candidate。输出及输入换版按[节点激活规则](lifecycle-state-event-model.md#61-node-activation)归属。
- 检查和验收固定 Candidate、工作约定和适用标准版本。
- 结果消费固定生产者、Artifact 版本、Evidence 及其适用轮次。
- Evaluation 固定被评对象、输入证据、评价器和标准版本。

当前指针可以帮助发现最新版本，但历史事实必须引用不可变版本或等价的内容摘要。

### 4.2 轮次与代际隔离

节点重入、已固定的输入候选变化、工作约定变更、授权撤销后重新授权，均可能产生新的有效代际。旧执行回执只能补充其原代际。

每个可被异步回报影响的工作范围，必须有可核对的激活身份或等价的代际标识。写入时检查回报所属代际仍是目标操作允许的代际。仅检查 Issue ID、节点名、Session ID 或 Agent 身份不足以防止旧执行写入。

持续协调按 Issue 上的具体委托核对。改派或撤销后，即使同一 Agent 再次获派，也只可依据新委托行动。对旧回唤、已排队的协调 Run 和在途 Worker 分别核对归属。涉及派发、修改候选或推进 Issue 的写入，在生效时复核当前委托。

### 4.3 Fencing（旧执行隔离）

当资源被重新分配、执行被接管或授权撤销时，仅发送停止请求不足以证明旧执行失去写入能力。

需要能区分新旧执行权的 fencing 语义：

- 新执行获得新的授权代际或等价凭据。
- 受控写入入口拒绝已失效代际的旧写入。
- 对不支持 fencing 的外部系统或本地文件副作用，必须通过工作目录隔离、分支 / 工作副本隔离、进程确认或人工核对降低冲突风险。
- 旧执行的迟到结果保留为历史证据，不得覆盖新执行的结果或当前交付。

Fencing 是安全语义要求，不预设一定由独立锁服务实现。

## 5. 派发与事件投递的一致性

### 5.1 持久化操作意图

权威状态转换和待执行的下游动作必须具有可恢复的关联。例如，SOP 节点已进入 Ready 后，系统需要能够查回“尚待派发”的动作；Run 已终态但结果尚未被节点消费时，需要能够查回“尚待消费”的结果。

意图可以由同一权威记录、待办动作记录或等价机制承载。关键要求是：进程重启后可以从权威事实重新判断哪些动作仍然有效。

### 5.2 Outbox / Inbox 语义

跨层通知与事件处理遵循以下语义：

- **Outbox 语义**：权威状态成功写入时，同时确保对应下游动作可被重新发现和投递。若底座无法在同一事务写入 Outbox，必须提供等价的可扫描待办与对账机制。
- **Inbox 语义**：接收方记录已处理的来源事件或业务操作身份，重复投递不会重复产生业务副作用。
- **At-least-once 投递**：允许同一动作被重复送达；正确性依赖幂等处理，而不是假设消息只送达一次。
- **结果回执**：下游动作分别记录已接受、已执行、已拒绝、失败或结果未知。仅发送成功不代表动作已生效。

不把 Exactly-once 作为跨网络、跨宿主的前提。对外部副作用无法提供幂等键时，必须先查询原动作结果或转人工核对，再决定是否重试。

### 5.3 命令与事件的区别

- **Command（命令）**：请求有权对象改变事实，例如改派 Issue、激活节点、停止 Run、接受 Candidate。
- **Event（事件）**：已经发生或被观察到的事实，例如 AssigneeChanged、RunStarted、CandidateAccepted。
- **Projection（投影）**：为查询构建的列表、计数和工作台视图，可重建，不拥有业务写入权。

命令可能被拒绝，不应提前发布“成功事件”。事件投递失败不能撤销已生效的权威事实；应恢复投递或重建投影。

## 6. 结果消费与交付一致性

### 6.1 生产与消费分离

生产者产生 Artifact / Evidence；接收方声明消费哪份结果、用于什么节点或工作、满足什么条件。一个结果可被多个消费者复用，但消费关系独立记录。

消费方至少核对：

- 生产者及原始 Issue / Run / SOP 节点归属；
- Artifact 的具体版本或摘要及其可获取性；
- 对应 Candidate 和工作约定版本；
- Evidence 覆盖的标准、环境、身份和时间；
- 当前消费节点 / Issue 是否仍接受该轮输入；
- 接收方当前读权和使用授权。

### 6.2 多消费者与版本固定

多个 Issue 或 SOP 节点可以消费同一个 Artifact 版本，但不能共享一个可变的“已通过”标记。每个消费者各自记录：

- 引用了哪个生产版本；
- 为何适用于本次输入和标准；
- 自己完成了哪些检查；
- 消费结果是接受、拒绝、待补充还是不适用。

生产方发布新版本不会自动改变既有消费者固定的引用。若新版本替代旧版本，消费者根据依赖策略决定继续使用旧版、显式迁移或重新核验。旧版本不可用或授权撤回时，相关消费标记为受影响并重新评估，不静默替换。

### 6.3 Candidate 与验收竞争

成员或受管执行沿原 Issue 提交材料。交付区继续按文件归集历史。工作约定要求对一份交付作决定时，提交方指明本次送审的一份或多份材料，固定附件 ID、仓库修订及适用工作约定，形成 Candidate。继续评论、上传参考资料或补交检查报告时，只有明确替代送审组合才切换当前候选。普通事项按各自的完成约定收尾。

| 动作 | 在原 Issue 的写入与结果 |
|---|---|
| 提交或替代送审候选 | 记录不可变的材料组合和来源，并将它设为当前待处理版本。替代时核对提交方所见的原候选。并发提交已有一方生效时，另一方先读取当前版本，再决定是否替代。 |
| 检查或验收 | 检查报告关联检查者实际检查的候选和标准，迟到的报告仍可归入原候选。具名验收由服务端在决定生效时核对决定者当前权限、所见候选、工作约定、适用标准及必需证据。通过后在原 Issue 保存含决定者、对象、标准与适用范围的 Decision。 |
| 完成或向下游交付 | 需要具名验收的 Issue，在写入成功状态时再核对有效决定仍覆盖当前候选和约定。单项更新、看板、批量逐项和启用的 PR 自动完成均遵循此条件。转交待验收可以先改派。若 PR 已合并、只差具名决定，验收生效后可按当前约定完成，同时复核仍然适用的 PR 条件。下游选用成果时记下实际使用的候选及所依据的决定或检查。 |

**换版先发生。** 如果验收人打开旧版后才提交接受，请求返回冲突，保留原检查记录。工作台显示原先查看和当前送审的版本及变更材料，验收人核对后再决定。这次过期请求不会产生有效的接受决定，也不会完成 Issue。

**接受先发生。** 决定保留在当时的候选及标准上。仍在进行的 Issue 明确送审新版后，重新判断受影响的检查和本项完成条件。已经完成的 Issue 按项目的重开或后续工作约定处理新增交付。此前已经接手的工作继续指向自己当时取用的版本。

原生 Issue 更新的 `expected_revision` 可用作写入保护。修订号冲突时重新读取原 Issue，只有候选、约定、标准、决定权限或必需证据的变化影响本次决定时，才需要验收人重新确认。仅有无关讨论时，可在新修订上复核同一决定后提交。候选切换、验收和成功完成各自在原 Issue 的权威写入点原子核对条件；验收与完成分次发生时，完成写入也要核对。重复提交同一已生效决定应返回原记录及其适用版本。实现沿用现有事务与条件更新，入口映射见[Multica 交付与写入源码](../research/05-source-evidence.md#交付换版与验收写入)。

## 7. 资源竞争与接管

### 7.1 Runtime 与执行容量

独立 Issue 可以交给同一 Agent 并行处理。不同 Agent 也可同时为同一 Issue 工作。Multica 在领取时检查同一 Agent 和同一 Issue 的活动执行。前一轮已派发、正在运行或等待本地目录时，后续轮次留在队列中。SOP 的节点就绪表示依赖已满足，实际开工仍取决于执行名额和工程目录。

| 等在哪里 | 约束与继续条件 |
|---|---|
| 等领取 | 本机 Daemon 先取得自己的空槽，中心再核对 Agent 并发上限及该 Runtime 可选的总上限。多个 Agent 共用同一 Runtime 时共享后者，同一 Daemon 管理的多个 Runtime 也共用本机槽位。出现空位后由原领取路径再次选择符合条件的任务。 |
| 已领取，等本地目录 | 同一 Daemon 上的普通原地 Issue Run 按真实路径互斥，跨项目绑定到同一路径也会相互等待。工作树模式只在准备快照时需要这把锁，随后在各自工作树执行。等待目录的 Run 此时仍占 Agent、Runtime 的相应额度和本机槽位。有余量且能取得所需工作副本的其他工作可以开始。 |
| 继续、取消或接管 | 正常释放目录后，由持有该任务的 Daemon 继续同一次准备和启动。等待中的任务可沿原 Run 取消。Daemon 重启或 Runtime 长期失联时，按实际回执走原生恢复；跨机接续前核对旧进程的写入与工作副本隔离。Issue 负责人及业务状态按原约定推进。 |

路径互斥覆盖同一 Daemon 管理的普通 Issue 执行。成员自己的编辑器、终端和外部进程仍可能写入原目录。并行完成的工作分别交回原 Issue 或受托节点，消费者固定实际使用的修订并按本项要求核对。目录选择见[执行平面](03a-execution-plane.md#项目如何选择工作目录)，领取和等待边界见[Multica 源码依据](../research/topic-03a/workspace-continuity.md#项目目录模式与并发容量的源码依据)。

### 7.2 接管流程

接管不是简单改派。至少需要核对：

1. Issue 当前负责人、工作约定和有效授权；
2. 旧 Run 的最后可信状态、停止请求和可能副作用；
3. 当前 Candidate、代码基准、Artifact 和未消费结果；
4. 原 Runtime 是否仍可能写入共享资源；
5. 新执行者的身份、读权、工具权限和 Runtime；
6. 需要继承的 SOP 激活、待决事项和预算。

接管后，新负责人以自己的身份和授权继续。旧执行回执归属原 Run；新执行使用新的 Run 或合法恢复关系。无法确认旧执行是否停止时，必须隔离其写入或等待核实，不得假定已释放。

## 8. 冲突处理策略

| 冲突类型 | 默认处理 | 是否可自动解决 |
|---|---|---|
| 同一 Issue 的负责人或状态并发变更 | 条件写入，失败方重新读取并由有权主体决定 | 仅当操作语义明确且条件仍满足 |
| 工作约定或验收标准并发修改 | 拒绝旧版本写入，要求合并为新版本 | 否，需有权成员确认 |
| 评论、独立附件并发追加 | 保留各自记录 | 是 |
| SOP 同一节点重复派发 | 以节点激活和稳定操作身份幂等查回原安排 / Run | 是 |
| 不同节点争用同一工作副本 | 隔离或显式串行化 | 仅在资源独立时 |
| Candidate 换版与验收并发 | 在 Issue 权威入口按版本和当前候选条件串行化 | 条件明确时 |
| 旧 Run 与新 Run 同时写入 | fencing、工作副本隔离或停止并确认旧执行 | 不能仅凭超时自动解决 |
| 迟到事件与新激活竞争 | 归属原代际，不允许推进新激活 | 是 |
| 同一 Artifact 被多个消费者采用 | 固定生产版本，各消费者独立记录消费 | 是 |
| 无法判断外部副作用是否已发生 | 查询原动作、核对证据或人工处理 | 否 |

不得使用全局 last-write-wins 处理责任、授权、候选、验收或流程推进等关键事实。

## 9. 恢复与对账

协调回合结束或成员的 Runtime 离线后，接手者按当前授权，从 Issue、Run 与交付记录查明并恢复尚待处理的跨层动作。

| 故障位置 | 恢复依据 | 恢复动作 |
|---|---|---|
| 权威状态已写入，派发尚未送达 | 当前对象版本与待执行意图 | 重新核对授权和前置，只补投仍有效的派发 |
| 派发已送达，发送方未收到回执 | 稳定操作身份、目标 Run 和领取状态 | 查回原安排 / Run，禁止重复创建执行 |
| Run 已启动，Daemon 或平台断联 | Run、Runtime 租约、宿主可核对身份与进程回执 | 先确认原执行状态和写入风险，再恢复或接管 |
| Worker 已终态，回唤合并、迟到或消费中断 | 原委派、源 Run、固定结果版本及目标 Issue 的消费记录 | 重读仍有效的委派，逐项查明接收方是否已消费。已处理项复用原记录，缺项待补，旧委托的回执保留原归属 |
| Run 已终态，结果未被 SOP 消费 | 原 Run 终态、结果版本和节点激活 | 重放结果消费，核对当前激活仍有效 |
| 状态已改变，通知失败 | 权威对象当前版本及通知待办 | 重发通知；通知不改变业务事实 |
| 结果投递成功，消费方回执丢失 | 生产结果身份和消费操作身份 | 查回消费记录，幂等补投 |
| 候选换版时旧检查迟到 | 原 Candidate / 标准版本及当前 Candidate | 保留旧检查，不推进新候选 |
| 资产已发布，项目采用动作失败 | Release 及项目配置当前版本 | 重试采用命令或由维护者决定新版本；不回滚 Release |
| 用量或宿主观察迟到 | 原 Run、原生请求身份和计量范围 | 更正对应来源记录，保留未知与更正轨迹，不改变业务终态 |

定期或按故障触发的对账，比较权威对象与待办动作、执行回执、结果消费和派生视图。对账可以发现并恢复缺失动作，不能凭推断制造执行成功、验收通过或费用数据。

## 10. 决策权与恢复责任

| 决策 | 有权主体 | 系统职责 |
|---|---|---|
| 修改 Issue 目标、范围、负责人或完成要求 | Issue 对应权限的成员 | 条件写入，保留版本和决定来源 |
| 改变项目工作流或采用能力版本 | 项目维护者 / 对应资产维护者 | 固定新版本和生效范围，不静默改写在途工作 |
| 推进或取消 SOP 受托范围 | 受托授权主体及流程规则允许的机制 | 校验当前授权、激活和在途节点 |
| 停止或接管 Runtime 执行 | 有权工作负责人、资源所有者及平台执行控制 | 停止新派发、核实旧执行、隔离写入并记录回执 |
| 接受 Candidate 或批准例外 | 工作约定指定的有权主体 | 对当前候选和标准条件写入决定 |
| 决定如何处理无法确认的副作用 | 业务责任人及相关资源所有者 | 暴露不确定性和影响范围，不自动重试可能重复的外部动作 |
| 修复派发、通知和投影失败 | 平台恢复机制 | 根据权威事实幂等重试，不代替业务决定 |

平台可以自动恢复技术动作，但不能自动替代业务取舍、授权扩大、验收或风险接受。
