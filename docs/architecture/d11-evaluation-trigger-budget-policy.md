# D11 · 评价触发与资源预算治理

> 本文定义 Evaluation 在什么条件下触发、使用什么评价方式、占用多少资源，以及失败、证据不足和预算耗尽时如何处理。
> D7 定义持续改进完整闭环；D11 将其中的评价入口和资源边界变成可执行治理规则。
> 本文是产品与运行策略契约，不定义调度服务、数据库、API、固定模型或统一计价换算。

## 1. 目标与边界

评价的目的不是给每次 Agent 执行打分，而是在有业务价值的地方取得足够证据，支持质量门禁、当前工作判断或跨工作改进。

D11 必须同时控制四件事：
1. **覆盖正确**：强制要求不漏检；普通工作不被无差别评价。
2. **评价匹配**：能用确定性规则回答的问题，不消耗模型评价；需要语义判断时才使用 Model-based Evaluator 或 Human Review。
3. **资源有界**：单次评价、单项工作、项目周期和团队周期均有明确预算及停止条件。
4. **结果可解释**：没有触发、未抽中、未能评价、评价失败和评价不通过是不同事实。

D11 不建立第二套 Run、队列、调度器或评价专用 Runtime。评价和 Benchmark 沿 Multica 现有 Task / Run / Runtime 链执行；Evaluation 记录固定目标、政策、评价器和结论。

## 2. 评价触发分为四种入口

| 触发类型 | 何时触发 | 是否可以影响业务推进 | 责任来源 |
|---|---|---|---|
| Mandatory Gate · 必需门禁 | Work Agreement、项目规则或 SOP 在工作开始 / 节点进入前声明必须完成的检查 | 可以；未完成或未通过时按预先声明的等待、退回或人工决定处理 | 有权项目成员 / Issue 约定及已发布规则 |
| Risk Trigger · 风险触发 | 出现预先定义的高风险工作特征、失败模式或异常信号 | 只有预先声明为门禁时才能阻断；否则是 Advisory | 项目 Evaluation Policy |
| Stratified Sampling · 分层抽样 | 对已结算的普通生产工作按类别和采样规则选择 | 不阻断原工作，作为质量观察和改进输入 | 团队 / 项目 Evaluation Policy |
| On-demand · 主动发起 | Issue 负责人、项目维护者或资产维护者因争议、复盘或提案主动请求 | 依请求目的决定；事后评价默认不改变已完成业务决定 | 对应对象的有权主体 |

触发入口不是四种 Evaluation 状态。只有实际创建评价任务时才有 Evaluation 记录；未抽中不创建空 Evaluation，也不将“没有评价”显示为“评价通过”。

### 2.1 Mandatory Gate：先声明，后执行

必需门禁必须在工作开始或对应节点进入前声明：
- 检查对象与固定版本（Run 终态、Candidate、Node Attempt 或其他适用对象）；
- 必须执行的 Scorer / Rubric 版本及检查条目；
- 通过条件、失败处理和证据不足处理；
- 是否需要具名 Human Review；
- 可用资源预算及预算耗尽时的处理人。

不允许工作完成后追溯性地把事后评分改称强制门禁。安全、隐私、合规、不可逆生产操作等强制要求不能被抽样代替。模型评价不能替代法律、合规或业务有权人的决定。

### 2.2 Risk Trigger：触发条件必须可说明

风险规则可使用：
- 影响范围、外部可见性、数据敏感度和操作可逆性；
- 工作新颖度、依赖不确定性和历史失败 / 返工模式；
- 交付退回、必需测试失败、异常重试或人工接管；
- Runtime / Adapter 能力未知、关键证据缺失；
- 在同类任务、相同原生单位和足够覆盖下观察到的资源异常。

风险规则必须说明输入事实、阈值来源和作用范围。模型自己生成的风险判断只能作为建议输入，不能单独将工作升级为阻断门禁。无法取得必要数据时标为 Unknown，不能默认低风险。

### 2.3 Stratified Sampling：抽样要代表工作总体

抽样只针对已结算的生产工作，不对仍在运行的 Run 作最终质量评价。分层至少考虑适用的：
- 工作类型 / 交付类型；
- 项目与风险级别；
- Agent / Runtime / Backend / 模型或工具链版本；
- SOP / Skill / Rule / Release 版本；
- 成功、失败、返工和被退回等结果类别。

采用分层随机样本与风险触发样本并行，避免只抽失败样本而失去正常工作的基线。抽样比例、最低样本数和周期由项目策略设置；团队默认值可作为起点，但应依据实际评价成本、样本量和发现率调整，不把某个百分比固化为所有团队的系统常量。

为保证可复现，抽样选择使用稳定的目标身份、分层键和策略版本；相同目标在相同策略下重放不会因重试而反复改变是否入样。策略版本变化后，才按新策略重新选择未来目标。

### 2.4 On-demand：人工发起也要有边界

人工可对具体 Run、Candidate、SOP Execution、资产版本或既有 Evaluation 请求评价。请求必须说明问题和目的，沿用请求者的读取权限，并受同样的预算、幂等和重试规则约束。

同一输入未变化时重复点击不创建重复评价。确需重评时，必须说明新证据、新评价器版本、标准变化或明确的复核理由。

## 3. 风险级别与默认评价组合

项目可以定义更细策略，但至少区分以下三档：

| 风险档 | 典型特征 | 最低覆盖要求 | 评价组合 |
|---|---|---|---|
| High · 高风险 | 安全 / 隐私 / 合规要求；不可逆生产操作；敏感数据；大范围共享基础设施或高影响变更 | 适用的确定性门禁全覆盖；工作约定要求的人工审核逐项完成 | Deterministic Scorer 优先；必要时 Human Review；模型评价仅补充分析，不能替代硬门禁 |
| Elevated · 提高关注 | 新技术路径、重要架构变更、历史反复失败、关键证据缺失或明显返工异常 | 全部必需确定性检查；按风险规则触发独立评价 | 确定性检查 + 针对性 Trace / Model-based Evaluation；必要时人工复核 |
| Routine · 常规 | 影响范围有限、可逆、已有成熟做法且证据充分 | 工作约定声明的检查全覆盖 | 确定性检查全覆盖；模型评价按分层抽样或主动请求 |

风险档用于决定评价覆盖，不直接决定 Issue 的业务状态。工作约定可以提高要求；项目策略不能降低团队或法定强制要求。项目负责人不能通过将工作标为 Routine 绕过必需门禁。

## 4. 先选择评价方式，再决定是否启动模型 Run

| 评价方式 | 适合的问题 | 默认处理 |
|---|---|---|
| Deterministic Scorer | 测试结果、退出码、必需 Artifact、版本 / 摘要、权限、结构契约、必需字段 | 能自动取得证据就优先执行；不需要模型 Run |
| Trace Scorer | 工具调用顺序、重试、恢复、步骤覆盖、上下文投递和执行效率 | 仅在对应宿主观察已授权且有足够覆盖时执行 |
| Model-based Evaluator | 需求覆盖、代码 / 文档质量、根因归纳、方案完整性等需要语义判断的问题 | 有明确评价问题、足够证据和预期决策价值时启动独立评价 Run |
| Human Review | 业务取舍、风险接受、例外批准、主观体验及法定 / 组织决定 | 由工作约定指定的有权成员决定；模型评分不能代签 |

同一个评价计划可以组合多种方式，但必须区分各自的证据和结论。确定性检查通过不表示语义质量通过；模型评价通过也不能覆盖确定性失败。

**评价的最小充分原则**：只执行能回答当前决策问题的评价器。已有可靠的 CI / 测试报告时，不再用模型重复判断相同事实；已经明确失败的必需确定性门禁，不启动昂贵模型评分来“投票翻盘”。

## 5. 评价对象何时稳定

正式 Evaluation 应针对可固定、可回读的输入：
- Run 评价：生产 Run 已到可信终态，固定其实际输入、输出、Trace 覆盖和所用资产版本。
- Candidate 评价：Candidate manifest 已提交并固定，评价绑定 Candidate、Work Agreement 和验收标准版本。
- SOP / Process 评价：对应流程实例或节点轮次已结束，固定定义版本、节点结果和相关交付。
- Asset / Release 评价：固定资产候选或发布版本、依赖和适用范围。
- Benchmark：固定实验定义、样本集、候选 / 基线、评价器和环境。

运行中观察可用于运维告警或停止执行，但不能伪装成终态 Evaluation。Run 失联或终态 Unknown 时，不得仅凭超时启动最终质量评价；先按 D5 恢复 / 核对规则确定可用事实。

## 6. 预算分层与资源记账

### 6.1 预算不是一个 USD 总数

每个 Evaluation / Benchmark 计划在启动前声明可用资源上限：
- 最大评价 Run 数与最大重试次数；
- 最大执行时长 / 等待时长；
- 可知的 Provider / Model 原生单位预算（Token、Credits、请求数等分别表达）；
- 如有可信费率，才可另设估算费用上限；
- 允许的人工审核数量或所需角色；
- 允许读取的证据范围与数据量。

不同宿主 Credits、Token、请求数和 USD 不得无依据换算成一个统一成本。缺少 Runtime 原生用量时，保持 Unknown，改用 Run 数、时间和并发等可控制上限；不能用订阅余额或推测价格补数。

### 6.2 预算按四个范围约束

| 范围 | 预算责任 | 目的 |
|---|---|---|
| 单次 Evaluation | 评价 Run 数、重试、时长、输入证据量和原生用量上限 | 防止单次评价失控 |
| 单个 Issue / Candidate | 本项可触发的评价次数、重评次数和人工复核次数 | 防止单项工作反复评分 |
| Project 周期 | 评价与 Benchmark 的周期资源额度、风险门禁预留量 | 避免某项目挤占全部治理资源 |
| Team 周期 | 团队总资源上限及强制门禁预留量 | 控制整体治理成本，保留高风险工作所需能力 |

项目与团队预算采用各原生计量单位分别核算。只有同一 Provider / Model、相同单位和可证明覆盖范围内才可比较或累计。资源额度可以由项目负责人配置；团队级强制门禁和保留额度由团队有权维护者控制。

### 6.3 预算预留与启动

启动评价前先核对预算资格。只有确定会启动的 Run 才占用相应预留；Run 结束后以实际回执结算，未消耗的预留释放。重复事件不得重复预留。

评价任务排队期间若预算、授权、目标版本或策略发生实质变化，开始前重新核验；不符合时不启动。评价已启动后的真实消耗仍归该评价 Run，即使评价后来失败、取消或被判定无效。

### 6.4 预算耗尽时如何处理

- **Mandatory Gate**：不静默跳过。按预先声明的策略等待额度恢复、转交有权成员，或使用已批准的等价确定性 / 人工核验方式。未完成门禁不能自动放行。
- **Risk Trigger**：若规则声明为阻断门禁，按门禁处理；若为 Advisory，保留未评价原因，不影响原业务完成条件。
- **Sampling**：预算耗尽后停止新增抽样，不影响已完成生产工作；记录抽样覆盖下降，不能把未抽样当成通过。
- **On-demand**：明确告知请求未执行及预算原因；请求者可调整范围或等待下一周期，不自动突破预算。
- **Benchmark**：达到实验预算即停止新增样本 / 重复次数，结论标为 Insufficient / Inconclusive，不以已完成部分宣称达到总体成功标准。

## 7. 失败、证据不足和重试策略

| 情况 | Evaluation 结果 | 后续动作 |
|---|---|---|
| 评价器成功且证据充分 | Completed | 返回业务门禁或 Advisory 结果 |
| 缺少必需证据、来源失权或覆盖不足 | Insufficient Evidence | 补证、等待或人工处理；不能自动给低分或通过 |
| 评价 Run 因瞬时 Runtime / 网络故障失败 | Failed | 仅在剩余预算内有限重试；重试沿原 Evaluation 身份与尝试关系，实际新 Run 独立计量 |
| 评价器 / Rubric 配置错误或输出不符合契约 | Failed | 停止自动重试，修正评价器版本后显式重新请求 |
| 评价结论为不通过 | Completed，结论为 Not Passed | 按门禁或 Advisory 语义处理；不是评价任务 Failed |
| 目标 Candidate / 标准已换版 | 原 Evaluation 保留原目标 | 不把旧结论套到新 Candidate；必要时按新版本请求评价 |
| 预算或授权不足 | 不创建运行中的 Evaluation，或保持 Requested / 等待 | 不启动 Run；记录未启动原因和责任方 |

默认自动重试只用于可识别的瞬时基础设施失败，次数由策略设定且必须大于零才允许重试。质量不通过、证据不足、权限拒绝、策略不适用和配置错误不是瞬时故障，不自动重试。

Evaluation 的失败不能改变被评生产 Run 的成功 / 失败事实；评价结论也不能越过 D6 的 Acceptance Decision。

## 8. 防止重复触发、评价递归和自我证明

### 8.1 幂等与重评

同一评价目标、目标版本、评价器 / Rubric 版本、策略版本和证据快照的重复触发，只能复用已有有效 Evaluation 或识别为重复，不创建新的评价 Run。

只有以下情况允许重评：
- Candidate、Artifact、工作标准或输入证据发生实质变化；
- Scorer / Rubric 有新版本，且请求者明确要重新评价；
- 原评价 Failed / Insufficient Evidence，且失败原因已解除或证据已补齐；
- 有权成员明确发起复核并说明原因。

旧评价保持原结论和输入引用，不覆盖为新结果。

### 8.2 排除治理活动的自动评价

默认抽样和风险触发的对象是生产工作。以下活动不自动进入同一抽样池：
- Evaluation Run；
- Benchmark / 回归实验 Run；
- Improvement Proposal 准备、知识整理和资产发布 Run；
- 由评价器自身触发的辅助 Run。

这些活动可以通过专门的维护者审计或评价器校准计划抽样复核，但该审计必须有独立预算、独立样本和明确停止条件，不能自动递归触发下一轮评价。

### 8.3 评价器校准独立于生产评分

评价器本身的质量通过固定的人工标注样本、已知结果集或定期复核来校准。不能仅用同一个 Model-based Evaluator 评价自己的历史评分，再把自评结果当作准确性证明。校准样本和 Rubric 版本变化时，保留原校准结论。

### 8.4 触发闭环的停止条件

一次评价触发链在以下任一情况结束：
- 已产生有效评价结论并回到原业务对象；
- 评价执行失败且达到重试上限；
- 证据不足且没有获准补证路径；
- 预算、授权或时间窗口耗尽；
- 目标版本被替代或请求被撤回。

评价产生 Finding 不会自动创建下一 Evaluation。是否升级为 Improvement Proposal 由维护者分诊；Benchmark 必须由提案显式启动；Benchmark 结果不会自动启动下一轮 Benchmark。

## 9. 评价策略的权威与版本

Evaluation Policy 是团队 / 项目配置中的版本化治理规则，不是新的任务对象或独立执行系统。

- **Team Policy**：定义团队强制门禁底线、可用评价器类别、团队资源上限和保留预算。
- **Project Policy**：在团队底线之上配置风险条件、抽样分层、周期预算和本项目允许的评价器。
- **Work Agreement**：可为具体 Issue / SOP 节点增加更严格的门禁、评价目标和预算，不得降低上层强制要求。
- **Asset Maintainer**：维护 Scorer / Rubric 版本及其适用范围，不自行决定项目抽样预算。
- **Evaluation Requester**：可以在授权内请求评价，但不能通过请求绕过策略、权限或预算。

每份 Evaluation 固定实际采用的 Team / Project Policy 版本、Work Agreement 版本、触发类型与原因、评价器版本、输入快照、预算预留 / 实际消耗和结果。策略升级只影响之后新触发的评价；已 Requested / Running 的评价按启动时固定的策略与输入处理，除非发生权限撤回或安全停用。

## 10. 默认运行策略与渐进启用

首期建议采用以下默认策略，后续依据真实数据校准，而不是把它固化成系统常量：

1. 必需的确定性检查按工作约定全覆盖；高风险门禁不得抽样。
2. 普通生产 Run 不做全量模型评分，先使用分层抽样和异常触发。
3. 对同一 Issue / Candidate，默认最多一次常规事后模型评价；只有新证据、新版本或明确复核理由才追加评价。
4. 瞬时失败的自动重试默认最多一次；评价器配置错误、权限失败和质量不通过不自动重试。
5. Benchmark 由 Improvement Proposal 明确发起，事先固定样本、重复次数、评价器和预算；不因 Benchmark 结论自动再开 Benchmark。
6. 评价预算与生产预算分开；强制门禁预留资源，抽样预算耗尽时停止抽样。
7. 治理活动不进入生产工作抽样池；评价器校准按独立计划进行。
8. 未知 Credits / Token / 费用保持未知，以 Run 数、时长和并发等已知上限控制资源。

渐进启用顺序：
- **阶段 A：确定性门禁与记录**。先对已有可回读的测试、Artifact 契约和验收要求执行，不启动普遍模型评分。
- **阶段 B：有限分层抽样**。选取少量代表性生产工作，验证评价器成本、证据充分性、发现率和误报。
- **阶段 C：风险触发**。在真实样本证明规则有效后启用异常触发，明确误报和漏报复核。
- **阶段 D：Benchmark 配额**。只为有明确跨工作收益的提案分配实验额度，保留团队强制门禁资源。
- **阶段 E：周期校准**。维护者根据评价覆盖、有效 Finding、人工推翻率、单次成本和后续改进收益调整策略。

## 11. D11 完成标准

1. 必需门禁、风险触发、分层抽样和人工发起的入口有明确边界。
2. 风险分层不能由单一模型判断决定，Unknown 不默认低风险。
3. 确定性检查优先于模型评价；Human Review 的决定权明确。
4. 评价目标必须稳定并固定版本；运行中观察不冒充终态评价。
5. 单次、单 Issue、Project 周期和 Team 周期均有资源上限。
6. 多种原生计量单位分开预算，缺失用量保持 Unknown。
7. 预算耗尽、证据不足、评价失败和质量不通过分别处理。
8. 评价重试有界，重复触发幂等，旧结果不被覆盖。
9. Evaluation / Benchmark / Improvement Run 默认排除于生产抽样，防止递归。
10. Team / Project Policy、Work Agreement、Scorer 维护者的权责和版本固定清楚。
11. 默认策略可以渐进启用和按真实数据校准，不强制所有工作都接受模型评分。
12. 全部评价仍沿现有 Multica Run 执行，不增加平行调度或成本账本。

## 12. 后续实现前置

D11 完成后仍需在技术方案中确定：
- Team / Project Policy 在现有 Project 配置和资产版本中的具体承载方式；
- 稳定抽样身份与幂等键如何映射到现有 Evaluation / Run 关联；
- 原生多单位预算预留与结算的并发写入边界；
- Evaluation Requested 在预算等待、权限撤回和策略变更时的恢复规则；
- Benchmark 样本存储、访问授权和复现实验环境；
- 校准样本维护、人工标注和 Scorer 版本治理的最小操作流程。

这些是现有对象和写入边界的技术承载问题，不要求增加新的 Run 系统或常驻协调服务。
