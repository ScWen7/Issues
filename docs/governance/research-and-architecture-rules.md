# AgentPlatform 研究与架构推进规则

本文是后续 AgentPlatform 研究、设计和远端产物维护的工作规则。它约束研究方法与架构推进方式，不是产品功能清单，也不替代各专题的正式设计。

## 1. 始终从整体产品目标出发

AgentPlatform 的目标是：成员把工作交给平台后，Main Bot 能利用团队获准的 Agent、本地 Runtime、项目上下文和成熟工作方法，自主组织协作、持续推进并交付结果。

研究任何局部机制前，先说明它在完整工作链中的位置、解决的问题，以及对其他职责层和专题的影响。局部技术问题不得反过来主导整体产品架构。

## 2. 以完整工作链组织研究

始终围绕以下链路审视方案：

成员提出目标并保留业务责任 → Main Bot 理解与规划 → 自主执行或组织 Agent 协作 → 使用项目能力和工作方法 → 通过成员本地 Runtime 完成执行 → 消费结果与证据 → 向责任方交付 → 评价和经验改进。

研究可以深入某一环节，但结论必须回到整条链路检查，不得把某一机制孤立建设成新的子系统。

## 3. 保持职责与事实归属清晰

- Issue 是业务工作和责任的权威归属。
- Issue Owner 对目标、授权范围、业务决定和最终验收负责。
- Main Bot 是 Issue 级智能协调者，负责理解、规划、组织、委派、选择方法、持续推进和交付汇总。
- Worker Agent 是受托执行主体；其权限和交付范围来自有效授权。
- Runtime 是本地执行资源，不是业务负责人或协调者。
- Run 记录真实受管执行；Session 只提供宿主连续性。
- SOP 是可复用工作方法，不是 Assignee、额外协调者或所有 Issue 的必经模式。
- 评价结论、交付证据和业务验收决定不能互相替代。

一个 Issue 可以由 Member 负责，同时委托 Main Bot 协调；Owner、Coordinator、Executor 可以是不同主体。

## 4. Main Bot 是统一协调主体，不叠加调度层

Main Bot 是当前产品目标中的 Issue 级主要协调者。它可以直接执行、委派一个或多个 Agent、跨 Runtime 组织工作、选择或组合 SOP，并根据结果重新规划。

不得在 Main Bot 下面为了沿用旧概念而强制增加 Squad Leader 或第二层总协调者。Multica 现有 Squad Leader 的 Issue 触发、唤醒、任务领取和回报能力可以被改造复用；其固定 Squad Roster、必须委派、不得直接执行等约束不能未经论证地继承。

Squad 是否保留为资源组织概念，不能预设为协作主线必需对象。不得为保留 Squad 而制造另一层调度权。

## 5. 优先复用 Multica，不复制控制平面

先核对 Multica 当前真实源码、数据模型、事务、派发、Daemon、Runtime、Session、事件和恢复能力，再判断缺口。

优先沿用原生 Issue、Task / Run、Agent、Runtime、Daemon、Backend、评论、Artifact 和权限机制。只有明确证明原生能力无法表达必要业务事实时，才提出最小扩展。

不得未经必要性论证新增：
- 第二套 Issue 或业务 Task 系统；
- 平行 Run / Runtime 控制平面；
- 中央常驻 Orchestrator 或 Coordinator Pool；
- 重复维护同一业务状态的状态库；
- 为潜在未来需求提前建设的复杂多活、热迁移或基础设施。

## 6. 研究深度服从架构问题，不钻牛角尖

源码级研究用于回答架构问题，不以分析函数数量或技术细节深度作为成果。

每次深入源码前明确：
1. 当前要回答的架构问题；
2. 这个问题对产品主线的影响；
3. 需要核实的最小源码范围；
4. 研究结果可能改变什么设计决定。

达到足以支持架构判断的证据后停止扩展。局部边缘情况放入未决清单，不得让其吞噬主线研究。

## 7. 控制机制数量与复杂度

提出新机制前，先说明：
- 现有哪个对象或机制无法承担；
- 真实场景为何要求新增；
- 最小可行替代是什么；
- 新机制会增加哪些状态、权限、维护和故障复杂度；
- 能否通过现有 Issue、Run、事件、评论、交付或授权表达。

优先选择概念少、职责明确、能渐进落地的方案。不要因为技术上可做就增加抽象层。

## 8. 区分事实、推断、建议与决策

所有研究结论明确区分：
- 上游源码已实现的事实；
- 从源码推导出的能力或限制；
- AgentPlatform 的设计建议；
- 已经确认的架构决策；
- 尚未解决的问题。

不得将研究建议写成已经冻结的产品设计，不得将上游项目的愿景描述成已实现能力。

## 9. 分阶段推进，但每阶段必须形成整体价值

每一阶段应有明确问题、边界、产物和退出条件。完成后检查：
- 是否解决了本阶段问题；
- 是否与现有对象模型、生命周期、状态机和跨层契约一致；
- 是否引入重复职责；
- 是否影响其他专题；
- 下一阶段是否真的依赖本阶段结论。

不为保持推进节奏而人为拆分无意义阶段，也不在关键边界未清楚时提前进入 API、数据库或部署设计。

## 10. 远端文档治理

- 正式架构、专题研究、源码证据和验证记录分开维护。
- 研究文档记录事实、推理和待决问题；只有经过整体一致性审查的结论才进入正式架构基线。
- 不写“之前是什么、现在改成什么”的历史叠加式正文；正式设计直接描述当前真实方向。
- 不重复创建已有概念或文档，不在多个入口复制不同版本的规则。
- 每次远端写入后核对文件、链接、分支差异和引用。
- 不因研究产出增加而自动合并架构基线；保持评审与决策边界。

## 11. 每次研究的交付要求

最终结果必须简明回答：
1. 本次研究在整体架构中的位置；
2. 已确认的事实与关键结论；
3. 对现有模块、对象和生命周期的影响；
4. 推荐的最简方案及理由；
5. 尚未解决且真正阻碍下一步的问题；
6. 下一阶段应推进什么，以及为什么。

核心检验标准：**研究是否让 AgentPlatform 的主线更清楚、系统更简单、方案更能落地，而不是让架构图和机制数量不断增加。**
