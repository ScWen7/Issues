# AgentPlatform 产品定位与现有架构审计

## 1. 审计范围与结论

审计对象为 `design/system-architecture-convergence` 分支中的产品总览、整体系统架构、核心对象、能力与上下文、团队 Wiki、代码 Wiki、SOP、执行平面、成本质量改进、D5–D7、VS0–VS5、研究治理及相关研究材料。

当前设计已经积累了大量有效的协作执行机制和跨层一致性约束，但产品叙事和能力组织仍以 Issue 协作、Main Bot 与 Agent 执行为中心。团队知识主要被放在“方法与上下文”或可选 Wiki 入口中；知识的采集、证据化、提炼、发布、检索、复用和效果反馈没有作为一条完整的基础能力主线。Harness 的持续改进已有较完整的候选、Benchmark、Release、Adoption 和效果观察机制，但与知识生命周期之间的关系尚未闭合。

**结论：保留 AgentPlatform 项目与已验证的底层机制，重新建立产品基线并按新目标融合现有架构。无需另起产品，也不应直接按现有模块边界继续扩展。**

## 2. 已有设计中应继承的能力

| 已有设计 | 可继承的机制 | 在总体产品中的位置 |

## 3. 需要重新定位或融合的部分

### 3.1 产品主线

当前总览以 Issue 协作作为产品核心，但没有把“团队知识进入研发并由研发反哺知识”作为基础价值。新主线应同时表达知识基础、产研工作、Harness 管控和证据驱动的持续改进。Issue 仍是工作归属，不等于产品价值本身。

### 3.2 能力与上下文

现有 C 模块把 Rule、Skill、Playbook、SOP、知识、工具配置及上下文准备放在同一能力与上下文域中，容易让知识退化为执行输入的一种资产。应区分：
- 知识资产：描述业务事实、项目事实、技术依据、历史决策和实践经验。
- Harness 资产：规定研发方法、约束、流程和验证标准。
- 工作上下文：当前 Issue 的目标、决定、讨论、交付和待办。
- 执行资源：Agent、Runtime、工具和宿主 Session。

四者通过有来源、有版本、有权限的引用协作，不合并成一个资产仓库。

### 3.3 团队知识管理

现有 `team-project-wiki.md` 定义了团队 Wiki、项目资料、来源刷新、引用和权限边界；`03b-capability-governance.md` 也描述了从项目证据提炼团队经验。但尚缺少作为一条端到端产品能力的完整设计，特别是：
- 不同来源的接入、同步、解析、结构保留和处理状态。
- 原始材料、解析证据、候选知识、正式知识之间的关系。
- 批量资料处理、增量更新、重复与冲突识别、知识失效和撤回。
- 知识分块与章节位置、来源修订、权限继承和可追溯引用。
- 检索排序、适用性判断、有效性过滤和面向 Issue / 阶段的知识交付。
- 研发过程自动发现知识候选、证据核验、发布治理和后续使用反馈。

因此，当前 Wiki 设计是入口和部分治理规则，不足以代表完整的团队知识管理能力。

### 3.4 Harness 与持续改进

D7 已区分当前工作修正、单次执行评价、跨工作持续改进；定义 Finding、Proposal、Candidate Revision、Benchmark、Release、Project Adoption 和真实效果观察。这些机制应继承。

需要补齐的是 Finding 的分类和路由：哪些问题形成知识候选，哪些进入 Harness 候选，哪些属于项目配置或工具问题；知识发布与 Harness 发布分别由谁负责；两类改进如何引用同一证据而保持独立生命周期。

### 3.5 Agent 协作与 Runtime

Main Bot、Worker、SOP、Multica 原生 Run 和本地 Runtime 的机制应保留，但不再以 Agent 组织模型作为顶层产品结构。Agent 协作复杂度必须由真实研发工作需要驱动。既有 Main Bot 授权、一次性协助、Squad 非必选、成员保留业务总责等已确认边界不应反复打开。

## 4. 当前设计的主要结构性问题

1. **知识基础地位不足**：知识被放在能力上下文中，Wiki 被描述为按需扩展；没有体现知识先于研发准备、贯穿研发并反哺下一轮的产品责任。
2. **知识与 Harness 边界不清**：知识和规则、Skill、Playbook、SOP 混在同一能力资产域，后续容易出现知识库与 Harness 各自维护重复内容。
3. **双飞轮连接不完整**：D7 偏重 Harness / 方法资产的持续改进，没有把知识生命周期纳入同一证据反馈体系。
4. **模块划分先于产品能力闭合**：A–I 九个模块、五层职责、多个 D / VS / E 阶段和大量细粒度对象同时出现，读者难以区分产品能力、业务对象、技术承载与工程阶段。
5. **技术细节过早进入产品总览**：派发幂等、Candidate Manifest、预算预留、Evaluation Task 隔离等细节有其必要性，但不应决定产品顶层结构，也不应在产品定位阶段推动 Schema / API 设计。
6. **工作台容易被误认为产品本体**：H 模块是查询和操作入口，不是团队研发能力本身。页面与视图应从用户工作和决策出发，而非围绕内部模块铺设。

## 5. 现有专题的处理建议

| 现有专题 / 设计 | 处理 | 说明 |
|---|---|---|
| Issue、生命周期、责任和交接 | 继承并收敛 | 保留 Multica 单一工作主线及既有授权边界 |
| Main Bot / Worker / Squad | 继承机制，降为执行组织方式 | 不作为产品一级能力中心，不重开已定角色问题 |
| SOP / Project Workflow | 继承并分清职责 | 项目阶段与责任交接不同于 SOP 内部节点 |
| Runtime / Host Adapter / Observation | 继承 | 按实际宿主能力接入，未知数据保持未知 |
| D5 派发与恢复 | 继承为工作可靠性契约 | 不复制 Multica 控制平面 |
| D6 交付与验收 | 继承为交付质量契约 | 保留 Candidate、Evidence、Acceptance 的事实边界 |
| D7 / D11 / VS3–VS4 | 继承机制，扩展知识改进路径 | 将知识提炼、发布、采用与 Harness 改进并列治理 |
| Team Wiki / 项目资料 | 提升并深化 | 形成来源接入、证据处理、知识编译、检索复用和有效性治理 |
| Project Code Wiki | 独立扩展 | 保留独立产品边界，不作为当前主线前置 |
| A–I 模块与五层架构 | 暂不冻结 | 依据新的能力域与对象关系重新映射，避免为兼容旧模块而保留多余边界 |
| E0–E4 工程阶段 | 暂缓推进 | 产品与业务架构融合前，不进入 Schema、API、部署或实现切片 |

## 6. 新架构必须回答的融合问题

1. 知识来源、原始资料、解析证据、候选知识、正式知识、知识修订和失效关系如何形成完整生命周期？
2. 团队知识、项目资料、代码知识和 Issue 工作上下文如何区分，又如何按权限组合进入一次研发？
3. 一次研发中哪些事实可自动提炼，哪些必须核验；如何防止对话猜测、过期文档和错误归因进入正式知识？
4. 知识与 Harness 如何共享来源、证据、版本和评测样本，同时保持各自的发布权责？
5. 研发执行证据如何同时支持交付验收、知识贡献、Harness Evaluation 和成本分析，而不复制权威记录？
6. Finding 如何区分知识缺失 / 错误、Harness 规则缺陷、流程设计缺陷、Agent 能力限制、Runtime / 工具故障和业务输入问题？
7. 知识和 Harness 的候选如何各自验证、发布、采用、观察效果和撤回？
8. 普通 Issue 如何低摩擦消费知识与 Harness，且不被强制套入复杂 SOP 或 Evaluation？
9. 如何从一个真实研发闭环逐步建设能力，而不是一次性实现所有模块？

## 7. 本阶段范围与下一步

本阶段只完成产品定位、现状审计和总体业务架构融合，不设计数据库 Schema、API、消息队列、部署拓扑或原型。

下一步按以下顺序推进：

1. 建立统一业务概念与事实归属：知识、Harness、工作上下文、执行资源、交付证据、评价与改进各自维护什么。
2. 设计团队知识完整生命周期及其与 Issue、Run 的关系，优先打通“来源 → 证据 → 候选知识 → 正式知识 → 检索复用 → 使用反馈”。
3. 将 D7 的 Finding 路由扩展为知识改进与 Harness 改进两条路径，定义共同证据和独立治理边界。
4. 重新映射现有五层与 A–I 模块，合并重复职责、降低实现复杂度。
5. 用一条通用研发工作链验证知识、Harness、执行和改进能否形成整体闭环。

本审计是架构融合工作的依据，不把历史讨论过程写入正式产品设计。
