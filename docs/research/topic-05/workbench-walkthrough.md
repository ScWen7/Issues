## 甲交回补丁，乙接着处理

打开原型，将演练身份切到甲，在项目列表进入甲负责的「导出结果缺少末页订单」。下面两次演练使用同一个 Issue、同一个合成基准 `orders@71c2a90` 和同一文件 `last-page.patch` v1。完成一条路径后重置原型，再从另一入口开始。

| 要观察哪一步 | 从本地提交 | 从平台请 Agent 协助 |
|---|---|---|
| 甲交了什么 | 甲点「从本地提交」，分别选择补丁与补交说明。只选补丁时，乙可打开 v1，交付详情仅呈现该版本及其依据。只选说明时，乙能看到甲披露的缺项，甲可随后补交 v1。两个选项都取消时，提交不可用。 | 甲点「在评论中请 Agent 协助」，再在演练条件中「载入 Agent 的执行回报」。v1 此时关联到一份 Run 回报，当前负责人仍为甲。 |
| 乙明天打开什么 | 切换到乙，回到原 Issue，查看带有甲署名的交付。若甲已附 v1，乙可展开补丁并下载具体文件。 | 切换到乙，在原 Issue 查看执行交回的交付和 Run。甲另行点「发送补交说明」后，乙能看到甲所披露的缺项。 |
| 末页已检查到什么程度 | 甲交了 v1，未附检查记录。乙可以读补丁，仍需核对实际导出的末页。 | 该 Run 的交付回执引用了 v1，未附检查报告。末页是否完整仍待核对。 |
| 哪部分已经可以使用 | 乙可从 v1 查看已分享的补丁。具备工程仓读权时，以所注基准准备自己的工作副本。只有甲声明还有一处修改待补时，乙才知道这项缺口及补交人。 | 基准、已交文件与待补部分逐项阅读。Run 回报只用于说明本次执行。甲在自己机器上尚未交出的修改仍由甲补交。 |

甲点「评论 @乙 查看」后，乙从提及通知回到原 Issue，甲仍负责。若甲点「将 Issue 改派给乙」，乙从指派通知回到同一份 v1 接着处理，补交原机改动的人仍为甲。切换到乙缺少仓库读权的演练条件，乙仍可查看和下载已共享的补丁，取得代码基准的回报动作暂不可用。本项的完成方式见 Issue 的工作约定。[产品路径](../../architecture/05-unified-workbench.md) · [原生评论、指派与交付](../05-source-evidence.md)

这组操作覆盖离线原型中的页面和角色状态。Run 回报、补丁内容和仓库读权均由固定数据模拟。进行中从下一执行段关联 Issue 的入口、宿主权限及取证依据见[宿主能力矩阵](../../architecture/execution-capabilities.md)。

## 订单从提出到交付

林提出“导出当前筛选条件下所有可见订单”，担任人工总责和指定验收人。首轮工作约定 D1 规定 XLSX、最多 5,000 条，超限提示缩小范围。实施由交付 Squad 负责，周提供 Leader 使用的 Runtime，甲、乙、丙分别承担后端、前端、独立核验职责。案例选用 Squad 自主规划、验证子 Issue 调用局部 SOP 的路径。

| 时点和操作者 | 打开哪里、看到什么 | 可做的动作、动作落在哪里 |
|---|---|---|
| 提出 · 林 | 在项目中建父 Issue，写明目标、数量上限、验收人，选交付 Squad；详情能同时看见“当前由交付 Squad 处理”和“林负责最终验收” | 创建后，具备资源与授权的 Leader 在父项分析；林答复具体业务问题并确认 D1。更换当前处理人后，仍能找到作出业务取舍的人 |
| 分工 · Leader、甲、乙 | 父项中并列前端与后端子项，可分别进入查看代码和自检。集成和验证行显示各自尚缺的前置交付 | Leader 只为需要独立交付的工作建立子 Issue。前后端分别开工；集成等候两份交付。协调记录保留在父项，执行记录跟随各自 Run |
| 变更 · 林、受影响的执行者 | 林在原 Issue 确认 D2，增加付款时间，未付款留空，使用上海时区。受影响的开发、验证工作可辨认本次要求和此前 D1 | 开发和验证引用同一决定并取得 D2 的项目材料。成员可展开查看哪些版本实际投递、加载或仍缺证据。私人会话仅共享成员选定且获准的内容 |
| 核验失败 · 丙、Leader | 从验证子项打开 C1 的报告。东区账号的文件含西区订单，A2 权限失败，A3 金额与付款时间通过。父项能显示“需要修复订单可见范围”并链接到该报告 | 丙交回失败报告；Leader 重开原后端子项，集成和复验等候修复。保留无关前端交付。一次“检查工作已完成”仍可产出需要返工的业务结论 |
| 复验 · 甲、集成人、丙 | 后端提交修复，原集成子项形成并审查 C2，丙在原验证子项发起针对 C2 的后继局部 SOP。可同时查看 C1 失败与 C2 按 D2 重验的结果 | C2 的报告归 C2 本轮，旧报告重发只定位到原记录。C2 的 A2、A3 均通过；其余验收项须取得各自证据。完整 SOP 的路径只改变内部托管与交接，仍引用同一候选与父项验收 |
| 等待补证 · 林、丙 | **仅装入仓库现有两份报告时**，C2 显示 A2/A3 的已知结果。A1 分页筛选、A4 数量边界、A5 页面表现、A6 候选与 UAT 一致性，均列出待补证据 | 林可查看两版差异或说明缺项；由实际责任人补交相应候选的获准材料。通知直达父项待决事项，成员无需在通知页另填一次工作结果 |
| 最终接受 · 林 | **在完整演练中**，假定已取得当前 C2 的其他必需核验材料及获准 UAT 条件。Squad 提交交付并按工作流将父项交给林。林进入对应该候选的 UAT，实际操作并读取导出文件 | 林在原父项对 C2 / D2 / A1–A6 明确接受或列出缺口退回。迟到的 C1 决定保留原作用范围。打开通知、评论同意一般建议、核验通过或 PR 合并，各自只产生对应事实。最终接受及完成入口一致性仍待真实集成 |
| 交付之后 · 团队维护者 | 从订单查看返工原因、已知用量和缺失范围，进一步进入与 C1/C2 相关的改进提案 | 维护者可提议补充“按角色核验导出范围”。候选知识或 Rule/SOP 变更按来源授权、实际依赖组合验证和审核发布；后续工作采用并观察效果。评价和 Benchmark 的运行费用归其活动。此订单的未采集费用显示未知，独立 CodeBuddy 协议探针的 0.69 Credits 仍归探针 |

## 轻量修改只需一个 Issue

成员已有项目权限、可用且获准的 Runtime 和 Agent，项目有明确低风险完成约定，按钮位置、目标文案和验证方式均已知。成员创建“将导出按钮改为‘批量导出’，并检查实际显示”，选择现有执行安排并提交。Agent 在本 Issue 的 Run 留下修改与显示检查。成员从结果打开可核对的实际显示并接受。两次业务提交分别是“创建并开始”和“查看结果后接受”，导航与点击次数仍待产品实测。

若成员自行修改，同一 Issue 可直接记录变更与核验。若原页面存在两个同名按钮，执行者在 Issue 中向提出人澄清具体位置。该问题只增加一次必要的业务答复。此对照要检查创建时能否复用已有项目、权限与安排，以及接受时能否直接使用原回执。[专题一的轻量路径](../../architecture/01-unified-work-lifecycle.md#125-最小路径修改导出按钮文案)

## 两个 Issue 竞争资源，随后 Leader 离线

设“订单批量导出”和同项目的另一项调查共用一台只有一个可用执行槽位的 Runtime。先让订单协调占用该槽位，前后端独立执行使用各自已授权机器。这个设置用于检验项目视图；如底座没有暴露可归属的占用者或可靠连接信息，页面应展示最近可核对的事件及“原因待确认”。其他私有工作的详情受原项目可见范围约束。

| 变化 | 项目列表与 Issue 应给出的判断 | 人的动作与继续条件 |
|---|---|---|
| 调查具备输入和授权，暂未获得槽位 | 调查显示“等待可用 Runtime”，可查看本事项的安排。订单的集成子项则显示“等待前后端交付” | 项目有权成员可调整优先级；原运行继续，实际排队和领取由 Multica 管理。领取、准备、Start 分别保留回执 |
| 周的机器断联 | 订单父项仍可读写。Leader 新一轮协调等待已授权资源。已有独立前后端 Run 在其他在线机器上可继续；失联机器上在途进程的实际结果等待核对 | 有权限的成员可在中心补充决定、提交现有交付、等待重连，或在父项申请或执行明确转交。机器所有者确认资源使用范围；业务总责人、当前负责人、资源提供者各按原职责行动 |
| 明确接管后，旧机重连 | 原工作约定、已接纳交付、待处理问题及最近的可靠执行回执可追溯。旧回报显示生产者、候选和原轮次 | 接管者核对在途副作用、凭自己的权限取得获准材料并执行新安排。旧回报不能再次驱动当前交接。原 Leader 恢复后按当前负责人及明确交还决定继续 |
| 资源已释放，但工作仍未运行 | 按当前事实区分待领取、准备中、权限已撤回、等待人工答复。只有对应的 Start 事实成立才显示已开工 | 恢复前复查当前授权、候选和轮次；待决定问题链接到原 Issue。若两个工作仍同等紧急，由现有项目责任人取舍 |

这组界面交互属于本轮推演。已有独立研究验证过任务凭据的作用域、撤回共享后的权限回执和跨机交接中迟到结果的归属，真实双 Issue 排队、Leader 接管及页面反馈仍待融合集成。[多 Issue 调度与接管](../../architecture/01-unified-work-lifecycle.md#10-多-issue-并行与异常接续) · [固定 Runtime 共享实验](../topic-03a/shared-runtime-identity.md) · [跨机接续实验](../topic-03a/machine-handoff.md)

## 场景覆盖

订单样本区分执行结束、检查结果和具名接受，项目样本分别呈现资源等待、前置交付缺失和待人决定。离线原型使用固定数据，测试范围限于页面状态和局部交互。真实成员的寻找时间、服务端完成入口的权限与版本校验、多客户端写入及跨机通知恢复都未由这组样本测量。
