# AgentPlatform · 双飞轮端到端场景验收

## 1. 验收目标与结论

本次验收以五个核心业务能力域为产品架构主体，使用两条端到端场景检查业务流程、对象归属、权责、证据、生命周期和反馈是否闭合：
- **场景 A：一项研发工作从需求进入到交付验收，再到经验沉淀。**
- **场景 B：研发中发现知识 / Harness 问题，形成改进、验证、发布、采用，并在下一轮研发观察效果。**

本次是架构级桌面验收，依据现有产品基线、统一对象模型、生命周期、跨层契约、知识管理、SOP、执行、D6、D7、D11 和工作台专题；不是已经完成真实运行环境的端到端工程测试。

**总体结论：两条链的主干成立，核心对象和责任边界基本闭合；但不能把所有步骤都视为自动化或强制流程。场景 A 可以作为首期主线，场景 B 是在基础证据、知识治理和 Harness 发布能力具备后逐步启用的改进闭环。当前不需要新增核心业务能力域或平行对象系统。**

## 2. 验收采用的产品边界

产品主体只有五个核心业务能力域：
1. 团队知识管理；
2. 产研工作与流程协作；
3. Engineering Harness 治理；
4. 执行与交付证据；
5. Evaluation、度量与持续改进。

组织身份、权限、项目配置和资产采用是各能力必须遵守的治理机制；工作台是用户入口；来源连接器与宿主适配器是接入实现。它们不构成额外业务能力域，也不要求成为独立产品或服务。

## 3. 场景 A：完整研发交付

### 3.1 场景前提

团队收到一项新需求，已有 PRD 或需求材料保存在权威资料来源；项目有既有代码仓、工程约束和可选 Harness 资产；成员使用不同本地 Agent 或人工参与研发。Issue 是本项工作的业务归属。

### 3.2 端到端流程与验收

| 阶段 | 业务动作 | 权威对象 / 能力 | 必须留下的事实 | 验收结果 |
|---|---|---|---|---|
| 1. 需求进入 | 从权威来源发现或提交需求资料，取得具体修订 | 来源系统；知识管理 | Source Item / Revision、取得状态、来源读权、修订和位置 | **通过**：上传或同步不等于正式知识；原文权威仍在来源系统 |
| 2. 需求理解 | 按项目和当前读权取得需求内容，必要时形成项目知识或 Issue 背景 | 知识管理；Issue | 需求证据、Issue 目标、范围、Work Agreement | **通过**：PRD 原文、提炼结论和当前工作约定区分；有权成员确认工作目标 |
| 3. 研发准备 | 从团队 / 项目知识检索历史方案、技术约束和踩坑经验；识别代码基准 | 知识管理；执行与交付证据 | Knowledge Revision、Evidence 引用、适用范围、代码仓与 commit 基准 | **通过**：按权限和相关性提供知识，不把全库或无关资料塞进上下文 |
| 4. 方法选择 | 依据工作类型选择必需 Rule、建议 Skill / Playbook，判断是否需要 SOP | Harness 治理；Issue | Harness Release、项目采用范围、本项固定版本、必需 / 可选区分 | **通过**：普通任务不强制启动 SOP；方法版本固定，不随默认配置静默换版 |
| 5. 工作组织 | 明确业务总责；选择成员自主执行、一次性 Agent 协助、持续 Main Bot 委托或 SOP | 产研工作与流程协作 | Work Agreement、Assignee、Delegation / 授权代际；必要时 SOP Execution | **通过**：一次 @Agent 不等于持续授权；Main Bot 不接管成员业务总责 |
| 6. 执行 | 通过成员本地宿主执行，必要时由平台受管派发 | Multica 原生执行；执行与交付证据 | Task / Run、Runtime、Session、Observation、原生 Usage；未知保持 Unknown | **通过**：中心派发不等于宿主启动；不同宿主的证据覆盖如实呈现 |
| 7. 研发过程交接 | 设计、实施、测试之间按工作需要交接结果或责任；必要时调用稳定 SOP | Issue / Project Workflow / SOP Execution | 阶段交接、节点激活、输入版本、Run 来源、决定和待办 | **有条件通过**：Project Workflow 管阶段 / 责任；SOP 管受托节点；探索性设计不强制变成 SOP |
| 8. 交付形成 | 生产代码、文档、测试报告等制品，明确本次送审组合 | 执行与交付证据 | Artifact、Candidate Manifest、Work Agreement 版本、证据定位 | **通过**：Run 成功不等于交付合格；文件最新版本不等于当前 Candidate |
| 9. 质量核验 | 执行工作约定要求的确定性检查；按策略触发独立 Evaluation | Harness；执行与交付证据；Evaluation | 检查结果、Evidence、Evaluation 输入版本和评价器版本 | **通过**：确定性门禁优先；Evaluation 不替代业务验收；预算不足不静默放行强制门禁 |
| 10. 业务验收 | 有权成员接受、部分接受、退回或要求补充 | Issue；Candidate / Acceptance Decision | 决定者权限、Candidate 身份、标准版本、Evidence、剩余责任 | **通过**：验收是 Issue 业务决定；评价通过、PR 合并或 Run 成功不能替代 |
| 11. 经验沉淀 | 从已确认决策、交付、故障、评审和测试中识别可复用经验 | 知识管理 | 候选知识、源 Issue / Run / Artifact / Evidence、适用范围和许可 | **有条件通过**：只提炼有证据和复用价值的内容；当前 Issue 完成不等待知识审批 |
| 12. 下一轮复用 | 后续 Issue 按范围、权限、版本检索并消费新知识 | 知识管理；Issue；Harness | Knowledge Release、选择 / 投递 / 加载 / 使用证据和反馈 | **通过**：知识发布不等于项目采用，采用不等于实际使用 |

### 3.3 场景 A 发现的设计约束

1. **需求文档不自动等于知识。** PRD 可作为本项工作的来源证据；只有可复用的业务事实、决策或经验才形成 Knowledge Revision。当前需求目标仍由 Issue / Work Agreement 确认。
2. **设计阶段不必强制套 SOP。** 复杂调查、方案比较和架构推理可以由负责人和 Agent 自主完成；稳定重复的实施 / 验证环节才逐步固化为 Playbook 或 SOP。
3. **质量门禁与评价必须分开。** 可确定性验证的要求应优先由 Script / Test 执行；模型评价适合判断复杂质量维度，不应成为唯一验收依据。
4. **知识沉淀不是交付门禁。** 经验提炼可以与当前交付并行，候选知识的核验和发布不阻塞 Issue 的业务完成。
5. **本地 Agent 的观测存在能力差异。** 未共享的 Session、工具活动和宿主用量不能由平台推断；无法观察的步骤保持 Unknown。

### 3.4 场景 A 结论

**通过，作为首期产品主线。** 需要优先落地的最小闭环是：Issue / Work Agreement → 权限正确的知识与 Harness 上下文 → 成员 / Agent 执行 → Artifact / Candidate / Evidence → 业务验收 → 有价值的知识候选。完整 SOP、模型评价和代码知识图谱按需启用。

## 4. 场景 B：知识与 Harness 自进化

### 4.1 场景前提

一次真实研发中，Agent 因知识过期、规范缺失或流程方法不适用而返工；执行、测试、评审和人工反馈留下证据。系统需要判断这是知识问题、Harness 问题、项目约定问题、Agent / Runtime 问题，还是证据不足。

### 4.2 端到端流程与验收

| 阶段 | 业务动作 | 权威对象 / 能力 | 必须留下的事实 | 验收结果 |
|---|---|---|---|---|
| 1. 发现信号 | 从返工、失败测试、人工纠正、Evaluation 或使用反馈发现异常 | Issue；执行与交付证据；Evaluation | 原始事件、Run / Candidate / Evidence、反馈主体与时间 | **通过**：主观反馈与宿主 / 测试事实分级，不混成同等证据 |
| 2. 形成 Finding | 对具体问题定位、影响和证据进行归纳 | Evaluation / 持续改进 | Finding、源 Issue / Run、证据引用、目标版本、可信度和缺项 | **通过**：证据不足时保留调查状态，不虚构根因 |
| 3. 根因分诊 | 判断问题属于知识缺失 / 过期、Harness 缺陷、项目约定、Runtime / Tool、Agent 能力或 Evaluation 失准 | Evaluation / 持续改进 | 分类依据、责任维护者、当前工作修正动作和跨工作改进价值 | **通过**：Finding 不默认进入 Harness；当前问题修复与跨工作改进可以并行 |
| 4A. 知识改进候选 | 补充或修订事实、经验、适用条件，核对来源和派生许可 | 团队知识管理 | Knowledge Item / Revision 候选、Evidence、来源版本、冲突和适用范围 | **通过**：知识维护者负责核验和发布，Agent 不自行升级强制规范 |
| 4B. Harness 改进候选 | 将已确认的实践或质量缺陷转成 Rule、Skill、Playbook、SOP、Script 或 Rubric 修改 | Harness 治理 | Harness Revision 候选、基线版本、目标行为、例外和回归要求 | **通过**：只有具备可执行 / 可验证定义时才转为 Harness；否则保留为知识 |
| 5. 候选验证 | 固定样本、基线、候选版本、评价标准和预算，执行对照 | Evaluation / 持续改进；Multica Run | Benchmark、Trial、输入快照、评价器版本、原生 Usage 和结果 | **有条件通过**：可比样本与硬门槛充分才形成 Passed；证据不足为 Inconclusive |
| 6. 审核与发布 | 对知识与 Harness 候选分别核验、批准和发布 | 知识管理；Harness 治理 | 各自维护者、审核决定、Knowledge / Harness Release | **通过**：两个发布过程独立；一个被拒不自动影响另一个 |
| 7. 项目采用 | 项目有权成员决定是否采用新版本、适用范围和在途处理 | 项目配置 / Adoption 治理 | Adoption 决定、版本、范围、生效条件、在途工作处理 | **通过**：Release 不自动改变项目采用；回退也是新决定 |
| 8. 下一轮消费 | 新 Issue 按权限和适用范围选择新知识与 Harness 版本 | 知识管理；Harness；Issue | Work / Run Asset Pin、ContextReceipt、宿主加载 / 使用证据 | **通过**：采用不等于使用，投递不等于加载，加载不等于结果正确 |
| 9. 真实效果观察 | 比较后续工作质量、返工、人工介入、周期和可用成本数据 | Evaluation / 持续改进 | 观察窗口、样本范围、对照基线、采用 / 使用证据、结果与不确定性 | **有条件通过**：Benchmark 通过不等于生产有效；样本不足不得宣称 Stable |
| 10. 再反馈或停止 | 判断是否继续改进、保持、回退或结束观察 | 知识 / Harness / 项目权威维护者 | 新 Finding、回退 Adoption、资产撤回 / 退役或停止原因 | **通过**：无有效新证据时停止循环，不自动递归触发评价或 Benchmark |

### 4.3 场景 B 发现的设计约束

1. **必须先修当前问题。** 当前 Issue 的返工不应等待跨工作提案、Benchmark 或资产发布。
2. **Finding 是问题记录，不是改进命令。** 它必须带证据和目标版本；分诊后才决定是否形成 Proposal。
3. **知识与 Harness 不能互相越权。** 知识维护者确认事实与经验；Harness 维护者确认方法和执行效果；项目成员决定采用。
4. **Benchmark 与生产效果是两种证据。** Benchmark 证明固定样本上的候选对照结果；生产观察证明实际采用后的效果，不能相互替代。
5. **成本统计必须保留原生单位和未知值。** 缺失 Credits / Token 不得估算成已知成本；治理 Run 与生产 Run 分开统计。
6. **防止自我进化递归。** Evaluation、Benchmark、知识整理和资产发布本身不进入生产自动抽样池；Finding 不自动创建下一轮 Evaluation。
7. **发布和采用由人或授权主体负责。** 自动提炼、自动评测可以减少工作量，但不能无授权地修改团队默认知识或 Harness。

### 4.4 场景 B 结论

**架构成立，但作为渐进式能力启用。** 首期先做到有证据的反馈和候选提炼；随后启用知识发布、Harness 回归验证、Benchmark、项目采用和生产效果观察。不得一开始就建设无人审核的自动自改系统。

## 5. 跨场景一致性检查

| 检查项 | 场景 A | 场景 B | 结论 |
|---|---|---|---|
| Issue 是否保持唯一工作归属 | 需求、责任和验收沿 Issue | Finding 可回指 Issue，当前修正仍回原 Issue | 通过 |
| Multica 是否保持唯一执行账本 | Run / Runtime / Usage 沿原生链 | Evaluation / Benchmark Run 仍标治理用途 | 通过 |
| 知识与 Harness 是否分开治理 | 分别选用并固定版本 | 分别形成候选、审核、发布和采用 | 通过 |
| Evidence 是否可共享 | 交付核验引用 Evidence | 知识和 Evaluation 复用同一 Evidence | 通过，需坚持单一权威记录 |
| 业务验收、评价和发布是否区分 | Issue 验收独立于 Evaluation | Benchmark、Release、Adoption、实际效果分离 | 通过 |
| 本地 Runtime 断联是否影响中心工作 | 其他成员可接续已共享工作事实 | 已记录 Finding 和提案仍可继续治理 | 通过，执行结果保留 Unknown |
| 权限撤回是否有传播边界 | 新的知识检索和投递按当前读权 | 受影响派生知识停止投递并复核 | 有条件通过，必须按来源 / 受众影响范围处理 |
| 普通研发是否被强制复杂化 | 不强制 SOP / 模型评价 | 改进链按价值与预算触发 | 通过 |

## 6. 场景验收发现的待补强事项

以下是专题契约需要明确或后续落地验证的事项，不构成新增业务能力域：

1. **需求来源与 Work Agreement 的确认边界**：明确 PRD / 资料是证据和背景，Issue 上有权成员确认的 Work Agreement 才是当前工作目标、范围和完成条件。已有契约具备基础，实施时需验证导入和变更路径不会绕过确认。
2. **知识消费回执的最小可观测性**：至少记录 Knowledge Revision 被选择和投递；宿主能提供时再记录加载 / 实际使用。不能支持逐项读取证明的宿主不应被判定为知识使用失败或成功。
3. **Evidence 的单一权威实现**：当前架构定义共享 Evidence，但来源 Anchor、宿主 Observation、交付 Evidence 的归属在实现切分时必须保持一个证据事实身份；不要由知识索引或 Evaluation 再复制一份。
4. **项目采用配置的范围与在途策略**：知识和 Harness Release 可以分别采用；项目配置变更必须明确新工作生效范围及在途工作是否保持原版本。
5. **知识权限撤回的在途处置**：区分停止新的检索 / 投递、已投递内容、已运行 Session 历史和历史审计证据；不能声称平台能删除成员本地已接收内容。
6. **生产效果的比较设计**：至少固定工作类型、风险层级、项目 / 版本、观察窗口和样本纳入规则；样本不可比时结论为 Inconclusive。

这些事项已有业务原则或部分专题规则，场景验收要求在后续契约审查与真实环境验证中落实，不在本阶段扩展成数据库 / API 设计。

## 7. 首期落地闭环与渐进顺序

### 首期必须跑通

1. Issue 建立 Work Agreement，保留业务总责和明确授权。
2. 能从已有权威来源按权限取得最相关的团队 / 项目资料，并固定来源版本。
3. 能按需选择团队 / 项目 Harness 的必需规则和建议方法。
4. 至少一种本地 Agent 宿主可沿 Multica 原生链执行；执行能力不足时允许成员人工补交结果。
5. 能固定 Artifact / Candidate，保留可核验的关键 Evidence，并由有权成员验收。
6. 能从当前工作形成有来源的知识候选，允许维护者核验后发布并在下一项工作检索。

### 后续逐步启用

- 多宿主统一观察和更完整的实际使用证据；
- 稳定重复流程的 SOP 自动推进与返工；
- 风险触发 / 分层抽样的 Model-based Evaluation；
- Harness Benchmark、回归样本积累和项目采用观察；
- 跨工作知识 / Harness 效果度量与自动候选发现。

## 8. 最终验收结论

场景 A 证明产品可以围绕 Issue 贯通知识、Harness、执行、交付和经验沉淀；场景 B 证明相同研发证据可以进入知识改进与 Harness 进化两条独立治理路径。两个飞轮共享工作和证据事实，不需要再造一套工作管理、执行、发布或评价系统。

**本轮架构级场景验收通过，带有明确的渐进启用条件。** 首期范围应聚焦场景 A 的低摩擦交付闭环，并确保知识候选能够回流；完整的自动评价、Benchmark 和生产效果闭环在基础数据可信后启用。

本报告不代表真实 Runtime / 宿主集成、知识检索质量、权限撤回传播或生产效果已经通过工程测试。上述事项需在对应实现阶段用真实环境和回执验证。
