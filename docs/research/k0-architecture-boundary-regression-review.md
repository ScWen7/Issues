# AgentPlatform · K0 第二轮架构边界回归审查

> 研究状态：完成  
> 审查分支：design/system-architecture-convergence  
> 审查对象：K0 第二轮补充调研、第一轮 K0 / K0-A 与当前 AgentPlatform 架构基线  
> 目标：纠正知识中心研究中的能力归属偏移，恢复从整体研发协作主线看待知识、项目资料、代码认知和工作上下文的边界。  
> 非目标：不重开产品定位，不新增一级能力域，不修改冻结的整体架构，不进入技术选型或实现设计。

## 1. 审查结论

用户指出的偏离成立。第二轮 K0 把项目资料、当前项目事实、模块地图、调用关系和动态项目认知视图放进了“团队知识中心”的产品设计范围，导致团队知识中心逐渐扩张成项目知识管理、代码 Wiki 和上下文编译平台的集合。

**需要修正的是第二轮研究的能力归属与产品边界，不是推翻 AgentPlatform 的整体架构。**

对照当前架构基线，AgentPlatform 已经明确：
- 团队知识管理、产研工作与流程协作、Engineering Harness、执行与交付证据、Evaluation / 度量 / 持续改进五个核心业务能力域；
- Issue 是研发工作的唯一业务归属；
- Project 是组织工作、项目成员、代码资源和项目配置的范围；
- 团队知识、项目知识和项目代码知识按适用范围、权限与代码基准区分；
- 团队 Wiki、项目资料和项目代码 Wiki 可以分别浏览或独立启用；
- Context Contract 是跨能力共享契约，当前工作按需取得团队知识、项目资料、代码依据和 Issue 上下文；
- 项目代码知识可独立扩展，不是当前主线成立的前置条件。

这些已有边界与用户本轮指出的方向一致。第二轮报告的问题是把“统一供给”误写成“统一归属”，把“可被上下文编译消费”误写成“应由团队知识中心维护”。

## 2. 核心纠偏：统一消费不等于统一维护

需要严格区分三个问题：

1. **内容属于谁、由谁维护？** 由其权威来源和业务责任决定。
2. **内容如何被发现和关联？** 可由平台统一导航、引用和权限检查。
3. **当前工作如何取得内容？** 通过 Context Contract 按 Issue 意图、项目、角色、代码基准和权限组合。

上下文编译是跨能力的协作与供给机制，不是团队知识中心独占的产品，也不是新增的第六个业务能力域。

## 3. 四类内容的正确归属

| 内容 | 权威归属 / 维护边界 | 平台中的作用 | 是否属于团队知识中心 |
|---|---|---|---|
| 跨项目可复用的业务规则、工程经验、通用技术实践、团队决策 | 团队知识资产，由对应领域维护者治理 | 被多个项目按范围复用 | 是 |
| 项目 PRD、业务说明、项目决策、接口约定、项目特有规则 | 飞书、Git、项目系统等原始来源；必要时形成项目范围知识，由项目责任人维护 | 项目上下文输入，可按需检索、引用或在项目知识视图浏览 | 不属于团队知识；可由知识管理能力按项目范围连接和治理 |
| 当前代码结构、模块地图、调用关系、API 实现、依赖与代码基准事实 | 项目代码仓和工具链；派生代码认知按仓库与 Commit 基准生成 | 为具体项目和 Issue 提供代码认知 | 不属于团队知识；项目代码知识是可选扩展 |
| 当前 Issue 目标、讨论、决定、责任、Run 和交付状态 | Multica Project / Issue / Run 及 AgentPlatform 对应工作、执行和交付权威对象 | 构成当前工作上下文 | 否 |

需要特别注意：
- 项目知识可以是长期可复用的项目资产，但其默认复用范围仍是该项目。
- 项目知识不因被平台连接、检索或生成摘要而成为团队知识。
- 只有项目经验经过来源派生许可、去敏、跨项目适用性重新核验和团队责任人确认后，才形成团队范围知识。
- 项目代码知识与团队通用技术经验不是同一种内容。代码地图和当前调用关系不是团队知识条目。

## 4. 团队知识中心应该管理什么

团队知识中心应收敛到团队范围的可复用知识资产和其治理：
- 跨项目可复用的事实、约定、技术经验和实践；
- 团队认可的架构原则、工程约束依据和通用业务知识；
- 从多个项目经验中提炼、经许可和独立核验的共性方法；
- 具有明确证据、适用范围、维护责任、有效状态和发布版本的知识主题及结论；
- 团队知识的来源追溯、冲突、撤回、复核和反馈。

K0-A 的粒度结论保持不变：以主题资产作为人工维护边界，以 Claim 作为检索和核验边界，以 Evidence 作为事实依据。它适用于团队正式知识，也可作为项目范围知识的内容组织参考，但不能据此把所有项目资料并入团队知识中心。

团队知识中心不承担：
- 项目 PRD、项目工程文档和代码仓的第二份权威副本；
- 每个项目的当前状态、模块清单和服务调用关系维护；
- 全仓代码摘要和完整代码图谱；
- Issue、Run、Session、交付和当前工作状态管理；
- 为所有项目持续生成、审核和发布项目 Wiki。

## 5. 项目资料与项目代码认知的正确位置

### 5.1 项目资料

项目资料是 Project 范围的上下文资源，不等于团队知识资产。
- 原始资料继续由飞书、Git、API 文档和项目系统等权威来源维护。
- 平台通过现有 Source Connection / Source Item / Revision 机制取得来源身份、修订、权限和可定位证据。
- 项目责任人可以维护项目范围的正式知识，例如项目业务规则、架构决策、接口约定和故障经验。
- 项目资料可以被 Issue 上下文按需引用，不要求全部编译成正式 Knowledge Item。
- 项目知识需要跨项目复用时，走既有派生授权和团队复审，不因统一检索而自动扩大作用域。

项目 Wiki / 项目知识视图可以作为独立产品能力设计和启用；不要求团队知识中心承担其全部编辑和运营职责。

### 5.2 当前项目事实与代码认知

项目概览、模块地图、当前调用关系、API 实现、数据结构和当前代码状态首先是项目 / 代码基准事实，不是团队知识。

| 内容 | 正确形态 |
|---|---|
| 项目目标和业务背景 | 项目权威资料或 Project 元数据 |
| 已批准的架构决策及理由 | 项目范围知识 / 决策资产，绑定证据和适用范围 |
| 当前仓库、目录、模块和入口 | 从代码仓与项目配置提取的当前事实 |
| 当前调用关系和依赖 | 在指定 Commit / 构建基准下派生的代码认知 |
| 当前 API 实现和数据结构 | 代码、Schema、OpenAPI 等权威来源；实现状态绑定代码基准 |
| 历史故障和已验证经验 | Issue / Run / Test 证据提炼出的项目知识；可迁移时再申请团队派生 |
| 项目概览 | 对项目元数据、项目资料、正式项目知识和代码认知的聚合视图 |

### 5.3 Project Cognition View 的重新定位

Project Cognition View 可以保留为一个有价值的项目浏览 / 认知视图，但应从第二轮 K0 的团队知识中心产品能力中移出。

**它是项目上下文的可重建聚合视图，而不是团队知识资产、独立知识类型或人工维护的项目 Wiki。**

- 视图身份属于 Project 的展示与导航入口，不新建 Knowledge Item。
- 视图内容来自 Project 元数据、已连接的项目资料、项目范围知识和可选的代码认知结果。
- 模块地图、调用关系和当前实现状态必须标明代码仓与 Commit / Tree 基准。
- 架构决策、业务规则和历史经验通过引用展示，不复制成第二份正文。
- 每次输出可记录输入来源和基准用于追溯；不需要为每次刷新创建正式知识 Release。
- 代码变化只触发相关派生视图刷新或影响分析，不直接判定项目知识失效。
- 人工只需确认重要决策和认知错误，不逐项维护自动提取的目录、依赖和 API 清单。

它可以在工作台的 Project 入口呈现，也可以由未来独立的 Project Wiki / Code Wiki 能力提供；这属于产品视图与可选扩展，不构成团队知识中心的核心资产。

### 5.4 代码认知应渐进生成

不要求完整代码图谱，也不把 AST / 符号锚点强加给所有知识。
- 基础导航：仓库、目录、模块入口和现有 API / 构建资料。
- 任务触发：Issue 涉及哪个模块，就分析该模块和必要上下游。
- 重点深化：对高风险、高变更频率、高返工模块增加调用关系和隐式约束分析。
- 按需扩展：只有跨模块影响分析反复需要时，才扩展更完整的代码关系图。

代码变化提供影响信号；事实是否变化仍需要结合具体语义、测试、运行证据或责任人复核。

## 6. 上下文编译与供给的正确位置

Argon 的“上下文编译与供给”方向仍然采纳，但必须调整归属。

它是围绕 Issue 工作主线的跨能力协作机制：
- 团队知识管理提供团队范围的正式知识及证据引用；
- Project 提供项目身份、成员、仓库、配置和项目资料引用；
- 项目资料连接提供权威来源和项目范围知识；
- 项目代码认知扩展提供指定代码基准下的结构和实现事实；
- Multica / Issue 提供当前工作目标、讨论、决定和责任；
- Harness 提供当前工作适用的方法、规则和验证要求；
- 执行与交付能力提供真实 Run、Artifact、Candidate 和 Evidence。

当前 Issue 依据 Context Contract 选择所需输入。上下文供给不要求所有工作经过统一的全量编译，也不要求所有来源都被复制进知识中心。

### 6.1 一次研发工作的上下文组合

| 输入来源 | 由谁提供 | 何时需要 |
|---|---|---|
| 团队知识 | 团队知识管理 | 存在可复用规则、经验或通用约束时 |
| 项目资料 / 项目知识 | Project 资源及其权威来源 | 需要理解项目业务、历史决策和特有约束时 |
| 项目代码认知 | 可选项目代码知识能力 / 当前仓库工具 | 需要定位模块、调用链和实现时 |
| Issue / Run 工作上下文 | Multica 与工作、执行权威对象 | 每项研发工作按当前状态取得 |
| Harness | Harness 治理与项目采用 | 依据工作类型、阶段和风险选择 |

不是每个 Issue 都必须取得全部输入。简单任务可以只使用 Issue 和少量团队规则；跨服务设计才需要深入项目资料和代码认知。

### 6.2 推式与拉式仍然成立，但不是知识中心独占

- 必须满足的团队 / 项目约束，可按项目采用和工作范围主动提供；
- 项目导航可在 Project 入口轻量呈现；
- 具体知识、项目资料和代码事实按需检索；
- 实际投递、宿主加载、实际使用分别记录；
- 不同 Agent 宿主能力不同，按 Hook、MCP、文件上下文或手动检索能力降级。

上下文准备和消费证据沿既有 Context Contract、ContextReceipt、Observation 与 Work / Run Asset Pin 语义，不新增上下文控制平面。

## 7. 对照现有整体架构：哪些不需要改变

当前架构基线已经覆盖本轮应保留的关键边界：
1. 五个核心业务能力域不变。
2. Issue 继续作为研发工作的唯一业务归属。
3. Multica Project / Issue / Task / Run / Runtime / Session / Usage 继续沿用。
4. Knowledge 与 Harness 继续分别治理。
5. Evidence 由权威来源或执行事实产生，被交付、知识和 Evaluation 共同引用。
6. Context Contract 已明确让知识、项目资料、代码和 Issue 提供上下文。
7. 团队 Wiki、项目资料和项目代码 Wiki 可以分别浏览或独立启用。
8. Project Code Wiki 可独立扩展，不作为当前主线成立的前置条件。
9. 身份权限、项目配置、工作台、来源连接器和宿主适配器继续作为横切实施事项。
10. 不新增 Project Context / Context Compiler 一级能力域，不建立第二套 Wiki、Issue、Run 或发布系统。

因此本轮不修改 product-foundation.md、system-architecture.md 或统一对象模型的冻结职责边界。现有架构通过 Context Contract 和可选项目知识扩展承接本轮结论即可。

## 8. 对第二轮 Argon 方案的边界修订

| Argon 方向 | 保留内容 | 修正后的归属 |
|---|---|---|
| 上下文编译与供给中心 | 根据工作意图组合高相关上下文 | 跨能力 Context Contract；不归团队知识中心独占 |
| 原始资料 + 编译态 | 来源证据与派生结果分离 | 来源连接、正式知识、项目派生视图、工作上下文分别治理 |
| 原子化 Entry | 精确结论和适用条件 | 正式知识主题内 Claim；仅独立治理需要时升级 |
| 项目认知视图 | 项目导航、当前认知和待确认信息 | Project 聚合视图；可重建，不属于团队知识资产 |
| 伴生式采集 | 从 Review、Test、Issue 和执行中发现候选 | 研发工作 / 执行证据触发知识或 Harness 改进，不监听即入库 |
| 项目成熟度分层 | 不同资料状态使用不同形成策略 | 项目 / 模块局部策略，不设永久项目等级 |
| 推式 + 拉式消费 | 必需约束、导航和细节检索 | 由工作主线按来源调用，不由知识中心包办 |
| 自动更新与失效 | 变化检测、影响分析、复核候选 | 各权威来源和项目认知按自身基准更新；不自动判定知识失效 |
| 知识向 Harness 转化 | 提出转化建议、沉淀评测样本 | Harness 独立候选、验证、发布和项目采用 |

## 9. 第一轮 K0 与 K0-A 应如何理解

### 9.1 K0 总体研究

第一轮 K0 的“团队知识中心”研究目标应收敛为团队范围可复用知识的组织、维护、治理和消费。

它可以研究项目知识和代码知识与团队知识的关系、引用、权限和派生，但不因此把项目 Wiki 和代码 Wiki 的全部产品设计纳入团队知识中心。

### 9.2 K0-A 粒度结论

K0-A 的主题资产 + Claim + Evidence 结论保持不变。
- 对团队知识，它定义正式团队知识如何维护。
- 对项目范围知识，它可作为内容组织参考。
- 它不决定项目资料、当前代码事实或派生项目视图都必须成为 Knowledge Item。
- 它不改变原始来源、Chunk、Evidence Anchor、Claim 和正式知识之间的身份边界。

### 9.3 第二轮报告需要调整的章节

- 将“团队知识中心同时承担上下文编译与供给”改为“团队知识中心是 Context Contract 的一个知识提供方；上下文编译与供给是跨能力协作机制”。
- 将 Project Cognition View 从团队知识中心核心产品能力移出，定位为 Project 聚合视图。
- 将项目资料、项目知识和项目代码知识分别归属其来源、Project 范围及可选代码认知能力。
- 保留伴生采集、知识治理、推式 / 拉式、质量维度和 Harness 独立转化，但按实际权威能力分流。
- 删除任何暗示所有项目事实、模块地图、调用关系都应进入团队知识中心的表述。

## 10. 下一步应回到 AgentPlatform 整体架构推进

本轮回归审查完成后，不继续扩张 K0 专题。下一阶段应回到整体架构，从一项完整研发工作反推各能力如何协作，重点审查：
1. Project 在现有 Multica 与 AgentPlatform 中提供哪些项目身份、资源、配置和上下文入口；
2. 团队知识、项目资料、可选代码认知如何在不重复维护的前提下被 Issue 发现和消费；
3. Context Contract 如何表达来源、适用范围、权限、代码基准、版本固定和宿主投递；
4. 哪些准备动作属于工作协作，哪些由知识管理提供，哪些由执行与交付负责；
5. 伴生采集如何从真实研发事件发现知识候选，但不增加新的工作队列；
6. 整体能力是否保持按需启用，不要求项目先建设完整 Wiki 或代码图谱才能使用 AgentPlatform。

这应作为整体架构的端到端一致性审查，而不是另起一个“项目上下文产品”专题。

## 12. 用一项完整研发工作回归验证能力协作

以“修改订单导出规则，支持新的区域筛选方式”为例。该场景同时涉及团队经验、项目业务资料、代码实现、Harness 和执行证据，可验证是否发生重复归属。

### 12.1 Issue 建立与上下文准备

| 步骤 | 权威来源 / 责任 | 本次取得的内容 | 不应发生的事 |
|---|---|---|---|
| 建立工作 | Multica Project / Issue；有权成员确认 Work Agreement | 目标、范围、责任、完成条件和决定 | 知识中心创建第二个研发任务 |
| 取得团队经验 | 团队知识管理 | 跨项目可复用的权限边界、导出测试经验 | 将项目订单规则误当团队通用规则 |
| 取得项目业务资料 | Project 资源和飞书 / 项目权威来源 | 当前 PRD、项目规则、历史决策和接口约定 | 将 PRD 正文复制成团队知识 |
| 取得代码依据 | 项目仓库和当前工作代码基准；必要时调用可选代码认知能力 | 订单模块入口、调用链、数据结构和当前实现 | 维护一份与代码仓并行的团队模块 Wiki |
| 取得方法 | Harness 发布与 Project Adoption | 适用 Rule、Skill、Playbook、测试和验收要求 | 将知识结论直接当作强制执行规则 |
| 形成工作上下文 | 当前 Issue 的 Context Contract | 按角色、权限、适用范围和预算组合必要输入 | 把所有来源统一搬进团队知识库 |

### 12.2 执行与结果

1. 当前负责人 / Main Bot 按 Issue 授权组织工作；协作者和 SOP 仅在明确委托范围内行动。
2. 成员本地 Agent 按本次授权读取项目资料和代码，受管执行沿 Multica Run。
3. 执行与交付证据能力固定实际 Artifact、Candidate、测试结果和 Evidence。
4. Issue 有权负责人按当前 Work Agreement 和 Candidate 作出接受、退回或待决定。
5. ContextReceipt 证明材料准备 / 投递；宿主 Observation 才能证明实际输入；不能证明的实际使用保持 Unknown。

### 12.3 完成后的知识反馈分流

| 新发现 | 进入哪里 | 决策 |
|---|---|---|
| 只对本项目成立的新业务规则 | 项目范围知识或项目原始资料 | 项目责任人确认；不自动提升团队范围 |
| 多个项目均可复用的区域权限测试方法 | 团队知识候选 | 逐来源派生许可、跨项目适用性核验、团队责任人发布 |
| 订单模块调用关系随代码变化 | 项目代码认知 / 当前代码基准视图 | 更新或重建派生视图；不创建团队知识条目 |
| 当前 Issue 暴露的执行缺陷 | 当前 Issue 修正 | 先完成本次工作，不因发现问题自动创建独立知识任务 |
| 稳定且可执行的通用检查方法 | Harness 候选 | 独立回归验证、审核发布和项目采用 |
| 根因未知或证据不足 | 保留待调查状态 | 不强行生成正式知识或规则 |

### 12.4 端到端审查结果

现有整体架构与跨层业务契约能够承载上述链路：
- Work Contract 由 Issue 提供；
- Context Contract 组合多来源工作依据；
- Capability Contract 固定本项采用的 Harness；
- Delegation / Execution Contract 约束 Agent 与 SOP 的受托行为；
- Delivery Contract 处理候选、制品和验收；
- Feedback Contract 将证据分流到知识、Harness、项目或 Runtime 改进。

因此不需要增加一个独立的 Project Context 能力域或 Context Compiler 控制平面。真正需要坚持的是：**各能力保留事实权威和维护责任，Issue 负责按需组合与消费。**

## 13. 本轮回归后的下一步

整体架构无需因第二轮 K0 扩张而重画。下一步应从现有跨层契约中挑选真实工作场景，审查“上下文选择 → 权限核对 → 版本固定 → 投递 → 实际消费”的端到端闭环，重点检查不同 Agent 宿主的能力差异与失败接续。该工作属于现有 Context Contract / 执行证据专题的深化，不重新建立知识中心专题，也不进入底层技术选型。


## 14. Context Contract 知识来源融合审查完成

后续研究已形成[Context Contract 中 Team Knowledge / Project Knowledge 融合审查](context-contract-knowledge-scope-integration.md)，并将结论同步到：
- [跨层业务契约与协作协议](../architecture/cross-layer-contracts.md)；
- [知识管理生命周期](../architecture/knowledge-management-lifecycle.md)；
- [核心业务对象与统一关系模型](../architecture/core-business-object-model.md)。

本轮确认：
1. Team Knowledge 与 Project Knowledge 共用知识内容和治理机制，分别归属 Team 与 Project。
2. Project Sources 可直接作为工作依据，不要求先提炼成 Project Knowledge。
3. Project Code Knowledge 是绑定仓库与代码基准的可选项目认知能力，不属于 Team Knowledge。
4. Team Knowledge 由项目引用时保留原身份和版本；Project Knowledge 跨项目复用时形成新的 Team Knowledge 候选并重新授权、核验和发布。
5. Context Contract 按 Issue 工作需要组合各权威来源，分别检查作用域、适用性、读权和版本，不把来源复制到知识中心。
6. 项目例外不能静默覆盖 Harness 强制规则；知识事实、强制方法和当前 Issue 决定分别沿各自权威机制处理。

本轮完成的是业务边界与契约语义收敛，不代表多宿主真实投递和使用能力已经全部验收。下一阶段进入场景验收：选取项目内功能开发和跨项目经验复用两类真实 Issue，检查来源选择、权限、版本、冲突、投递和宿主观察。
