# K0 · 团队知识中心调研与产品设计研究

## 1. 调研目的

K0 不是先选一个 RAG 产品，也不是先建设 Wiki 页面。它要回答：研发团队长期需要维护哪些知识资产、这些知识如何从现有工作中形成、谁对其正确性和有效性负责、成员和不同 Agent 如何低摩擦地使用，以及如何避免知识中心变成第二套文档系统。

本研究承接：
- [产品定位与总体设计基线](../architecture/product-foundation.md)：团队知识是研发能力基础。
- [整体系统架构](../architecture/system-architecture.md)：团队知识管理是五个核心业务能力域之一。
- [知识管理生命周期](../architecture/knowledge-management-lifecycle.md)：定义来源、证据、候选、发布、检索、更新和反馈链路。
- [核心业务对象与统一关系模型](../architecture/core-business-object-model.md)：定义 Source、Evidence、Knowledge、Harness 与 Issue / Run 的对象关系。
- [专题三 B 来源与知识实证](03b-source-evidence.md)：已经完成的来源权限、上下文投递和知识贡献实验。

**K0 的目标是把“知识管理生命周期”提升为可长期运营的团队知识中心产品设计，明确使用者体验、知识组织、维护责任、知识质量和运营机制。** 本阶段不决定数据库、向量引擎、文档解析供应商、服务拆分或部署方式。

## 2. 调研结论摘要

### 2.1 核心判断

团队知识中心既不能是原始资料仓库，也不能只是自动生成 Wiki，更不能只是一套向量检索服务。

建议采用：

**来源为依据、知识资产为中心、证据为纽带、研发工作为入口、维护责任分布到领域。**

- 原始资料继续由飞书、Git、项目系统等权威来源维护。
- 知识中心保存来源身份、修订、权限、可定位证据，以及经整理、核验后可跨工作复用的知识资产。
- 人和 Agent 消费的是有适用范围、有效状态和证据依据的知识，不是直接把所有原始文档切块塞进上下文。
- 项目研发产生的新事实和经验，经提炼和治理后进入项目知识或团队知识。
- 知识维护责任由业务 / 技术领域和项目责任人承担，不建立一个需要专职人员逐条整理所有资料的中央编辑部。

### 2.2 关键产品决策建议

| 问题 | K0 当前建议 | 原因 |
|---|---|---|
| 原始资料还是知识条目为中心？ | 来源证据作为可信依据，知识资产作为浏览、维护和复用中心 | 原文保持权威，团队消费的是提炼后的知识 |
| 是否建设统一 Wiki？ | 提供统一知识中心体验，但不要求所有来源迁入同一 Wiki | 避免复制飞书和 Git 的编辑职责 |
| 是否所有资料都要编译成知识？ | 否。原始资料可直接检索；只有具备复用价值的结论才形成正式知识资产 | 降低噪音和整理成本 |
| 是否每条知识都要人工审批？ | 按风险、范围和证据强度分级治理 | 普通经验不应被繁重流程阻塞，高风险规范需要确认 |
| 谁维护知识？ | 领域 / 项目分布式维护，平台提供发现、提醒、证据和审核机制 | 知识正确性需要靠近事实责任人 |
| 是否自动定期复核全部知识？ | 以来源变化、项目变化、使用反馈和风险触发为主，定期复核只用于高风险或无可跟踪来源的知识 | 避免大量无意义巡检 |
| 知识如何进入研发？ | 从 Issue / 项目工作意图触发，返回少量高相关且有证据的知识包 | 不增加独立知识任务，不污染上下文 |

## 3. 知识中心应该管理什么

### 3.1 不把所有内容都称为知识

需要区分四种不同内容：

| 内容类别 | 示例 | 是否正式知识资产 | 处理方式 |
|---|---|---|---|
| 权威来源资料 | PRD、飞书文档、接口文档、代码、评审纪要 | 通常不是；它们是来源 | 保留来源身份、权限、修订和结构化定位，可直接检索和引用 |
| 可复用知识 | 已确认的业务规则、架构决策、技术约束、踩坑经验、排障方法 | 是 | 形成稳定知识条目，关联来源证据、适用范围、维护者和有效状态 |
| 派生导航 / 摘要 | 项目概览、模块地图、主题摘要、跨文档索引 | 视用途而定 | 可由 Agent 生成，标明自动生成、依据和核验状态；不冒充权威事实 |
| 当前工作上下文 | Issue 目标、讨论、临时调查、未确认假设、交付待办 | 否 | 留在原 Issue / Run；只有可复用部分才提炼为知识候选 |

关键原则：文档被接入不代表知识已经形成；模型摘要不代表事实已经核验；Issue 完成不代表其中所有内容都值得沉淀。

### 3.2 知识资产类型

建议以少量稳定类型起步，不建立庞大本体：

1. **事实与约定**：业务规则、系统行为、接口契约、项目限制。
2. **决策与理由**：架构决策、技术选型、业务取舍、替代方案及原因。
3. **实践与方法**：经实际使用验证的实现方式、排查步骤、测试策略。
4. **问题与踩坑**：现象、触发条件、影响范围、根因证据、解决与预防方式。
5. **项目 / 系统说明**：项目目标、模块职责、关键流程、依赖和现状。
6. **待确认认识**：有价值但证据不足的假设、问题和待调查结论，明确不能作为强制依据。

Harness 资产不属于以上知识类型。Rule、Skill、Playbook、SOP、Script 和 Evaluation 是研发方法与约束，应在 Harness 中独立维护。

### 3.3 知识粒度：主题资产承载多条可核验结论

不建议把每个段落、每个 Chunk 或每个事实都建成一个需要独立维护的知识条目。这样会导致知识数量爆炸和维护负担。

建议采用两层表达：
- **知识资产 / 主题页**：以一个稳定主题组织内容，例如“订单导出权限规则”“Android 设备证明兼容性”“服务 X 的调用链”。
- **知识主张 / 结论段落**：在主题页内明确表达事实、适用条件、例外和证据引用。需要精确版本、单独核验或独立失效的结论可以单独标识。

来源 Chunk / Block 是检索和定位单元，不是知识资产身份。一个主题页可以引用多份来源、多个 Issue 和多个 Run；一个来源也可以支持多个主题页。

这种粒度兼顾人工可读、Agent 检索和证据追溯，避免原始文档与知识条目一一复制。

## 4. 知识如何组织与发现

### 4.1 三个正交维度

知识组织不应只靠一个目录树。建议同时维护：

**作用域（回答谁能在什么范围复用）**
- 团队：跨项目可复用，必须明确团队受众和派生许可。
- 项目：项目业务事实、决策和约束，默认不跨项目。
- 代码基准：项目代码知识必须绑定仓库与 commit / tree。
- 工作：当前 Issue 上下文，不进入正式知识中心，除非提炼为可复用资产。

**主题（回答内容属于什么领域）**
- 业务域 / 产品域；
- 技术栈 / 系统 / 服务；
- 工程实践 / 测试 / 发布 / 运维；
- 安全、质量、合规等横切主题。

主题应允许多标签和关联，不要求在导入时先选一棵复杂分类树。先由领域维护者在真实内容中逐步形成，避免分类先于知识。

**内容类型（回答它是什么性质的知识）**
- 事实、决策、实践、问题经验、系统说明、待确认认识。

作用域、主题和内容类型相互独立，不能用目录位置隐式推断权限、权威性或内容类型。

### 4.2 建议的知识中心用户视图

知识中心应围绕成员要完成的事情组织，而不是暴露内部对象和索引结构。

| 视图 | 用户要解决的问题 | 核心内容 |
|---|---|---|
| 团队知识首页 | 团队有哪些可复用知识，最近有什么变化？ | 领域入口、常用知识、最近更新、待复核提示、知识健康概览 |
| 项目知识 | 这个项目有哪些业务事实、架构决策和历史经验？ | 项目主题、项目资料、代码基准、关联团队知识 |
| 搜索 / 问答 | 当前问题应该参考什么？ | 适用知识、结论摘要、来源证据、版本、冲突和适用范围 |
| 知识详情 | 这条知识为什么可信，是否仍然有效？ | 正文、适用条件、证据、来源修订、维护者、版本、关联和反馈 |
| 资料接入与处理 | 新资料是否已取得、解析、可检索？ | 来源连接、一次性导入、处理进度、失败原因、来源修订 |
| 知识贡献与复核 | 哪些经验待提炼，哪些知识需要确认？ | 候选知识、证据、重复 / 冲突、审核决定、撤回与复审 |
| 知识健康 | 哪些知识可能过期、失去来源或无人维护？ | 来源同步异常、失效引用、过期风险、重复主题、无主知识 |

这些是同一个知识中心的工作视图，不是七个独立子系统。工作台可从 Issue 直接进入相关知识，不要求成员先进入知识中心再开始研发。

### 4.3 搜索和问答不能取代浏览与维护

知识中心同时需要：
- 关键词 / 结构化过滤：按项目、主题、类型、状态、来源和版本定位。
- 语义检索：处理自然语言问题和概念相近的经验。
- 主题浏览：帮助成员理解某个领域已经积累了什么。
- 证据展开：从结论回到原文、代码位置或实际 Run / Artifact。
- 冲突呈现：并列展示不一致来源、版本、范围和权威性，不强行合并成一个答案。

回答应优先返回少量可用结论，并支持展开证据；不能用一个生成式答案掩盖来源冲突或资料缺失。

## 5. 知识从哪里来：三条入口，一个治理体系

### 5.1 权威资料接入

- 持续连接：飞书知识空间 / 云文档、Git、代码仓和未来其他资料源。
- 一次性提交：Markdown、PDF、HTML、表格、URL、成员灵感。
- 资料进入后记录来源身份、修订、读取权限、结构位置、取得时间和处理状态。
- 外部来源仍在原系统编辑；知识中心提供引用、检索、派生和治理。

### 5.2 研发过程提炼

优先从真实研发活动发现候选：
- 已确认的业务澄清和决策；
- 经核验的缺陷根因与解决方案；
- 评审和测试中反复出现的遗漏；
- 能迁移到其他工作的问题排查方法；
- 代码 / 项目结构变化中值得维护的系统说明；
- 人工纠正、返工、阻塞和知识错误反馈。

提炼时先问“是否可复用”，再问“属于团队还是项目”。不是每个 Issue 都必须生成知识候选。

### 5.3 成员主动贡献

允许成员提交一句话、URL、文档或对现有知识的修正建议。提交动作应尽可能轻量，系统补充来源、归属、主题建议和候选草稿。

### 5.4 统一治理而非三套流程

三条入口最终进入同一知识治理流程：
- 来源资料可以直接检索，但不自动成为正式知识。
- 研发经验先形成候选，证据不足时保持待确认。
- 主动贡献可以直接创建草稿，但正式发布仍遵循相应风险和范围规则。

## 6. 知识维护机制：分布式责任，而不是中央编辑部

### 6.1 责任角色

| 角色 | 责任 | 不应承担的责任 |
|---|---|---|
| 来源维护者 / 作者 | 维护原始资料，确认来源修订与派生许可 | 不自动负责派生知识的正确性 |
| 项目负责人 / 项目领域维护者 | 确认项目事实、项目知识适用范围和项目内修订 | 不自动拥有跨项目发布权 |
| 团队领域维护者 | 维护团队领域知识、核验跨项目适用性、处理冲突与复审 | 不要求其逐条整理所有原始资料 |
| 贡献者（成员 / Agent） | 发现、提炼、补充证据、提出修订和反馈 | 不可自行把候选升级为高风险正式规则 |
| 知识中心机制 | 自动同步、检查、去重建议、失效发现、提醒和审计 | 不替责任人作业务事实确认 |

同一人可以兼任多个角色；角色是某个知识范围和操作的责任，不是新的组织层级。

### 6.2 治理分级

建议根据内容风险和复用范围决定发布门槛：

| 等级 | 内容示例 | 发布方式 |
|---|---|---|
| 低风险、局部事实 | 项目内部的实现说明、已核实的操作记录 | 项目维护者快速确认；可按预授权规则自动整理 |
| 可复用经验 | 技术踩坑、排障经验、测试方法 | 证据和适用范围核验；团队领域维护者确认跨项目复用 |
| 高影响约定 | 业务规则、安全要求、架构原则、强制工程规范 | 必须由对应业务 / 技术责任人确认；若转成 Harness 规则，另走 Harness 发布 |
| 未确认认识 | 假设、未经复现的猜测、单次模型判断 | 保持草稿 / 待确认，不作为正式依据和强制上下文 |

治理分级不能只用一个“可信度分数”代替。来源权威、证据强度、适用范围、风险和审核责任是不同维度。

### 6.3 复核与失效采用事件触发

优先触发复核的事件：
- 权威来源新修订、删除、撤回或权限变化；
- 项目架构、接口、代码基准或业务口径发生变化；
- 知识被反馈错误、过期、冲突或不适用；
- 多次检索命中但持续被标记无关；
- 知识被用于高风险决定或成为 Harness 规则依据；
- 维护者离开、责任范围变化或知识长期没有可联系维护者。

定期复核只针对高风险、无可追踪来源或变化无法自动感知的知识。不要给所有知识设置相同的 30 / 90 天过期时间，也不要因为长期未被访问就自动删除仍然有效的知识。

## 7. 知识质量与健康运营

### 7.1 每条正式知识需要能回答

- 这条知识解决什么问题？
- 它适用于哪个团队 / 项目 / 系统 / 版本 / 环境？
- 结论由哪些来源和证据支持？
- 哪些情况不适用或存在例外？
- 谁对它负责，最近一次核验依据是什么？
- 当前是有效、待复核、冲突、被替代还是已撤回？

### 7.2 知识健康信号

不建议以知识条目数量、Chunk 数量或 Wiki 页面数量作为核心 KPI。更有意义的指标：
- 来源可追溯率与来源修订核对成功率；
- 正式知识的维护责任覆盖率；
- 过期 / 冲突 / 失效内容的发现与处理时长；
- 检索结果的适用率、证据可打开率；
- 被明确选择、投递和可观察使用的知识比例；
- 知识帮助 / 无关 / 错误反馈；
- 重复调查减少、返工减少的真实案例。

“检索命中”“投递给 Agent”“Agent 实际使用”“帮助了交付”必须分开统计。宿主不能证明的环节保持 Unknown。

### 7.3 知识运营应围绕问题队列，而非内容巡检

维护者日常需要处理的是少量明确事项：
- 新候选待核验；
- 来源更新影响了哪些知识；
- 有冲突需要业务负责人确认；
- 某条知识被多次报告错误；
- 无人维护或高风险知识需要重新认领；
- 某条知识可能适合转为 Harness 方法。

不要求维护者定期逐篇打开所有 Wiki 页面。

## 8. 与 Harness、Issue 和执行底座的关系

### 8.1 与 Harness

- Knowledge 提供事实、经验、约束依据和历史失败案例。
- Harness 提供团队认可的工作方法、强制规则、SOP 和验证标准。
- 一条知识只有在形成明确执行要求、适用范围、例外和验证方法后，才转化为 Harness 资产。
- Harness 的 Evaluation / Finding 可反馈知识缺失、过期或不适用，但知识和 Harness 分别审核、发布和采用。

### 8.2 与 Issue / Run

- Issue 是当前研发工作的唯一业务主线。
- 知识中心按 Issue 目标、项目、阶段和接收者权限提供上下文。
- Run、Artifact、Evidence 是知识提炼的来源证据，不自动成为知识。
- 知识贡献与复核不阻塞当前 Issue 的交付验收。
- 已送达宿主的内容可能保留在本地历史，权限撤回后停止新的检索 / 投递，不声称平台可以远程删除本地历史。

### 8.3 与 Multica / TeamAI / WeKnora

- Multica 继续提供 Issue、Run、Runtime 和项目工作上下文，不另建工作控制平面。
- TeamAI 的命名空间、增量索引、角色作用域、经验采纳和受控发布机制可作为方法参考，但不能把其 Git 经验仓直接当成完整团队知识中心。
- [WeKnora](https://github.com/Tencent/WeKnora)：来源接入、异步解析、Wiki 编译、Chunk / Wiki 修订、权限范围和 MCP 消费可复用或借鉴；它解决知识处理和检索的部分底座问题，不自动替代 AgentPlatform 的团队 / 项目责任、知识派生许可、Issue 关联和 Harness 改进治理。当前文档重点参考其[文档处理管线](https://github.com/Tencent/WeKnora/blob/main/website-docs/02-architecture/03-document-pipeline.md)与[Wiki 能力](https://github.com/Tencent/WeKnora/blob/main/website-docs/03-features/14-wiki.md)。
- [Backstage TechDocs](https://backstage.io/docs/features/techdocs/) 的 docs-like-code 机制，以及 [Software Catalog](https://backstage.io/docs/features/software-catalog/) 的软件与 Owner 目录，说明代码旁文档和责任导航适合工程知识；但它不是跨飞书、Issue、项目经验和团队知识的统一来源治理中心。
- [Onyx](https://onyx.app/search) 的 permission-aware connector 说明企业搜索必须把来源 ACL 纳入检索与回答范围；其[连接器机制](https://docs.onyx.app/overview/core_features/connectors)和检索能力不等于团队知识的维护责任与发布治理。

## 9. 对现有研究与实验的审查

### 9.1 已有成果，不应重复研究

仓库中专题三 B 已完成比普通概念设计更深入的实证：
- TeamAI 42 项来源导入、角色检索、内容改动和失效测试；
- Multica PostgreSQL handler / 权限测试及新增撤权对照；
- 真实 Codex CLI 0.144.6 App Server 请求探针，检查开发与核验角色实际收到的章节正文；
- 项目来源修订、章节变化、队列重选、历史线程携带旧内容和失权后新线程重建的对照；
- C1 / C2 两份原始核验报告提炼团队经验，覆盖项目私有内容拒绝、来源派生许可、独立团队审核、发布、撤回、恢复、复审和退役；
- 知识贡献实验执行 45 项正反向检查，后续另补 5 项单来源撤回回归。

### 9.2 已有实验的边界

上述实验并不意味着生产知识中心已经实现：
- 飞书真实租户的持续同步、真实群组权限同步、复杂嵌套块、通知延迟仍需联调；
- 订单来源与权限时钟采用可控合成夹具，不能据此宣称所有来源协议已验证；
- 语义检索排序、广域知识发现和长期知识健康运营尚未通过真实团队样本验证；
- 真实生产环境中的多人并发编辑、长期版本维护、跨项目知识规模化复用仍待验证。

K0 应继承已证明的机制，研究尚未回答的产品问题，不重复跑已完成的合成实验。

## 10. K0 需要继续验证的关键问题

1. **知识资产粒度**：主题页 + 证据化结论是否足够，哪些类型需要独立版本和独立审核？
2. **团队与项目的关系**：项目知识提升为团队知识时，如何确定适用范围、去敏、派生许可和责任人？
3. **知识维护责任**：领域维护者如何认领，项目人员变化时如何交接，如何避免出现无人维护的知识？
4. **知识来源权威等级**：PRD、Issue 决定、代码、测试、运行事实发生冲突时，按什么规则展示和裁决？是否需要按问题类型定义权威来源，而不是全局统一排序？
5. **知识中心的编辑体验**：哪些内容在原来源修改，哪些派生知识可在中心编辑？怎样避免两处都能改同一事实？
6. **不同成熟度项目**：有 PRD / 架构文档的项目与几乎没有文档的项目，是否使用不同的知识形成策略？
7. **搜索效果**：关键词、结构化过滤、语义检索和主题导航怎样组合？如何用真实 Issue 建立可评测的检索样本？
8. **知识维护成本**：团队每周需要投入多少维护时间？哪些提醒真正有价值？哪些必须自动处理？
9. **来源权限与派生权限**：不同源系统权限语义如何映射，派生知识对不同受众的授权如何表达和撤回？
10. **WeKnora 的承载边界**：哪些能力直接复用 WeKnora，哪些应由 AgentPlatform 管理，如何避免建设两个重叠的知识治理系统？

## 12. 当前阶段结论

当前可以确定的方向是：**知识中心以可复用知识资产为维护和消费中心，以权威来源和 Evidence 为可信依据；采用团队 / 项目作用域，按主题组织，按风险治理，由领域和项目责任人分布式维护，按 Issue 意图进入研发。**

暂不冻结的内容：
- 主题页与更细粒度知识条目的最终比例；
- 是否将 WeKnora 作为知识处理 / 检索底座；
- 各资料类型首期接入范围；
- 知识中心页面与工作台页面的具体形态；
- 团队知识维护者的具体组织配置；
- 自动发布和复核策略的具体阈值。

K0 完成标准不是写出一套更大的知识库架构，而是拿真实资料和真实研发任务证明：团队知道什么值得维护、谁负责、如何更新、如何判断有效，以及下一位研发者如何可靠地复用。

K0 完成后，再带着明确的知识中心产品设计进入 P0，核验现有 Multica、来源连接和本地宿主是否满足这些实际需要。
