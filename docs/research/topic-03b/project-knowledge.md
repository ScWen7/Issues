# 订单文档改版后，开发与核验实际收到什么

专题三 B 第二阶段 · 2026-11-15。案例沿用订单导出 Issue 的 D2 决定、C1 返工和 C2 通过记录。业务负责人在原文修订开发说明。平台需要回答三个问题：开发与核验分别应取哪些段落，来源或授权改变后哪些工作受影响，项目这次返工能向团队公开哪一条经验。[设计稿](../../architecture/03b-capability-governance.md) · [一次实跑的结构化回执](fixtures/project-knowledge.json)

## 一份需求，两种角色

开发和核验都需要 D2 的业务约定“按当前可见订单导出，新增付款时间，未付款留空”。开发另需付款事件的时区转换规则。独立核验者另需从区域、跨区与只读角色核查导出范围，本例用单独授权的核验笔记提供对应段落。核验者本来就有整份订单需求的读权，他在当前核验任务里搜索开发专用标记时仍得到空结果。财务私有段落则在授权、角色和宿主输入三个层面都有对照。

需求从修订 1 到 2，维护者在前面增加可选文案，又将“开发说明”改名为“开发时区”，改写正文。共同业务约定和开发说明沿用各自的标题块 ID。当前任务搜索用标题或正文匹配；开发能按新标题找到新段落，旧文案、财务材料和未选可选项没有返回。查询只遍历当前任务的角色范围并核对源读权；这轮没有测语义排序或广域知识发现。[检索、组合与引用模型](../../../prototypes/topic-03b/knowledge/source_context.py)

改版后有两种不同的影响。**尚在队列中的开发和核验都要重新选择**，因为两份队列都固定了订单需求的源修订。核验者重选后，两段正文逐字相同。**回看已经送达的输入，只有开发回合用了发生变化的旧正文。** 平台按来源、章节和正文摘要查出该回合。旧核验结论是否继续有效，要看其依据的标准和实际检查项。

| 实际模型请求 | 当轮命中的正文 | 随历史发送的正文 |
|---|---|---|
| 开发，新线程 | 共同业务约定、开发时区 | 无 |
| 核验，独立线程 | 共同业务约定、角色核验说明 | 无 |
| 收回开发者读权后，在原开发线程发一条空材料指令 | 无 | 共同业务约定、开发时区 |
| 同一开发进程和工作目录，新建线程发相同指令 | 无 | 无 |

四次请求均未出现财务标记、旧版开发说明或可选文案。探针遍历整个模型请求中的字符串，并核对完整段落及所在字段。Codex 对每轮采样都从当前会话历史准备模型输入。实际产品在权限收缩、历史中包含已失权正文时，使用干净线程按当前权限重建工作上下文；已发送内容保留为历史事实。必需材料仍缺时，受影响节点等待。上表后两行是使用合成段落的宿主对照。[Codex 固定版采样输入](https://github.com/openai/codex/blob/5d1fbf26c43abc65a203928b2e31561cb039e06d/codex-rs/core/src/session/turn.rs#L270-L292)

## 权限与来源变化后的工作台行为

| 情况 | 实测结果 |
|---|---|
| 成员刚失去文档读权、退出项目、或在排队后源授权到期 | 交付前复核，旧队列停止。失去开发者的个人读权时，仍获准的核验者继续工作。仅核验笔记授权到期时，核验者仍能搜索另一份需求文档。 |
| 文档读取半途停下、固定版本读取期间源头再次改稿，或读权服务暂时失联 | 原子切换完整快照，失败保留前次成功的修订与核对时间。当前性或读权尚未证实的来源不返回片段。普通接收者看到缺失提示，有权维护者可查具体原因。 |
| 核验章节从仍可读的文档删除，随后整份核验笔记由来源确认撤回 | 旧队列失效，按旧段落可找到三个既有核验投递。搜索“订单”仍返回另一份来源中可用的共同约定。失权或临时读不到单独处理；删除结论以权威源的撤回或完整修订为据。 |
| 读到相同的完整版本 | 相同章节可重复刷新，更新最后核对时间。历史按当时实际送达的版本和摘要查询，展示原文时另查当前权限。 |

## 一次返工成为团队经验

C1 的付款时间检查 A3 已通过，失败点是东区普通账号拿到了西区订单。C2 在同一个 Issue 与节点使用相同标准和核验器，东区清单恢复正确，跨区账号仍能导出两区订单。第一份候选经验含项目订单号，评审退回。第二份只写测试方法：分别用区域和跨区账号导出，核对各自的订单集合，再单独验证付款时间列。

项目审阅者凭当前读权查看原报告和决定。普通团队成员只见条目标识、范围、版本与获准文案。一次提案重试复用原提案；源管理者对精确文案及受众授权，独立团队发布者核对两份证据后发布。单个成员失去原报告读权、团队派生授权撤回、源修订或撤回，分别走相应处置。对照中，来源先改后恢复、先撤回再恢复都产生新的变更代次，即使正文恢复到原来字节也要取得新授权、重新审核。45 项贡献检查通过，历史派发仍能追溯当时采用的正文摘要。团队经验供后续工作选用，把经验升级为验收规则另走规则发布与 Issue 决定。[贡献实验与实际决策序列](knowledge-contribution.md)

## 复跑

从本仓库根目录执行。需要 Python 3.11+、Git、官方 Codex CLI 0.144.6。四个回合使用本机模型端点；输出目录须为新目录。每次会生成新的线程和回合 ID。固定的章节摘要、实际位置、拒绝条件及两份核验报告均在运行中逐项校验。

```bash
work=$(mktemp -d)
python3 prototypes/topic-03b/knowledge/order_knowledge.py "$work/evidence" --codex /absolute/path/to/codex
```

`summary.json` 同时包含所选章节、各搜索对照的结果、变更影响、实际宿主回合与贡献审核记录，是本案例用于评审的合成证据。真实产品按角色单独提供团队经验和项目证据。持续集成还复跑 3A 的工作流、执行与接收测试和 3B 第一轮订单核验。[订单入口](../../../prototypes/topic-03b/knowledge/order_knowledge.py) · [工作流](../../../.github/workflows/asset-release-research.yml)
