# 组合材料怎样进入真实 Codex 回合

在订单案例中，平台已为一个角色选定 Issue 决定、章节、Role、Skill 与可选 Playbook。对这些材料的验证落在三个位置：派发前选定的版本与摘要、原生宿主接受的输入、实际送往模型的请求。一次原生回合另外可以用 `thread/read` 查到完成状态。[宿主探针](../../../prototypes/topic-03b/composition/observe_composition.py)

## 同一个 Skill 在哪些地方可见

| 操作 | 实际观察 |
|---|---|
| 将独立合成的校准 Skill 放入独立工作目录，然后调用 `skills/list` | Codex 返回该 Skill 的原生名称、已启用状态和磁盘路径。另起一个校准回合，只发普通指令，模型收到的是目录中的名称、描述与文件定位。Skill 正文的专属标记在整个请求内缺席。 |
| 在工作回合通过 `turn/start` 显式提交 Skill 的名称与路径 | Role、工作材料和 Playbook 在当轮普通文本中；Skill 的完整文件由宿主读取，进入单独的 `<skill>` 消息，其中保留文件头和正文。探针逐字核对文件及原生包装，再从实际消息中取出正文计算 SHA-256。选择记录里的顺序适用于平台组装；两种输入通道在宿主处有各自的位置。 |
| 在同一次请求中查看工具定义和回合内容 | 请求中可以看到 `exec_command` 等宿主工具。回环模型只返回固定文本，`thread/read` 回读这次已完成回合只有一条成员输入和一条 Agent 回复。此次回执可证明材料进入模型输入，实际调用工具或通过验收分别取各自的执行证据。 |

源码解释了这一差异。Codex 为可供模型发现的 Skill 生成包含元数据的清单，再按目录预算处理条目和描述。显式 Skill 输入先按路径与启用状态查找；找到后在本轮读取文件文本，成功才生成包含文件内容的宿主输入项。已选择、已列入目录、正文已送达分别保留证据。[目录与元数据预算](https://github.com/openai/codex/blob/5d1fbf26c43abc65a203928b2e31561cb039e06d/codex-rs/core-skills/src/render.rs#L155-L219) · [按路径选择](https://github.com/openai/codex/blob/5d1fbf26c43abc65a203928b2e31561cb039e06d/codex-rs/core-skills/src/injection.rs#L149-L187) · [读取正文](https://github.com/openai/codex/blob/5d1fbf26c43abc65a203928b2e31561cb039e06d/codex-rs/core-skills/src/injection.rs#L80-L109) · [组装本轮输入](https://github.com/openai/codex/blob/5d1fbf26c43abc65a203928b2e31561cb039e06d/codex-rs/core/src/session/turn.rs#L584-L624)

## 两个角色的十二个派发条件

每个角色都经历六种条件。两处预算只差一个字节的对照用于确认必需材料整体交付。最后一次修复明确采用包含付款时间的快速导出 v2，两位角色在各自的原生 Skill 之外都实际收到了这第二份 Skill。

| 条件 | 开发已送达正文（UTF-8 字节） | 核验已送达正文（UTF-8 字节） | 两个角色共发出模型请求 |
|---|---:|---:|---:|
| 全部材料可容纳 | 707 | 731 | 2 |
| 恰好容纳必需项，省略可选 Playbook | 604 | 619 | 2 |
| 预算比必需项少 1 字节 | 0 | 0 | 0 |
| 必需的快速导出 v1 与 D2 冲突 | 0 | 0 | 0 |
| 发布修复版本后重新选择，保留 Playbook | 798 | 822 | 2 |
| 已经选好材料，送达前撤回开发者的源读权、核验者的工具使用权 | 0 | 0 | 0 |

独立复跑共收到 7 个请求，含 6 个工作回合和 1 个目录校准回合。6 个工作请求的未压缩 HTTP 请求体为 52,123–52,831 字节；具体大小随宿主的临时路径和请求标识变化。每个业务正文的长度、摘要和归属都由探针校验。[订单场景和准入条件](../../../prototypes/topic-03b/composition/order_composition.py)

## 怎样核对每个场景

使用官方 Codex CLI 0.144.6。每次获准派发使用独立的宿主进程、配置目录、工作目录和新线程，只将本次选中的技能实际放入该工作目录。这样可以在相同宿主条件下比较两个角色和两档材料预算。既有长期线程如何在权限收缩时处理，沿用上一阶段的对照。[旧线程与新线程的撤权实验](project-knowledge.md)

1. 调用前固定 Issue、节点、角色、Run、尝试与各材料引用。原生宿主可发现的项目级测试 Skill 清单与实际准备的目录逐一对应。系统自带的 Skill 由宿主另外管理。
2. 每个已放行场景都完成一个原生回合。端点读取真正的 HTTP 请求体，保存 SHA-256、未压缩字节数和材料出现的字段位置。每份材料各有独立标记，检查遍历整个请求里的文本值。缺失的必需正文、额外出现的未选正文、正文落在工具描述或其他位置，都会使测试失败。同一回合再从宿主读回，检查线程只包含这一次已完成的执行。
3. 订单入口在准备宿主目录之前按当时的授权和约定重新组装，保留已排队的身份。开发读权、核验工具授权各自撤回后，原来已就绪的案例在此处停止。对包含冲突、或必需正文超出预算的场景，实验派发入口同样直接结束。没有创建工作目录、线程或回合；端点请求计数在处置前后相同。同一次测试还核对所有成功回合的身份与端点总请求数。
4. `wire_request_bytes` 是回环端点实际收到的整份未压缩 HTTP 请求体大小，含工具定义、开发者指令、技能目录、文件包装和业务正文等。选材预算只计入选中业务正文的 UTF-8 字节。真实提供方的 Token 计量和费用使用相应的用量回执。

单独运行下列命令会按输入 JSON 已记录的状态重放，每个 ready 都进入宿主。重演排队后撤权的过程，请从订单总入口运行，它会在每个场景送达时调用授权复核。输出的 `cases` 按场景给出 `selected`、`observed_sha256` 与真实线程和回合，独立校准位于 `catalog_control`，其一次请求单列计数。

```bash
python3 prototypes/topic-03b/composition/observe_composition.py \
  --plan "$work/plan.json" --output "$work/host.json" --codex /absolute/path/to/codex
```
