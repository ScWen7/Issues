# 已打开的成员会话怎样接订单

订单节点仍是 `verify-order-export`，使用 D2 核验候选 C2。要决定能否在原会话开工，先问这个会话由谁控制、下一条模型请求会带上哪些历史、当前生效的项目工具与 Hook 从何而来。本轮把成员的个人回合放在订单回合之前，分别观察了两次真实的模型协议请求、MCP 子进程、工作簿结果和节点消费。模型端点在本机按固定次序返回工具指令和结束消息。成员、授权和订单使用实验数据。[复跑入口](../../../prototypes/topic-03b/cross-host/order_existing.py) · [机器可读回执](fixtures/existing-session.json)

## 怎样读这些结果

| 成员正在做什么 | 业务提示送到哪里 | 取到了什么证据 |
|---|---|---|
| 成员在 Codex 终端完成个人回合，明确向工作台共享该端点和已知历史，在订单回合期间停止输入 | 原线程 | 真实前台 TUI 仍在线。第二个通过认证的客户端重新加入相同线程，在不同 turn 调项目核验工具。实验还单独验证连接端点时缺少令牌会被拒绝 |
| Codex 旧回合的历史授权收回，或历史中多了一个未选中的回合 | 同一宿主的新线程 | 本机先只核对回合 ID 与状态。原线程没有订单请求，两次新请求都未出现旧标记。三份工作簿随原订单的尝试 2 入账 |
| Codex 旧线程还开放个人同名 MCP，或缺少原配置版本回执 | 同一宿主重新限定工具的新线程 | 原线程收到零次订单请求。新线程回读的项目 MCP、模型请求里的工具名、实际调用的提供方一致 |
| Claude Code 的已有进程由成员通过控制流协作，历史授权与已知 Hook 配置匹配 | 原 Session 的新 prompt | 原生工具调用、前后 Hook、服务事件以及第二次 Messages 请求用同一调用 ID 对齐。一次工具执行只产生一条服务事件 |
| Claude Code 旧历史撤回，或原会话启用了未批准的额外 Hook | 另开严格配置的进程和 Session | 额外 Hook 在旧个人回合确实触发过。两种情形下原会话的订单请求数均为零，新会话完成原节点核验 |
| 两种宿主已选好原会话，工具执行前撤回任务授权 | 服务拒绝，原节点等待 | 宿主把拒绝送回本轮模型。没有可接收的核验报告，节点消费和制品关联数均为零 |

**订单在会话开始后才派到成员时，也做了单独验证。** Claude Code 先完成个人回合，此时 MCP 列表、任务凭证、派发和工具账本都是空的。控制者随后签发订单，沿原控制流增加项目 MCP、配置指定工具权限并回读，再由同一 Session 的新 prompt 调用工具。接收器读回三份工作簿，重投仍只消费一次。本例在已知为空的 MCP 集合上新增项目服务；带有成员原配置的现场须核对已有连接与权限。[晚到派发实验](../../../prototypes/topic-03b/cross-host/claude_late_binding.py)

其他复用场景在启动时已配置本次工具，使用隔离成员环境和固定的本机模型端点。Codex 的 MCP 检查按线程进行，Hook 清单按工作目录查询。Claude Code 用启动配置、控制流、已连接 MCP 来源与工具 Hook 交叉确认。真实商业模型的内部路由以及任意成员 IDE 的全量配置不可从上述读数外推。工作台向团队共享本次派发、宿主与调用标识、观察范围、报告及具名制品。个人历史正文只留在本机实验观察中。[Codex 实验](existing-codex.md) · [Claude Code 实验](existing-claude.md) · [源码依据](existing-session-sources.md)

## 两个会改变派发决定的反例

**Codex 检查完历史后，成员仍可以输入。** 平台客户端加入正在运行的 App Server，读到唯一的已授权回合。成员随后在同一线程发出另一条合成消息；平台再发送无业务数据的诊断请求时，后者实际带上了刚加入的成员消息。全程零订单提示、零 MCP 调用。因此，原线程直连只适用于输入来源受控、历史授权可保持到本轮提交的情形。双方还能独立输入且无法协调时，直接在新线程按当前权限组装订单上下文。[原生顺序实验](../../../prototypes/topic-03b/cross-host/codex_existing.py)

**Claude Code 的工具成功返回后，Hook 仍可修改模型看到的内容。** 实验 Hook 在成功的项目工具响应外层加了一条演示备注。服务回执、Run 和调用 ID 正确，原生工具结果与第二次模型请求均为修改后的摘要。标准核验入口因服务摘要不同拒绝建立本次执行证明。节点消费和制品关联均为零。控制者随后让相同 Run 在新受管会话里重新执行只读核验，从未修改的报告消费一次。两次服务执行分别记录。若业务允许某种转换，应在该契约里明确允许转换的字段和核验方法。[Hook 实验](../../../prototypes/topic-03b/cross-host/claude_existing.py)

## 复跑

从仓库根目录执行，使用专题三 B 上一阶段固定的两种 Linux 宿主二进制。临时路径应当尚不存在。回归只上传筛选后的摘要。

```bash
python -m pip install XlsxWriter==3.2.9 openpyxl==3.1.5 websockets==16.0 pexpect==4.9.0
python prototypes/topic-03b/cross-host/order_existing.py /tmp/order-session-evidence \
  --codex /path/to/codex --claude /path/to/claude
```

每个一般场景单独建账。`cases` 保存原会话与最终会话、工具调用、返回和消费记录。`concurrent_input` 保存两个 Codex 客户端交替发言后的可见性观察。`post_hook_result` 将变更过的响应与干净会话的复验分开保存。真实员工的组织账号、未接入平台的 IDE 窗口、生产订单服务和正式业务验收属于现场验证范围。
