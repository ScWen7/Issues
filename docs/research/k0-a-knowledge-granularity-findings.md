# K0-A · 知识资产粒度研究结论

> 研究状态：完成  
> 研究分支：design/system-architecture-convergence  
> 研究范围：知识资产的组织粒度、证据关系、局部维护和研发消费；不涉及底层技术选型。

## 1. 结论

**团队知识中心采用“主题知识资产 + 可独立核验的结论单元 + 来源证据”的组织方式。**

主题资产是成员浏览、领域维护、归属和长期运营的主要边界；结论单元是检索、引用、核验、局部修订和失效判断的主要边界；来源证据是结论成立与否的依据。三者不能混为一层。

这里的“可独立核验”不等于“每条结论都必须成为一个独立知识资产”。只有当一条结论确实需要独立的适用范围、责任人、发布/撤回、版本演进或冲突裁决时，才将它提升为独立 Knowledge Item。其余结论保留在主题资产内部，以稳定的结论标识和证据锚点管理。

这不是整篇文档模式与原子知识模式的折中拼盘，而是明确划分三种边界：

- **主题边界**：人如何理解、浏览、维护一组相关知识。
- **结论边界**：系统如何精准检索、核验、更新和判断失效。
- **证据边界**：结论依赖哪些来源修订、具体位置和实际执行事实。

### 1.1 三种组织模式的最终判断

| 模式 | 适合承担的职责 | 不适合承担的职责 | 结论 |
|---|---|---|---|
| 整篇文档作为知识资产 | 原始材料归档、完整复盘阅读、保留上下文 | 精确检索、局部更新、不同结论独立失效、跨项目派生 | 保留为来源或主题附件，不作为唯一知识组织方式 |
| 每条原子结论独立成为知识资产 | 少数需要独立治理的规则、关键决策、可单独撤回的高风险结论 | 普通知识的主要组织方式；承载复杂背景、维护领域关系 | 仅作为例外提升机制，不作为默认方式 |
| 主题资产 + 可核验结论 + 来源证据 | 主题浏览、细粒度检索、证据追溯、局部维护、分布式责任 | 不能省略结论边界与证据治理，否则会退化成普通长文 | **推荐作为默认组织方式** |

## 2. 研究依据与真实样本

本轮优先使用仓库已有研究和原始记录，没有重新运行专题三 B 已完成的合成实验。

### 2.1 业务规则：订单导出 D2、C1 / C2

主要资料：
- [订单文档改版后，开发与核验实际收到什么](topic-03b/project-knowledge.md)
- [从一次区域订单导出返工到团队测试经验](topic-03b/knowledge-contribution.md)
- [C1 原始核验报告](topic-03a/fixtures/order-export-c1.json)
- [C2 原始核验报告](topic-03a/fixtures/order-export-c2.json)
- [订单导出实证](03a-source-evidence.md)

真实观察：
- D2 是同一 Issue、同一核验节点使用的业务规则；C1 的付款时间检查 A3 通过，但东区普通账号拿到了西区订单，结果为返工。
- C2 使用相同规则和核验器，东区结果排除西区订单，跨区账号仍能导出两区订单，结果通过。
- 这不是一个“订单导出结论”可以概括的单一事实：至少存在可见范围、跨区账号行为、付款时间列三个可分别观察的检查结论，同时它们又必须放在同一个业务规则和核验主题下理解。
- 复盘中第一稿包含项目订单号，被退回；第二稿提炼为团队测试方法，并经来源派生授权与独立团队审核后发布。团队读者只看到批准文案，不能读取原始项目报告。
- C1 的来源修改、撤回、恢复会影响派生知识的新投递资格；C2 的证据仍然有效时，不应被 C1 的变化一并作废。

粒度判断：
- 整篇文档模式会把范围检查、付款时间检查和跨区行为绑定成一个整体，局部证据变化容易造成整篇知识重审。
- 原子模式若把每个检查结果拆成孤立知识，会丢失“同一 D2 标准下如何组合检查”的背景；若把项目订单事实直接原子化发布，还容易造成权限与派生边界错误。
- 主题资产可维护“订单导出权限与核验”主题，内部列出各结论、适用角色和各自证据；可复用的测试方法在获得派生许可后形成团队范围的独立知识资产。项目原始报告仍留在项目范围。

### 2.2 技术决策与授权边界：来源权限、派生许可和发布复审

主要资料：
- [知识贡献与复审实证](topic-03b/knowledge-contribution.md)
- [专题三 B 来源与知识实证](03b-source-evidence.md)
- [统一业务对象模型](../architecture/core-business-object-model.md)

真实观察：
- 项目读取权、每份证据的对外提炼许可、目标团队受众授权、独立团队发布权是不同权限；拥有其中一项不代表拥有其他权限。
- C1 / C2 两份证据组合成一条团队测试经验时，授权绑定目标受众、正文摘要、稿号、每份证据摘要及其变更代次。
- 只管理 C1 的成员可以撤回 C1 对指定团队文案的派生许可；这会暂停该派生知识的投递，但不影响 C2 的来源、其他受众许可和历史派发。
- 来源内容即使恢复成完全相同的字节，来源变更代次仍不同；重新授权后仍需独立复审。证据矛盾或来源撤回可以使知识退役。
- 团队知识的正文发布与 Harness 规则发布分开治理；从测试经验升级为验收规则，需要另走 Harness / Issue 的责任链。

粒度判断：
- 整篇文档难以表达“只撤回 C1 这一份证据的派生许可，而保留 C2 及已发生的历史派发”。
- 原子结论便于隔离许可，却可能把一条由多份证据共同支持的综合经验拆散；也可能误以为每条证据各自等于一条知识。
- 主题资产承载整体测试方法和复审背景；内部结论分别列出支持证据、派生范围和有效状态。涉及不同授权、发布、撤回或生命周期的结论才独立提升为 Knowledge Item。

### 2.3 项目 / 系统说明：来源修订与角色化上下文

主要资料：
- [订单文档改版后，开发与核验实际收到什么](topic-03b/project-knowledge.md)
- [知识来源与可见性](topic-03b/knowledge-sources.md)
- [知识管理生命周期](../architecture/knowledge-management-lifecycle.md)

真实观察：
- 订单需求从修订 1 到修订 2，维护者新增可选文案、将“开发说明”改名为“开发时区”并改写正文；共同业务约定和开发说明沿用各自标题块 ID。
- 开发与核验使用同一业务主题，但需要不同段落；开发需要时区转换说明，核验需要角色范围核验说明。核验者即使有整份需求文档的读取权，也不应收到仅适用于开发角色的材料。
- 两份在途队列都固定了旧来源修订，因此都必须重新选择；已送达历史只需按真实使用过的旧正文定位影响。权限收缩后，原线程历史仍可能包含旧内容，需用干净线程按当前权限重建。
- TeamAI 的代码知识新鲜度检查还区分 current、stale、missing、unknown，并以仓库身份、路径和代码基准核对锚点；它说明系统说明不能只有一篇不带基准的静态描述。

粒度判断：
- 整篇文档作为唯一知识单元，不能自然表达角色差异、局部改名和某段内容的独立变化。
- 原子模式若只返回孤立段落，成员无法理解模块、业务和角色之间的关系，也容易让 Agent 将局部说明误当成完整系统事实。
- 主题资产维护项目系统说明和导航；每条结论标注适用角色、模块、代码基准、来源位置和有效状态。检索时只返回授权且相关的结论，同时保留主题摘要与相邻背景入口。

### 2.4 踩坑经验：从失败事实到可复用方法

主要资料：
- C1 / C2 原始核验报告与知识贡献实验
- [知识贡献与复审实证](topic-03b/knowledge-contribution.md)

真实观察：
- C1 单次失败并不能证明通用方法；C2 在同一标准、同一核验器下的复验提供了对照。
- 值得推广的不是“订单号为某值的这次失败”，而是“区域账号与跨区账号分别核对订单集合，并单独检查付款时间列”的方法。
- 这个方法仍需要保留其来自哪两次 Run、哪项规则、哪些检查位置和哪次独立审核的依据。

粒度判断：
- 整篇复盘便于了解过程，但后续研发只需要其中的测试方法时，难以精准提取。
- 原子模式可能把“区域账号检查”和“付款时间列检查”变成互不关联的碎片，丢失组合验证的必要性。
- 主题资产保留复盘脉络；经验证、可迁移的测试方法作为主题中的结论单元，必要时独立发布为团队知识。

## 3. 三种模式在真实维护操作中的对照

| 维护操作 | 整篇文档 | 原子知识 | 主题资产 + 结论 + 证据 |
|---|---|---|---|
| 新增一条结论 | 追加文档并重审整篇；难区分新增内容是否影响原结论 | 新建条目，容易形成大量细碎条目 | 在主题中新增结论，绑定证据；仅影响相关主题修订 |
| 修订一个结论 | 整篇修订，其他内容也随版本变化 | 只改单条，但要维护与主题、相邻结论的关系 | 结论局部修订；主题修订记录整体结构变化，其他结论不必重新核验 |
| 一条证据被反驳 / 撤回 | 整篇通常被标为待复核，影响范围过大 | 直接使单条失效，但多证据综合结论和背景容易丢失 | 只标记依赖该证据的结论待复核；其他结论和证据不受牵连 |
| 一份来源支持多个主题 | 复制文档或跨文档引用，容易重复 | 多条原子知识引用同一来源，维护链接复杂 | 同一来源修订 / Evidence Anchor 被多个主题的结论引用 |
| 证据仅对一个项目可见，但结论想跨项目复用 | 容易把原文连同私有内容整体复制 | 原子条目若缺少来源派生授权容易泄露 | 主题结论只发布获准的派生文案；原始证据留在项目范围，权限分别校验 |
| 主题中部分内容过期 | 整篇状态难以表达“局部过期” | 精确，但每条都需要独立身份和维护 | 局部结论待复核 / 失效，主题保留有效内容并显示局部状态 |
| 同主题有冲突来源 / 不同适用范围 | 冲突混在正文中，难定位 | 单条可能被错误覆盖或重复建条目 | 结论并列声明来源、版本、适用范围和冲突；未裁决前不强行合并 |
| Issue 只需要其中一条结论 | 返回整篇，噪音大 | 返回单条，但缺乏必要上下文 | 返回结论 + 适用条件 + 主题摘要 + 证据入口 |
| 人工理解完整背景 | 强 | 弱，依赖大量交叉链接 | 强，主题提供叙事，结论提供精度 |
| 长期维护成本 | 单条修改影响面大，审查边界粗 | 条目数量、去重、关系和审核责任膨胀 | 以主题分配维护责任，结论按需独立治理，成本相对可控 |

### 3.1 关键发现

1. **来源修订与知识修订不能一一绑定。** 一个来源变化可能只影响某几个证据锚点和结论；一个结论也可能由多份来源共同支持。
2. **证据单元不等于知识单元。** 解析块、段落、代码符号和 Run 回执用于定位与证明，不应自动生成 Knowledge Item。
3. **检索粒度不等于维护粒度。** Agent 可以只取一条结论，维护者仍然通过主题资产理解它与其他结论的关系。
4. **发布边界由独立治理需求决定，不由文本长度决定。** 一句话规则如果有独立授权、适用范围和撤回要求，可以独立成项；十页说明如果只有一个共同维护责任，也可以仍是一个主题资产。
5. **主题本身不能替代结论核验。** 不能因为主题整体已发布，就推断其中每一条结论都仍有效；也不能因为一条结论过期，就把整个主题全部作废。

## 4. 推荐的内容组织模型

### 4.1 三层内容关系

**第一层：主题知识资产（Knowledge Topic / Knowledge Item）**

承担：
- 稳定主题身份、名称、摘要和主题范围；
- 团队 / 项目作用域及主题标签；
- 主题维护者与协作维护者；
- 主题内结论目录、关联主题和导航；
- 主题整体版本与内容组织变化。

主题是人工维护和浏览的主要入口。它不应复制权威来源全文，也不应把全部证据嵌入正文。

**第二层：结论单元（Claim）**

每条结论至少表达：
- 清晰、可验证的主张，而不是泛泛摘要；
- 类型：事实 / 约定、决策 / 理由、实践 / 方法、问题 / 踩坑、系统解释或待确认认识；
- 适用范围、版本 / 环境、前置条件和例外；
- 结论状态：有效、待复核、冲突、被替代、失效或未确认；
- 支持证据、反例和未解决问题；
- 维护责任（默认继承主题维护者，可显式指定不同责任人）。

Claim 默认是主题修订中的结构化内容，不默认是独立资产。它应具有稳定的局部标识，以支持局部引用和来源影响分析；局部标识本身不等于独立发布权或独立生命周期。

**第三层：来源证据（Evidence / Evidence Anchor）**

每条证据应指向：
- 来源身份与来源修订；
- 精确位置：章节 / 块 / 页 / 表格单元 / 代码符号 / Issue / Run / Artifact 检查位置；
- 内容摘要或可校验摘要；
- 取得、解析和核验事实；
- 当前权限、来源代次和可访问性；
- 证据角色：支持、反驳、限定条件或背景。

一个证据可以支持多个结论；一个结论可以由多份证据共同支持。证据记录不等于把原始资料复制成知识。

### 4.2 主题、结论、证据的版本关系

- 来源修订不可变；同一来源后续变化产生新修订或新变更代次。
- 主题 Knowledge Revision 固定该版本的主题结构、结论集合、适用范围和维护信息。
- 结论在主题内有稳定局部标识；内容变化形成该主题新修订中的结论新版本。
- Evidence 引用必须指向明确来源修订与位置；不以“当前文档”这种可变指针作为唯一依据。
- Knowledge Release 发布某个 Knowledge Revision；历史工作固定引用当时选用的 Release / Revision。
- 如果某条结论需要独立发布、撤回、授权、版本或冲突治理，则将其提升为独立 Knowledge Item，拥有自己的 Knowledge Revision / Release；原主题通过引用纳入该结论，不复制正文。

这与现有对象模型保持兼容：沿用 Knowledge Item、Knowledge Revision、Release、Evidence 和 Work / Run Asset Pin，不新增“每条结论都必须有完整生命周期”的普遍规则。现有对象模型中的 Knowledge Item 可代表主题资产，也可代表确实需要独立治理的结论资产。

### 4.3 哪些情况需要把结论提升为独立 Knowledge Item

至少满足一项明确的独立治理需求，并且其复用价值足够稳定：

1. 适用范围与主题其他结论明显不同，需独立决定团队 / 项目范围。
2. 需要独立发布、暂停、撤回或退役，不能跟随主题整体发布。
3. 来源许可、受众或敏感级别不同，需要独立授权和复审。
4. 需要独立版本化，且历史工作必须精确固定这一条结论。
5. 冲突需要由不同领域责任人裁决，不能由主题维护者统一处理。
6. 被多个主题、多个项目或多个工作流高频复用，作为独立身份比重复引用更清晰。

不应仅因以下原因拆分：
- 一段文字很短；
- 一条结论能被语义检索命中；
- 文档解析成一个 Chunk；
- 一份来源中有多个段落；
- 模型可以把句子拆成主谓宾；
- 希望统计“知识条目数量”。

## 5. 四类知识的默认组织方式

| 知识类型 | 默认主题资产 | 结论单元 | 何时独立成项 |
|---|---|---|---|
| 业务规则 / 业务约定 | 业务主题，例如订单导出规则与权限边界 | 规则主张、角色差异、例外、版本条件、验收口径 | 规则有独立责任人、授权范围、发布节奏或需要单独撤回 |
| 技术决策 / 架构选择 | 系统 / 架构主题，例如某服务边界与技术决策 | 决策、背景、备选项、取舍理由、适用边界、后续验证 | 决策会跨主题复用或需独立 ADR 生命周期；被替代时需单独追溯 |
| 踩坑经验 / 故障复盘 | 故障主题或领域实践主题 | 现象、触发条件、根因、验证过程、修复和预防方法 | 已验证的通用方法被多个项目采用，或需要独立发布为团队经验 |
| 项目 / 系统说明 | 项目 / 系统主题或模块主题 | 模块职责、调用关系、代码事实、接口边界、运行约束 | 某条跨项目通用架构约束或独立组件契约需要单独治理 |

## 6. 编辑、检索与维护规则

### 6.1 人工编辑

- 领域维护者在主题视图中维护一组相关结论，不要求成员在几十个原子条目之间来回跳转。
- 每条结论显示证据完整性、适用范围、当前状态和最近核验依据。
- 修改一个结论时，默认只要求核验该结论及其直接依赖；主题结构或共同前提变化时，才扩大到相关结论。
- 对同一结论的修订必须说明改变了什么、为什么改变、哪些证据新增 / 撤回。
- 原始来源继续在飞书、Git、Issue 或代码仓等权威位置维护；知识中心只编辑派生知识，不成为第二份原始文档。

### 6.2 Agent 检索

Agent 检索的返回单位不是“整篇主题”也不是“裸原子句”，而是**结论包**：

1. 本次工作相关的结论正文；
2. 适用范围、条件和例外；
3. 最小必要的相邻背景 / 主题摘要；
4. 支持与反驳证据的引用和来源修订；
5. 结论有效状态、冲突提示和维护责任；
6. 可展开的完整主题入口。

如果同一问题命中多个互相依赖的结论，应组合返回；如果只命中一个结论，也必须带上足以避免误用的上下文。来源权限检查先于内容返回；无法证明当前可访问或有效的证据不能作为当前有效结论静默投递。

### 6.3 局部更新和失效

| 变化事件 | 最小影响范围 | 不应发生的事 |
|---|---|---|
| 来源新增或修改 | 受影响 Evidence Anchor、依赖结论及其待复核状态 | 不重写整个主题，不自动把来源新内容当结论 |
| 单条证据撤回 / 权限收缩 | 依赖该证据的结论、相关派生授权和新投递资格 | 不连带撤销无关证据支持的结论 |
| 结论被反驳 | 该结论及依赖它的结论；主题显示局部冲突 | 不静默覆盖历史版本 |
| 结论适用范围变化 | 该结论的适用声明和相关受众投递 | 不把新范围套用到主题内所有结论 |
| 主题结构重组 | 主题新修订与受影响结论的导航关系 | 不因此自动改变结论本身的事实版本 |
| 多来源冲突 | 冲突结论并列保留，等待有权责任人裁决 | 不按更新时间或模型置信度自动覆盖 |
| 结论被替代 | 新旧结论建立替代关系，定义生效范围 | 不删除旧版本和历史工作引用 |

历史工作保留当时固定的知识版本与投递事实。来源当前权限收缩后，查看原文仍按当前权限控制；平台不声称能够远程删除已进入宿主历史的内容。

### 6.4 维护责任

- **主题维护者**对主题范围、结构、导航、结论完整性和责任覆盖负责。
- **结论责任人**仅在结论被显式分配独立责任时负责其事实核验和适用范围。
- **来源维护者**负责原始来源及其修订，不自动承担派生知识正确性。
- **领域 / 项目发布者**按既有知识发布治理规则确认候选；高风险、跨项目知识需相应独立确认。
- **Agent**可发现、归纳、提出候选和提示影响，不自行决定高风险事实、派生授权或正式发布。

默认先由主题维护者承担结论维护，不为每条结论强制分配一个 Owner；只有确有独立治理需要时才拆分责任。这样避免“条目拆得越细、Owner 越多、无人维护”的责任碎片化。

## 7. 对现有对象模型的修订建议

### 7.1 保持不变的对象边界

- Source Item / Source Revision 仍代表权威来源身份和不可变修订。
- Evidence Anchor 仍是解析结构中的位置定位，不是知识对象。
- Evidence 仍表示某个可核验观察或对来源内容的引用；无需为每个 Chunk 建立 Evidence 业务记录。
- Knowledge Item / Knowledge Revision / Knowledge Release 沿用现有身份、修订和发布语义。
- Harness Asset / Revision 继续独立于 Knowledge。
- Work / Run Asset Pin 只固定实际被选用的版本，不因每次检索命中就创建。

### 7.2 需要补充的语义

1. Knowledge Item 默认可代表一个主题资产；必要时也可代表独立治理的结论资产。
2. Knowledge Revision 应能表达有序主题结构及其结论单元，而非只有一段无结构正文。
3. 主题内结论需有稳定的局部标识，支持引用、证据依赖、局部状态和变更影响分析；局部标识不自动获得独立 Release。
4. 结论应能关联多份支持 / 反驳 / 限定证据，并声明适用条件、范围和有效性。
5. 独立结论资产通过 Knowledge Item 身份与主题建立引用关系，不复制相同正文。
6. 来源变化的影响分析应落到 Evidence → Claim → Topic 的依赖关系，不以来源文档或整篇主题为唯一失效单位。
7. 主题修订与结论内容修订应区分：主题目录 / 导航调整不代表所有结论事实都变了；结论变化也不必导致无关结论重新核验。

本轮只提出内容语义补充，不设计数据库 Schema、API、索引或部署结构。

## 8. 证据强度与未决事项

### 8.1 已由现有实证支持

- 来源修订、权限、角色范围和实际宿主输入必须共同决定本次可用内容；整篇文档权限不等于每个角色都应收到整篇内容。
- 结论派生许可与来源读取权分离；多份证据组合发布时，必须逐份追溯来源和授权。
- 来源撤回、同字节恢复、证据变更和冲突会产生不同治理结果；历史发布和历史派发不能被新状态覆盖。
- C1 / C2 的事实和测试经验可以分开表达；项目证据可保持私有，团队只获得批准的派生结论。
- 代码知识需要绑定代码基准并区分 current、stale、missing、unknown；静态说明不能冒充当前实现事实。
- 知识与 Harness 分开治理；同一执行证据可以支持知识改进与方法改进，但两者的发布和采用不同。

### 8.2 本轮形成的设计判断，仍需后续验证

- 主题资产 + 结论单元是否能在真实团队规模下保持可维护，尤其是主题过大、跨主题重复和多人同时编辑时。
- 主题修订中结论局部版本的最合适表达方式，以及独立结论提升为 Knowledge Item 的触发阈值。
- 真实飞书文档、复杂表格、代码图谱等不同来源中，Evidence Anchor 的稳定性和局部变更判定。
- 主题维护者的实际工作量、结论复核频率和 Agent 自动提炼的可接受程度。
- 检索时结论包应带多少相邻背景，才能兼顾上下文完整和宿主上下文预算。

### 8.3 不属于本轮范围

- 数据库、存储、向量检索、全文检索、解析供应商和部署选型；
- 知识中心页面视觉与工作台交互原型；
- 团队维护者的组织编制和具体人员分配；
- 自动发布阈值和具体运营 KPI；
- 生产规模下的并发编辑、索引性能和服务可用性验证。

## 9. 最终设计准则

后续 K0-B 至 K0-F 和架构融合应遵守以下准则：

1. **以主题组织知识，不以原始文档或 Chunk 组织知识。**
2. **以结论作为检索和核验的最小语义单元，不要求每条结论都是独立资产。**
3. **以证据引用支撑结论，不把摘要、模型推断或检索片段当作事实本身。**
4. **以独立治理需求决定是否拆分 Knowledge Item，不按字数、段落或检索命中拆分。**
5. **局部事实变化只影响依赖它的结论；主题结构变化不自动改变所有结论事实。**
6. **主题维护者承担默认维护责任；只有确有必要才把结论责任独立出去。**
7. **Agent 消费结论包，同时能够回到主题和证据；不能只返回裸句子。**
8. **项目证据和团队派生结论分别治理；任何跨范围复用都必须满足来源许可和适用性核验。**
9. **知识与 Harness 分开维护；知识经验转成规则或 SOP 时进入 Harness 自身的验证和发布流程。**
10. **知识中心是团队研发能力的长期积累，不是把所有资料重新写一遍的第二套文档系统。**
