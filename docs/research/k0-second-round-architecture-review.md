# AgentPlatform · K0 第二轮补充调研与架构评审

> 研究状态：完成  
> 研究范围：融合 Argon 对团队知识中心的补充设计；不修改 AgentPlatform 整体产品架构，不进入数据库 Schema、API、部署或工程实现。

## 1. 执行摘要

### 1.1 核心结论

第一轮 K0 确定了团队知识中心的资产治理基础；K0-A 确定了主题资产、结论单元和 Evidence 的粒度边界。Argon 的重要贡献，是指出知识中心不应停留在“管理和检索知识”，而应成为研发工作中的上下文编译与供给能力。

本轮融合后的定位：

**团队知识中心以可复用知识资产为治理核心，以权威来源和 Evidence 为事实依据，以项目认知视图为项目级上下文入口，以编译和供给能力将适用知识送入 Issue 与 Agent 的实际工作。**

知识中心需要区分四种性质不同的内容：

1. **权威来源与证据层**：原始资料、代码、决策、执行与测试证据；权威仍归原系统或原业务对象。
2. **正式知识层**：以主题资产组织，内部包含可独立核验的结论单元；少数需要独立治理的结论才拥有独立 Knowledge Item 身份。
3. **派生认知层**：项目认知视图、模块地图、服务关系、摘要和差异分析；从来源与正式知识编译，不成为第二份权威文档。
4. **工作上下文层**：根据 Issue、项目、角色、Agent 能力、权限和代码基准动态编译的上下文包；属于一次工作输入，不是长期知识资产。

### 1.2 Argon 九个方向评审

| Argon 方向 | 判断 | 融合后的决定 |
|---|---|---|
| 上下文编译与供给中心 | 采纳 | 作为知识中心核心能力定位，与知识治理并列 |
| 原始资料 + 编译态知识 | 采纳但调整 | 区分正式知识、派生认知、临时上下文 |
| 原子化 Knowledge Entry | 采纳但调整 | 结论单元是检索与核验粒度，不是默认独立资产 |
| 项目认知视图 | 采纳 | 动态派生的项目认知入口，不是人工维护的第二份 Wiki |
| 伴生式知识采集 | 采纳 | 由研发事件触发候选发现，不对所有事件调用 LLM |
| 项目成熟度分层 | 采纳但调整 | 按领域 / 模块的资料和实现成熟度选策略，不给项目贴永久等级 |
| 推式 + 拉式消费 | 采纳 | 必需约束主动供给，导航轻量提供，细节按需检索 |
| 自动更新与失效检测 | 采纳但调整 | 自动发现变化、分析影响、起草 Diff；不由代码变化直接判定知识过期 |
| 知识向 Harness 转化 | 采纳但调整 | 自动提出候选，独立评测、审核、发布和项目采用 |

### 1.3 不采纳的具体细节

- 不以每条 100–500 字 Entry 作为唯一正式资产形态。
- 不采用代码、PR、PRD、ADR 的全局统一来源优先级。
- 不使用单一 Confidence / Utility Score 判断知识正确性。
- 不因 AST、文件路径或 Commit 变化直接将知识判为失效。
- 不强制所有知识绑定 AST、符号或代码路径。
- 不以检索频次、采纳次数作为 Harness 自动晋升门槛。
- 不对所有 Agent 和宿主承诺确定性注入或 100% 召回。
- 不为项目认知视图另建一套人工维护的项目 Wiki。
- 不复制 Issue、Run、Session、PR 或项目文档作为新的权威工作对象。

## 2. 第一轮研究基线与本轮边界

### 2.1 第一轮已经确定的方向

第一轮 K0 的基础定位是：来源为依据、知识资产为中心、证据为纽带、研发工作为入口、维护责任分布到领域。

K0-A 已完成，确定：
- 主题知识资产是人工浏览、维护和责任归属的主要边界；
- 结论单元是检索、引用、核验和局部失效的主要边界；
- Evidence 是结论依据；
- 结论默认不独立成为 Knowledge Item；只有确有独立适用范围、责任、发布 / 撤回、版本或冲突治理需求时才提升为独立资产；
- 来源 Chunk / Block 是解析与定位单元，不是知识资产身份。

本轮不重开这些决定，而是补充编译态、项目认知视图和知识供给。

### 2.2 Topic 3B 实证边界

本轮继承以下已有实证，不重复运行已完成的合成实验：

- TeamAI 来源导入、角色检索、内容变化和失效的 42 项测试；
- Multica PostgreSQL 项目权限、任务访问与撤权后的索引删除对照；
- 真实 Codex CLI 0.144.6 App Server 请求探针，核对开发与独立核验角色实际收到的正文；
- 来源修订后在途队列重新选择、历史线程携带旧正文、失权后新线程按当前权限重建；
- C1 / C2 项目证据提炼团队经验，包含项目私有信息拒绝、逐来源派生授权、独立审核、发布、撤回、恢复、复审和退役；
- 知识贡献 45 项正反向检查及 5 项单来源撤回回归。

这些实验验证了来源权限、证据追溯、派生授权、投递和撤回机制的关键行为；不等于生产飞书同步、广域语义检索排序、多人并发维护和长期知识运营已全部验证。

## 3. 四种知识组织模式比较

### 3.1 模式本质

| 模式 | 维护中心 | Agent 消费 | 主要风险 | 判断 |
|---|---|---|---|---|
| A. 原始资料中心 | 文档、代码和原始记录 | 原文 / Chunk 检索 | 旧版本冲突、噪音、缺乏适用范围和责任 | 不作为知识中心主模型；保留为来源底座 |
| B. 原子化知识中心 | 每条事实 / 经验独立资产 | 精确 Entry | 条目爆炸、主题关系丢失、责任碎片化 | 不作为默认维护模型 |
| C. 主题知识资产中心 | 主题资产及其结论单元 | 结论 + 条件 + 证据 | 若没有编译层，Agent 仍需自行拼上下文 | 作为正式知识治理核心 |
| D. 编译态知识中心 | 结构化知识及动态派生物 | 面向任务的上下文包 | 若把派生物都当正式资产，会形成多份真相 | 采纳为知识中心运行能力，不替代 C |

结论：**C 负责长期知识治理，D 负责知识编译与供给；两者组合，而不是二选一。**

### 3.2 业务规则：订单导出 D2 / C1 / C2

真实材料：
- [项目知识与真实宿主输入](topic-03b/project-knowledge.md)
- [知识贡献与复审](topic-03b/knowledge-contribution.md)
- [C1 原始核验报告](topic-03a/fixtures/order-export-c1.json)
- [C2 原始核验报告](topic-03a/fixtures/order-export-c2.json)

事实：
- C1 的付款时间列检查通过，但东区普通账号拿到了西区订单，整体返工。
- C2 在同一 D2 规则和核验器下修复了区域订单集合问题，跨区账号仍能导出两区订单，整体通过。
- 团队最终提炼的是“分别使用区域账号和跨区账号核对订单集合，并单独检查付款时间列”的测试方法，而不是把订单号、项目报告原文发布给团队。
- C1 和 C2 是不同证据；C1 单独撤回时，不应让 C2 的来源、许可和历史派发一起失效。

四种模式的结果：
- A 能保存完整报告，却不能自然表达“付款时间通过、可见范围失败”的不同结论，也不适合只给后续 Issue 返回其中一项。
- B 可以分别保存区域范围、跨区行为、付款时间结论，但若把每个检查点都建成独立资产，会失去组合验证方法和 D2 背景。
- C 维护“订单导出规则与核验”主题，内部包含各检查结论和证据依赖；经授权的通用测试方法可以成为独立团队知识。
- D 面向当前核验任务生成结论包，按角色选择所需结论和证据，不必将整个主题或两份报告塞入宿主。

### 3.3 架构决策：Knowledge 与 Harness 的边界

真实依据：[核心业务对象与统一关系模型](../architecture/core-business-object-model.md)。

现有架构明确区分 Knowledge 与 Harness：
- Knowledge 表达可核验事实、经验和解释；
- Harness 表达可执行或可评估的方法、约束和规则；
- 两者可以共享最小 Release、Project Adoption 和工作版本引用机制；
- 但内容模型、核验标准、维护责任和评价方式不同。

A 将架构讨论原文作为知识，Agent 仍需从长文中找出当前有效决定。B 将每条决定拆成独立原子资产，能精确消费，却可能丢失决策背景、备选方案和被替代原因。C 以“服务边界与架构决策”为主题，分别记录决定、理由、适用范围、替代方案和证据；独立影响多个项目的约束才独立成项。D 根据当前 Issue、项目和改动范围，编译相关 ADR 结论、服务契约与 Harness 约束，不把全部架构材料注入每个 Agent。

### 3.4 技术故障复盘：从项目证据到团队经验

真实依据：C1 / C2 的失败与修复，以及 [知识贡献实验](topic-03b/knowledge-contribution.md)。

- A 适合阅读完整故障经过，但下一个项目只需要其中的预防方法时，检索范围过大。
- B 能把根因、修复和预防方法分别存储，却可能把一次偶然现象误当作通用知识。
- C 保留故障主题、现象、触发条件、根因、修复和验证过程；其中已验证且可迁移的方法成为结论单元，跨项目发布时重新核验和授权。
- D 面向当前任务只编译相关避坑结论、适用条件和复现 / 验证依据；不将整段 Agent 对话当作正式知识。

一次失败不自动形成通用经验；一次成功也不自动证明方法普遍有效。必须区分观察事实、根因推断、修复动作和独立验证结果。

### 3.5 项目模块与系统调用关系

真实依据：
- [知识来源与可见性](topic-03b/knowledge-sources.md)
- TeamAI 的代码知识图谱、代码新鲜度和角色化检索机制，详见专题三 B 研究。
- Backstage TechDocs 与 Software Catalog 官方机制。

A 依赖工程文档或代码全文搜索，难以提供稳定模块导航和责任关系。B 将模块、API、函数说明拆成大量条目，容易失去系统级关系。C 维护“支付系统架构”主题，包含模块职责、关键调用路径、重要契约和经确认的技术约束。D 根据当前 Issue 触及的服务和模块，动态生成项目认知视图和相关结论包。

模块调用图、API 清单、依赖关系可以由代码和接口描述动态提取；“为什么这样拆分”“哪些行为是业务不变量”仍需要有依据的知识结论。

### 3.6 总体取舍

1. 原始资料是事实来源，不是唯一消费形态。
2. 主题资产是长期维护入口，不能被原子条目替代。
3. 结论单元是精确消费与核验单元，不等于独立发布资产。
4. 编译态是知识中心运行结果，不能把所有派生结果都当作正式知识。
5. 项目认知视图是编译态的重要产品视图，不应变成新的人工维护文档。

## 4. 知识资产、结论、Evidence 与编译态的关系

### 4.1 四类核心内容及其权威性

| 内容 | 定义 | 权威归属 | 生命周期 |
|---|---|---|---|
| Source / Evidence | 原始来源修订及其可定位证据，或 Run / Test / Artifact 等真实观察 | 原系统、Issue、Run、Artifact 等原权威对象 | 来源修订、权限和观察事实生命周期 |
| Knowledge Topic / Item | 可长期复用的主题知识身份 | 知识维护者与知识治理 | 稳定身份、多次不可变 Revision、Release |
| Claim | 主题中的具体结论、条件、例外、适用范围和证据依赖 | 所属主题修订；独立治理时归独立 Knowledge Item | 默认随主题 Revision 版本化；独立项有自己的版本 |
| Compiled View / Context Package | 按范围、工作意图、接收者和基准编译的派生结果 | 编译输入清单与规则版本，不成为新的事实权威 | 可重建、可追溯；实际投递时固定本次输出摘要 |

### 4.2 主题资产与原子结论同时存在，但承担不同职责

主题资产负责主题身份、标题、摘要、范围和主题关系；结论组织、顺序、共同背景和导航；默认维护责任和整体完整性；人工浏览、编辑和审查入口。

结论单元负责具体主张；适用项目、系统、版本、角色和环境；前置条件、例外和反例；支持、反驳和限定证据；局部状态、局部引用和影响分析。

主题内结论需要稳定的局部标识，便于跨修订识别和证据依赖分析；但局部标识不自动获得独立发布权。

### 4.3 结论何时独立成为 Knowledge Item

满足明确的独立治理需求时才提升：
1. 适用范围明显不同，需要独立控制受众；
2. 需要独立发布、暂停、撤回或退役；
3. 来源派生许可或敏感级别不同；
4. 需要独立版本和历史工作引用；
5. 冲突需由不同责任人裁决；
6. 被多个主题、多个项目长期复用，独立身份更清晰。

不能仅因结论短、检索频繁、模型能拆句或解析成一个 Chunk 就独立成项。

### 4.4 主题修订不意味着全部结论重新发布

需要区分主题目录、导航和摘要变化；某一结论的正文或适用条件变化；结论证据变化；主题共同前提变化；主题整体范围或维护责任变化。

局部结论变化只更新相关 Claim 的内容与依赖状态；主题结构变化生成主题新 Revision，但不自动改变所有结论事实；共同前提变化时才扩大复核范围。

历史工作固定引用当时实际选用的 Knowledge Revision / Release。新主题版本不覆盖历史工作。

### 4.5 编译态知识不是一个新知识等级

建议区分三个编译产物：

**A. 正式知识编译结果**
- 从证据中提炼并经过治理的主题和结论；
- 可长期复用；
- 有稳定身份、版本、适用范围、维护者和发布状态。

**B. 派生认知视图**
- 项目概览、模块地图、调用关系、代码导航、主题摘要、变化影响报告；
- 由来源与正式知识自动生成；
- 标明生成时间、输入基准、来源和未确认部分；
- 可以缓存和版本化以便追溯，但不作为第二份权威知识正文。

**C. 工作上下文包**
- 针对某个 Issue、角色、Agent 和当前代码基准编译；
- 由正式知识、项目认知视图、权威来源片段和当前工作事实组成；
- 记录实际选择、投递和可观察的宿主消费证据；
- 不进入长期知识中心，除非从中发现可复用经验并走知识提炼。

### 4.6 避免主题、Entry、Chunk、项目 Wiki 重复

- Chunk / Block / AST 节点：解析与定位单元，不是知识资产。
- Claim：主题中的结论单元，必要时可独立升级。
- Topic：长期维护和浏览入口。
- Project Cognition View：动态聚合投影，不复制主题正文。
- Context Package：一次工作上下文，不作为持久知识。
- 原始 PRD / Git 文档 / Issue：仍由原系统维护，不在知识中心重写。

知识中心可以提供统一浏览体验，但不建立第二套项目 Wiki 编辑系统。

## 5. 项目认知视图（Project Cognition View）

### 5.1 定位

**项目认知视图是项目当前可解释状态的动态聚合视图，是项目知识中心的导航与上下文入口，不是新的正式知识资产类型。**

它回答：
- 项目是什么，服务什么业务目标？
- 系统由哪些关键模块和服务组成？
- 模块之间如何调用和依赖？
- 重要 API、数据结构和不变量是什么？
- 哪些架构决策和技术约束仍适用？
- 当前代码实现与已确认知识是否存在差异？
- 哪些部分未知、待调查或证据不足？

### 5.2 项目认知的三类内容

| 类型 | 例子 | 生成 / 维护方式 | 权威 |
|---|---|---|---|
| 已确认、相对稳定的项目知识 | 业务目标、模块职责、架构决策、接口契约、重要不变量 | 主题知识资产维护；Agent 提议修订，责任人确认 | Knowledge Revision + Evidence |
| 随代码 / 来源变化的项目事实 | 目录、模块、路由、API、依赖、表结构、测试覆盖、当前 Commit | Connector / 确定性分析提取，绑定来源和代码基准 | 当前代码、API 定义、数据库定义、测试与运行事实 |
| 动态派生视图 | 项目概览、服务关系图、模块地图、变化影响摘要、知识覆盖和待确认区域 | 根据前两类内容按需编译、增量刷新 | 输入来源清单与编译版本；不独立成为事实权威 |

### 5.3 项目认知视图是否需要独立身份和版本

需要一个稳定的项目视图身份，作为项目入口和导航；但不需要将每一次视图输出都创建为独立 Knowledge Item。

应区分：
- Project：已有项目对象，拥有项目身份和配置；
- Project Cognition View：该项目的固定视图类型 / 入口；
- Cognition Snapshot：某一时间点、某个代码基准和来源修订下的可追溯派生快照；
- Knowledge Revision：视图中引用的正式知识版本。

快照版本用于回溯“当时系统认知是什么”，不等于发布了一份新的正式项目知识。

### 5.4 自动生成与人工确认边界

| 内容 | 默认方式 | 确认要求 |
|---|---|---|
| 仓库、目录、模块和文件清单 | 确定性提取 | 通常无需人工逐项确认 |
| API 路由、接口结构、数据模型 | OpenAPI / 路由 / Schema / 代码提取 | 对外契约以权威定义为准；推断内容标注待确认 |
| 模块调用和依赖关系 | 静态分析、构建配置、运行证据 | 区分静态依赖与真实运行调用 |
| 业务目标、业务概念和规则 | 来源提炼 | 业务责任人确认高影响结论 |
| 架构决策和模块职责 | ADR / Issue Decision / 技术资料提炼 | 对关键决策和边界由责任人确认 |
| 当前实现状态 | 代码与测试基准提取 | 不推断业务意图，不将代码存在等同于行为正确 |
| 已知问题和历史故障 | Issue / Finding / Run / 复盘提炼 | 根因与解决方案须有证据；推断与观察分开 |
| 项目整体摘要 | 根据已确认知识和事实自动生成 | 标记生成时间、基准和未知项，不作为权威事实 |

人工确认不应变成逐字段签字。优先确认影响业务规则、架构边界和高风险决策的结论；低风险、可确定提取的结构事实由系统维护。

### 5.5 代码变化后的影响分析

代码变化只触发：
1. 识别受影响仓库、文件、符号、接口、模块或测试；
2. 找出依赖这些来源或锚点的 Claim 和派生视图；
3. 比较旧、新基准下的结构和语义差异；
4. 判断变化可能影响哪类事实；
5. 生成影响报告和复核建议；
6. 由责任人或适当的确定性核验确认结论是否改变。

状态区分：
- Current：在指定基准下完成核验，证据匹配；
- Changed / Suspect：来源发生变化，影响尚未判定；
- Stale：原证据或基准已不再代表当前事实，且需要复核；
- Missing：引用目标不存在或已删除；
- Unknown：无法取得完整来源或无法确认影响。

这些状态描述证据 / 锚点与基准的关系，不是统一的知识正确性分数。代码变化可能与业务结论无关，不能直接把知识判为过期。

### 5.6 是否需要完整代码图谱

不需要以全仓库完整代码图谱作为项目认知视图的前置条件。

建议渐进式：
- 第一层：仓库、目录、模块、入口、构建和 API 的确定性骨架；
- 第二层：Issue 实际涉及的模块和上下游调用链；
- 第三层：高风险、高变更频率、高返工模块的深度认知；
- 第四层：仅在跨模块影响分析确有价值时扩展更完整的依赖图。

不要求所有知识绑定 AST 或符号。业务规则、决策、流程经验可以引用 PRD、Issue、Run、测试或其他证据。只有代码事实确实依赖具体实现位置时才使用代码锚点。

### 5.7 避免重复项目 Wiki 和工程文档

- 项目认知视图自动生成结构导航和摘要，不复制完整工程文档。
- 正式架构决策仍由 Knowledge Topic / ADR 类知识资产维护。
- 代码地图和调用关系由当前代码基准派生。
- 原始 API 文档和工程文档继续在权威来源维护。
- 项目视图提供统一入口、状态、来源和责任链接。
- 人工只修正认知错误或确认重要结论，不手工维护系统生成的目录、依赖图和代码清单。

## 6. 知识形成：资料接入与伴生采集统一治理

### 6.1 多种入口，一个知识治理流程

入口包括：
- 外部权威资料连接：飞书、Git、API 文档、项目系统；
- 一次性资料提交：Markdown、PDF、HTML、表格、URL 和成员灵感；
- 研发伴生采集：PRD 修订、Issue Decision、Commit、PR Review、测试、Run、Artifact；
- Agent 主动发现：人工纠偏、工具拒绝、重复失败、调查和排障；
- 人工修订：成员对已有主题或结论提出修订。

入口不同，但最终统一为：

**来源取得 / 执行观察 → Evidence → 候选结论 → 去重与冲突分析 → 适用范围和派生授权 → 核验 / 审核 → Knowledge Revision / Release。**

来源资料可以直接检索，不代表正式知识；研发事件只产生候选，不自动发布。

### 6.2 伴生采集的事件策略

| 事件 | 发现动作 | 是否默认调用 LLM | 可能产物 |
|---|---|---|---|
| PRD / API 文档修订 | 对比来源修订与受影响 Claim | 只对语义变化或影响不明的内容调用 | 结论更新候选、冲突提示 |
| Commit / Merge | 确定性分析变更文件、接口、模块及关联知识 | 不默认；命中高价值知识依赖时再调用 | 认知视图更新、知识影响报告 |
| Review 驳回及修复 | 关联评论、修复 Commit、最终 Review 结论 | 适合提炼错误模式和正确做法 | Gotcha / 实践候选 |
| 测试失败及修复 | 对照失败报告、修复前后和复测结果 | 适合生成经验候选 | 根因假设、验证方法、预防建议 |
| Issue Decision | 读取有权成员确认的决定、理由、适用范围 | 可协助整理，不替代决定 | 决策知识候选 |
| Agent 纠偏 / 工具拒绝 | 识别重复纠偏、无效工具调用和失败重试 | 聚合后分析，不因单次失败沉淀 | 知识缺口、规则候选 |
| 普通 Commit / 普通对话 | 记录可关联的事件 | 否 | 通常不产生知识候选 |

### 6.3 低负担确认

伴生式采集不是监听所有事件、每个事件都调用 LLM，也不是要求开发人员每次 Commit 后手工整理知识。

适合人类确认的事项：
- 这条结论是否真的成立；
- 是否可以从项目范围派生到团队；
- 是否改变了业务规则或架构决定；
- 是否属于长期适用的方法；
- 是否应该转化为 Harness。

系统可以自动完成事件关联、证据定位、变更摘要、重复与冲突候选、主题归属建议、受影响范围分析和复核任务聚合。

成员通过 PR / Issue / 工作台的轻量确认处理候选；高影响知识由相应责任人确认。知识中心不强制成员重复填写原始资料。

### 6.4 项目知识向团队知识的派生

沿用 Topic 3B 已实证的独立权限边界：
- 项目来源读取权；
- 每份来源证据的派生许可；
- 目标团队 / 受众授权；
- 独立团队发布权。

项目知识转团队知识必须：
1. 选出可迁移的结论，而不是复制整份项目文档；
2. 去除项目特定标识和敏感内容；
3. 逐份确认来源证据允许对目标受众派生；
4. 重新核验结论在其他项目是否成立；
5. 由团队领域维护者独立确认发布；
6. 保留项目证据引用和授权代次，按权限决定谁能查看原文。

**作用域和晋升路径是两个独立维度。** 项目知识不因存在时间长或被频繁检索而自动晋升团队知识；团队知识也不因被某个项目采用而改变其原始范围。

## 7. 冲突处理、知识有效性和质量表达

### 7.1 不采用全局统一来源优先级

不同事实类型的权威来源不同。需要先识别“当前争议究竟是什么事实”，再判断对应的权威来源。

| 事实类型 | 主要权威依据 | 需要注意 |
|---|---|---|
| 当前业务意图与规则 | 当前有效的产品 / 业务决策、已批准 PRD、Issue Decision | 代码实现可能尚未跟上，不能用代码覆盖业务意图 |
| 已批准的架构决策 | 被有权主体确认的 ADR / 架构 Decision | 代码可能偏离已批准架构，需报告偏差 |
| 当前实际实现 | 指定 Commit 的代码、构建结果和测试 | 代码存在不证明业务行为正确 |
| 对外 API 契约 | 已发布 API 定义、服务提供方确认的契约 | 实现和文档冲突时记录契约偏差 |
| 线上实际行为 | 可核验的生产观测、事件、日志和运行结果 | 单次观测不自动成为长期规则 |
| 缺陷根因和修复有效性 | 原始失败证据、修复差异、独立复测 | 模型解释不能代替复现和验证 |
| 团队实践是否有效 | 多次可比执行、独立评价和后续反馈 | 采纳次数只说明使用信号，不证明正确 |

同一主题可以并列保存不同时间、版本和范围的事实。无法裁决时保留冲突并路由给有权责任人，不让模型用一个合成答案掩盖冲突。

### 7.2 知识质量不能由单一 Confidence 表示

建议将知识质量表达为多个独立维度：

| 维度 | 回答的问题 | 典型信号 |
|---|---|---|
| 证据完整性 | 结论是否有可定位、可核对的依据？ | 缺少证据、来源读取失败、证据撤回 |
| 来源权威性 | 该来源是否有权说明这一类事实？ | 正式决策、原始代码、测试、观察、自述 |
| 当前性 | 证据与指定来源 / 代码基准是否一致？ | 当前、变化待分析、缺失、未知 |
| 适用性 | 是否适用于当前项目、版本、角色和环境？ | 适用条件匹配、范围不明、存在例外 |
| 冲突状态 | 是否存在未裁决的相反证据？ | 无冲突、冲突待裁决、已裁决 |
| 治理状态 | 是否已由相应责任人核验并发布？ | 草稿、待核验、已发布、待复核、撤回 |
| 使用反馈 | 在真实研发中是否有帮助？ | 被选择、投递、实际使用证据、帮助 / 无关 / 错误反馈 |

这些维度不能随意压成一个概率分数。检索排序可以综合考虑，但必须保留各维度的原始状态和原因。

### 7.3 更新、失效和影响分析

触发信号包括：
- 来源新增、改版、删除、撤回和权限变化；
- 代码、API、依赖、测试基准变化；
- Issue 决策和架构约束变化；
- 生产故障、评测 Finding 和人工纠偏；
- 知识被报告错误、冲突或不适用；
- 维护责任人离开或责任范围变化。

处理顺序：
1. 记录变化事实；
2. 定位依赖该来源的 Evidence Anchor / Evidence；
3. 找出受影响 Claim、主题和项目认知视图；
4. 生成影响范围、差异和不确定项；
5. 按风险决定是否暂停新投递；
6. 由确定性检查或责任人复核；
7. 发布新修订、确认无影响、标记冲突或退役；
8. 保留历史工作引用与当时投递事实。

**代码变化只触发影响分析或复核，不能直接判定知识过期。** 只有证据失效、结论被反驳、适用范围变化或有权责任人确认后，才改变知识事实状态。

## 8. Agent 知识消费：推式与拉式结合

### 8.1 供给对象是上下文包，不是原始文档集合

知识中心按当前工作准备 Context Package，输入包括：
- Team / Project 和项目认知视图；
- Issue 目标、工作类型、阶段和当前决定；
- 当前接收者身份、角色和来源权限；
- Agent 宿主能力与可用上下文通道；
- 代码仓、分支 / Commit 和本次变更范围；
- 有效 Knowledge Revision / Release；
- 相关 Harness Release 与项目采用版本。

返回内容：
- 当前工作必须知道的规则和约束；
- 与本次任务相关的结论包；
- 必要的项目认知摘要；
- 适用条件、例外和冲突提示；
- Evidence 来源、修订和定位；
- 可继续深挖的主题入口。

### 8.2 三层供给

| 层次 | 方式 | 适合内容 | 典型时机 |
|---|---|---|---|
| 必需约束 | 确定性推式 | 安全红线、项目明确采用的规则、当前工作约定 | Issue 启动、阶段进入、工具执行前 |
| 项目导航 | 轻量推式 | 项目认知摘要、模块地图、知识域导航、重要未知项 | Agent 会话初始化、项目切换 |
| 任务深潜 | 按需拉式 | 具体业务规则、ADR、模块关系、历史故障、证据详情 | Agent 推理遇到未知或跨域问题 |

推式不等于把整个团队知识库塞进 System Prompt；拉式也不意味着把所有责任交给 Agent 自己想起搜索。二者互补。

### 8.3 不同 Agent 的消费策略

| 消费者 | 必需推送 | 按需检索 |
|---|---|---|
| PM / 需求分析 Agent | 领域词汇、业务范围、已确认规则、重要历史决策 | 相关业务例外、存量功能和冲突来源 |
| Architect Agent | 项目认知摘要、服务边界、架构红线、已采用 ADR | 跨服务依赖、API 契约、历史决策理由 |
| Coding Agent | 当前 Issue 约束、目标模块高相关知识、项目级规则 | 具体实现细节、模块避坑、历史故障和相关接口 |
| Review Agent | 变更范围适用的安全和工程约束、业务验收标准 | 对应模块历史问题、ADR 和证据详情 |
| QA / Verification Agent | 当前验收标准、业务规则、角色和边界条件 | 历史缺陷、测试方法、反例和相关证据 |
| 人类成员 | 结论摘要、主题导航、最近变化与待确认事项 | 原文、完整背景、证据链和变更 Diff |

### 8.4 不同宿主能力不一致时的降级

不能假设 Codex、Claude Code、Qoder、CodeBuddy 等宿主拥有相同 Hook、MCP、上下文观察和会话重建能力。

供给通道按能力降级：
1. 宿主支持明确的启动 / 工具 Hook 时，使用确定性推式；
2. 宿主支持 MCP / 工具调用时，提供受权限控制的检索和证据读取；
3. 宿主只能接收启动指令或文件上下文时，提供精简导航和工作材料；
4. 无法证明宿主已加载时，只记录投递回执；
5. 无法观察实际使用时，Usage 保持 Unknown，不推断为已使用。

### 8.5 必须区分的消费事实

沿用 Topic 3B 实证，严格区分：
- 命中 / 展示；
- 成员或 Agent 选择；
- 实际投递；
- 宿主加载 / 可见；
- 实际使用；
- 对交付或质量的影响。

每个环节只有获得对应证据才可标记完成。ContextReceipt 证明材料准备和投递；宿主 Observation 证明实际输入；工具、决策和交付证据才能进一步支持使用与效果判断。

权限在检索和投递前复核。权限撤回后停止新的投递；已送达宿主的历史内容可能仍存在，平台不能声称可以远程清除。

## 9. 知识向 Engineering Harness 的转化

### 9.1 Knowledge 和 Harness 的边界

Knowledge 回答事实是什么、为什么这样设计、适用什么情况、历史上发生过什么、有哪些经验和例外。

Harness 回答 Agent 应该怎么做、哪些行为必须遵守、流程如何执行、哪些结果必须验证、失败时如何拦截和接续。

知识可以作为 Harness 的依据，但不自动变成 Harness。

### 9.2 四种转化路径

| 知识形态 | 可能的 Harness 形态 | 转化条件 | 独立验证 |
|---|---|---|---|
| 明确、稳定、可判定的约束 | Rule / Principle | 适用范围、例外、违反后果明确 | 规则适用性和反例检查 |
| 可复用的多步骤实践 | Skill / Playbook / SOP | 输入、步骤、输出和责任边界清楚 | 用真实任务验证可执行性和成功率 |
| 确定性、重复执行的检查 | Script / Hook / Tool | 能定义输入、输出、权限和失败行为 | 自动化测试、误报漏报和安全检查 |
| 可客观判定的质量要求 | Evaluation / Rubric / Regression Case | 有明确标准、样本和判定证据 | 基线、对照集、误差和稳定性评估 |

专职 Sub-Agent 可以是上述 Harness 能力组合的交付形态，但不因知识密集就自动孵化；需要证明其独立职责、上下文隔离和效果价值。

### 9.3 转化流程

1. 知识中心识别高价值、稳定、可执行的知识；
2. Agent 生成 Harness 转化建议，指出目标类型、适用范围、失败案例和待补验证；
3. 对应 Harness 维护者创建独立候选修订；
4. 使用历史失败样本、正向样本和反例进行评测；
5. 完成审核和 Harness Release；
6. 项目有权成员决定是否采用；
7. 后续执行和 Evaluation 反馈真实效果。

访问频次、采纳率和 Agent 反馈仅用于发现候选，不作为自动发布条件。Knowledge Release 与 Harness Release 分别治理，项目采用也分别决定。

## 10. 与现有能力域的关系

本轮不新增一级能力域，不改变 Issue、Multica Run 和 Harness 的既定边界。

| 既有能力 / 对象 | 本轮融合后的关系 | 明确不做 |
|---|---|---|
| 团队知识管理 | 管理来源、Evidence、主题知识、结论、项目认知视图及其治理 | 不复制原始文档，不建立第二套 Wiki |
| Issue / Project | 提供工作意图、项目范围、决定、当前任务和责任 | 不建立知识专用 Issue 或平行任务队列 |
| Multica Task / Run / Runtime | 提供真实执行、会话、工具和执行证据；项目与 Issue 是上下文来源 | 不另建知识执行 Runtime 或 Run |
| Engineering Harness | 消费已确认知识，独立维护 Rule、Skill、Playbook、Script、Evaluation | 不把知识正文直接等同于 Harness 资产 |
| Evaluation / Finding / Proposal | 发现知识缺口、过期、错误或可转化的改进机会 | 不用评价分数直接改变知识正确性或自动发布 |
| Source Connection / Evidence | 负责来源连接、修订、权限、定位和证据关系 | 不把解析 Chunk 作为正式知识资产 |
| Project Adoption / Release | 沿既有发布和采用语义固定知识 / Harness 版本 | 不新建通用发布系统 |

上下文编译与供给是知识中心的能力，不是新增一个独立控制平面。Issue 仍然是研发工作的业务主线。

## 11. 对现有研究与对象模型的补充建议

### 11.1 K0 总体研究文档补充

第一轮 K0 应增加以下产品定位：

“团队知识中心不仅管理可复用知识资产，还承担面向研发工作和 Agent 的上下文编译与供给。其输出包含正式知识、派生项目认知和一次性工作上下文，三者具有不同的权威性和生命周期。”

增加 Project Cognition View 产品视图：
- 项目入口和认知摘要；
- 稳定知识、当前事实和动态派生视图的区分；
- 来源、代码基准、更新时间和未知项；
- 受影响知识和待确认区域；
- 直接进入相关主题和 Issue 的导航。

### 11.2 K0-A 补充

K0-A 原结论保持不变。补充：
- Claim 是知识内容的语义和核验边界；
- 编译态不等于独立 Knowledge Item；
- 主题 Revision 和 Claim 局部变化需要区分；
- Context Package 以结论包为核心，同时带最小必要背景和证据入口；
- Project Cognition View 不属于新的知识资产类型。

### 11.3 统一对象模型补充建议

沿用 Source Item / Revision、Evidence Anchor、Evidence、Knowledge Item / Revision、Release、Project Adoption、Work / Run Asset Pin、ContextReceipt、Observation、Issue、Run、Artifact、Evaluation、Finding 和 Improvement Proposal。

建议补充的业务语义：
1. Knowledge Revision 可表达主题结构及其 Claim 单元。
2. Claim 具有稳定局部标识和证据依赖，但默认不独立发布。
3. Project Cognition View 是 Project 上的派生视图身份；Cognition Snapshot 记录指定输入基准下的可追溯输出，不成为新的权威知识资产。
4. Context Package 是编译结果，记录输入清单、接收范围、编译规则版本和实际输出摘要；被实际投递时由现有 ContextReceipt / Observation 体系记录。
5. 变化影响链按 Source / Evidence → Claim → Topic / Project Cognition View → Context Package 追踪。
6. 不为每个 Chunk、每次检索或每次编译创建新的业务资产。

以上是对象语义补充，不是数据库 Schema 或 API 设计。

## 12. 外部机制研究：WeKnora、TeamAI、Backstage TechDocs、Onyx

### 12.1 WeKnora

公开仓库和版本记录显示，WeKnora 已包含文档接入、解析、知识库检索、Wiki 编译、Wiki 页面修订、Chunk 编辑与历史、Feishu 来源接入和 MCP 消费等能力。官方项目说明将 RAG、Agent 和 Wiki 放在同一知识库体系中；近期 Release 记录还包含 Wiki 页面修订 Diff / Revert、Feishu Docx blocks API 同步、Chunk 分页和文档处理并发诊断。

可借鉴：
- 来源接入与处理状态；
- 文档结构保留和 Chunk / Wiki 的版本维护；
- Wiki 自动组织与修订；
- MCP 作为知识消费入口；
- 文档处理与知识组织在同一处理链路中协作。

不能直接等同于 AgentPlatform 的知识中心：
- Wiki 页面和自动摘要不自动等于经团队责任人确认的正式知识；
- 文档 ACL、派生许可和跨项目知识晋升仍需结合 AgentPlatform 的业务授权；
- 不负责 Issue / Run 工作上下文、项目责任和 Harness 改进治理；
- 不应因为 WeKnora 能生成 Wiki，就把所有项目认知复制成另一套手工 Wiki。

依据：[WeKnora 仓库与项目能力说明](https://github.com/Tencent/WeKnora) · [WeKnora Releases](https://github.com/Tencent/WeKnora/releases)。

### 12.2 TeamAI

TeamAI 的 Team Context 并非只有一个向量库：
- learnings 保存团队经验；
- teamwiki 保存代码知识图谱；
- rules、docs、skills 等资产有不同消费方式；
- teamai recall 统一搜索经验、代码图谱和团队文档；
- Session 结束时可根据纠偏、工具拒绝和失败重试提示贡献经验；
- 贡献者与 Agent 在工作流中决定具体分享内容和命名空间；
- 经验可以形成草稿、审核分支和 PR；
- 代码知识可增量导入，并在召回时显示来源新鲜度；
- 项目与角色命名空间影响可见范围；
- 使用反馈用于排序和维护候选。

特别值得注意：TeamAI 文档明确说明 Confidence 是活动 / 采纳信号，不是知识正确概率或任务成功概率。高频召回低采纳可以生成质量更新草稿；提升为 Rule / Skill / Doc 也需要工作流和审核分支，而非简单自动覆盖。

可借鉴：
- 伴生采集和低负担贡献；
- 经验、代码知识、Harness 资产分开管理；
- 命名空间与角色范围；
- 增量索引与代码锚点新鲜度；
- 反馈驱动维护候选；
- 受控的知识转化工作流。

不直接照搬：
- TeamAI 的 Git 仓库分发模式不等于 AgentPlatform 的权威知识中心；
- Activity Confidence 不应成为 AgentPlatform 的知识正确性指标；
- 经验晋升门槛不能替代业务责任人、证据核验和 Harness Evaluation。

依据：[TeamAI Team Context 官方使用指南](https://github.com/Tencent/teamai-cli/blob/main/docs/guide/knowledge.md) · [TeamAI 产品概览](https://github.com/Tencent/teamai-cli/blob/main/docs/product-overview.md)。

### 12.3 Backstage TechDocs 与 Software Catalog

TechDocs 采用 docs-like-code：工程文档以 Markdown 与代码同仓，CI / TechDocs CLI 生成静态站点，Backstage Reader 展示文档。Software Catalog 通过代码仓中的元数据文件发现服务、API、系统和 Owner，支持关系浏览和责任导航。

可借鉴：
- 文档与代码基准保持关联；
- 项目 / 服务目录和 Owner 导航；
- 项目认知视图通过实体关系聚合服务、API、系统和文档；
- 文档生成与文档权威维护分离。

限制：
- TechDocs 是文档发布与浏览机制，不是 Evidence → Claim → Knowledge 的完整治理模型；
- Catalog 的 Owner 主要用于责任可发现，不自动构成运行时授权；
- 不应将 Backstage Catalog、TechDocs 直接当作 AgentPlatform 的完整项目认知和知识中心。

依据：[TechDocs](https://backstage.io/docs/features/techdocs/) · [TechDocs Architecture](https://backstage.io/docs/features/techdocs/architecture/) · [Software Catalog](https://backstage.io/docs/features/software-catalog/) · [Catalog Relations](https://backstage.io/docs/features/software-catalog/well-known-relations/)。

### 12.4 Onyx

Onyx Connector 将外部应用文档同步到自身索引，拉取 Owner / 更新时间等元数据，并在 Enterprise Edition 同步来源文档权限。它说明企业知识检索不能只考虑文本相关性，还需要来源权限和文档元数据。

可借鉴：
- Connector 持续同步；
- 来源权限进入检索可见性；
- 文档集和连接器范围过滤；
- 索引处理状态和来源元数据。

限制：
- Onyx 的文档同步与权限过滤不等于 AgentPlatform 的知识派生许可、独立复审、项目知识晋升和 Harness 治理；
- 不能将“有权限读取原文”推导为“有权限把内容派生给更广受众”。

依据：[Onyx Connectors 官方文档](https://docs.onyx.app/overview/core_features/connectors)。

## 13. 已有实证、官方能力、设计推断与待验证假设

### 13.1 仓库已有实证直接支持

- 来源权限、角色范围和实际宿主输入必须共同决定知识投递。
- 同一文档的不同章节可以服务不同角色；整篇文档可读不意味着整篇都应注入。
- 来源修订后，在途队列必须重新选择；历史宿主输入要按真实送达正文追踪。
- 项目证据派生为团队经验需要逐来源授权、目标受众授权和独立团队审核。
- 单来源撤回不应影响其他证据和历史派发。
- 同字节恢复仍可能是新授权代次，需要重新复审。
- TeamAI 的代码知识新鲜度可以区分 current、stale、missing、unknown。
- Multica 撤权后可通过搜索索引同步移除受影响实体，但已送达宿主历史可能仍保留。
- Knowledge 与 Harness 必须分开治理和发布。

### 13.2 官方文档 / 公开机制说明

- WeKnora 提供文档接入、知识库检索、Wiki、Chunk / Wiki 修订、Feishu 来源、MCP 等能力。
- TeamAI 提供经验贡献、代码知识图谱、角色 / 项目命名空间、采纳反馈、维护草稿和受控晋升工作流。
- Backstage TechDocs 提供 docs-like-code 与静态文档生成；Software Catalog 提供软件实体和 Owner / API 关系。
- Onyx Connector 提供来源同步、元数据和 Enterprise Edition 权限同步。

这些属于官方公开能力说明；除仓库已明确记录的固定提交和测试外，不将其误称为本轮重新完成的源码实跑。

### 13.3 基于案例形成的设计推断

- 知识治理和上下文编译应是同一知识中心的两项核心职责。
- Project Cognition View 应为可重建派生视图，而不是新的人工知识资产。
- 项目成熟度应该按领域 / 模块差异化，而非项目永久等级。
- 编译结果应固定输入基准和实际输出，以便复核历史上下文。
- 推式与拉式消费应按宿主能力降级，不能把供给等同于使用。

### 13.4 仍需真实项目验证

- 多仓库项目中，模块和服务关系能否稳定从代码、API、构建和运行证据中提取；
- 真实飞书租户持续同步、复杂文档结构和权限变化；
- 项目认知视图在多人协作和代码持续变化时的维护成本；
- PR / Review / Test 伴生采集的误报率和开发者确认成本；
- 不同宿主的实际推式注入、MCP 检索、会话重建和 Observation 能力；
- 结论包需要携带多少相邻背景，才能兼顾准确性和上下文预算；
- 知识变化影响分析能否正确识别“代码变化但业务结论不变”；
- 知识到 Harness 的独立评测是否能真实降低返工和重复缺陷。

### 14.2 维护责任

- 来源维护者：维护原始资料和来源授权。
- 项目 / 领域维护者：确认项目知识、模块认知和适用范围。
- 团队领域维护者：核验跨项目可复用性、派生许可和团队知识发布。
- Harness 维护者：独立验证并发布工程方法资产。
- Agent：发现变化、提炼候选、生成差异、做影响分析和提出更新建议。
- 平台：负责来源同步、权限检查、证据定位、变更追踪、编译、供给和审计。

不建立中央编辑部；不要求开发者重复维护原始文档。

### 14.3 知识运营从逐篇巡检转向问题队列

维护者只需要处理少量高价值事项：
- 新候选待核验；
- 来源更新影响了哪些结论；
- 代码变化可能影响哪些项目认知；
- 冲突需要业务或技术责任人确认；
- 知识被反馈错误或不适用；
- 无主或高风险知识需要重新认领；
- 有成熟知识适合转化为 Harness。

## 15. 对第一轮 K0 的补充与后续研究

### 15.1 应补充到 K0 总体设计的内容

1. 核心定位增加上下文编译与供给中心。
2. 将知识资产、派生认知、工作上下文区分为不同性质的内容。
3. 将 Project Cognition View 纳入项目知识的统一入口。
4. 明确伴生式采集与外部资料接入共用一个知识治理流程。
5. 明确不同成熟度项目采用不同知识形成策略。
6. 明确推式 + 拉式消费及宿主能力降级。
7. 明确来源 / 代码变化先做影响分析，不直接判定知识失效。
8. 明确 Knowledge → Harness 是独立改进链路。

### 15.2 K0-A 的结论保持不变

K0-A 原结论保持不变。新增的编译态和项目认知视图属于其上层派生与消费机制，不要求每个 Claim 都成为独立知识资产。

### 15.3 后续研究顺序建议

| 工作包 | 重点研究 | 交付 |
|---|---|---|
| K0-B · 责任与治理 | 主题维护者、项目维护者、团队发布者、派生许可、复审和交接 | 责任矩阵与知识治理工作流 |
| K0-C · 来源权威与冲突 | 按业务事实、架构、代码实现、运行行为和测试结果区分权威依据 | 来源权威与冲突裁决规则 |
| K0-D · 消费体验与上下文编译 | Issue 驱动的项目认知、推式、拉式、不同宿主降级和真实上下文验收 | 知识中心核心用户旅程与消费契约 |
| K0-E · 持续维护与项目认知 | 项目成熟度、伴生采集、认知视图增量更新和知识健康队列 | 项目认知与运营机制 |
| K0-F · Harness 转化 | 知识候选、Rule / Skill / Script / Evaluation 独立验证和采用 | 知识改进与 Harness 进化闭环 |

这些工作包仍属于 K0 团队知识中心产品研究，不重开 AgentPlatform 整体架构，不提前进入技术选型。

## 16. 最终结论

AgentPlatform 团队知识中心不应该被设计成一个“原始文档 + 原子知识条目 + 向量检索”的知识库。

它应当成为一个围绕研发工作持续运行的知识治理与上下文编译系统：

- **原始资料和执行证据**提供可核验事实；
- **主题知识资产与 Claim**沉淀团队真正需要长期维护的经验、规则、决策和系统认知；
- **项目认知视图**把稳定知识和当前项目事实组织成可理解、可重建的项目入口；
- **Context Compiler**根据 Issue、Project、角色、Agent 和代码基准编译适用上下文；
- **推式 + 拉式供给**让知识进入不同 Agent 的真实工作；
- **伴生式采集与影响分析**让研发过程自然产生知识更新候选；
- **Harness 独立验证与发布**将稳定经验转化为可执行、可评估的团队能力。

最终产品原则：

**长期维护的是知识和证据关系；动态生成的是项目认知和工作上下文；真正送给 Agent 的是经过权限、适用性和有效性约束的结论包。**

这既保留第一轮 K0-A 的粒度决策，也吸收 Argon 对上下文编译、伴生采集、项目认知和研发飞轮的关键贡献。
