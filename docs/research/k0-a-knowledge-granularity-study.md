# K0-A · 知识资产粒度研究任务书

## 1. 任务目标

在 K0 团队知识中心研究中，独立完成知识资产粒度与内容组织模型研究。比较三种候选模式，并用真实研发知识样本检验其长期维护成本、复用效果、证据追溯和版本演进能力，最终给出可落地的知识内容模型。

本专题不是数据库 Schema 设计，也不是知识库引擎选型。先确定团队究竟维护什么、以什么粒度维护，再讨论技术承载。

## 2. 已有产品基线

AgentPlatform 是团队 AI 研发能力平台，以团队知识为基础、以 Issue 产研工作为主线、以 Engineering Harness 管控研发质量，并通过真实执行证据和持续改进形成正向飞轮。

团队知识中心的定位：连接权威来源、证据处理、知识治理和研发消费；原始资料继续由飞书、Git、代码仓和项目系统等原系统维护。知识中心不成为第二套文档编辑系统，不把所有资料自动变成知识，也不把 Chunk 当作知识资产。

五个核心业务能力域：团队知识管理、产研工作与流程协作、Engineering Harness 治理、执行与交付证据、Evaluation / 度量 / 持续改进。

## 3. 本轮必须比较的三种模式

### 模式 A：整篇文档 / 复盘作为知识资产

一份故障复盘、技术方案或决策记录整体作为一条知识。研究其优点（上下文完整、维护直观）和缺点（检索粒度粗、局部结论难独立复用、局部过期可能导致整篇修订）。

### 模式 B：原子化结论，每条结论独立成为知识资产

将一份材料拆成多条事实、规则、经验或决策，每条独立维护、发布和检索。研究其优点（精确复用、局部更新）和缺点（对象膨胀、上下文丢失、重复关系、审核与维护成本高）。

### 模式 C：主题知识资产 + 可独立核验的结论 + 来源证据

以稳定主题作为人工浏览和维护入口；主题内包含多个结论单元，每个结论可独立标注适用范围、状态、维护责任和证据引用；只有在确实需要独立发布、撤回或冲突治理时才提升为独立知识身份。研究这一模式能否兼顾可读性、细粒度检索与局部治理，避免所有结论都成为独立资产。

不得预设模式 C 一定胜出。必须通过样本和操作场景验证。

## 4. 必须使用的真实知识样本

至少选取以下四类，每类从仓库已有研究、设计或可验证资料中选取具体样本；不得只用抽象例子：

1. **业务规则 / 业务约定**：例如订单导出规则、角色可见范围、业务字段约定。重点检查规则变更、例外和权威来源冲突。
2. **技术决策 / 架构选择**：例如项目架构决策、组件选型、技术边界。重点检查决策理由、被替代方案、适用项目和演进历史。
3. **踩坑经验 / 故障复盘**：优先复用 Topic 3B 中 C1 返工、C2 修复和从项目经验提炼团队测试经验的案例。重点检查项目私有证据、跨项目派生、局部结论和证据撤回。
4. **项目 / 系统说明**：例如项目模块职责、调用路径、代码结构说明。重点检查代码基准绑定、局部代码变更、跨模块关系和生成说明与人工决策的差异。

如仓库缺少合适样本，明确缺口和所需样本，不得虚构为已验证事实。

## 5. 每种模式都要执行的对照操作

对四类样本分别模拟或重建以下维护操作，记录三种模式需要修改什么、影响哪些引用、是否需要重新审核：

- 新增一条结论；
- 修订一个结论但保留同一主题中的其他结论；
- 某条结论被证据反驳或来源撤回；
- 一份来源支持多个主题或多个结论；
- 一条结论同时适用于多个项目，但原始证据只对一个项目可见；
- 一个主题中的部分内容过期，其他内容仍然有效；
- 同一结论存在冲突来源或不同版本适用范围；
- 后续 Issue 只需要其中一条结论，Agent 如何检索和引用；
- 人工浏览者如何理解完整背景、决策过程和相邻结论。

## 6. 评价维度

至少比较：

| 维度 | 需要回答的问题 |
|---|---|
| 人工可维护性 | 领域维护者是否容易阅读、编辑、审查和理解整体主题？ |
| Agent 检索粒度 | 能否只返回本次工作真正需要的结论，同时保留必要上下文？ |
| 证据可追溯性 | 每个结论能否定位到来源修订和精确位置？ |
| 局部更新成本 | 修改或撤回一个结论会影响多少无关内容？ |
| 版本语义 | 主题版本、结论版本和来源版本如何关联？历史工作引用什么？ |
| 冲突治理 | 同一主题中的不同结论、不同来源、不同适用范围如何并存？ |
| 权限与派生许可 | 项目私有证据能否支持经授权的团队派生结论，而不泄露原始内容？ |
| 重复与合并 | 如何识别重复结论、跨主题引用和后续合并？ |
| 维护责任 | 谁对主题、结论和来源变化负责？是否出现责任碎片化？ |
| 规模化 | 知识数量和项目数量增长后，结构是否仍然可理解和可治理？ |

不要用主观打分代替分析。若使用评分表，给出可观察依据和权重理由。

## 7. 需要形成的最终结论

1. 推荐的知识资产粒度与内容组织模型，以及不推荐模式的具体原因。
2. 主题、结论、证据、来源修订之间的关系和身份边界。
3. 哪些结论应独立版本化，哪些只需作为主题内容修订。
4. 主题与结论的维护责任如何分配，如何避免知识被切得过碎。
5. 搜索 / 问答返回结论时，如何保留相邻背景、适用条件和完整主题导航。
6. 来源变更、结论失效、冲突、撤回时的局部影响规则。
7. 对 Knowledge Item / Revision / Evidence 现有对象模型的修订建议。
8. 哪些结论已由现有实证支持，哪些仍是设计假设和后续待验证事项。

## 8. 研究纪律

- 优先阅读和引用仓库已有真实研究与原始证据，尤其 `docs/research/topic-03b/project-knowledge.md`、`knowledge-contribution.md`、`knowledge-sources.md`、`docs/research/03b-source-evidence.md`。
- 继承已有的来源权限、撤回、派生许可、独立审核和宿主真实输入结论，不重复运行已完成的合成实验。
- 不能把 TeamAI、WeKnora、Backstage 或 Onyx 的产品概念直接拼成 AgentPlatform 设计；必须围绕团队维护问题做取舍。
- 不提前设计数据库表、API、向量索引或部署架构。
- 不增加新的一级能力域，不改变 Issue、Multica Run 和 Harness 的既定边界。
- 最终文档只记录研究结论、证据和仍未解决的问题，不记录冗长的讨论过程。

## 10. 研究完成记录

K0-A 已完成。最终结论见[知识资产粒度研究结论](k0-a-knowledge-granularity-findings.md)。

本轮结论：默认采用“主题知识资产 + 可独立核验的结论单元 + 来源证据”。主题是人工浏览和维护边界，结论是检索、核验和局部更新边界，证据是事实依据。结论只有在需要独立适用范围、责任、发布 / 撤回、版本或冲突治理时，才提升为独立 Knowledge Item。详见最终研究报告；本任务书保留为研究范围和验收依据。
